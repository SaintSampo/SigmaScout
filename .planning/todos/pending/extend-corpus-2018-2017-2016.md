# Extend the corpus back to 2018, then 2017, then 2016

> **Scope: 2018 first.** 2017 (Steamworks) and 2016 (Stronghold) follow, in that order, as
> separate passes. 2018 is deliberately first because it is the hard one (see the additivity
> section below) — the two easy seasons should not be done while the hard one's shape is
> unknown.
>
> **2021 is never part of the corpus.** It was the at-home/remote season with no conventional
> 3v3 alliance matches, so there is nothing for a match predictor to ingest. This is a
> `permanent exclusion`, not a deferral — the same rule the predecessor file set.
>
> **Provenance.** Every number below was measured on 2026-09-06 by read-only probes against the
> TBA API and `data/corpus.sqlite`. Read them, do not re-measure them — re-running the probes
> spends TBA rate limit for no gain.
>
> **Predecessor.** This file succeeds `.planning/todos/completed/extend-corpus-2019-2020.md`,
> which closed 2026-09-04.

**Priority is `high`** because the user stated intent directly on 2026-09-06: after 2018 lands,
2017 and 2016 follow. That declared intent is what `priority` records here — it does **not**
mean the payoff arithmetic below is large. Read "What this buys, and what it does not" for the
honest counterweight before treating `high` as a reason to rush this.

## What this buys, and what it does not

Origins require at least 2 distinct prior seasons in the corpus
(`MIN_PRIOR_SEASONS_FOR_HEADLINE`, `packages/harness/score.ts`).

- Today's corpus — 2019, 2020, 2022, 2023, 2024, 2025, 2026 — yields five origins: 2022, 2023,
  2024, 2025, 2026.
- Adding 2018 promotes **exactly one** new origin: **2020**, which is a 3,806-match fragment
  season. 2019 gains only one prior and stays ineligible.
- The real gain is that the **thinnest origin's selection window roughly doubles**: 2022
  currently selects on 2019 + 2020 = 18,749 official quals; with 2018 it selects on ~33,000.
- **The risk, stated plainly.** 2018 is the one season whose structure violates the model's
  core additivity assumption, so hyperparameters selected partly on 2018 may transfer *worse*
  to normal seasons. This is testable with the existing rolling-origin harness — compare the
  origin-2022 parameter set selected with and without 2018 — and that comparison should **gate
  promotion**. Do not assume the backfill is a free win.

## The one hard part — 2018 is anti-additive

**OPEN MODELLING DECISION.** This is the only part of the 2018 job with no precedent anywhere in
the codebase — everything else in this file is data entry.

### F-A — the observation

`corr(red totalPoints, blue totalPoints)` over official qualification matches. The seven corpus
seasons come from `data/corpus.sqlite`; 2018 is measured directly against TBA:

| season | corr(red, blue) totalPoints | n |
|---|---|---|
| 2018 | **-0.4567** | 3,248 qual alliance-sides, 18 events (TBA) |
| 2019 | +0.3282 | 14,929 |
| 2020 | -0.0003 | 3,820 |
| 2022 | +0.3785 | 12,064 |
| 2023 | +0.3461 | 13,558 |
| 2024 | +0.2395 | 14,141 |
| 2025 | +0.5192 | 14,821 |
| 2026 | +0.3592 | 15,191 |

A separate 10-event / 858-match sample gave **-0.4239**. The point is not the magnitude — it is
that **the sign flips** relative to every other season.

### F-B — the cause, measured per component

The shared Scale. From the 858-match sample, red-vs-blue correlation within the same match:

| breakdown field | corr(red, blue) | reading |
|---|---|---|
| `teleopScaleOwnershipSec` | **-0.9109** | near-perfectly zero-sum |
| `teleopSwitchOwnershipSec` | -0.1362 | each alliance owns its own Switch — normal |
| `vaultPoints` | +0.0528 | normal |
| `endgamePoints` | +0.1895 | normal |

Mechanism, in one line: the Scale is a single shared field element, so a second of red ownership
is a second blue cannot have. Contest-intensity: red + blue `teleopScaleOwnershipSec` summed —
min 0, p10 96, median 124, p90 136, max 143, mean **118.8**, against 135s of teleop. The Scale is
contested essentially the whole match.

### F-C — the normalization lever

Scale-derived points are `2*autoScaleOwnershipSec + teleopScaleOwnershipSec +
teleopScaleBoostSec`. These are two DISTINCT statistics over the same sample — neither is
derived from the other:

1. Scale-derived points averaged **65.5 points per alliance-side**.
2. The mean per-side share of that alliance's own total was **18.8%**.

Both are means over alliance-sides, so 18.8% is a mean of ratios, not `65.5 / mean(total)` —
together they imply a mean alliance total in the ~350 range but do not pin one, and this file
does not compute one.

The decisive pair:

| quantity | corr(red, blue) |
|---|---|
| `totalPoints` | -0.4567 |
| `totalPoints` minus Scale points | **-0.0642** |

Removing the Scale essentially restores additivity. This matters because OPR, EPA and Sigma1 all
assume alliance score = sum of independent per-team contributions, and 2018 violates that
directly — a strong opponent literally subtracts from your score. The `-0.0642` result is **a
lever that exists**, not a decision to pull it; a Scale-normalized 2018 is one candidate
treatment among several and the choice has not been made.

## The 2018 component map is clean

The verified identity holds exactly:

`autoRunPoints + autoOwnershipPoints + teleopOwnershipPoints + vaultPoints + endgamePoints +
adjustPoints + foulPoints == totalPoints`

37 distinct `score_breakdown` keys were observed.

- **Roll-up hazards, never read:** `autoPoints`, `teleopPoints`, `totalPoints`.
- **Per-robot fields, never read** (Assumption A1 / Pitfall Sigma1-2): `autoRobot1/2/3`,
  `endgameRobot1/2/3`.
- **Diagnostic-only counts:** `foulCount`, `techFoulCount`.

Two data-quality notes, each with its disposition:

- **Residual.** 33 of 3,108 official alliance-sides mismatch (**1.06%**), all at -1 or -2. This
  becomes a `KNOWN_TOLERANCES` entry, the same treatment 2019's known mismatches got. It is
  roughly **10x** 2019's rate (2019 was 1 in **18,051**) and therefore deserves a proper recon
  sweep before the module is authored — a tolerance that large should be understood before it
  is accepted.
- **Nulls.** 140 alliance-sides carry null `adjustPoints` and null `autoSwitchAtZero` — **all
  140 from `2018cc` (Chezy Champs), an offseason event.** The existing `tryParseBreakdownPair`
  malformed-degradation path already covers exactly this class; the phase-03 security audit
  measured 1,004 of 4,757 2024 offseason matches failing the same way. **Not a new problem.**

Suggested phase grouping for `groups.ts`: auto = `autoRun`, `autoOwnership`; teleop =
`teleopOwnership`, `vault`; endgame = `endgame`. Placing Vault in teleop is a judgement call of
the same class `groups.ts`'s own header already documents for 2023 `link` and 2025 `algae`.

## The 2018 RP rules are easier than 2019's

Two bonuses; base rates over n=3,248 qual alliance-sides: `autoQuest` **61.98%**, `faceTheBoss`
**15.33%**.

### `faceTheBoss` — solved

`endgamePoints >= 90` gives **100.000%** agreement, 0 false positives, 0 false negatives. Exact,
numeric-only, therefore fully reachable from `predictThresholds`. No conservative branch needed.

### `autoQuest` — a real design choice, and this file does not make it

Both options, with their measured numbers:

| option | rule | agreement | FP | FN |
|---|---|---|---|---|
| 1 | `autoRunPoints >= 15 && autoSwitchAtZero` | **96.429%** | 0 | 116 |
| 2 | `autoRunPoints >= 15 && autoSwitchOwnershipSec > 0` | **99.569%** | 13 | 1 |

- Option 1 matches the house never-overstate preference, but `autoSwitchAtZero` is a boolean and
  is **unreachable from `predictThresholds`** — 2019's `completeRocket` asymmetry problem
  returning.
- Option 2 is numeric-only and therefore reachable, with better agreement and no asymmetry, but
  it introduces false positives, which cuts against never-overstate.

All 116 of Option 1's false negatives are the `autoSwitchAtZero === false` case specifically —
zero of them were "not all robots ran". A threshold sweep on `autoSwitchOwnershipSec`, following
the `scripts/recon-rp-thresholds-2019-2020.ts` pattern, would likely find a cut point that is
both exact and reachable. **Recommend that sweep as the deciding step** — the decision waits for
it.

`autoRunPoints` takes only 0 / 5 / 10 / 15 (counts 12 / 107 / 574 / 2,555) — a clean 3-robot
count at 5 points per robot.

## THE TRAP — two hardcoded test season lists, both now closed

**CORRECTED 2026-09-06 (quick task 260906-8kd):** this section previously claimed THREE
hardcoded test season lists, naming `packages/core/districts/pointModel.test.ts` as one of
them. That claim was wrong. `pointModel.test.ts` was never a defect — see below. The real trap
was always two files, and quick task 260906-8kd closed both.

**Registering a season without editing an iteration list used to ship an entirely unproven
component map with a fully green test suite.** The distinction that matters is *iteration list*
(fails silently) vs *equality assertion* (fails loudly):

| file | what it hardcoded | status |
|---|---|---|
| `packages/core/algorithms/breakdown/groups.test.ts` | a module-level `const SEASONS = [2019, 2020, 2022, ...]` feeding three `for...of` sites | **CLOSED** — now iterates the exported `BREAKDOWN_REGISTERED_SEASONS` (`breakdown/index.ts`) |
| `packages/core/algorithms/breakdown/reconciliation.test.ts` | a module-level `const REGISTERED_SEASONS = [...]` feeding one `describe.each` and one `it.each` | **CLOSED** — now iterates the same `BREAKDOWN_REGISTERED_SEASONS` |

`BREAKDOWN_REGISTERED_SEASONS` is exported from `breakdown/index.ts`, derived from
`SEASON_COMPONENT_MAPS` the same way `rules.ts` derives `RP_REGISTERED_SEASONS`. Registering a
new season there now automatically extends both breakdown test files with no second edit to
either file's iteration source.

`packages/core/districts/pointModel.test.ts` was never one of the traps. It already iterates
`DISTRICT_REGISTERED_SEASONS` and its equality assertion (line 37) is a deliberate LOUD pin that
fails the instant a season is registered without the pin being updated. It was, and remains, the
exemplar the two breakdown files were just brought up to — not a defect that needed fixing.

The closing claim this section used to make — that only `rules.test.ts` is self-correcting "and
the other three are not" — was wrong for the same reason the file count was wrong. The real
distinction: an *iteration list* fails silently when a season is registered but not added to it;
an *equality assertion* fails loudly the instant the registered set no longer matches the pinned
literal. A registry-driven suite needs exactly one of the latter, not one per file. The
predecessor file already logged this trap after the 2019/2020 job, and it will recur in shape
(a new pin to update, not a new silent gap) on 2018, 2017 and 2016 — see "Then 2017, then 2016"
below.

**What a 2018 executor actually needs: which pins will fail, by design, when 2018 is
registered.** There are three, one per registry family, and each is a one-line literal edit
rather than a bug:

- `packages/core/algorithms/breakdown/groups.test.ts` — the `BREAKDOWN_REGISTERED_SEASONS` pin
  added by quick task 260906-8kd
- `packages/core/algorithms/sigma1/rp/rules.test.ts` — the existing `RP_REGISTERED_SEASONS` pin
- `packages/core/districts/pointModel.test.ts` — the existing `DISTRICT_REGISTERED_SEASONS` pin

The payoff: three loud, self-announcing failures now replace what used to be two silent green

## District key spellings changed — and this has bitten before

2018's districts are `chs, fim, in, isr, mar, nc, ne, ont, pch, pnw` (10). 2019's, for
comparison, are `chs, fim, fma, fnc, in, isr, ne, ont, pch, pnw, tx` (11). So **`mar` becomes
`fma` and `nc` becomes `fnc`** — two new key spellings the codebase has never seen — and `tx`
did not exist in 2018. This is the identical re-keying class already documented at
`apps/web/src/lib/districtNames.ts:13` for `in` and `tx`, so the pattern for handling it exists;
the point is that registry 5 is not a pure append.

## Then 2017, then 2016

2017 (Steamworks) and 2016 (Stronghold) are conventionally additive games, so the hard season is
being done first and the two that follow should be routine. Because the job repeats three times,
two one-time investments are worth making **up front**, on the 2018 pass:

1. **DONE, 2026-09-06 (quick task 260906-8kd).** Make the two hardcoded test season lists
   registry-driven — see THE TRAP, above (corrected count: two files, not three). Paying this
   once removes the same silent failure from all three remaining passes.
2. **DONE, 2026-09-06 (quick task 260906-w38).** Generalize `scripts/recon-*-2019-2020.ts` into
   season-parameterized scripts rather than copying them a third time. The three probes now sit
   on a shared spine (`scripts/recon-shared.ts`) and take `--seasons`:
   `recon-tba-fields-2019-2020.ts` → `recon-breakdown-fields.ts`,
   `recon-rp-rates-2019-2020.ts` → `recon-rp-rates.ts`,
   `recon-rp-thresholds-2019-2020.ts` → `recon-rp-thresholds.ts`. **2018, 2017 and 2016 need no
   new script files.** (`recon-tba-fields.ts` and `recon-rocket-rp-2019.ts` were deliberately left
   alone — the first is a one-shot that also probed Statbotics, the second is genuinely
   season-specific.)

   **The substantive change, not just a rename: RP flags are now found by enumerating EVERY
   boolean field, never by matching names.** The old per-season `RP_FLAGS`/`SUPPORT_FLAGS`/
   `CANDIDATES`/`BOOLEAN_CANDIDATES` records are gone. Measured 2026-09-06, a name filter fails in
   both directions — it finds **zero** RPs for 2016, whose Breach and Capture RPs are named
   `teleopDefensesBreached`/`teleopTowerCaptured` with no RP-shaped name anywhere, and it falsely
   admits `quintetAchieved` (2022), `coopertitionCriteriaMet` (2023/2025) and 2025's `g###Penalty`
   fields. Since 2016 is in this job's own scope, that was not a hypothetical.

   Equivalence proven before the old scripts were retired, by re-running the new ones and
   comparing mechanically: the 2019 (51-row) and 2020 (34-row) field tables came back
   byte-identical; the full 2020 rates walk reproduced 186/52/3,806/7,612 and every flag rate and
   `rp`-distribution row; the full 2020 thresholds walk reproduced 7,640 alliance-sides and all
   five committed rows byte-identically. Enumeration is a strict superset — the rates re-run adds
   one row (`tba_shieldEnergizedRankingPointFromFoul`, 0 of 7,612) that the hardcoded list never
   tracked. Nothing previously recorded changed.

   **Do not "clean up" the two event filters.** `recon-rp-rates.ts` filters by
   `IN_SEASON_EVENT_TYPES` (types 0-6); `recon-rp-thresholds.ts` filters by `EVENT_TYPE_TIERS`,
   which also admits preseason. That is why the same 2020 season is 7,612 alliance-sides in one
   document and 7,640 in the other. Both are correct. Unifying them would silently move every
   number in `docs/data/tba-rp-thresholds-2019-2020.md`.
