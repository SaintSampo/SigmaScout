<planner_decisions>

**PD-01 — S1's target moves from `2024wvrox` to `2022oncmp`, and the move is upward.**
The outline named `2024wvrox` as the 135-match picker target on the strength of CONTEXT's own
"maximum 135" measurement, which is correct about qualification counts and silent about RP
eligibility. Baseline item 4 shows that event publishes no pmf on any row, so the picker never
renders there at all — the tab shows 08-09's unavailable state. `2022oncmp` at 134 rows is the
largest slate the picker can ever actually be handed, and it carries 67 teams against `2024wvrox`'s
30. The retarget therefore costs one row and buys 37 teams and a target that exists. It is held
honest by shipping `2024wvrox` as a control in the same file.
— <reversibility rating="reversible">A spec's target event key and its asserted row count.</reversibility>

**PD-02 — The Simulation tab joins `event-scroll-regions.spec.ts`'s shared block behind a real run,
rather than getting a parallel, weaker block of its own.**
The tab's scroll region does not exist until a simulation completes, which is exactly why 08-09
could not add it at shell stage. The alternative — a separate simulation-only structural describe —
would let the sixth tab drift to a different definition of "sibling region" than the five that
already have one, which is the drift `touchDrag`'s own extraction was done to prevent. So the
`beforeEach` becomes tab-aware and drives a run for `simulation` only, and all four shared tests
plus the vertical-drag test then apply unchanged.
— <reversibility rating="reversible">A `beforeEach` branch and two array entries.</reversibility>

**PD-03 — The four scroll-region assertions are extracted to `apps/web/e2e/support/scrollRegions.ts`
before the Compare spec needs them.**
`compare-narrow-legibility.spec.ts` needs `assertNoPagePan`, `assertOverflows` and
`assertNoIntermediateScroller` for C1, and copying them would create the second hand-maintained
copy of a nested-scroll definition in a repo that already extracted `touchDrag` for exactly that
reason. The extraction is mechanical: the four functions move verbatim, their doc comments — which
carry two hard-won findings, the coupled-axis false positive and the "a region that never overflows
proves nothing" rule — move with them, and `event-scroll-regions.spec.ts` imports them back.
`assertOverflowsY` is the one genuinely new sibling, needed because the picker is a VERTICAL
bounded scroller and the existing helper only measures the horizontal axis.
— <reversibility rating="reversible">A pure move plus one new sibling function.</reversibility>

**PD-04 — Every new spec runs on the LOCAL projects; `event-scroll-regions.spec.ts` keeps its
deployed-origin projects and is red there until the phase deploys.**
Quick task 260830-p6s built the local-origin family precisely so a developer can render-and-look at
a page they just built. All of this plan's surfaces are unshipped Phase 8 code, so the local
projects are the only ones that can be green at execution time, and they read real R2 bytes through
the preview proxy. `event-scroll-regions.spec.ts` is a pre-existing file that also runs on
`pixel-10` and `phone-390` against the deployed apex; its six-trigger assertions go red there until
Phase 8 reaches `main` and `.github/workflows/deploy.yml` publishes. That is this repo's stated
convention for a spec committed ahead of its deploy, not a defect — `table-layout-quality.spec.ts`'s
header records the identical lifecycle. The plan's own green run is the local one, and the SUMMARY
states the deployed half explicitly so nobody reads a post-merge red as a regression.
— <reversibility rating="reversible">A test expectation that a push to `main` makes true.</reversibility>

**PD-05 — At most one `data-testid` may be added to a component, and only if a needed region carries
none.**
07-20 forbade component edits outright because it asserted against a deployed build any edit would
invalidate. That constraint does not apply here — the local projects rebuild from source — but the
spirit does: this plan is evidence, not implementation. So the rule is bounded rather than absolute.
If the rank-distribution table's scroll region ships without a testid, add exactly one following the
established `{tab}-table-scroll` convention, change nothing else in that component, record it in the
SUMMARY as a departure with the sibling plan named, and re-run. Prefer an ARIA role or visible text
over adding anything. Halting the phase's last plan over a missing one-line attribute would be worse
than the departure.
— <reversibility rating="reversible">One attribute, in-convention, no behaviour change.</reversibility>

**PD-06 — S3's `does not degrade performance` half is a printed measurement with a generous ceiling,
not a tight regression bound.**
Browser Monte Carlo runtime varies with visitor hardware, which is D-07's own stated reason for
there being no committed benchmark file. A tight bound here would be a flake generator. The spec
therefore prints the measured elapsed at the phase's worst case and asserts only a ceiling loose
enough that only a real hang or a pathological regression trips it. The number itself is the
deliverable; the assertion is the guard.
— <reversibility rating="reversible">A constant in a spec.</reversibility>

**PD-07 — The `is the page responsive during the run` question routes to the human checkpoint rather
than to a conditional assertion.**
RESEARCH A3 estimates the whole run at well under 100ms, which would make an in-flight
responsiveness assertion either vacuous or conditionally skipped — and a conditionally skipped case
is the silent-green shape this plan exists to prevent. SC-2's "without blocking the page" is
structurally guaranteed by 08-07's Worker and proven there; this plan contributes the measured
runtime at the maximum and routes the felt-responsiveness judgement to a human on real hardware,
where it is answerable.
— <reversibility rating="reversible">Where one judgement is asked.</reversibility>
