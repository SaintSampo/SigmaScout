<objective>
**Build D-07's run control: the one region that turns 1000 draws into something a person can watch,
and give SC-2's "measured and recorded" a durable home.**

Four states in one region. **Idle** — an accent `Run simulation` button, disabled until a start
match is selected. **Running** — an 8px determinate progress bar driven by the Worker's own
`completedDraws`, a live counter beside it, a ticking elapsed timer beneath it, the picker inert and
the rank table holding its pre-run placeholder. **Complete** — one full-ink line stating how long it
took, and the button relabelled. **Error** — inline `Simulation failed to run.` plus Retry, never a
silently-stuck bar.

D-07's user framing, verbatim: *"I love the timer idea. lets have some kind of way to indicate live
progress too, and then they see the total time running the sim took."* All three of those — live
progress, a total time, and the fact that the page stays usable while it happens — are what this
plan renders.

Purpose: this plan owns two obligations nothing else in the phase does.

1. **SC-2's "recorded".** ROADMAP SC-2 requires the simulation's runtime to be *measured and
   recorded*. D-07 accepted the consequence that there is no committed benchmark file — runtime
   varies by visitor hardware and is not regression-testable — and CONTEXT's planner note gives
   "recorded" its only durable home: one representative measured runtime captured into this plan's
   SUMMARY at execution time. Without it `/gsd-verify-phase` may reasonably read SC-2 as unmet.
   Task 3 makes that number a real-browser measurement against real published bytes rather than an
   anecdote.
2. **UI-SPEC's S2 backstop row.** 08-07 shipped the two mock failure modes that make the error path
   testable and explicitly declined to claim the row, recording it as this plan's. Task 2 authors it
   and drives both modes through the rendered surface.

Output: a state machine, a four-state region, the wiring that makes the picker inert and the rank
table patient, a committed real-browser measurement spec, and the permanent proof that Vite emits a
worker chunk now that a real call site exists.
</objective>

<planner_decisions>

- **PD-01 — The run state and the Worker live in a `useSimulationRun` hook, not inside
  `RunControl`.** 08-14's rank table reads the finished `SimResult`, so a result owned privately by
  the button's own component would have to be lifted a wave later anyway, and lifting state after a
  consumer exists is how a second copy appears. The hook owns everything stateful — construction,
  termination, timing, the run-id guard — and `RunControl` becomes a pure function of props, which
  is what lets its four states be asserted in an environment with no `Worker` at all.
  **Reversibility: reversible** (an internal split behind a fixed rendered surface).

- **PD-02 — Staleness is prevented by derivation at render time, never by an effect that clears
  state afterwards.** `SimulationTab` computes a `simulationSignature` string from
  `artifact.algorithmVersion`, the selected start match key, the remaining-match count and the
  baseline count; `start()` stores the signature it ran under; the completed result is exposed only
  when the stored and current signatures are equal, evaluated during render. An effect-based reset
  would repaint one frame with a distribution belonging to a different start match before correcting
  itself, and a correction that runs after the frame has already painted is not a prevention. The
  signature's doc comment must state exactly what it detects (a change of start match, a match
  moving from upcoming to played, a roster change, a republished algorithm version) and what it does
  not (a pmf revised under an identical match count and an identical `algorithmVersion`) — a
  freshness check that overstates its own reach is worse than one that states its limit.
  **Reversibility: reversible.**

- **PD-03 — The button reads `Re-run simulation` only when a completed result for the CURRENT
  selection exists; otherwise `Run simulation`.** The outline's row says "relabeled 'Re-run
  simulation' once a result exists **or the start match has changed**", while UI-SPEC's own Idle row
  says the idle state covers "no run yet, **or start match changed since the last run**" and carries
  the `Run simulation` label. These disagree, and UI-SPEC is the design contract, so the label
  reverts to `Run simulation` when the selection changes. It also reads better: after picking a
  different match the next press is a first run of that choice, not a repeat of the last one.
  **Reversibility: reversible.**

- **PD-04 — The completion line reads `Simulated 1000 draws in {elapsed}s`, one word changed from
  UI-SPEC's Copywriting Contract row, and the change is recorded rather than smuggled.** The
  contract's literal says `matches`, which is wrong under every reading: the run performs
  `SIMULATION_DRAWS` draws over however many qualification matches remain — often 40, sometimes 135,
  never 1000 — and the counter directly above it in the same region has already called the same
  quantity `draws`. Shipping a completion line that contradicts the counter two lines above it, on a
  page whose premise is that its numbers are honest, is not a defensible reading of a contract. The
  executor records the deviation in the SUMMARY, naming the contract row and the one word.
  **Reversibility: reversible** (a single exported copy constant).

- **PD-05 — A run whose elapsed time rounds below 0.1s renders `<0.1s`, not `0.0s`.** Realistic runs
  on a small event are genuinely tens of milliseconds, so this is a live case rather than a
  hypothetical. `0.0s` asserts that the run took no time, which is false and reads as a broken
  timer; `<0.1s` asserts only what one decimal place can resolve, which is true. The exact
  millisecond value is preserved unrounded in the completion element's measurement attributes and in
  SC-2's SUMMARY line, so nothing is lost — only the display is bounded. **Reversibility:
  reversible.**

- **PD-06 — The counter advances in `PROGRESS_CHUNK_DRAWS` steps and is never interpolated.**
  08-07 emits one progress message per 50-draw chunk, so a 1000-draw run produces exactly 20
  updates: 50, 100, ... 1000. UI-SPEC's `347 / 1000 draws` is an illustration of the FORMAT, not a
  claim that every integer is reachable. Smoothing the number between two reported values — a
  requestAnimationFrame tween, an eased bar, a synthetic counter — would display a draw count the
  Worker never reported, which is a fabricated number dressed as a measured one. The bar's width and
  the counter's text both derive from the same `completedDraws` field, so they cannot disagree.
  **Reversibility: reversible.**

- **PD-07 — The user-facing elapsed time is measured on the main thread from the Run handler to the
  arrival of the `result` message; `computeMs` never becomes rendered text.** This is 08-07's PD-05
  honoured at the call site it was written for. The main-thread interval is what the visitor
  actually waited through — it includes Worker construction, the structured-clone transfer of the
  request, the draw loop, and the transfer back — whereas `computeMs` is the draw loop alone.
  Publishing both would invite a "which one is real" question with no good answer.
  **Reversibility: reversible.**

- **PD-08 — The completion element carries four measurement `data-*` attributes and renders none of
  them as text: `data-elapsed-ms`, `data-compute-ms`, `data-team-count`, `data-remaining-matches`.**
  SC-2 needs a number readable from a real browser, and every alternative is worse: a temporary
  `console.debug` has to be added and reverted (and one day will not be), a permanent one is noise
  in every visitor's console, and reading React state through devtools is not a procedure anyone can
  repeat. Four small numeric attributes on one element are invisible to the reader, assertable in
  jsdom, readable in a real browser's Elements panel, and are what Task 3's spec prints. Their doc
  comment must state that they are a measurement affordance and must never be promoted into rendered
  copy (PD-07). **Reversibility: reversible.**

- **PD-09 — One Worker per run, and it is terminated on the terminal message, on a new run, and on
  unmount.** A dedicated Worker is cheap to create and there is nothing to gain from holding an idle
  thread between runs, while holding one across a SPA navigation is the client-side leak RESEARCH's
  Security Domain names. Terminating on the terminal message also means the common path leaves
  nothing alive at all, so the unmount cleanup is a backstop rather than the only defence.
  **Reversibility: reversible.**

- **PD-10 — A monotonically increasing run id guards every message handler, as defence in depth
  rather than as the primary mechanism.** `terminate()` is specified to stop delivery and 08-07's
  mock models that, but a message already dispatched into the task queue when `terminate()` runs is
  not something this component can prove is impossible in every real engine. Each handler compares
  the id captured when its Worker was constructed against the current one and returns early on a
  mismatch. The guard's comment must say it is redundant with `terminate()` and why it is kept
  anyway, so a later reader does not delete it as dead code or, worse, start relying on it instead of
  terminating. **Reversibility: reversible.**

- **PD-11 — No cancel affordance and no watchdog timeout, both sourced rather than omitted.**
  UI-SPEC's run-control table lists three states plus an error state and none of them offers a
  cancel, and 08-07's PD-06 already establishes that the only mechanism that could work mid-run is
  `terminate()`. A watchdog timeout is worse than absent: 08-07 guarantees every exit from
  `runSimulationJob` emits a terminal message, so a run that produces neither a result nor an error
  means the Worker itself died — which surfaces on `onerror` — and a timer that gives up on a slow
  visitor's device would manufacture a failure out of slowness. Recorded here so the absence reads
  as a decision. **Reversibility: reversible.**

- **PD-12 — SC-2's measurement is a committed Playwright spec on the `local-desktop` project, not a
  hand-run browser session.** That project builds the app, serves it from `vite preview`, and
  proxies `/v1` to the real `data.sigmascout.org` bytes — a real Chromium, a real module Worker, and
  real published artifacts, which is exactly the combination 08-07's first prohibition says a mock
  cannot stand in for. A committed spec also makes the measurement repeatable by the next person,
  which a devtools screenshot is not. The spec asserts the measurement's shape and prints the
  numbers; it asserts no threshold (see the third prohibition). **Reversibility: reversible.**

- **PD-13 — The error region renders the fixed copy only; the thrown error's `name` and `message`
  never reach the DOM.** UI-SPEC fixes the string, 08-07 deliberately keeps its error payload to a
  name/message pair with no stack so a developer can tell an invalid-request rejection from an
  unknown-team-key throw in the console, and rendering internals into a page is how an internal
  identifier becomes a user-facing string nobody meant to ship. **Reversibility: reversible.**

- **PD-14 — No `checkpoint:decision` in this plan.** `REVERSIBILITY_GATES` is on and only a
  `one-way` rating earns a gate. Every task here adds new component files, edits two files this
  phase already created, widens one regex in `playwright.config.ts`, and publishes nothing: no R2
  object, no schema change, no dependency, no migration. `git revert` undoes the whole plan.

- **PD-15 — The 8px progress-bar height is a locally declared `PROGRESS_BAR_H_PX` constant with a
  doc comment naming `matchAxis.ts`'s `MATCH_GEOMETRY.BAND_H`, not an import of it.** UI-SPEC locks
  the height at 8px "matching the app's existing `BAND_H = 8` visual vocabulary", and matching a
  vocabulary is not the same as sharing a source of truth: `BAND_H` is the height of a prediction
  band on a score axis, and coupling a progress indicator to it would mean a future change to the
  match plot's geometry silently resizes a progress bar. The doc comment carries the cross-reference
  so the shared value is visible to a reader without being enforced on a compiler.
  **Reversibility: reversible.**
