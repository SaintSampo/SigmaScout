<objective>
Turn the proven single-artifact path into the whole published data set, and measure what it costs.

Purpose: Success Criterion 1 asks for two things that are easy to conflate — artifacts covering every
page, *and* per-page payload sizes measured and recorded as a budget. The second is not paperwork.
`04-CONTEXT.md` D-05 names the two artifacts most at risk (the ~3,750-row year-wide teams table and
the 292-match team page) and requires the budget to name them explicitly, because page load speed is
this project's stated top UX priority and a payload regression is otherwise invisible until someone
notices the site got slow.

**The tension this plan resolves.** `04-CONTEXT.md` states it outright and forbids papering over it:
D-12 calls for a *scheduled* re-baseline that overwrites live state, while D-24 makes publishing a
local CLI command running against a 336 MB corpus that lives on one machine. A schedule that only
runs when a laptop is on is not a schedule. This plan takes option (a) from the CONTEXT's own two:
the re-baseline is defined as an explicitly manual, human-triggered operation performed before and
after an event weekend, and the budget doc says so plainly in those words. Option (b), CI-based
publishing with a corpus snapshot in R2, is recorded in the same doc as the named follow-on that
becomes worth doing if manual re-baselining proves impractical — it is already in `04-CONTEXT.md`'s
Deferred Ideas, and this plan does not build it.

Output: the full published artifact set for 2022-2026 across the three shipped algorithms, one
committed budget doc with real measured numbers, and a test that fails when a payload outgrows them.
</objective>
