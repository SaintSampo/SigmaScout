<objective>
Stand up the Worker project and build the two pieces of genuinely new engineering this phase needs:
the batched state store, and the subrequest budget that keeps a busy Saturday from silently starving
an event.

Purpose: `04-RESEARCH.md` says outright that this phase is "almost entirely reuse and orchestrate",
with one exception — "the D1 batching layer and the subrequest-budget bookkeeping, which has no
existing analog to reuse". That is what this plan is. Both are small; both are the kind of small that
fails at exactly the wrong moment if it is written casually.

The subrequest budget is worth understanding before writing it. Cloudflare's free plan caps a Worker
invocation at 50 subrequests, and R2, D1 and KV binding calls all count. `04-RESEARCH.md` works the
peak-tick arithmetic at the measured 38-concurrent-event peak and lands at ~46-49 — under the cap, but
with almost no slack, and its own Pitfall 1 points out that figure is a per-event average rather than
a worst case: an elimination-bracket flurry resolving across several events in one tick multiplies the
artifact writes and can blow past 50 well before 38 events. The platform's response to exceeding it is
a throw, not a throttle. So the naive design does not degrade — it fails, and it fails on the busiest
day of the season. D-15 exists because the user asked for exactly the opposite behaviour: overload
should become delay.

Output: a deployable Worker skeleton with its D1 database created and migrated, a state store that
costs two subrequests regardless of how many teams a tick touches, and a budget that defers rather
than throws.
</objective>

**The read.** `readScopedState(db, algorithmId, scopeKind, scopeKeys)` builds one prepared statement
with a placeholder per key and binds them all:
`SELECT scope_kind, scope_key, algorithm_version, state_json, generation, computed_at FROM
algorithm_state WHERE algorithm_id = ? AND ((scope_kind = ? AND scope_key IN (?,?,...)) OR scope_kind
= 'league')`. One statement, one subrequest, however many teams. The league row rides along in the
same query rather than costing a second one — a separate lookup would double the read cost for a value
every tick needs.

Guard the key count: D1 and SQLite both have a bound-parameter ceiling, and the peak tick's ~21 keys is
nowhere near it, but a caller that one day passes a thousand should get a named error rather than an
opaque driver failure. Chunk or throw — chunking is fine as long as the chunk size is a named constant
and the common path stays one statement.

**The write.** `writeScopedState(db, rows)` maps every row to an upsert prepared statement and hands
the whole array to `db.batch([...])` in one call:
`INSERT INTO algorithm_state (algorithm_id, algorithm_version, scope_kind, scope_key, state_json,
generation, computed_at) VALUES (?,?,?,?,?,?,?) ON CONFLICT(algorithm_id, scope_kind, scope_key) DO
UPDATE SET algorithm_version = excluded.algorithm_version, state_json = excluded.state_json,
generation = excluded.generation, computed_at = excluded.computed_at`.

Write the module header to state the transaction semantics plainly, because they differ from the other
two stores this Worker talks to and the difference is load-bearing: a D1 batch is a transaction and
rolls back whole, so a rejected write means **none** of these rows advanced this tick. There is no
partial-success handling and there must never be one; on failure the caller re-attempts the whole batch
next tick. R2 is the opposite (each put succeeds independently) and KV is eventually consistent, so
three different failure models sit side by side in one Worker and conflating them is how a subtle
inconsistency gets shipped.

**Idempotency.** Add `readEventCursor` / `writeEventCursor` over `event_cursor`, and
`hasAlreadyFolded(cursor, matchKey, orderedMatchKeys)`. The cursor's `last_folded_match_key` is the
anchor: a tick folds only matches that come after it in the event's own order, then advances it. That
is what makes a retried invocation, an overlapping invocation, or an unchanged TBA payload a genuine
no-op rather than a double count — and a double count is not a cosmetic bug here, it is a team's rating
updated twice for one match, which then propagates through every subsequent prediction.

Skipping a write for an unchanged row matters too: plan 04-03's serializer is key-sorted and stable
precisely so an untouched team re-serializes byte-identically. Compare before writing and drop
unchanged rows from the batch. That is a direct saving against D1's 100,000-rows-written-per-day free
allowance.

**Testing without a real D1.** Write a small fake `D1Database` in the test file — `prepare()` returning
a bindable statement, `batch()` accumulating, both counting calls — rather than reaching for a
Miniflare integration harness. The properties under test are call counts and SQL shape, and a fake
makes them assertable in milliseconds. The real thing gets exercised end to end in plan 04-07.

**`SubrequestBudget`.** A small class holding `cap`, `reserve` and `used`, with `tryConsume(n)`,
`consume(n)` (throws if it would exceed, for call sites where exceeding is a genuine bug), `remaining`,
and `used`. Export `SUBREQUEST_CAP = 50` and `SUBREQUEST_RESERVE` (start at 4) as named constants with
comments giving their provenance: the cap is the documented Workers free-plan per-invocation limit, and
the reserve exists because the tick's own fixed costs — the manifest read, the batched state read, the
batched state write — must never be the calls that get squeezed out.

The whole point of `tryConsume` returning a boolean rather than throwing is D-15: work that does not fit
this tick is **deferred**, not attempted. A `consume` that throws is for the fixed costs, where running
out means something upstream miscounted.

**`rotate(items, offset)`.** Returns the list rotated to start at `offset % items.length`. The caller
persists an offset that advances by the number of events actually processed, so the next tick starts
where this one stopped. That is the mechanism D-15 asks for, and the reason it is needed is worth
writing into the header: a Worker that iterates live events in a stable order and stops at the
subrequest cap serves the same front-of-list events every single tick and never reaches the tail — the
tail events are not delayed, they are permanently omitted, and nothing about that is visible in a log.
The user's own framing was that hitting the limit should mean requests catch up when they can. Rotation
is what makes that literally true.

Sort the event list by event key before rotating so equal-comparing entries have a deterministic total
order, following the precedent `selectMatchesChronological` set. A rotation over an unstable order is
not a rotation over anything.

**Where the offset lives.** In D1, not KV — a per-tick write to KV would burn the 1,000-writes-per-day
free allowance in a single event day. Reuse the `event_cursor` table with a reserved key, or add a
one-row table; pick one, implement it, and say which in the module header with the KV reason stated.

**The no-starvation test.** Build a list of, say, 40 events and a cap that admits 6 per tick. Tick
repeatedly, advancing the offset each time, and collect which events were processed. Assert that after
`ceil(40/6)` ticks every event has been processed at least once. Then assert the counterfactual
explicitly with a second test that runs the same loop with the offset pinned at 0 and shows events past
index 5 are never reached — so the test file itself records why rotation is not optional.

**On the measured cap.** The code-side budget is what this task can prove. What a real invocation
actually consumes on the deployed Worker is measured in plan 04-07 and recorded in the budget doc; this
plan's `must_haves` marks that as a backstop truth for exactly that reason. Do not write a comment or a
SUMMARY line claiming the deployed peak has been verified.
