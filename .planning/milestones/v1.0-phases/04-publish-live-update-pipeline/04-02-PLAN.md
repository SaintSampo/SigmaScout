<objective>
Define, once, the exact shape of every file the site will fetch — and the rounding rule that makes
those files small enough to be worth fetching.

Purpose: D-01 makes one page render exactly one fetch, which means the schema for each page IS the
contract between this phase and Phases 5-8. Getting it wrong is cheap now and expensive the moment
plan 04-04 publishes ~61,000 objects against it. This plan writes the five schemas and their tests
with no publishing machinery attached, so the contract can be reviewed on its own merits.

The rounding rule is the other half. `04-CONTEXT.md` D-06 leaves the per-field precision to the
planner's discretion, and it matters more than it looks: the two artifacts D-05 names as most at risk
are the year-wide teams table (~3,750 rows) and the 292-match team page, and unrounded doubles cost
roughly three times what display-relevant precision does. The rule is written as code with an
explicit tie-breaking contract rather than as prose, because "we rounded" without saying how is the
kind of claim that cannot be checked.

Output: five page schemas, a tested rounding module, and the corpus reader D-08's scheduled-match
parameters need.
</objective>

  <action>
Create `packages/harness/rounding.ts` implementing D-06's rounding rule, and
`packages/harness/rounding.test.ts` covering the behaviours above. Write the tests first — every
behaviour listed is a concrete input/output pair, which is exactly the case where writing the

The rule, and the reasoning to record in the module's file header:

| Field class | Decimals | Why |
|---|---|---|
| Display metrics (`TeamMetric.value`, `TeamMetric.spread`, component means and variances) | 2 | These are shown as `X ± Y` on a page; a third decimal is never rendered and never read. |
| Predicted and actual alliance scores | 2 | Same reason; FRC scores are integers, and a predicted score's second decimal is already below what any reader acts on. |
| Probabilities (`pRedWin`, per-match win probability) | 4 | Phase 8's simulation draws from these, so they keep more digits than anything merely displayed. A Brier score is quadratic in this value, so 4 decimals keeps the published number and the harness number agreeing to well inside any figure the site quotes. |
| RP pmf entries | 5 | Phase 8 draws ranking points from these repeatedly across a 1000-run simulation, where a truncation bias would compound rather than cancel. |
| Alliance-total predictive `variance` | 4 | It is the square of a spread the page shows to 2 decimals; rounding it as coarsely as the spread would visibly distort the derived `±`. |

Exports: `roundTo(value, decimals)`, `roundMetric`, `roundProbability`, `roundPmf`, and
`ROUNDING_RULE` (the table above as plain data: a record from field-class name to decimal count).

`roundTo` implements half-away-from-zero explicitly — take the sign, scale, `Math.round` the
magnitude, unscale, restore the sign — rather than relying on `Math.round`'s own half-up-toward-
positive-infinity behaviour, which is asymmetric for negatives. State that choice in the header:
symmetric rounding means a metric and its negation round to the same magnitude, which is the
behaviour a reader comparing two teams' deltas would expect.

`roundPmf` rounds every entry, then computes the residual `1 - sum` and adds it to the entry with the
largest rounded value. Adding the residual to the largest entry (rather than distributing it, or
adding it to index 0) keeps the correction relatively smallest and is deterministic; when two entries
tie for largest, take the lowest index so the function is a pure function of its input. Document that
tie-break in the header — an undocumented tie-break is exactly the kind of thing that quietly differs
between the offline and online paths and breaks D-14's equivalence assertion.

The module's file header must also state the boundary plainly: this module is for building published
artifacts only. It is never called from the scoring path, the prediction sidecars, or anything a
committed digest hashes. Name `computePredictionStreamDigest` as the thing whose input must stay
unrounded, and say why (a promoted version's digest is the record that a run reproduces).
