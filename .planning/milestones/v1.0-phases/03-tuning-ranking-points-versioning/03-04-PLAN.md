<objective>
Give Sigma1 within-season online adaptation in the classical adaptive-Kalman sense, and make
the on/off question answerable by measurement rather than argument.

Purpose: ALGO-05 asks the harness to validate WHETHER adaptation improves predictions. D-05
fixes the meaning of "adapts online" as innovation-driven noise adaptation; D-07 fixes its
granularity at one scalar per team; D-08 fixes what happens if it does not pay — it ships
disabled and the negative result is written up. This plan builds the mechanism and the two
registry entries; plan 03-05 runs the two independent searches and plan 03-06 records the
verdict.

Output: `adaptation.ts`; adaptation parameters on `Sigma1Params`; the on/off registry pair.

The comparison itself is deliberately NOT in this plan. Building the mechanism and judging it
in the same plan is how "iterate until it wins" happens by accident.
</objective>

**`packages/core/algorithms/sigma1/adaptation.ts` (new).**

The classical adaptive-Kalman idea, stated concretely for this model: under a correctly
specified filter, the NORMALIZED innovation `innovation / sqrt(pooledVariance)` has unit
variance. A team whose recent normalized innovations are consistently larger than that is one
the filter is under-reacting to — its true ability is moving faster than the process noise
allows — and its process noise should grow. A team whose normalized innovations are
consistently smaller is one the filter is over-reacting to, and its process noise should shrink.

Exports:
- `InnovationStats` — a per-team running EWMA of SQUARED normalized innovation, plus an
  observation count. Not an `ExpandingStats`: this must be a recency-weighted window (a regime
  change is precisely what it exists to detect), so it uses its own EWMA with
  `params.adaptationEwmaAlpha`.
- `emptyInnovationStats()` — the cold-start value is exactly 1.0 with count 0, i.e. "assume the
  filter is correctly specified until this team's own data says otherwise". A cold start of 0
  would make every new team's factor slam to the minimum bound.
- `foldInnovation(stats, normalizedInnovation, alpha)` — the EWMA fold, pure, returning new
  stats.
- `adaptationFactor(stats, params)` — returns `1` exactly when `params.adaptationEnabled` is
  false OR when `stats.count < params.adaptationMinObservations`; otherwise
  `clamp(pow(stats.meanSquaredNormalizedInnovation, params.adaptationExponent), params.adaptationMinFactor, params.adaptationMaxFactor)`.
  Returning the literal `1` on the disabled path (rather than computing and happening to get 1)
  is what lets the caller multiply unconditionally while adaptation-off stays bitwise identical
  to the pre-adaptation arithmetic — multiplication by an exact 1.0 is exact in IEEE-754, and
  the test in Task 2 proves it end to end rather than trusting the reasoning.

D-07's granularity is enforced by the shape itself: ONE `InnovationStats` per team, folded from
the team's AGGREGATE normalized innovation across that match's components, never one per
component. Per-team-per-component would multiply free parameters by roughly 13 over data that
is already sparse per team — structurally the same trap as the failure log's collapsed 4D
model. State that in the module header with the decision ID.

The aggregate normalized innovation for one team in one match is the root-mean-square of that
team's per-component normalized innovations, iterating `state.componentOrder` (the fixed array),
never a freshly enumerated key list.

**`packages/core/algorithms/sigma1/params.ts`.** Add, each with a doc comment naming D-05/D-07
and carrying the "Phase 3 hyperparameter, default unverified" phrasing so the sensitivity screen
finds them:
- `adaptationEnabled: boolean` — default `false`. D-08: the default promoted version ships
  adaptation OFF unless the measurement says otherwise, so `false` is the honest default from
  the first commit rather than something flipped back later.
- `adaptationEwmaAlpha: number` — default 0.2, matching `consistencyEwmaAlpha`'s reasoning
  (one off match must not swing the factor).
- `adaptationExponent: number` — default 0.5, so the factor scales with the ratio of observed
  to expected innovation STANDARD deviation rather than variance; a gentler default than the
  raw variance ratio.
- `adaptationMinFactor` / `adaptationMaxFactor` — defaults 0.25 and 4.0. An unbounded adaptive
  filter can destabilize: an over-large factor inflates `P`, which inflates the Kalman gain,
  which produces a larger innovation next match, which inflates the factor again. The clamp is
  the documented stability bound, not decoration.
- `adaptationMinObservations: number` — default 3. Below it the factor is exactly 1: a team's
  first match cannot tell you its regime is changing.

`Sigma1ParamsSchema` gains the matching entries (`z.boolean()` for the flag, `z.number().finite()`
for the rest). `SIGMA1_PARAM_KEYS` picks them up automatically since it is derived and sorted.
Note in `params.ts` that `adaptationEnabled` is a MODE, not a numeric knob, and is therefore
excluded from the sensitivity screen's sweep (plan 03-05 searches it as two separate runs per
D-06, never as a dimension inside one run).

**`packages/core/algorithms/sigma1/index.ts`.**
- `Sigma1TeamState` gains `innovationStats: InnovationStats`. `coldStartTeamState` seeds it
  with `emptyInnovationStats()`. `carrySeason` resets it to `emptyInnovationStats()` — a year
  of layoff makes last season's regime evidence stale, the same reasoning that re-inflates
  posterior variance at a boundary.
- `applyTeamProcessNoise` multiplies its `q` by `adaptationFactor(teamState.innovationStats, params)`
  before calling `applyProcessNoise`. Both the within-event and the event-boundary magnitudes
  are scaled — D-05 names process noise as the adaptation target, and a factor that applied to
  only one of the two would make the adaptation's effect depend on the event calendar.
- `applyAllianceUpdate` already computes `innovation` per component and `pooledVariance` is
  available from the same teammate beliefs and measurement noise. Compute each team's
  per-component normalized innovation there, RMS them across `componentOrder`, and fold the
  result into that team's `innovationStats` in the same pass that already writes
  `covariance` / `consistency` / `matchCount`. No second loop over the alliance.
- `teamMetrics` is UNCHANGED. Claude's Discretion, resolved: adaptation does NOT touch the
  published consistency spread. That number is what the site shows as `±` and it must stay a
  direct empirical estimate of the team's own residual spread; letting a responsiveness knob
  move it would make a displayed uncertainty partly a function of a tuning parameter. Say so in
  a comment at the `teamMetrics` definition.

**`packages/core/algorithms/sigma1/adaptation.test.ts` (new).** Pure unit tests: cold-start
stats give a factor of exactly 1; a run of large normalized innovations drives the factor up
and it saturates at exactly `adaptationMaxFactor` (assert `toBe`, not `toBeCloseTo` — the clamp
must return the bound itself); a run of small ones saturates at exactly `adaptationMinFactor`;
`adaptationEnabled: false` returns exactly 1 regardless of stats; a team below
`adaptationMinObservations` returns exactly 1; `foldInnovation` is pure and returns new stats.
