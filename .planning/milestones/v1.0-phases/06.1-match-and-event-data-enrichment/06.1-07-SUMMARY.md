## Deviations from Plan

### Documented (not auto-fixed) discrepancy

**1. Two page kinds beyond `team/{teamKey}/{year}` moved — investigated, and the cause is entirely pre-06.1 Phase-6 work, never this phase's own**

- **Found during:** Task 2, comparing the real republish's per-page-kind summary against `docs/publish-budget.md`'s prior recorded figures.
- **What was expected:** the plan's own framing (and its acceptance criteria) assumed only `team/{teamKey}/{year}` would move, since this phase's three items (event rank/total, predicted+actual per-bonus RP, history-row percentiles) all land on that one artifact.
- **What was measured:** `teams/{year}` grew from 2,721,887 to 3,577,069 bytes (max), and `event/{eventKey}` grew from 276,105 to 285,437 bytes (max) — both real, both confirmed by re-running the exact publish command a second time and getting byte-identical results (ruling out non-determinism).
- **Why:** two Phase-6 commits (`06f468ad`, `bf1e3228`), dated 2026-08-26 — after the prior recorded 2026-08-25 run and before this 06.1 phase began — added phase-group metrics (`phaseAuto`/`phaseTeleop`/`phaseEndgame`, value+spread+percentile) to every algorithm's `teamMetrics()` output and a per-metric `tier` field to the `teams/{year}` artifact. Both commit messages state "Not yet visible on the site — requires an artifact republish." This run is the first republish since they landed, so their effect was swept in.
- **Why not "fixed":** there is nothing to fix — this is not a bug introduced by this plan or this phase; it is real, pre-existing, already-committed, already-tested (typecheck clean, full suite green at the time) work that had simply never been published. Reverting or hiding it would misrepresent what the published artifacts actually contain.
- **Files modified:** `docs/publish-budget.md` only — the investigation and attribution are documented there in a dedicated section, in this SUMMARY, and cross-checked by reading the unmodified `buildEventArtifact`/`buildTeamsArtifact` source directly.
- **Verification:** `buildEventArtifact` and `buildTeamsArtifact` read directly (no `redBonusRp`/`percentile`/`rank`/`totalTeams` reference in either); a second dry-run of the same command byte-for-byte reproduced the same `teams`/`team`/`event`/`events`/`compare` figures, ruling out non-determinism.
- **Committed in:** `6f0d250f` (Task 3 commit).

**2. `teams/{year}`'s measured maximum now exceeds its own committed `budgetMaxBytes` ceiling — a real, open finding, deliberately not fixed**

- **Found during:** Task 3, running `pnpm vitest run packages/harness/payloadBudget.test.ts` against the updated document.
- **What was measured:** `teams/{year}`'s new maximum, 3,577,069 bytes, exceeds its committed `budgetMaxBytes` of 3,500,000 bytes by 77,069 bytes. `payloadBudget.test.ts`'s internal-consistency check fails with exactly this assertion. The absolute-ceiling test (`TEAMS_PAGE_ABSOLUTE_MAX_BYTES = 5,000,000`) still passes.
- **Why:** entirely `bf1e3228`'s per-metric `tier` field (deviation #1 above) — never this phase's own scope, and never a page kind this phase's Task 1 projection checked (Task 1's projections, following the plan's own literal instruction, checked only the `team` [singular] 375,000-byte ceiling).
- **Why not fixed:** this plan's own first prohibition — "MUST NOT raise a committed payload budget ceiling... in order to make a failing gate pass" — applies here exactly as it does to the `team` ceiling the plan explicitly names. Shrinking the artifact (e.g. revisiting `bf1e3228`'s own documented Common-tier-omission trade) is a source-code change outside this docs-only plan's scope fence and outside its single-republish authorization. Raising the ceiling to make the test green would hide a real measurement, exactly what this plan's own philosophy exists to prevent.
- **Files modified:** none beyond `docs/publish-budget.md`'s own honest documentation of the failure.
- **Verification:** `pnpm vitest run packages/harness/payloadBudget.test.ts` — 9/10 pass, the one failure is this exact, named, expected assertion. `pnpm test` (full suite) — 1421/1422 pass, same single failure, no other regression.
- **Committed in:** `6f0d250f` (Task 3 commit). Logged to `.planning/WINDOWS.md` ledger entry #11 (`unmet-truth`, phase `06.1`, status `open`) for a future developer decision.
