# Phase 06.1 Plan 08: Close G-06.1-26/G-06.1-28 gap closure Summary

Gated bonus-RP dots on qualification comp level end-to-end (core predicate, pipeline, and client)
so a played playoff match never renders earned/missed dots even against the 54,671 already-published
artifacts that still carry stale playoff bonus arrays, and removed the per-event tier-basis caption
per the developer's pre-resolved checkpoint decision, signing T-06.1-24 as an accepted risk.

## What Was Built

**G-06.1-26 (major, Task 2 + Task 3).** `isBonusRpCompLevel` is now the single exported predicate
(`packages/core/algorithms/sigma1/rp/constants.ts`) expressing "FRC awards bonus ranking points in
qualification play only." All three previously-independent copies of that rule now call it:

- **Predicted side** (`packages/core/algorithms/sigma1/rp/distribution.ts`'s `rpPmfForMatch`): the
  existing literal `compLevel !== "qm"` short-circuit was replaced by `!isBonusRpCompLevel(compLevel)`
  — a behaviour-identical refactor, proven so by `digest.test.ts` still reproducing both committed
  `sigma1@2.0.0` versions bitwise (3 tests, 0 skipped).
- **Actual side** (`packages/harness/publish.ts`'s `actualBonusFlagsForSeason`): a playoff match now
  `continue`s before any other eligibility check, producing genuine ABSENCE (no map entry) rather than
  `null` — this was the real defect (G-06.1-26's root cause): the actual side had NO comp-level gate at
  all before this plan.
- **Client guard** (`apps/web/src/components/team/BonusRpDots.tsx`): a new REQUIRED `applicable: boolean`
  prop forces every dot to `unknown` (with a label saying the bonus is not awarded outside qualification
  matches) regardless of what `states` carries. `MatchTable.tsx` threads `match.compLevel` into both
  `PredictedScoreLine` and `ActualScoreLine` and passes `applicable={isBonusRpCompLevel(compLevel)}` to
  both `BonusRpDots` call sites. This is the defence-in-depth layer that makes the fix effective
  immediately, with no republish, against artifacts already sitting in R2.
- **Artifact-assembly defence-in-depth** (`packages/harness/publish.ts`'s `buildTeamSeasonArtifact`,
  Rule 2 addition beyond the plan's literal per-task file list — see Deviations): `redBonusRp`/
  `blueBonusRp` switched from an always-present direct assignment to a conditional spread, and BOTH the
  predicted and the pre-existing actual per-bonus spreads are now also gated on
  `isBonusRpCompLevel(match.compLevel)`. This makes the artifact-build boundary itself refuse to publish
  either kind of per-bonus data for a playoff row even if a caller's `Prediction` or
  `actualBonusFlagsByMatchKey` map happens to carry populated values for it — proven by a dedicated
  invariant test (Task 3) that deliberately feeds exactly that shape.
- Extended as a fourth `browserSafeSchemas.test.ts` entry point (`rp/constants.ts`, checked for Node
  built-ins only, matching plan 05-05's precedent for the breakdown leaf module).
- Two new `MatchTable.test.tsx` cases (2024 `sf`, 2026 `f`) prove a played playoff row renders every
  dot `unknown` even when the artifact still carries populated actual arrays — the RED output before
  the fix is quoted verbatim below.
- Two new `publish.test.ts` invariant cases: `actualBonusFlagsForSeason` maps a match IFF `compLevel`
  is `qm`, asserted over one mixed stream of all five comp levels (non-vacuous: stream length 5, map
  size 1); `buildTeamSeasonArtifact`'s `sf` row carries NEITHER predicted nor actual per-bonus keys
  while a `qm` row in the same artifact carries all four.
- `.planning/todos/pending/republish-playoff-bonus-arrays.md` records the deliberately-deferred
  republish (PD-16).

**G-06.1-28 (cosmetic, Task 1 + Task 4).** The per-event tier-basis caption (`EventSection.tsx`) —
four words of muted text with the season-final-basis explanation in its hover tooltip, rendered once
per event card — is removed entirely, along with the now-dead `hasTieredTile` computation. Per Task
1's resolved checkpoint (**option-a**, "remove it completely — no explanation anywhere"), no
replacement explanation was added anywhere on the site. `TierKeyRow.tsx` and `TierKeyRow.test.tsx` were
deliberately left untouched (those were option-b/c's targets). The surviving comment above the
`MetricValue` call in `EventSection.tsx` now records plainly that the season-final basis is
deliberately not stated on this surface, naming the Task 1/option-a decision, so a future reader finds
the reason rather than assuming an oversight. `06.1-08-PLAN.md`'s own threat register was edited in
place: T-06.1-24 (Repudiation, tier colour with no stated basis, severity high) moved from its
contingent `mitigate (option-b/c) / accept (option-a)` disposition to a flat `accept`, signed
**Jacob Williams**, **2026-08-26** — an accepted risk, not a closed one.

## No Republish Was Run (PD-16)

No republish was run, and none was needed. The pipeline gate (`actualBonusFlagsForSeason`'s new
comp-level check, `buildTeamSeasonArtifact`'s new conditional-spread gates) only affects artifacts
produced from now on — the ~54,671 team-season artifacts already in R2 still carry stale playoff
bonus arrays in their raw JSON. What makes this safe to defer is the client guard:
`BonusRpDots`'s REQUIRED `applicable` prop structurally forces every bonus dot to `unknown` for a
non-qualification `compLevel` regardless of what the artifact's JSON contains, so no surface on the
site reads the stale data even though it is still physically present in the published bytes. A full
republish costs ~23 min wall clock and rewrites all 54,671 objects (measured, plan 06.1-07), and the
"one authorized republish per phase" discipline exists specifically because 06.1-07's run swept in
unrelated committed-but-unpublished work and blew a payload ceiling (WINDOWS.md ledger #11) — spending
an unplanned republish now would repeat that exact risk for a defect the client already can't render.
The deferred republish is tracked at
`.planning/todos/pending/republish-playoff-bonus-arrays.md`, to be verified opportunistically the next
time a scheduled republish runs (Phase 7 or the live cron).

## Deviations from Plan

### Auto-fixed / auto-added

**1. [Rule 2 - missing critical functionality] `buildTeamSeasonArtifact` gated its own per-bonus field
assembly on `isBonusRpCompLevel`, not just `actualBonusFlagsForSeason`.**
- **Found during:** Task 3, while designing the `buildTeamSeasonArtifact` cross-side invariant test the
  plan's own `<behavior>` section specifies.
- **Issue:** The plan's `must_haves.truths` requires "A `buildTeamSeasonArtifact` row for a played
  playoff match carries NEITHER `actualRedBonusRp`/`actualBlueBonusRp` NOR `redBonusRp`/`blueBonusRp`
  as properties (absent, asserted with `not.toHaveProperty`)" — as a property of `buildTeamSeasonArtifact`
  itself, not merely as a consequence of a well-behaved caller never supplying that data. Before this
  fix, `buildTeamSeasonArtifact`'s predicted-side fields (`redBonusRp`/`blueBonusRp`) were an
  unconditional direct assignment sourced straight from whatever the caller's `Prediction` object
  carried, with no comp-level check at all; the pre-existing actual-side conditional spread checked
  only "is there a map entry", not "is this comp level eligible." A caller that (like the artifacts
  published before this plan, or a future non-Sigma1 algorithm) supplied populated bonus data for a
  playoff row would have had it published verbatim.
- **Fix:** `redBonusRp`/`blueBonusRp` switched from direct assignment to conditional spread (mirroring
  `rank`/`totalTeams`'s own existing "genuinely absent, not merely undefined" convention), and both the
  predicted and the pre-existing actual per-bonus spreads are now gated on
  `isBonusRpCompLevel(match.compLevel)`. This does not add a new copy of the qualification-only rule —
  it is one more call site of the same single `isBonusRpCompLevel` predicate, inside the same file
  (`publish.ts`) the plan already names as owning the "actual gate."
- **Files modified:** `packages/harness/publish.ts` (already in the plan's `files_modified` frontmatter;
  not in Task 3's own per-task `<files>` list, which only names test/pipeline files — the code change
  was necessary to make Task 3's own specified test assertion literally true).
- **Verified:** the new `publish.test.ts` invariant case deliberately feeds a `Prediction` carrying
  populated `redBonusRp`/`blueBonusRp` AND a populated `actualBonusFlagsByMatchKey` entry for the `sf`
  match, and confirms both are structurally absent on the parsed row. All 46 pre-existing
  `publish.test.ts` cases still pass unmodified.
- **Commit:** `7120952e`
