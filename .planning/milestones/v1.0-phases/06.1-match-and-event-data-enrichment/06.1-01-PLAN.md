<objective>
Prove the event-standing path end to end — TBA's `/event/{key}/rankings` endpoint through a new
corpus table, through the publish boundary, onto a rendered "Rank 5 of 32" line in the team page's
event card — for one season (2024) before widening to 2022–2026.

Purpose: this is the only one of the phase's three items that traverses **every** layer the phase
touches (external API → ingest → corpus → publish → artifact schema → rendered page). The other two
(per-bonus RP, per-event rarity tiers) start inside the pipeline with their data already in hand.
Proving the longest path first, on one season, means an architectural dead end at the ingest or
artifact boundary surfaces after one commit instead of after every layer is already built.

Output: a working `event_rankings` corpus table populated for all of 2024, a new TBA capability in
`packages/ingest`, two new optional fields on `TeamSeasonEventSchema`, and the phase's one
genuinely-new rendered element pinned in `EventSection.tsx`.
</objective>

"also" in the ROADMAP sentence *"a new third-party endpoint, so it **also** needs a COVERAGE.md

addition to the ingest work", not "a second X where there was one". Answering the real underlying
question anyway:

- **The noun.** `event_rankings` introduces the corpus's first per-`(event_key, team_key)` fact
  table. The corpus today keys `team_media` on `(team_key, year)`, `matches` on `match_key` with
  `event_key` plus JSON team arrays, and `events` on `event_key`. There is no existing generalized
  "a fact about this team at this event" shape for `event_rankings` to join.
- **The decision: `add-alongside`.** A brand-new table mirroring TBA's own event-scoped endpoint
  shape, exactly as `team_media` mirrors the team-scoped media endpoint. One row type does not
  make a pattern, and inventing a shared `team_event_facts` shape from a single instance would be
  speculative generalization against a corpus that deliberately has no migration tooling.
- **Accepted debt, and what would force a promote.** The moment a *second* per-`(event, team)` fact
  is needed — event-scoped OPR standing rows for Phase 7's Insights tab, or alliance-selection
  results for Phase 8 — that is the trigger to promote to one shared `team_event_*` shape rather
  than adding a third sibling table. Recorded here so the third table is a conscious decision, not
  a drift.

Advisory. Non-blocking. Recorded; moving on.

<planner_decisions>
Decisions this planner made where no source artifact dictated one. Each carries a reversibility
rating per `REVERSIBILITY_GATES`.

- **PD-01 — Offseason events are IN the `event_rankings` ingest scope.** RESEARCH.md's Open
  Question 1, settled here so Task 1 is deterministic; recorded as an explicit COVERAGE.md row by
  plan 06.1-04. Rationale: TEAM-04's "attended event" is not scoped to in-season, the team page
  already renders event sections for offseason events, 553 of 1,581 corpus events are offseason
  (a third of all event cards would be silently rankless), and TBA computes these rankings itself
  from official match results — a materially different trust boundary from the self-reported
  `score_breakdown` that Phase 3's RP fold excludes. Cost delta ≈ 553 requests ≈ 1 minute.
  **Reversibility: reversible** — undoing means deleting rows from a local gitignored corpus and
  re-running one ingest pass.
- **PD-02 — A `null` TBA response body and an empty `rankings: []` array both store zero rows;
  the distinction is preserved in the ingest run's own counters, not in the corpus.** RESEARCH.md
  Pitfall 2 explicitly left this to the planner with an instruction to pick deliberately. A
  "checked, nothing there" marker row cannot exist in a per-`(event, team)` table when the answer
  is "zero teams", so the honest record of the distinction lives where it is actionable — three
  separate counts in the ingest log. **Reversibility: reversible.**
- **PD-03 — The standing line is text, not a `Badge`.** `Badge variant="secondary"` is this
  codebase's status-pill treatment (the `Upcoming` badge); a rank is data, not status, and the
  sketch-findings skill's rule is that colour carries meaning and never decorates.
  **Reversibility: reversible.**

No decision in this plan is rated `one-way`: every new published field is `.optional()`, so an old
artifact still parses and a new field a client ignores breaks nothing; the corpus is local and
gitignored with no migration tooling to unwind. The costly ones are the published-schema additions
(`TeamSeasonEventSchema.rank`/`.totalTeams`) — undoing them costs another full ~22-minute
republish, which is why plan 06.1-07 spends exactly one. Rated **costly**, not one-way, so no
`checkpoint:decision` is inserted.
</planner_decisions>
