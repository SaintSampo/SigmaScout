  <behavior>

- A team with a rating in only the immediately prior season starts from that rating alone, with the missing prior year contributing nothing rather than being read as 0.
- A team appearing for the first time starts at the rookie baseline `EPA_NORM_MEAN - EPA_INIT_PENALTY * EPA_NORM_SD`, i.e. 1450 in normalized units.

- `carrySeason` invoked with `boundary.isColdStart === true` returns the initial state unchanged — the cold-start season has nothing to carry from, by definition.

`runSeasonsMode` currently loops seasons and, inside each, constructs a fresh `WalkForwardSimulator` whose `runAll` calls `initState` per algorithm per season. That discards every rating at each boundary, which D-16 forbids. Restructure:

- Hoist state ownership out of `runAll`. Add an optional `initialStates?: ReadonlyMap<string, unknown>` parameter to `WalkForwardSimulator.runAll` and have it return the final state per algorithm id alongside the prediction records, so the caller can thread them. Keep the existing single-algorithm `run<S>` signature untouched — `replay.season.test.ts` and other callers depend on it.
- In `runSeasons`, hold a `Map<algorithmId, unknown>` of live states across the season loop. Before replaying season N (for N after the cold-start season), call `algorithm.carrySeason?.(state, { fromSeason: N - 1, toSeason: N, isColdStart: isColdStartSeason(N) })` for each algorithm that implements it, and pass the resulting states into `runAll` as `initialStates`. An algorithm without `carrySeason` (OPR) keeps Phase 1's behavior of starting each season fresh — say so in a comment, since OPR is season-pooled by design and a cross-season OPR is a different algorithm, not a bug fix.
- Seed the expanding-window score statistics at each season start from the prior season's final values, as RESEARCH.md's `expandingStats.ts` comment specifies. This is the same season-boundary hook, so it belongs in the same place rather than in a second loop.
- Add a `--cold-start-season <year>` CLI flag defaulting to `COLD_START_SEASON`, so extending the corpus to 2016 is a flag, not an edit (D-19).
- Preserve the existing per-season progress line, and extend it to state whether each algorithm carried state into this season or started cold — a silent regression to per-season resets is otherwise invisible in a two-hour run.

Verification for this task is a short-range real run rather than the full range: `pnpm harness --seasons 2022-2023 --algorithm opr,epa --out reports/carry`. Two seasons is the minimum that exercises exactly one boundary, and it keeps the feedback loop to minutes instead of an hour.

**What this task deliberately does NOT verify, and why (CONTEXT.md D-14).** This is the point in Phase 2 where EPA's cross-season behavior first meets real corpus data, so it is the natural place a reader would expect Success Criterion 2's numeric agreement check against Statbotics' published per-team EPA values to happen. It cannot. Statbotics' public API is down: `api.statbotics.io/v3/year/{year}`, `/v3/team_year/{team}/{year}`, and `/v3/team/{team}` all returned HTTP 500 and the blog returned HTTP 403, verified live 2026-08-13; the website returns 200 but is a client-rendered shell fed by that same dead API, so there is no reference series to compare against. Per **D-14 this blocked outcome is accepted, not worked around** — SC-2 stays worded as-is in ROADMAP.md and Phase 2 verification marks it blocked-on-external-dependency with the HTTP 500s as evidence. Options considered and rejected in D-14: running Statbotics' Python model against this corpus to synthesize references, and pulling values from Wayback snapshots.

EPA's correctness is therefore established by the two mechanisms that do not depend on a third party, both of which this phase does carry: the synthetic-fixture unit tests in `epa.test.ts` and `carryover.test.ts` (hand-computed EWMA values, the decaying learning rate, the D-08 elim divergence, every carry case in Task 1's behavior block), and the walk-forward structural proofs (the leak-proof Proxy over `OUTCOME_KEYS`, the expanding-window score SD, and T-02-08's assertion that a 2022-2023 run's 2022 slices are byte-identical to a 2022-only run's). State this explicitly in the SUMMARY rather than leaving SC-2 silently unaddressed — the omission is a recorded decision, not an oversight, and a reader of this plan must be able to tell those apart.
  </action>
