- **PD-01 — verification reads the PUBLIC artifact origin, not the bucket, and therefore uses no credential at
  all.** `packages/harness/r2Client.ts` has a working `getObject` that would read the bucket authoritatively
  with SigV4. It is deliberately not used. Phase 4 D-25 is that the browser reads artifacts from
  `https://data.sigmascout.org` with no compute in the path; a 200 from the bucket proves the PUT landed, while
  a 200 from the origin proves the PUT landed AND the CDN serves it AND CORS is intact AND the exact URL a page
  will build resolves. The second is a strictly stronger claim about the thing this plan exists to establish.
  It also means `scripts/verifySubsetPublish.ts` reads no environment variable, signs nothing, and can be run
  by anyone at any time — the strongest available posture under `.claude/CLAUDE.md`'s Secrets handling rule,
  which exists because it was broken once and a live R2 token had to be rotated.
  **The one thing a public read is weaker at — CDN staleness under `max-age=60` — is closed by construction,
  not by waiting:** the verifier appends a per-run cache-busting query parameter and sends `cache: "no-store"`,
  and every criterion for a key that existed before this plan additionally asserts that the post-publish
  `generation` DIFFERS from the pre-publish `generation` recorded in `<baseline>`. A stale read fails loudly
  instead of passing quietly. **Reversibility: reversible.**

- **PD-02 — published algorithm versions are RESOLVED from the public algorithms manifest, never hardcoded and
  never hand-typed.** `https://data.sigmascout.org/v1/manifest/algorithms.json` returns
  `algorithms: [{ id, version, ... }]` — measured at planning time as `opr@3.0.0+baseline`,
  `epa@1.0.0+baseline`, `sigma1@2.0.0+tuned-2026-08`. The verifier reads it once per run and builds each key
  through `artifactKey({ page: "event", eventKey, algorithmId, version })`, the same function the publisher
  uses. Hardcoding a version string is how a verifier ends up checking a key nothing wrote; hand-typing one is
  how it ends up checking the wrong key and reporting a 404 as a publish failure. A `--version <id>=<ver>`
  override exists for the case where the manifest and the local tree disagree, and Task 1 asserts the version
  the verifier resolved is byte-identical to the version segment in the publisher's own `Published "<key>"`
  line — a disagreement is reported, never worked around. **Reversibility: reversible.**

- **PD-03 — the expectation table is committed source, and every expectation is an equality or a named
  enum, never a floor.** `PUBLISHED_SUBSET` in `scripts/verifySubsetPublish.ts` carries, per entry, the exact
  `matches` length, the exact `upcoming` length, the exact `teams` length, the exact count of team entries
  carrying `rank`, and a declared alliance expectation. The numbers are the corpus figures in
  `<subset_selection>`, measured at planning time. A floor ("at least one team has a rank") passes on an
  artifact that lost 77 of its 78 ranked teams; an equality does not. The one place a floor is used is
  `record`/`rp` presence, because the corpus can honestly hold a ranking row with NULL record columns for a
  traced stale event (07-05's own second `must_have`) — there the criterion is "at least one, and record the
  count", with the count reported so a shortfall is visible. **A mismatch is reported as a finding and routed,
  never resolved by editing the table** (this plan's first prohibition). **Reversibility: reversible.**

- **PD-04 — a correction to the outline's Notes, recorded rather than absorbed: this plan ADDS seven keys, it
  does not only overwrite.** The outline's gate-placement note says 07-10 "overwrites a dozen-odd existing keys
  in place under the naming the deployed client already reads, **adds no new key**, deletes nothing, and is
  idempotent". The first and third clauses are exactly right; the second is not, and could not be, because the
  same outline row requires "at least one offseason event" and RESEARCH.md Pitfall 1 establishes that
  `publishSeasons` has never published an event artifact for ANY offseason event. Seven of the fifteen chosen
  events returned 404 at planning time, all seven `is_offseason = 1`. **This strengthens the no-gate argument
  rather than weakening it.** An added key destroys nothing and shadows nothing; it is linked from nowhere
  until 07-15 turns Events-list rows into links; removing it is one idempotent `deleteObject` call against a
  key whose name is deterministic; and it NARROWS the 404 window those links will open rather than widening it.
  The overwrite half is the half with any risk at all, and it is bounded to eight keys under `max-age=60`.
  **Reversibility: costly** (production bytes on a live site), **not one-way** (nothing is deleted and every
  key is re-writable from reverted code in about thirty seconds each).

- **PD-05 — no `checkpoint:decision` in this plan, deliberately.** The approved outline puts this phase's two
  gates at 07-17 (the republish write pass, where D-01/D-02's redefinition and D-05's key rename become the
  published contract) and 07-19 (the destructive delete pass, ~18,222 R2 objects plus the D1 rows). Both
  placements rest on the same test: irreversibility is realized at the publish/delete moment, and a gate
  belongs at the point of no return rather than where an already-locked decision would be re-litigated. This

  touches no D1 row, deploys no Worker, and overwrites every key it touches idempotently — so re-running it
