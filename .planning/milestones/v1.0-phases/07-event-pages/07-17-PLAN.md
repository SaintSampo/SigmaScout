## The manifest problem, stated before it is solved

This is the single most important thing in the plan and it is not in the outline row, so it is
argued here rather than assumed.

Every page artifact key carries an algorithm segment — `v1/teams/{year}/{id}@{version}.json` — so
writing the renamed set ADDS keys beside the old ones and removes nothing. `v1/manifest/algorithms.json`
carries no algorithm segment. It is one shared key with room for one truth, and `publishSeasons`
overwrites it on every non-`--skip-state` run.

After 07-16, `buildAlgorithmsManifest` reads the promoted version file's own `id` — which now reads
the renamed id — so the manifest that run writes names `opr`, `epa`, and the renamed id, and carries
no entry for the pre-rename one. Two deployed consumers break on that, both silently or noisily but
neither harmlessly:

| Consumer | What it does | What happens |
|---|---|---|
| The deployed browser | `useAlgorithmVersion(algorithmId)` returns `data?.algorithms.find(c => c.id === algorithmId)?.version`, and every route gates its artifact query on `enabled: version !== undefined` | The client is still on the pre-rename id until 07-18, so the lookup returns `undefined` and **every artifact query on Teams, Events, Team, Event and SearchBox stays disabled** — permanent loading skeletons, no error, on a site that deploys on every push |

<liveness_protocol>
## How to tell a long-running publish apart from a dead one

`publishSeasons` is structurally quiet: `BoundedUploader.publish` logs nothing per object, and the
whole run emits roughly sixteen lines — one cold-start line and one
`publish: season {year} [{id}]: {n} matches replayed` per season per algorithm, arriving in bursts of
three at each season boundary — before the final `publish: summary` block. At the measured ~23-minute
wall clock that is one burst roughly every four to five minutes. **A silent console is the expected
state, not a symptom.** This project has already recorded the cost of inferring death from a quiet
log and a truncated process list; that inference is prohibited here.

Establish liveness from durable state, in this order, and stop at the first positive:

1. **The run log.** Every invocation is tee'd to `reports/publish/07-17-republish.log`. Check its
   modification time and line count. A log whose mtime is under five minutes old, or whose line count
   has grown since the last check, is a live run — no further check is needed.
2. **The bucket.** Poll the public origin (no credential) for
   `v1/teams/{year}/vpr@2.0.0+tuned-2026-08.json` walking 2022 → 2026 in order. Seasons are processed
   in ascending order and each season's uploads complete inside that season's block, so a 404→200
   transition on 2022, then 2023, and so on is unambiguous forward progress and also tells you where
   the run is. `pnpm verify:subset --baseline` prints status/generation/bytes per entry and always
   exits 0, which is the credential-free way to do this without hand-writing URLs.
3. **The process**, last and only if 1 and 2 are both stale. Confirm the `tsx`/`node` process is gone
   using a full, untruncated listing — a `head`-truncated process list is not evidence of anything.

Declare the run dead ONLY when the log's mtime is older than ten minutes AND no new `vpr@` object has
appeared since the previous check AND the process is confirmed absent, in that order. Then resume by
re-running the SAME full-range invocation (see PD-05 — never a narrowed season range), and expect a
NEW `generation`; the mixed-generation check in Task 4 is what surfaces the consequence.

**Prohibited:** killing the run because the console is quiet; starting a second run while the first
may still be alive (two concurrent passes interleave two generations across the same keys and neither
is then the run that produced the bucket); narrowing the season range to "resume"; and reporting a
wall clock from memory rather than from the log's own first and last timestamps.
</liveness_protocol>
