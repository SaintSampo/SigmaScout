**Cleanup — the one-way door.** Only after the client is confirmed live on `vpr@`: delete every
orphaned `sigma1@…` R2 object (~18,222 keys) via `deleteObject` over the same deterministic key
enumeration `publishSeasons` walks — idempotent and resumable, since a missing key counts as success;
run the one-off `DELETE FROM algorithm_state WHERE algorithm_id = 'sigma1'` against remote D1, which a
`vpr` reseed does **not** do on its own and which has no existing script or analog; deploy the Worker
with `DEFAULT_LIVE_ALGORITHM_IDS = ["vpr"]`; re-measure `docs/publish-budget.md` against the
D-18-enlarged schema; and re-confirm ROADMAP SC-1's D-19 amendment is present in the tree. Carries a
`checkpoint:decision` — deleted objects and D1 rows are unrecoverable without a third republish.

Purpose: this is the phase's second and last point of no return, and the only one where the word
one-way is literal. 07-17's write pass added keys beside the old ones and deleted nothing, so it was
recoverable by re-publishing. 07-18 moved the reader and deleted nothing, so it was recoverable by
`git revert` — a property that plan states explicitly and repeatedly, always with the same
qualification: *only while 07-19 has not run*. This plan spends that property. After it, reverting the
client onto the retired prefix points a browser at objects that do not exist, and restoring them costs
a third full republish under a reverted rename.

What makes the spend safe is not care in the moment — it is that the two systems which read the
retired id have each been moved off it first, deliberately, in separate waves. 07-18 moved the browser
and proved it against the deployed apex. This plan moves the second reader, the one nobody is
watching: the deployed Worker, which still folds the retired id off its retained D1 rows and still
WRITES artifacts under it once a minute. That deploy is step one of four, and the ordering of all four
is this plan's central technical claim rather than its housekeeping.

Output: a bucket, a database, a manifest and a live-fold tier that carry exactly three algorithm
identities; a re-runnable command that asserts the fourth is gone; a payload budget that records what
the delete pass cost; and a set of documents that say what was observed rather than what was planned.

## The ordering argument, stated once so no task has to re-derive it

Four production mutations. Their order is derived from two mechanical facts about deployed systems,
not from a preference for tidiness, so it is argued here and then simply followed.

**Fact one — the deployed Worker WRITES.** `apps/worker/src/scheduled.ts` calls `writeArtifactObject`
for the `event`, `team` and `teams` page kinds on every tick that advances an event, under whichever
algorithm id it is folding. The deployed bundle has been folding the retired id since before wave 11,
because 07-16 edited `wrangler.toml` and deliberately did **not** deploy. A delete pass run against a
Worker still on the retired id would race a live tick and re-create objects behind it. The deploy must
come first.

**Fact two — the deployed Worker RESOLVES its modules from the manifest.**
`buildAlgorithmModules(manifest, liveAlgorithmIds)` keeps only entries whose id is in the DEPLOYED
`LIVE_ALGORITHM_IDS` and throws `EmptyLiveAlgorithmTierError` when that filter empties the set.
Collapsing the manifest before the deploy leaves the running Worker asking for an id the manifest no
longer names — a throw every minute, indefinitely. This is 07-17's `T-07-17-01` with the arrow
reversed, and it is why the transitional four-entry manifest exists at all. The manifest collapse must
come after the deploy.

Those two facts fix `deploy → collapse`. The remaining two are ordered by the general rule that
reversible steps precede irreversible ones, and that among irreversible ones the fast, instantly
verifiable step precedes the long one.

| # | Operation | Blast radius | Reversible? | If it fails, what you are left with |
|---|---|---|---|---|
| 1 | `pnpm worker:deploy` — the renamed live-fold tier | the once-a-minute cron | **Yes.** `wrangler rollback`, or simply redeploy | The previous bundle still deployed, still folding the retired id off its retained D1 rows, still writing retired keys. The site is unaffected — 07-18 moved the browser to the renamed prefix — and the four-entry manifest still serves both readers. Nothing is destroyed. Retry or stop; either is safe |
| 2 | `pnpm manifest:algorithms --drop-id <retired>` | one shared, algorithm-agnostic key | **Yes**, from the fresh capture taken in step 0 | If compose or validation fails: the manifest is untouched at four entries, which is harmless. If the PUT fails: R2 object writes are atomic per object, so the live body is either the old four-entry one or the new three-entry one, never a torn one. Retry |
| 3 | `DELETE FROM algorithm_state WHERE algorithm_id = '<retired>'` on remote D1 | ~4,599 rows (07-17 records the exact retained counts) | **No**, except by re-applying a seed file | If the statement never ran: retained rows intact, harmless, the newly-deployed Worker does not read them. If it ran over-broadly — a lost or widened `WHERE` — the live ids' state rows go too, and the Worker cold-starts every algorithm on the next tick. Published artifacts are unaffected; only incremental live folding degrades until reseeded. The named undo is re-applying `reports/publish/seed-{opr,epa,vpr}.sql` from 07-17's run |
| 4 | ~19,000 `deleteObject` calls | the retired prefix in R2 | **No** | A partial pass leaves some retired objects orphaned beside the renamed ones. **The two truly irrecoverable outcomes, stated plainly rather than softened.** After step 3, restoring
the retired id's D1 rows requires a replay under the retired id, which requires reverting the rename in
source. After step 4, restoring the retired objects requires a third full republish under a reverted
rename — roughly 23 minutes and ~57,000 PUTs — plus reverting every consumer 07-18 moved. Neither is a
`git revert`. That is what the gate in Task 2 exists to authorize.

- **PD-01 — the operation order is derived, not chosen, and the derivation is in the plan body rather
  than in an executor's head.** The two mechanical facts (the deployed Worker writes artifacts; the
  deployed Worker resolves its modules through a manifest filter that throws when empty) fix
  `deploy → collapse` with no room for preference. The remaining ordering — collapse before D1 delete
  before object delete — follows the reversible-first rule, with one additional argument that decides
  collapse-versus-object-delete on its own merits: collapsing first means no manifest ever names an id
  whose objects have been removed, while deleting first would leave, for the ten-odd minutes of the
  delete pass, a live manifest entry resolving to a version whose objects 404. A stale browser tab
  holding the four-entry manifest gets a clean absent-entry in the first arrangement and a 404 storm in
  the second.
  — <reversibility rating="reversible">An ordering decision, recorded before anything runs.</reversibility>

- **PD-02 — the D1 row delete runs BEFORE the R2 object delete, and the reason is diagnostic rather
  than architectural.** Both are irreversible and either order is architecturally safe once the deploy
  has landed. The tie is broken by three properties of the D1 statement: it is the one operation in
  this phase with **no analog anywhere in the repository** (PATTERNS.md names it as one of only two such
  items), it completes in seconds, and its correctness is confirmable instantly by a `GROUP BY`
  read-back. Discovering that `wrangler d1 execute --remote` fails for an authentication or
  database-name reason eight minutes into a nineteen-thousand-key delete pass is strictly worse than
  discovering it against an untouched bucket. The unprecedented operation goes first, while every other
  system is in a known state and every observation is cheap.

  The counter-argument is real and is recorded: an over-broad D1 delete is the single highest-consequence
  event available in this plan, since it would take the freshly-deployed Worker's state down along with
  the retired rows. It is answered by a guard rather than by reordering — the same `WHERE` clause is run
  as a `SELECT COUNT(*)` first and matched against 07-17's recorded retained counts, the statement uses
  `=` and never `LIKE`, the read-back afterwards asserts the three live ids' counts are UNCHANGED rather
  than merely present, and the three seed files are confirmed on disk beforehand as the named undo.
  — <reversibility rating="costly">A sequencing decision between two irreversible operations. The decision itself is free; what it orders is not.</reversibility>

- **PD-03 — the enumeration is a deliberate SUPERSET and the over-enumeration is reported as a
  measurement, not as failures.** `publishSeasons`' own per-event guard is `predictions.length === 0 &&
  upcoming.length === 0`, which cannot be reproduced without a full walk-forward replay. Rather than
  replay a season to learn which events to delete — which would be absurd and would also introduce a
  second, independently-derived enumeration that could silently disagree with the first — the tool
  enumerates every event row `selectEventMeta` returns and every (team, season) pair appearing in any
  played or scheduled match, with offseason INCLUDED. That is roughly 5 + 5 + 1,581 + 17,670 = ~19,261
  keys against the ≈18,222 RESEARCH.md derives as actually existing.

  The superset is not sloppiness, it is the correct shape for this operation. `deleteObject` treats a
  missing key as success, so an over-enumerated key costs one request and nothing else, while an
  under-enumerated key is a permanent orphan nobody will ever look for again. The offseason-inclusive
  scope specifically catches the handful of offseason event and team keys 07-10 published under the
  retired prefix through single-event mode, which an offseason-excluded enumeration would miss by
  construction. The expected 404 count is stated before the run and reported after it as the
  measurement of the over-enumeration.
  — <reversibility rating="reversible">An enumeration strategy in a script, proven by dry run before it deletes anything.</reversibility>

- **PD-04 — the tool refuses live ids mechanically, and refuses an implausible key count as well.**
  `--retired-id` is required with no default: an ops tool whose destructive target has a default is a
  footgun, and the one-character difference between the retired and renamed segments is exactly the
  typo class this guards. Any id that is a member of `PUBLISHED_ALGORITHM_IDS` — which after 07-18's
  collapse holds exactly the three live ids — raises `RefusedLiveAlgorithmIdError` before enumeration
  even begins, so the tool structurally cannot be pointed at live data.

  failed to open, a season range that parsed wrong, or a query that returned nothing produces a small,
  plausible-looking key count and a fast, clean, entirely wrong run. A hard band around the projected
  ~19,261 turns that into an abort. Both guards are unit-tested and both are exercised as real CLI
  invocations before the gate, because a guard nobody has watched fire is a guard nobody knows works.
  — <reversibility rating="reversible">Two error classes and a constant.</reversibility>
