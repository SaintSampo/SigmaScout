`tier` fields on the live `v1/event/2024casf/...` artifact — so the tier-boxing 07-01 wired and 07-11 will

concrete: `--seasons` publishes no event artifact for any of the 259 corpus events with no ranking rows, so

<planner_decisions>

- **PD-01 — the per-event state is CAPTURED as a reference through the existing `onMatchComplete` hook, and
  `teamMetrics` is called once per event afterwards — not once per match inside the hook.** This is the shape
  RESEARCH.md's measurement script used and the shape its 9–26 ms per (season, algorithm) figure describes:
  one `algorithm.teamMetrics(stateAsOfEventEnd, eventRoster)` call per distinct event, against a walk-forward
  replay that already costs 16–29 seconds per season. The alternative — deriving as-of-event metrics from the
  `metricHistory` rows the hook already computes — was rejected on a semantic ground, not a cost one: the last
  history row for a (team, event) pair is that TEAM's state after ITS last match at the event, while D-10
  specifies the state at the EVENT's end, and the two differ for any team whose last qualification match is
  not the event's. It would also silently omit every team present only in `upcoming`, since a team with no
  played match has no history row at all.
  **Capturing a reference is safe and that is a checked fact, not an assumption:** all three algorithms'
  `update()` return a NEW state object (`sigma1` returns a fresh literal with a fresh `teams` Map, `epa` the
  same, `opr` returns a fresh `{ perEvent, lastEventByTeam }` or the identical state on a genuine non-`qm`
  no-op). Because the stream is chronological, the last write for one event key is that event's last match no
  matter how many events interleave across a weekend. **Reversibility: reversible** (an internal mechanism; no
  published byte depends on which seam produced the value).

- **PD-02 — `buildEventTeamsStanding`'s fourth parameter is REQUIRED, not optional.** An optional pool is an
  opt-out, and an opted-out artifact parses, uploads, and renders a page with every tier box dark and nothing
  red anywhere — the silent-degradation shape `<threat_model>` T-07-09-01 and T-07-08-04 both name. The
  function is module-private with exactly two call sites, so "required" costs two edits and buys a compile
  error for any third call site that forgets. `EventTeamStandingInput.metrics` widens from
  `Record<string, TeamMetric>` to `Record<string, TeamMetricWithPercentile>`; a plain `TeamMetric` is
  assignable to the widened type, so every existing test caller keeps compiling untouched, and
  `roundTeamMetricRecord` already accepts that exact type and already passes `percentile` through unchanged.
  **No schema change is needed anywhere** — `TeamMetricSchema` has carried optional `percentile` since Phase 6.
  **Reversibility: reversible.**

- **PD-03 — `withEventPercentiles` applies NO metric-name allowlist, deliberately diverging from
  `withHistoryPercentiles`.** Two independent reasons, and they agree.
  First, the UI contract: `07-UI-SPEC.md`'s Breakdown table row is "one column per
  `metricKeysFor(algorithmId, season)` key — `MetricValue`, tier-boxed, including the algorithm's Total", and
  `metricKeysFor` returns every season component plus the total. A four-name allowlist would leave every
  component column permanently untiered while the three phase groups lit up, which is not a smaller version
  of D-11's design, it is a different one.
  Second, the payload arithmetic, which is the same argument reaching the opposite conclusion because the
  denominator is three orders of magnitude smaller. `HISTORY_PERCENTILE_METRIC_KEYS`'s own doc comment
  justifies its cut against 292 `metricHistory` rows per team-season; an event artifact carries ONE metrics
  record per team. Measured against the real corpus: the largest roster anywhere in 2022–2026 is 78 teams
  (`2023cur`, `2023dal`, `2023joh`), 2024 Sigma1 publishes 17 metric names, and a percentile key costs about
  20 bytes — roughly 26.5 KB worst case, against 64,563 bytes of headroom under the committed `event`
  `budgetMaxBytes`. It fits, it is measured rather than hoped, and Task 2's dry-run measurement is what
  confirms it on a real event rather than on this arithmetic. **Reversibility: costly** (narrowing the set
  later needs another full republish, though nothing breaks and no migration is needed — the same wording
  `HISTORY_PERCENTILE_METRIC_KEYS` uses for its own cut).

- **PD-04 — the season-final fallback applies ONLY to an event with no captured state, and it lives in one
  named helper used by both call sites.** An event whose matches are all still scheduled produces no
  `onMatchComplete` call for its key, so no snapshot exists — and "as of that event's end" is not a quantity
  that exists yet. The latest state is the only defensible answer and it is exactly what is published today,
  so this branch is a no-change, not a degradation. Putting it in `metricsAsOfEvent` rather than inline at two
  call sites is what stops the two paths from acquiring two different fallback rules; widening it beyond the
  no-captured-state case is this plan's second prohibition. **Reversibility: reversible.**

- **PD-05 — `runEventMode` is restructured onto a full-season replay so its published percentile is ranked
  against a genuine season pool.** This is the largest single decision in the plan and it was not taken
  lightly. `runEventMode` today replays only the target event's matches from a cold start, so it has no
  season-final pool at all. Three options existed:
  (a) rank against the event's own roster — forbidden by `percentiles.ts`, by `TeamMetricSchema.percentile`'s
  own doc comment, and by 07-11's third prohibition; it is this plan's first prohibition;
  (b) publish no percentile in single-event mode — honest, but it makes 07-10's subset publish a rehearsal of
  everything EXCEPT the highest-risk new computation in this plan, leaving 07-17's gated one-shot republish as
  the first real exercise of the merge, and it leaves 07-01's and 07-11's tier boxes dark on the very data
  those plans are supposed to be verified against (07-11's flagged assumption 1 states the opposite);
  (c) replay the season, capture per-event states through the same hook, build the pool from the season-final
  state.
  (c) is what this plan does. Cost: one season replay per `--event` invocation, 16–29 s measured
  (RESEARCH.md Q3) against a currently near-instant command, or roughly 4–7 minutes across the whole of
  07-10's subset. It is a hand-run CLI command with no documented latency claim anywhere in the repo.
