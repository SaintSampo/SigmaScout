## CORRECTION to the phase's own research - read this before anything else

**RESEARCH.md Pitfall 1 and the phase outline both state that there is no `9999` literal in the tree
and that re-enabling presim is "a republish command, not a code change." That is false at HEAD.**
Verified this session:

```
package.json:40:    "publish:seasons": "tsx --env-file=.env packages/harness/publish.ts --seasons 2016-2020,2022-2026 --include-offseason --presim-from-season 9999",
```

`docs/publish-budget.md:54-55` says the same thing in prose ("the temporary flag, commit `1a759198`,
added to the script"), and `docs/simulation-architecture.md:180` repeats it. The committed npm script
is what pins the sentinel; `DEFAULT_PRESCHEDULE_FROM_SEASON = 2026` in `packages/harness/publish.ts`
is only what applies when nobody overrides it, and the script always overrides it.

**Consequence if this correction is missed:** an executor runs `pnpm publish:seasons` exactly as the
skill says to, the run takes about forty-five minutes, spends a full R2 write pass, prints no
`presim:` line at all, and the pre-schedule stop is still dark - with a green-looking run report. The
research's advice ("run the next publish without the flag") cannot be followed by running the project's
own publish script, because the flag is inside it.

Both the outline's framing and the research's framing are otherwise sound: the *fix* is small, and
there is no deep code hunt. It is one string in `package.json`, plus a tripwire test so it cannot
silently come back.

## Assumption-delta record - Delta A, owned here, unconditional

<assumption_delta_decision>
**Delta A - the sidecar's algorithm-key segment.**

**Noun that is now primary:** a member of `PUBLISHED_ALGORITHM_IDS` (`opr` / `epa` / `bpr`), not the
retired research id `vpr`.

**Decision: PROMOTE. Unconditional** - it does not depend on 09-09's rung-1 outcome, on which
algorithms turn out to produce sidecars, or on anything decided at this plan's own checkpoint.

**Rationale:** every presim sidecar in R2 is `vpr`-keyed, and `vpr` left `PUBLISHED_ALGORITHM_IDS` on
2026-09-09. The key therefore names something no reader can resolve: the browser builds its request
through the same `preScheduleKey` and asks for an id the manifest no longer advertises, so the
pre-schedule stop 404s on all three published algorithms. Keeping the `vpr` objects alongside the new
ones would ship dead bytes under an unreachable name - roughly 641 objects at a 138.7 KB median,
counting against a 10 GB free tier for a name nothing can ask for. `add-alongside` is therefore not on
the table; the orphans are deleted.

**Mechanism, stated because it is easy to over-build:** `preScheduleKey` takes the publisher's own
`algorithm.id` (`publish.ts:1751`). The re-key happens BY REPUBLISHING. There is nothing to rename,
nothing to alias, and no migration script to write - Task 1 proves the new key shape on a dry run and
Task 5's republish is what writes it.

**Out of scope, stated explicitly:** the BPR->SPR **display** rename is another agent's work in
flight. **The key segment stays `bpr`.** Treat every `SPR` encountered as `BPR` and continue. A key
segment change would be a second, unrelated one-way R2 migration hiding inside this one.

**Delta B is not decided here.** 09-09 decides what the sidecar *is* - rung 1's
`{roster[], matchesPerTeam, perTeamPmf[]}` at ~2-3 KB, or the existing priced-schedule shape if rung 1
failed at its checkpoint. **This plan executes the write either way and must work either way.** Do not
assume rung 1 shipped; read what `buildPreScheduleArtifact` actually produces at HEAD and publish that.
</assumption_delta_decision>
