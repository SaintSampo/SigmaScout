## The three formulations, pinned here so an executor does not have to invent them

### 1. `winSource` — where the win probability comes from

One resolved quantity feeds the outcome half, and the config picks its source:

- **legacy member:** `pRedWinEffective = standardNormalCdf(marginMean / marginSd)` — the exact analytic
  limit of what today's 4,000 draws estimate when they compare two independent Gaussian scores. This is
  09-04's behavior and must be whatever 09-04 already implemented; if 09-04 wrote it differently, **use
  09-04's expression unchanged** and record the difference rather than re-deriving it here.
- **`"p-red-win"`:** `pRedWinEffective = input.pRedWin` — the published float, used directly, with no
  rescaling, no recalibration and no clamp unless it is outside `[0, 1]` or non-finite.

where `marginMean = red.scoreMean - blue.scoreMean` and
`marginSd = Math.sqrt(red.scoreVariance + blue.scoreVariance)`, both already inside `analyticRpPmf`.

### 2. `tieModel` — how tie mass is carved out

- **legacy member:** `pTie = 0`. Today's branch is unreachable, so zero is its faithful analytic limit,
  not a simplification.
- **`"discrete-margin"`:** real FRC scores are integers, so the observed margin is the rounding of a
  continuous latent margin and a tie is the event that it rounds to zero:

  `pTie = standardNormalCdf((TIE_MARGIN_HALF_WIDTH - marginMean) / marginSd) - standardNormalCdf((-TIE_MARGIN_HALF_WIDTH - marginMean) / marginSd)`

  with `TIE_MARGIN_HALF_WIDTH = 0.5`. Degenerate guard, ordered before the division: if `marginSd` is
  not finite or is at or below zero, `pTie = Math.abs(marginMean) < TIE_MARGIN_HALF_WIDTH ? 1 : 0`.

The split, for both tie models:

```
pRedStrict  = pRedWinEffective * (1 - pTie)
pBlueStrict = (1 - pRedWinEffective) * (1 - pTie)
```

so `pRedStrict + pTie + pBlueStrict` is algebraically exactly 1 (and within 1e-12 in IEEE754 floats —
state the tolerance, do not claim bitwise unity for a sum of products). The red outcome half is
`{ winRp: pRedStrict, tieRp: pTie, 0: pBlueStrict }` folded into the RP index space (blue's is the
mirror image). All `winRp` values are 2 or 3 and all `tieRp` values are 1 across every registered
season, so no index is fractional.

**Why proportional splitting and not `pRedWin - pTie/2`.** Both were considered. Subtracting half the
tie mass needs a clamp when `pTie/2 > pRedWin`, and a clamp is a silent third model that would confound
09-06's attribution. Proportional splitting never goes negative, never needs a clamp, and buys an exact
algebraic identity worth having: **conditional on a decisive result, the model's win probability is the
published `pRedWin` to the last bit.** It is also a very close approximation to the literal latent-
rounding answer — the two differ by roughly `pTie * (pRedWin - 0.5)`, which at the 1.09% base rate and
a 0.3 probability offset is about 0.003, a third-order term. **Record this choice and this reasoning in
`docs/models/rp-layer-config-arms.md`;** D-14 gave the approach and left the formulation to Claude, and
a later reader is entitled to know which formulation was chosen and why.

### 3. `marginal` — which family a variable is fitted with

```
resolveDeclaredFamily(variable, config) =
  config.marginal === "negative-binomial" ? variable.marginalFamily : "gaussian"
```

One expression, one call site, feeding 09-03's `fitMarginal(mean, variance, declared)` third argument
and nothing else. 09-03's contract is that the negative-binomial path is reachable **purely** by
changing `declared` — no second entry point, no branch inside `marginals.ts` keyed on anything else —
and this resolver is where the config-to-declaration translation lives so that contract stays true.
Under the legacy member every variable is forced to `"gaussian"` regardless of what it declares, which
is what makes flipping all 34 declarations in this plan a no-op for production.
