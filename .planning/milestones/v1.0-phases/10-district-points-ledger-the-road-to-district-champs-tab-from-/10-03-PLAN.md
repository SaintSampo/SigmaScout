<objective>
The district data contract this phase's three writers and one reader all meet on.

Today `v1/district/{districtKey}.json` has exactly one producer (`scripts/publishDistricts.ts`),
carries no per-event state, no predictions and no byte budget, and the live-windows manifest has
no district concept at all. This plan closes all four gaps at once, as a contract rather than as
four separate code paths:

1. **The four per-team-per-event state facts** (qual matches played and total, alliances picked,
   playoffs done, awards posted) on the district artifact, so the ledger decides grey versus blue
   from published facts and never infers them client-side (CONTEXT "The four state facts,
   sourced").
2. **The baked-pmf shape** for unstarted events, with inline-versus-sidecar decided by MEASURED
   serialized bytes for `2026pnw` against a stated rule (CONTEXT Claude's Discretion; RESEARCH
   Pitfall 6), plus the per-season award base-rate table's placement and the per-team decoration
   bucket that selects a row from it.
3. **`districtKey` on the live-windows manifest entry**, populated by the offline manifest writer,
   so the Worker can derive district liveness from member-event liveness with no corpus and no
   second R2 read (RESEARCH Open Questions 2 and 3) — **plus the small path that gets the field
   into production.** At HEAD that manifest has exactly one writer, inside the full
   `pnpm publish:seasons` run (~109,000 R2 Class A writes, a generation bump, a mandatory
   four-file D1 seed, a prune owed for six hours), so a new entry field would be unreachable at
   any sane price. Task 4 adds `scripts/publishLiveWindows.ts` / `pnpm publish:live-windows`:
   the same `buildLiveWindowsManifest`, the generation string read off the live manifest rather
   than minted, one object uploaded, a `--dry-run` that writes nothing and says what it would
   have written.
4. **One shared pure producer**, `applyDistrictRankings` in `packages/harness`, that merges a
   TBA-shaped rankings payload into an artifact read back from R2 and recomputes the `locks.ts`
   verdicts. This is the outline's assumption-delta decision: PROMOTE. The artifact goes from one
   producer to two, so the merge becomes one shared pure function both callers use rather than two
   implementations of the same shape that can drift.

Purpose: 10-05 (Worker) and 10-06 (publisher) are both blocked on this contract, and 10-07 cannot
render a grey cell or an unstarted-event histogram without it. Nothing here simulates, fetches, or
writes to R2 — this plan is schemas, one pure merge, one manifest field, one budget line, and one
small publisher that 10-09 runs. **No task in this plan executes that publisher**: executor
subagents have no network, every test of it drives the dry-run path with an injected upload
function, and the real command is 10-09 Task 5's.

Output: the artifacts listed in `must_haves.artifacts`, plus a measured byte number for `2026pnw`
recorded in `docs/publish-budget.md` and in this plan's SUMMARY.

**Operator note (already satisfied at planning time):** the byte measurement reads a local,
gitignored copy of the live artifact at `data/fixtures/phase10/district-2026pnw.json`. It was
present and 106,920 bytes when this plan was written (126 teams, 303 `eventPoints` rows, 0
`remainingEvents` rows — a finished season, which is why the measurement must SYNTHESIZE the
worst case). Executors have no network; there is no other way to obtain it.
</objective>
