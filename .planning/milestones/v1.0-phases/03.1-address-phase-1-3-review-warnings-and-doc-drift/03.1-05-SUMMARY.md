## Pre-Task-2 Regression Evidence (required by success criterion 1's spirit)

Running `npx tsx scripts/reviewFrontmatterLint.ts` against the repository state after Task 1's commit but before Task 2's corrections (`9850dbb9`) reported:

```
reviewFrontmatterLint: 3 review file(s) checked, 0 problems
```

This is the honest, correct result, not a false negative — and it is worth explaining why. `01-REVIEW.md` and `03-REVIEW.md`, pre-Task-2, had no `resolution:` frontmatter key and zero `#### Resolution` body subsections: exactly behavior case 1 ("a fresh, unresolved review is valid"), which the linter correctly does not flag. `02-REVIEW.md`'s existing resolution block was already internally consistent. The drift Task 2 closes — a review file's bookkeeping disagreeing with what actually happened in the codebase (fixes landed in Phases 03.1-01 through 03.1-04 with no corresponding resolution record) — is a *review-vs-reality* drift, which this linter's own doc comment explicitly states is out of scope: it checks only that a review file's frontmatter agrees with its own body, not that either agrees with the outside world. That narrower, actually-catchable invariant is what the ten synthetic fixture tests in `reviewFrontmatterLint.test.ts` prove the linter enforces (e.g. `resolution.resolved=3` against a body with 2 subsections correctly reports a problem naming both numbers). After Task 2 lands, the real-files case in the test suite is what pins the corrected state going forward.
