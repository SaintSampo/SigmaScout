## Silent-drop policy (WR-04, WR-06)

### Q1 — WR-06: played, non-tied match with empty `winning_alliance`

| Option | Description | Selected |
|--------|-------------|----------|
| Derive winner from scores | `redScore > blueScore ? red : blue`; match stays in the scored population. The review's own suggested fix | ✓ |
| Leave null, count as exclusion | Strictly faithful to what TBA reported; costs the match | |
| Throw on ingest | Most aligned with throw-over-plausible-wrong-number, but one bad row blocks an ingest run | |

**User's choice:** Derive winner from scores

### Q2 — WR-04: foreign key enforcement

| Option | Description | Selected |
|--------|-------------|----------|
| `PRAGMA foreign_keys = ON` | Write-time failure, where the bug is | ✓ |
| Read-time orphan count | Nothing can newly abort; bug surfaces further from its cause | |
| Both | Pragma plus a count for pre-existing rows | |

**User's choice:** `PRAGMA foreign_keys = ON`

### Q3 — Where the signal surfaces (asked twice)

First pass offered harness exclusion report / ingest run log / both. User replied "what do you suggest for this."

**Claude's analysis:** the first two answers had made the original options partly obsolete — deriving the winner means the match is recovered rather than dropped (so it never reaches exclusion accounting), and `foreign_keys = ON` means the write throws (so there is no silent drop left to count). Recommended instead an explicit corpus flag column, matching DATA-02's discipline that every quirk appears as a flag, so ingest counts and harness reporting read one stored fact rather than two counters that can drift.

| Option (revised) | Description | Selected |
|--------|-------------|----------|
| Corpus flag column | `winner_imputed` beside `replayed` / `has_score_breakdown`; costs a schema column and a corpus rebuild | ✓ |
| Ingest run log only | No schema change, but a later harness run cannot distinguish imputed from reported | |
| Both flag and ingest count | Most visible, but the count is derivable from the flag | |

**User's choice:** Corpus flag column

### Q4 — Regression baseline (asked twice)

First pass offered assert-zero / no-assert. User replied "I need more context here."

**Claude's analysis:** explained that `data/corpus.sqlite` is 351 MB and gitignored, so such a test only runs locally and skips in CI — which cuts in favour of the test here, since re-ingestion (when these rows would first appear) happens locally. Also noted assert-zero is right for only one of the two: an orphan match is never legitimate, but an imputed winner is legitimate-but-noteworthy, and asserting zero there would eventually fail on valid data.

| Option (revised) | Description | Selected |
|--------|-------------|----------|
| Orphans only | Assert 0 orphans; report imputed winners without asserting | ✓ |
| Both pinned at zero | Strongest tripwire, but a legitimate TBA quirk turns the suite red and creates hand-edit pressure | |
| Neither — report only | No corpus-dependent tests; nothing re-checks after a re-ingest | |

**User's choice:** Orphans only

## Where the new throws go (WR-05, P1 WR-01, P3 WR-02)

Two constraints were surfaced before the questions: prediction sidecars are written *before* scoring, so check placement decides whether bad data can reach an artifact; and the OPR safeguard collides with Phase 3's D-04, which froze OPR/EPA as baselines with `costly` reversibility.

### Q1 — WR-05 validation placement

| Option | Description | Selected |
|--------|-------------|----------|
| At prediction emission | Names the algorithm and match; stops a NaN reaching a JSONL sidecar | ✓ |
| At the scoring boundary | Cheapest; but the bad value is already persisted before it is caught | |
| Both | Belt and braces; two checks to keep in sync | |

**User's choice:** At prediction emission

### Q2 — Behavior on failure

| Option | Description | Selected |
|--------|-------------|----------|
| Throw and abort the run | Matches throw-over-plausible-wrong-number; one bad match kills a multi-hour run | |
| Quarantine and count | Keeps long runs survivable; published score comes from a narrowed population unless the count is read | ✓ |

**User's choice:** Quarantine and count

### Q3 — OPR drift safeguard activeness

| Option | Description | Selected |
|--------|-------------|----------|
| Detect only — test plus hard throw | Season-scale property test plus throw on `denom <= 0` / non-finite residual; every published number stays byte-identical | ✓ |
| Test only, no runtime throw | Nothing can newly abort; drift would still propagate silently in production | |
| Detect and correct | Self-healing via resync/symmetrization, but moves OPR ratings and reopens D-04 | |

**User's choice:** Detect only — test plus hard throw

### Q4 — P3 WR-02: fully-rejected parameter grid

| Option | Description | Selected |
|--------|-------------|----------|
| Abort with a named error | A fully-rejected grid means the search space is misconfigured; continuing publishes a screen with a silent hole | ✓ |
| Skip and report unscreenable | Long search survives one bad bound; "couldn't be tested" is a legitimate published answer | |

**User's choice:** Abort with a named error

### Follow-up — bounded quarantining (asked twice)

Claude raised an unasked-for consequence of Q1+Q2: a NaN usually means a team's state is already corrupt, so quarantines cascade, and an unbounded count could hollow out a season while producing a Brier score that looks good because the hard cases left.

User replied: "Ive been kinda guessing on this and the last few answers. give me more context. break it down in simple terms." Claude re-explained the whole area in plain language — what predict/update does, what a `NaN` probability is, why emission-time checking matters, and why the OPR baseline is frozen — and confirmed it would have recommended three of the four answers unprompted. The question was then narrowed, since the count travelling with the score is a house convention rather than a real choice.

| Option (revised) | Description | Selected |
|--------|-------------|----------|
| Yes, add a hard stop | Bad outcome becomes impossible rather than merely visible; threshold left to the planner | ✓ |
| No — the count is enough | Simpler; every long run stays completable | |

**User's choice:** Yes, add a hard stop

**Offered to revisit earlier answers; user chose "No — they're fine."**
