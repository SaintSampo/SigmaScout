- **Open design question resolved: drive the property test indirectly through `opr.update`, do not export `IncrementalInverse`.** `IncrementalInverse` is a non-exported class in `opr.ts` (line 257) and `applyObservation` is likewise module-private. Decision: leave both private and drive the test through the module's public `opr.update` surface, comparing `state.ratings` against `solveRidgeOpr(state.observations, ...)`. Rationale, recorded here because CONTEXT.md asks for it: (a) the existing equivalence test at `opr.test.ts` lines 370-431 already proves that surface reaches `applyObservation` and `rank1Update`, so no coverage is lost; (b) exporting a private class purely to test it widens `opr.ts`'s public API against the file's own encapsulation choice; (c) the drift being measured is a property of the shipped path, so exercising the shipped path is strictly more faithful than exercising an internal one.

- **Property-test shape and tolerance:** 5,000 synthetic matches over a 400-team pool (10,000 sequential `applyObservation` calls, since each match applies a red and a blue observation), with a fresh `solveRidgeOpr` comparison after matches 1,000, 3,000 and 5,000. Tolerance: every rating finite at every checkpoint, and every rating within `1e-6 * Math.max(1, Math.abs(batchRating))` of the batch solve — a relative tolerance with an absolute floor, matching the order of magnitude of the existing equivalence test's six-decimal closeness assertion but expressed relatively so it does not tighten as ratings grow. Rationale: 5,000 matches is the low end of the review's own "5,000-15,000 sequential updates" prescription and roughly a third of a real season, which is the drift-accumulation axis that matters; the team pool is held at 400 rather than the review's 1,500-3,700 because `solveRidgeOpr` is a dense O(n^3) decomposition and a 3,700-square solve run three times would make this a multi-minute test rather than a CI gate. Escape valve: if the test exceeds 30 seconds wall clock, reduce the team pool (never the match count) and record the reduction and the measured time in the SUMMARY.

- **Guard testability, stated honestly.** The residual branch is reachable through the public surface (a `MatchResult` carrying a non-finite score produces a non-finite residual) and is the branch the regression test exercises. The `denom` branch is not reachable through the public surface: `denom` equals one plus a positive quadratic form while the inverse stays positive-definite, so it is provably greater than one on well-formed input. It is defense in depth, and the property test's finiteness assertions are what would surface a real loss of positive-definiteness. Record this split in the SUMMARY rather than manufacturing a fake reachability path.
