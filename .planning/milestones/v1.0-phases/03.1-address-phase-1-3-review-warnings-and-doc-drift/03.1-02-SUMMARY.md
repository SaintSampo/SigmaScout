# Phase 03.1 Plan 02: Prediction validity and quarantine bound Summary

**Closed 01-REVIEW WR-05 by validating `pRedWin` at every algorithm's `predict()` return site and giving the harness a bounded, counted quarantine for anything that fails — plus fixed a real latent NaN bug the new check surfaced in Sigma1's season-sd link mode.**

## Accomplishments
- New `packages/core/scoring/predictionValidity.ts`: `isValidPRedWin`/`assertValidPRedWin`, a dependency-free leaf (zero imports) that is now the single shared source of truth for "is this win probability valid," called from `opr.ts`, `epa.ts`, and `sigma1/index.ts` immediately before each returns its `Prediction`.
- Every emission-time throw names the algorithm and the match key (e.g. `pRedWin NaN is not a valid win probability (opr.predict (2024test_qm1)) — must be finite and within the closed interval [0, 1]; refusing to publish this prediction`), so a malformed value is attributable without re-running.
- `packages/harness/score.ts`'s `aggregateScores` gained a fourth exclusion branch (`ExclusionCounts.quarantined`), using the exact same `isValidPRedWin` predicate — the emission-time assertion and the scoring-time quarantine can never disagree about what "valid" means.
- Three new exported constants (`QUARANTINE_ABSOLUTE_LIMIT = 25`, `QUARANTINE_SHARE_LIMIT = 0.005`, `QUARANTINE_SHARE_MIN_POPULATION = 200`) bound the quarantine: `aggregateScores` throws rather than publishing a Brier score computed on a materially narrowed population once either bound is crossed.
- `brier.ts` and `calibration.ts` are untouched, exactly as D-05 requires — they remain the reference for the invariant `predictionValidity.ts` protects upstream of.
- D-09's asymmetry preserved: `grep -n "quarantin" packages/core/algorithms/opr.ts` returns no matches — the solver's `denom <= 0`/`residual` abort (03.1-03's territory) was not touched or normalized into the per-prediction quarantine policy.

## Decisions Made
- **Regression test placement (planning_notes discretion, followed as prescribed):** the `opr.predict` end-to-end throw case lives in the new `predictionValidity.test.ts`, not `opr.test.ts`, to avoid a file conflict with plan 03.1-03 (owns `opr.test.ts` exclusively in the next wave).
- **`sigma1/index.ts`'s validation context uses `linkMode`, not a bare algorithm id string** — `predict()` has no `options.id` binding in scope (only `state`, `match`, `linkMode`, `params`), and threading a new parameter through the module was explicitly out of scope per the plan's action text ("do not thread new parameters through the module"). `sigma1:${linkMode} predict (${match.matchKey})` identifies which of the three prebuilt modules produced the value.
- **Quarantine throw message** follows `seasonSplit`'s module-prefixed convention (`score: ...`), naming the algorithm id, season, comp-level view, quarantined count, candidate count, and which of the two named constants was crossed.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Sigma1's `season-sd` link mode produced a real `NaN` win probability via `0/0`**
- **Found during:** Task 1, running the plan's own required verification command (`sigma1/sigma1.test.ts`) after wiring in `assertValidPRedWin`
- **Issue:** `winProbability("season-sd", margin, seasonScoreSd, ...)` in `linkFunctions.ts` computed `logistic(margin / seasonScoreSd)` with no guard for `seasonScoreSd <= 0`, unlike modes 2 (`predictive-variance`) and 3 (`normal-cdf`), which already had documented degenerate branches for their own zero/negative-variance cases. A pre-existing test (`makeSigma1 — ... produces identical state via update() across all three modes ...`) exercised exactly this: after one update, two alliances with identical observed history produce `margin === 0` and an expanding-window `seasonScoreSd === 0` (only 2 alliance-score observations folded, both equal), so `0/0 === NaN`. The test never checked `pRedWin`'s value before this phase, so the bug was silent until `assertValidPRedWin` started checking it.
- **Fix:** Added the same sign-only-step-function degenerate branch (`seasonScoreSd <= 0 → margin === 0 ? 0.5 : margin > 0 ? 1 : 0`) that modes 2/3 already used, matching the file's own established convention exactly.
- **Files modified:** `packages/core/algorithms/sigma1/linkFunctions.ts`, `packages/core/algorithms/sigma1/linkFunctions.test.ts`
- **Verification:** New test (`winProbability — season-sd mode's own degenerate seasonScoreSd branch`) plus the full suite; confirmed neither committed digest (`sigma1@2.0.0+tuned-2026-08.json`, `sigma1@2.0.0+tracer-check.json`) can be affected — both are `id: "sigma1"` (the `predictive-variance` mode), never `sigma1-seasonsd`.
- **Committed in:** `257939c9` (Task 1 commit)

**2. [Rule 3 - Blocking] `ExclusionCounts.quarantined` becoming required broke three downstream files not in the plan's declared `files_modified`**
- **Found during:** Task 2, running `npx tsc --noEmit` per the task's own verification requirement
- **Issue:** `packages/harness/artifact.ts`'s `ExclusionCountsSchema` (a Zod schema, `satisfies`-checked against the real `ExclusionCounts` type via `HarnessArtifact = z.infer<...>`) and inline `ScoreSlice` fixture literals in `packages/harness/report.test.ts` and `packages/harness/tune.test.ts` all constructed `exclusionCounts` without the new field, failing to typecheck once it became required.
- **Fix:** Added `quarantined: z.number().int().nonnegative()` to `ExclusionCountsSchema`; added `quarantined: 0` to every affected fixture literal.
- **Files modified:** `packages/harness/artifact.ts`, `packages/harness/report.test.ts`, `packages/harness/tune.test.ts`
- **Verification:** `npx tsc --noEmit` exits 0; full `npx vitest run` (599 passed, 1 pre-existing skip) exits 0.
- **Committed in:** `ea361568` (Task 2 commit)
