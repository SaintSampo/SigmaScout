# Phase 3.2: Swap OPR to event-scoped and re-issue affected figures - Context

**Gathered:** 2026-08-21
**Status:** Ready for planning

<domain>
## Phase Boundary

OPR stops meaning "season-pooled ridge regression" and starts meaning what TBA and Statbotics
mean by it: a fit over one event's matches only. That change propagates through four surfaces —
the algorithm module, the harness registry, a full 2022-2026 walk-forward re-run, and every
published figure derived from the retired baseline — with the season-pooled baseline preserved
as recorded history rather than deleted from the record.

**In scope:** rewriting `packages/core/algorithms/opr.ts` to event scope; re-running the full
2022-2026 harness; capturing the retired baseline before its code is deleted; re-issuing the
affected figures; measuring (not fixing) early-event rank-deficiency behavior; restating the
SC-3 verdict against the new baseline.

**Out of scope:** any change to Sigma1's promoted parameters (frozen, see D-10); any cold-start
mitigation or fallback scheme for early-event OPR (D-08); publishing artifacts (Phase 4);
re-tuning any algorithm against the new baseline.

</domain>

<decisions>
## Implementation Decisions

### Event scoping mechanism

- **D-01:** **Event scope is a keyed per-event sub-fit, not a reset.** `packages/harness/replay.ts`'s
  `buildSeasonStream` produces ONE chronological match list per season across all events, and
  `packages/corpus/db.ts`'s `selectMatchesChronological` breaks ties on `event_key` — so
  concurrent regionals genuinely interleave in the stream. Resetting state when `eventKey`
  changes would corrupt every simultaneously-running event. State must be partitioned by
  `eventKey` (already present on `UpcomingMatch`/`MatchResult`, so no contract change is
  needed). — **Reversibility:** reversible — internal to `opr.ts`'s state shape.

- **D-02:** **Cold start is literal zero.** A team with no observations at an event has rating 0.
  Direct consequence the planner must not paper over: for the first match of every event both
  alliances predict a 0-0 score and `pRedWin` comes out exactly 0.500, a flat 0.25 Brier on
  those matches. Rejected: seeding at the league-mean per-team share (a modeling addition TBA
  does not make, so "OPR" would again mean something of our own); carrying the team's rating
  from its previous event as a prior (puts cross-event information back in, which is precisely
  what 04-CONTEXT D-09 scoped out). — **Reversibility:** costly — every re-issued figure is
  measured with these predictions included; changing it means another full re-run and re-issue.

- **D-03:** **`opr.ts` is rewritten as a plain per-event solve.** `IncrementalInverse` and the
  Sherman-Morrison/RLS path (~250 of the file's 514 lines) are removed. That machinery exists
  only because n≈3,700 made a fresh solve cost ~110-420ms; at ~40 teams per event a direct
  solve is microseconds. **Honest cost, stated so the planner does not discover it mid-task:**
  this retires plan 03.1-03's season-scale drift property test, whose premise (season-scale
  accumulation) disappears with pooling. The numerical-breakdown guard from 01-REVIEW WR-01
  must survive in some form — a finiteness assertion on the solved ratings — even though the
  specific `denom <= 0` Sherman-Morrison invariant it guarded no longer exists.
  Rejected: keying the existing incremental machinery by `eventKey` (carries ~250 lines whose
  stated reason for existing is gone); keeping both scopes constructible in code.
  — **Reversibility:** one-way — the season-pooled implementation is deleted; restoring it
  means recovering it from git history and re-establishing every figure measured against it.

- **D-04:** **`teamMetrics()` headlines the team's most recent event's OPR.** Per-event sections
  render their own event's value; the metric-history series becomes per-event segments rather
  than one continuous curve. This satisfies 02-CONTEXT D-27's requirement that every algorithm
  supply a `TOTAL_METRIC_KEY` value. Rejected: returning per-event values with no season
  headline (breaks D-27); a match-weighted average across events (invents a third quantity
  neither TBA nor Statbotics publishes and calls it OPR).

- **D-05:** **Only qualification matches feed the event fit.** Playoff matches are still predicted
  and still scored — they simply do not update the regression, because playoff alliances are
  hand-selected and are not a random draw. Today `selectMatchesChronological` applies no
  comp-level filter, so OPR currently updates on `qm/ef/qf/sf/f` alike; this is a deliberate
  second change riding along with the scope change, accepted for TBA fidelity.
  **Flagged for the researcher:** the claim that TBA computes event OPR/DPR/CCWM over
  qualification matches only was stated with medium confidence during discussion and the user
  intends to verify it. Verify against TBA's own documentation before this is implemented; if
  TBA in fact includes playoffs, D-05 should flip rather than the project shipping a third
  definition. — **Reversibility:** costly — flipping it after the re-run means re-running.

### Baseline fidelity

- **D-06:** **The ridge term is dropped entirely; the solve becomes a minimum-norm pseudo-inverse
  via SVD** — which is what TBA does, and `opr.ts` already imports `SingularValueDecomposition`.
  Rationale grounded in the arithmetic: ridge shrinkage is roughly `lambda / (observations + lambda)`.
  Under season pooling a team had ~30-40 alliance observations by mid-season, so
  `OPR_RIDGE_LAMBDA = 3` biased ratings by ~7-9%. Under event scope with quals only a team
  finishes a regional with about 12, so the same lambda=3 would shrink every rating by roughly 20%
  and far more early — "freezing lambda" would have held a constant fixed while roughly tripling
  its effect, shipping a weaker opponent than event OPR has to be. Rank deficiency stops being a
  divergence risk and becomes a well-defined min-norm answer. Removes `OPR_RIDGE_LAMBDA` from the
  public surface. Rejected: re-picking lambda on tune seasons only (still a tuned-by-us constant
  inside a baseline); freezing lambda=3. — **Reversibility:** one-way — this defines the shipped
  baseline every SC-3 number is measured against.

- **D-07:** **SC-5's measurement is an accuracy curve plus a rank diagnostic.** Headline: Brier
  and winner accuracy bucketed by how many qualification matches the event had completed at
  prediction time, pooled across all five seasons — that states the cost in the project's own
  units. Alongside it: the design matrix's rank versus team count at the same checkpoints, which
  explains the curve's shape. Rejected: either half alone — a rank diagnostic that never states
  the prediction-quality cost is a numerics note, and a curve with no mechanism leaves a future
  reader with the shape but not the cause.

- **D-08:** **Mitigation of degraded early-event OPR is explicitly OUT of scope.** SC-5's wording
  is "measured and documented", not "measured and mitigated". A degraded early-event baseline is
  a true fact about event-scoped OPR and belongs in the record as one. Any fallback scheme is a
  modeling addition needing its own phase and its own criterion, and adding one mid-phase would
  reopen D-02 and quietly make the baseline ours again.

- **D-09:** **OPR's headline stays all-matches; a warm-only cut is reported alongside.** The
  headline number must remain all-matches because EPA and Sigma1 predict the exact same match
  set and comparability is what SC-3 rests on. `docs/models/` additionally reports the cut
  excluding each event's opening matches, so a reader can see how much of OPR's gap is
  structural cold start versus modeling. Rejected: a warm-only headline — it changes the
  denominator SC-3 was originally measured on, which 03-CONTEXT D-02 should veto.

### Re-run scope

- **D-10:** **The promoted Sigma1 version stays bit-frozen.** The committed parameter set in
  `data/algorithm-versions/` is untouched, 03-CONTEXT D-15's digest gate keeps passing unchanged,
  and SC-3 is restated purely by re-scoring the existing Sigma1 against the new OPR. **One
  variable moves in this phase and it is OPR.** Event OPR is a weaker opponent than season-pooled
  OPR; if Sigma1's parameters were re-tuned in the same phase that weakened its opponent, no
  reader could distinguish a real improvement from a redefinition — exactly what 03-CONTEXT D-02
  and 04-CONTEXT D-11 forbid. — **Reversibility:** reversible — a later re-tune is additive under
  03-CONTEXT D-13's version identity scheme.

- **D-11:** **The re-run covers the same five algorithms as `tuned-v3`:** `opr, epa, sigma1,
  sigma1-defaults, sigma1-adapt`. That is the exact field behind the current
  `docs/models/sigma1-tuning-results.md` tables, so every table can be re-issued like-for-like
  rather than differing in both baseline and field. The two remaining Phase 2 link-mode variants
  (`sigma1-seasonsd`, `sigma1-normalcdf`) stay out — 04-CONTEXT D-03 already ruled them
  harness-only and they are not published either way.

- **D-12:** **No reproduction control is asserted on EPA/Sigma1.** EPA and Sigma1 never read OPR
  and the match stream is unchanged, so their re-run figures should come out identical to the
  published ones; asserting that was offered as a free control proving the only thing that moved
  is OPR, and the user declined it. **Recorded tradeoff, not a re-litigation:** an unintended
  change to the shared stream during the rewrite would be indistinguishable from the OPR swap in
  the re-issued figures. Partial compensation falls out of D-14 — the tuning-results tables are
  re-issued with retired and new columns side by side, so unexplained EPA/Sigma1 movement would
  at least be visible to a reader comparing columns.

- **D-13:** **Season-pooled OPR gets one final full run and a committed fingerprint before its
  code is deleted.** Run it over 2022-2026, then commit a small fingerprint — per-season Brier
  and winner accuracy plus a hash over its prediction stream — mirroring 03-CONTEXT D-15's
  existing digest convention. A few hundred bytes; `reports/` stays gitignored per the failure
  log's repo-hygiene rule. Without this, once D-03 deletes the code the retired numbers exist
  only as prose in a markdown file with nothing to check them against, which is thin for
  something 04-CONTEXT D-11 calls "not optional bookkeeping." Rejected: citing the existing
  published figures (the underlying `reports/tuned-v3/artifact.json` is gitignored and likely
  already gone); archiving the full artifact (conflicts with repo hygiene).
  **Sequencing constraint for the planner:** this run must complete and its fingerprint must be
  committed BEFORE the D-03 rewrite lands.

### The record and the SC-3 restatement

- **D-14:** **A new `docs/models/opr-baseline-change.md` carries the narrative; the tuning-results
  tables are re-issued.** The new document holds the whole story — why the switch, both number
  sets side by side, the SC-3 restatement, and D-07's early-event measurement.
  `docs/models/sigma1-tuning-results.md` gets its tables re-issued with the new numbers plus a
  pointer to it. Rejected: editing tuning-results in place only (D-07's rank-deficiency
  measurement has no natural home in a Sigma1-tuning document); a new document only (leaves the
  project's most-read results document carrying numbers it announces as wrong).

- **D-15:** **Both SC-3 verdicts are stated, with the new one current.** The record carries the
  PASS against season-pooled OPR — dated, with its numbers, as what was measured through
  Phase 3 — and the newly measured verdict against event OPR as the current one. **Required
  framing, not optional garnish:** event OPR is the weaker opponent, so any widening of Sigma1's
  margin is attributable to the baseline changing and NOT to Sigma1 improving, and the record
  must say so outright. That sentence is what keeps 04-CONTEXT D-11's honesty requirement from
  being satisfied only in the letter. Per 03-CONTEXT D-02, if the new verdict is a shortfall it
  is recorded as a shortfall with a named decision about what to change — never a rewording.

- **D-16:** **Live docs are re-issued; SUMMARYs are annotated.** `docs/models/` and
  `.planning/PROJECT.md` get their OPR figures replaced outright. Each affected Phase 1-3 SUMMARY
  gets a dated "superseded by Phase 3.2" note pointing at `opr-baseline-change.md`, with its
  original numbers left intact — rewriting a completed plan's measured results would falsify the
  execution record. **Blocking action before planning:** this is a softer reading than SC-2's
  literal wording ("every OPR figure in ... the Phase 1-3 SUMMARYs ... reflect that run rather
  than the retired one"), so SC-2 must be reworded through `/gsd-phase` BEFORE planning — openly,
  and before any new numbers are known, so it cannot be mistaken for fitting the criterion to a
  result.

- **D-17:** **04-CONTEXT D-11's misattributed figures are corrected in place with a dated note.**
  D-11 cites 2025: 0.7539 and 2026: 0.7819 as Sigma1 losing holdout winner accuracy to
  season-pooled OPR. Those are the **untuned** Sigma1 rows from
  `docs/models/sigma1-tuning-results.md:129-141`. The **promoted** Sigma1 scored 0.7657 and
  0.7873 against OPR's 0.7618 and 0.7825 and won — `sigma1-tuning-results.md:151-160` records
  SC-3 as passing 8/8. D-11 is this phase's scope source and Phase 4 reads it directly, so an
  uncorrected version keeps propagating a wrong premise. The correction is marked as dated
  errata, not a silent edit, and it strengthens D-11's argument rather than weakening it.

### Claude's Discretion

- The exact file/module decomposition of the rewritten `opr.ts` (single module with an internal
  per-event map versus a small helper module) is the planner's call.
- The bucket boundaries for D-07's accuracy curve (per-match-index versus grouped ranges) and
  the specific rank statistic reported are the planner's call, provided the curve reports Brier
  AND winner accuracy and the rank figure is stated against team count.
- The exact shape of D-13's fingerprint file, provided it mirrors 03-CONTEXT D-15's existing
  digest convention and stays within repo-hygiene limits.

## Existing Code Insights

### Reusable Assets
- `SingularValueDecomposition` from `ml-matrix`, already imported by `opr.ts` and already used by
  `solveRidgeOpr` — D-06's min-norm pseudo-inverse builds on it rather than adding a dependency.
- `ratingEligibleTeams` / `allianceObservation` — the D-07 surrogate policy and the Open Question 3
  disqualification policy are orthogonal to scope and should survive the rewrite unchanged. Both
  carry substantial reasoning in their doc comments; preserve it.
- `WalkForwardSimulator.run` works identically over a single event's match list or a whole
  season's stream (`replay.ts:141`), which makes per-event verification of the new module cheap.
- `packages/harness/promote.ts`'s `computePredictionStreamDigest` — the existing mechanism D-13's
  retired-baseline fingerprint should reuse.

### Established Patterns
- Structural enforcement over convention (the `toLeakProofUpcoming` Proxy; 03.1 D-11's
  unconstructible-invalid-params rule). Where D-05's quals-only rule can be enforced by
  construction rather than by a comment, prefer that.
- Doc comments in this codebase carry the *reasoning*, including rejected alternatives and
  measured numbers. The rewritten module is expected to explain why there is no ridge term and
  why state is keyed by event, not merely that it is.
- Guards abort loudly rather than degrading silently (`applyObservation`'s breakdown guard,
  01-REVIEW WR-01). D-03's surviving finiteness assertion should follow that shape.

### Integration Points
- `packages/harness/cli.ts`'s `ALGORITHMS` registry — where SC-1's "not reachable" is enforced.
- `packages/harness/metricHistory.ts` — consumes `teamMetrics` per match; D-04's per-event
  segmentation surfaces here first.
- `packages/harness/artifact.ts` — `buildArtifact` REQUIRES every algorithm's `version` to carry
  the `{codeVersion}+{paramSetName}` shape and throws otherwise, so the event-scoped module's
  version string is load-bearing, not cosmetic.

</code_context>

<specifics>
## Specific Ideas

- The yardstick throughout is **what TBA and Statbotics actually publish**, not what is
  internally most defensible. That preference decided D-05 (quals only) and D-06 (no ridge)
  against alternatives that would have been easier or lower-risk, and it is the standing
  tiebreaker for any similar question the researcher surfaces.
- The user intends to verify the TBA quals-only claim in D-05 independently. Present the
  evidence for it plainly in research output rather than treating it as settled.

</specifics>

<deferred>
## Deferred Ideas

- **Re-tuning Sigma1 against the event-scoped baseline.** Sigma1's promoted parameters were tuned
  against a different opponent. A re-tune may be worth doing once the new baseline settles, but it
  must be its own phase with its own criterion — doing it here would make the SC-3 claim
  uninterpretable (D-10).
- **A cold-start fallback for early-event OPR.** Explicitly out of scope per D-08. If D-07's
  measurement shows severe degradation, that finding is the input to a future phase's decision,
  not a trigger to widen this one.
- **Event OPR at multi-division championships.** Championship divisions and Einstein have a
  different event structure than a regional; whether each division is its own scope was raised as
  an available topic and not opened. Worth a researcher note.
- **An event-boundary hook on `AlgorithmModule`**, analogous to the existing `carrySeason`
  season-boundary hook. Not needed for this phase (D-01 keys state internally), but if a later
  algorithm wants event-boundary behavior the contract has no place for it.

</deferred>
