# Phase 3.2: Swap OPR to event-scoped and re-issue affected figures - Research

**Researched:** 2026-08-21
**Domain:** Algorithm correctness (least-squares rating recovery), numerical linear algebra, walk-forward harness re-run cost, documentation/record integrity
**Confidence:** HIGH (TBA's own source code and this repo's own committed code/tests were read directly; all cost estimates come from this repo's own prior measured runs, not extrapolation)

## Summary

This phase's central technical risk — "does D-05/D-06's understanding of what TBA actually computes match reality" — is **resolved with HIGH confidence**: TBA's own backend source (`src/backend/common/helpers/matchstats_helper.py`, fetched directly from `github.com/the-blue-alliance/the-blue-alliance`) confirms both locked decisions exactly as stated. OPR is fit **qualification matches only** (`if match.comp_level != "qm": continue`, in both the team-mapping and the M-matrix builder), via a **plain Moore-Penrose pseudo-inverse with no regularization** (`np.linalg.pinv(M)`, no ridge/shrinkage term anywhere in the file). D-05 does not need to flip. D-06's "no ridge, min-norm SVD solve" is exactly TBA's own method, not merely inspired by it.

The implementation consequence is unusually favorable: `ml-matrix`'s `SingularValueDecomposition.solve()` (already used by `solveRidgeOpr`) **already computes the minimum-norm least-squares solution by default** — it zeroes singular values below its own `threshold` getter (`(Number.EPSILON/2) * max(m,n) * s[0]`) before inverting, with no argument needed. Implementing D-06 is **subtractive**: delete the `.add(Matrix.eye(n).mul(lambda))` ridge term from `solveRidgeOpr`; the very next line already does the right thing. No new tolerance-selection logic is needed anywhere in this phase.

The harness re-run cost is real but bounded and well-evidenced from this repo's own prior runs, not estimated from scratch: a full 2022-2026 season-pooled-OPR-only run has been measured twice at 78-82 minutes; a full 5-algorithm run (the shape D-11 requires) was measured at 6h03m, with OPR's season-pooled cost (~131ms/update at ~3,700-team scale) estimated as roughly 2.5h of that total. The rewritten event-scoped OPR operates on ~39 teams/event (verified directly against the corpus: mean 38.7, median 38, p10-p90 27-53 across 979 non-offseason 2022-2026 events) — a microsecond-scale solve, not a 131ms one — so the NEW 5-algorithm re-run should be dominated by EPA/Sigma1's existing ~3.5h cost, not by OPR. Combined with D-13's mandatory extra final run of the OLD algorithm (~1.5-2.5h), this phase pays for roughly 5-7 hours of real wall-clock harness time across its two required runs — a real cost the plan must sequence and checkpoint around, not a rounding error.

One landmine was found that is not in CONTEXT.md and must be designed around: `packages/harness/digest.test.ts`'s CI gate globs **every** `.json` file in `data/algorithm-versions/` and parses it against `PromotedVersionSchema`, which requires a Sigma1-shaped `params` field. If D-13's retired-OPR fingerprint is naively committed into that same directory, CI breaks on the very next push — not because OPR changed, but because the fingerprint file doesn't parse as a promoted Sigma1 version. The fix is a one-line placement decision: commit D-13's fingerprint to a directory `digest.test.ts` never scans.

**Primary recommendation:** Implement `solveRidgeOpr` as a subtractive change (drop the ridge term), reuse `SingularValueDecomposition`'s existing default min-norm behavior unchanged, reuse `computePredictionStreamDigest` (already algorithm-agnostic) for D-13's fingerprint but commit it **outside** `data/algorithm-versions/`, and sequence the two required harness runs as separate, explicitly time-boxed tasks rather than one undifferentiated "re-run the harness" step.

### Pattern 1: Event-keyed state, not event-reset state (D-01)

**What:** `OprState` becomes `Map<eventKey, PerEventOprState>` (or equivalent), where each event's sub-state is independently accumulated. Because `buildSeasonStream` interleaves concurrent events chronologically, a single mutable "current event" pointer would corrupt any two events running at once — confirmed structurally: `replay.ts`'s own header states this is the reason cross-event interleaving exists (`[VERIFIED: packages/harness/replay.ts:101-115]` — quoting: *"two events running concurrently in real time contribute matches to a single merged stream ordered by when they were actually played, not grouped by event"*).

**When to use:** Any per-event algorithm state replayed through `WalkForwardSimulator` over a season-wide stream.

**Example (recommended shape, not existing code):**
```typescript
// packages/core/algorithms/opr.ts (rewritten)
export interface OprState {
  readonly perEvent: ReadonlyMap<string, PerEventOprState>; // keyed by eventKey
}
interface PerEventOprState {
  readonly observations: readonly OprObservation[]; // qm-only, this event only
  readonly ratings: ReadonlyMap<string, number>;
}
```

### Pattern 2: Subtractive ridge removal — the min-norm solve already exists

**What:** `solveRidgeOpr`'s existing structure already IS a minimum-norm pseudo-inverse solver once the ridge term is removed — `SingularValueDecomposition.solve()` unconditionally zeroes singular values at or below its own `threshold` getter before inverting (`Ls.set(i, i, 0)` when `Math.abs(this.s[i]) <= e`, `e = this.threshold`) — `[VERIFIED: node_modules/.pnpm/ml-matrix@6.15.0/node_modules/ml-matrix/src/dc/svd.js:430-442]`. Quoting the relevant lines:
```js
solve(value) {
    let Y = value;
    let e = this.threshold;
    ...
    for (let i = 0; i < scols; i++) {
      if (Math.abs(this.s[i]) <= e) {
        Ls.set(i, i, 0);
      } else {
        Ls.set(i, i, 1 / this.s[i]);
      }
    }
```
and the threshold itself (`[VERIFIED: .../svd.js:527-529]`, quoted verbatim):
```js
  get threshold() {
    return (Number.EPSILON / 2) * Math.max(this.m, this.n) * this.s[0];
  }
```
This is the same family of tolerance NumPy's `pinv` uses by default (a relative cutoff scaled by the largest singular value and matrix dimension) — no hand-tuning is needed or appropriate.

**When to use:** Directly in the rewritten `opr.ts`. Delete the line `.add(Matrix.eye(n).mul(lambda))` from the current `solveRidgeOpr` (`[VERIFIED: packages/core/algorithms/opr.ts:210]`, current text: `` const MtM = M.transpose().mmul(M).add(Matrix.eye(n).mul(lambda)); ``); the next line (`new SingularValueDecomposition(MtM).solve(Mts)`) needs no change at all.

**Anti-pattern to avoid:** Do not hand-roll a singular-value cutoff or port a "reasonable-looking" epsilon from another language — `ml-matrix`'s own default already matches the standard convention and is what the existing code already calls.

### Pattern 3: Rank/condition diagnostics are also already available on the same object

`SingularValueDecomposition` exposes `.rank` (`[VERIFIED: .../svd.js:511-521]`, tolerance `Math.max(this.m, this.n) * this.s[0] * Number.EPSILON`) and `.condition` (`s[0] / s[min(m,n)-1]`) as getters. SC-5's rank-vs-team-count diagnostic (D-07) can call `new SingularValueDecomposition(M).rank` directly on the checkpointed design matrix rather than hand-computing rank — this is the exact same primitive `docs/models/sigma1-identifiability.md`'s own rank/condition-number checks already report on (that document's own numbers — e.g. "2022: 3,520 x 775, Rank 767, Condition number 7.08" — come from this same class, giving in-repo precedent for the reporting shape `[CITED: docs/models/sigma1-identifiability.md]`).

### Anti-Patterns to Avoid

- **Re-deriving Sherman-Morrison/RLS keyed by event:** D-03 explicitly rejects this. At ~39 teams/event a direct dense SVD solve is microseconds; the ~250-line incremental-inverse machinery exists only because season pooling made a fresh solve cost 16 CPU-days/season. That reason is gone.
- **Committing D-13's retired-baseline fingerprint into `data/algorithm-versions/`:** see Pitfall 1 below — this breaks the D-15 CI gate.
- **Treating "matches completed" bucketing for SC-5 as requiring a harness/sidecar schema change:** it does not (see Code Examples / SC-5 section) — this is a read-only reporting problem over already-recorded data.

## Common Pitfalls

### Pitfall 1: D-13's retired-baseline fingerprint breaks CI if placed in `data/algorithm-versions/`

**What goes wrong:** `packages/harness/digest.test.ts`'s `listVersionFiles()` reads **every** `.json` file in `ALGORITHM_VERSIONS_DIR` (`data/algorithm-versions/`) and calls `PromotedVersionSchema.parse(raw)` on each one (`[VERIFIED: packages/harness/digest.test.ts:46-51, 112-115]`, quoting: `` return readdirSync(ALGORITHM_VERSIONS_DIR).filter((name) => name.endsWith(".json")).sort(); `` then `` const promoted: PromotedVersion = PromotedVersionSchema.parse(raw); ``). `PromotedVersionSchema` requires `params: Sigma1ParamsSchema` as a non-optional field (`[VERIFIED: packages/harness/promote.ts:76-85]`, quoting: `` params: Sigma1ParamsSchema, `` inside the exported `PromotedVersionSchema` object). OPR has no Sigma1-shaped hyperparameters — a bare retired-OPR fingerprint dropped into this same directory will fail that `.parse()` call the moment CI (or any local `pnpm test`) runs, unrelated to anything about OPR's own correctness.

**Why it happens:** The directory-scan CI gate was written when the only thing ever promoted there was Sigma1. D-13 introduces the first non-Sigma1 committed artifact this project has ever produced, and the phase's own instruction ("mirror D-15's digest convention") is easy to over-literally read as "put it in the same directory."

**How to avoid:** Commit D-13's fingerprint file to a **new, separate directory** — `data/retired-baselines/` is recommended — that `digest.test.ts` never scans. This still satisfies the "committed, small, mirrors the digest convention" requirement (same `computePredictionStreamDigest` function, same shape idea: per-season headline metrics + a SHA-256 over the prediction stream) without being inside the CI gate's directory scan.

**Warning signs:** `pnpm test -- packages/harness/digest.test.ts` failing with a Zod validation error naming a field like `params` immediately after committing the retired-baseline file — this is the exact failure mode to watch for if the file is placed wrong.

### Pitfall 2: Normal-equations solve (SVD of M^T M) squares the effective condition number

**What goes wrong:** Both TBA's own implementation and this codebase's existing `solveRidgeOpr` solve via the **normal equations** — they build (or, for TBA, directly accumulate) the Gram matrix `M^T M` and take its pseudo-inverse, rather than computing `SingularValueDecomposition(M)` on the raw `m×n` design matrix and using `.solve()` directly on that. This is a well-known numerical tradeoff: forming `M^T M` squares the matrix's condition number (`κ(M^T M) = κ(M)^2`), so a design matrix that is merely poorly conditioned becomes measurably worse-conditioned once squared. Early in an event, this compounds the already-thin design matrix's rank deficiency.

**Why it happens:** It is the same shape TBA's own `matchstats_helper.py` uses (`build_Minv_matrix` builds `M` as the `n×n` co-occurrence/Gram matrix directly via nested loops over alliance teammates, then calls `np.linalg.pinv(M)` on that — never on a raw `m×n` design matrix `[VERIFIED: fetched via gh api repos/the-blue-alliance/the-blue-alliance/contents/src/backend/common/helpers/matchstats_helper.py, build_Minv_matrix method]`). Matching this is **correct for fidelity** — it is not a bug to fix, it is the thing being replicated.

**How to avoid:** Do not "fix" this by switching to `SingularValueDecomposition` on the raw design matrix `M` instead of `M^T M` — doing so would make SigmaScout's numbers a genuinely different (better-conditioned, and therefore different) computation than what TBA publishes, defeating the phase's stated goal. Instead, treat this condition-squaring as an expected, named contributor to D-07's early-event noise measurement — the SC-5 write-up should note that some of the measured early-event degradation is attributable to this fidelity-preserving numerical choice, not only to the design matrix's true rank deficiency.

**Warning signs:** If a future contributor "improves" the solve to use `SVD(M).solve()` directly and OPR's numbers silently drift from what TBA's `/event/{key}/oprs` endpoint reports for the same event, this is why.

### Pitfall 3: TBA does not special-case surrogates — this project's D-07 policy is a deliberate, pre-existing divergence

**What goes wrong (if unaware):** A planner re-reading "match what TBA and Statbotics publish" as this phase's yardstick could reasonably wonder whether the existing surrogate-offset logic (`ratingEligibleTeams`/`allianceObservation`) should also be revisited for fidelity.

**What TBA actually does:** `matchstats_helper.py`'s `build_Minv_matrix`/`build_s_matrix` iterate `match.alliances[color]["teams"]` with no surrogate exclusion or offset logic anywhere in the file — every listed team's column is included and every team's rating is updated, surrogate or not `[VERIFIED: fetched matchstats_helper.py, full file read — no `surrogate` reference anywhere]`.

**How to avoid mis-scoping:** This phase's own Code Context section already settles this — surrogate/DQ handling is explicitly out of scope and must survive unchanged (`ratingEligibleTeams`/`allianceObservation` are "orthogonal to scope"). This research confirms that decision is a **known, named divergence from TBA's literal practice**, not an oversight — worth one sentence in `opr-baseline-change.md` so a future reader who diffs SigmaScout's OPR against TBA's on a surrogate-affected event understands why the numbers won't match exactly, rather than filing it as a bug.

### Pitfall 4: Statbotics does not currently publish plain OPR as its primary metric

**What goes wrong (if unverified):** Assuming Statbotics is a second live source to fidelity-check OPR against.

**What was found:** Statbotics' current primary model is EPA (already a separate baseline in this project); historically Statbotics computed a variant called "ixOPR" that incorporates a prior during ongoing events, not TBA's plain per-event OPR `[CITED: WebSearch summary of Statbotics' public blog/GitHub — MEDIUM confidence, not independently source-verified this session]`. This means "matching what TBA and Statbotics publish" for OPR specifically reduces, in practice, to matching TBA — Statbotics is not a second independent OPR implementation to reconcile against.

**How to avoid:** Do not block this phase on finding a Statbotics OPR number to compare against; none is currently published in the form this project's baseline needs. Note this plainly in `opr-baseline-change.md` rather than silently dropping the "and Statbotics" framing.

## Code Examples

### Verified: TBA's actual OPR computation (source-confirmed)

```python
# Source: github.com/the-blue-alliance/the-blue-alliance
# src/backend/common/helpers/matchstats_helper.py (fetched directly this session)

@classmethod
def build_team_mapping(cls, matches):
    team_set = set()
    for match in matches:
        if match.comp_level != "qm":  # only consider quals matches
            continue
        ...

@classmethod
def build_Minv_matrix(cls, matches, team_id_map):
    n = len(team_id_map.keys())
    M = np.zeros((n, n))
    for match in matches:
        # only consider quals matches that have been played
        if (match.comp_level != CompLevel.QM) or (not match.has_been_played):
            continue
        for alliance_color in ALLIANCE_COLORS:
            alliance_teams = match.alliances[alliance_color]["teams"]
            for team1 in alliance_teams:
                team1_id = team_id_map[team1[3:]]
                for team2 in alliance_teams:
                    M[team1_id, team_id_map[team2[3:]]] += 1
    return np.linalg.pinv(M)  # <-- plain Moore-Penrose pseudo-inverse, no ridge
```
This confirms, with source-code certainty: (1) qualification matches only [D-05], (2) no ridge/regularization term anywhere [D-06], (3) rank-deficiency is handled by `np.linalg.pinv`'s own default SVD-based zero-threshold, exactly the behavior `ml-matrix`'s `SingularValueDecomposition.solve()` already provides by default.

### Recommended: the subtractive fix to `solveRidgeOpr`


### SC-5's Brier/accuracy-by-checkpoint bucketing — no schema change needed

`PersistedPredictionRecord` already carries `matchKey`, `eventKey`, `compLevel`, `season`, `algorithmId` per line, written to `predictions-{season}.jsonl` **in the same chronological order the season was replayed** (`[VERIFIED: packages/harness/predictions.ts:61-93]` for the schema fields; `[VERIFIED: packages/harness/cli.ts:513-541]` for write-in-stream-order — `writePredictionLine` is called once per record inside the `for (const r of records)` loop over `WalkForwardSimulator.runAll`'s output, which itself iterates `this.#matches` in the corpus's total chronological order). A reporting script can therefore, reading one season's sidecar file top to bottom for `algorithmId === "opr"`:

```typescript
const qmCompletedByEvent = new Map<string, number>(); // eventKey -> count seen so far
for (const line of sidecarLines) {
  const rec = JSON.parse(line) as PersistedPredictionRecord;
  const completedBefore = qmCompletedByEvent.get(rec.eventKey) ?? 0;
  bucket(completedBefore).push(rec); // predict-before-update: `completedBefore` is exact
  if (rec.compLevel === "qm") {
    qmCompletedByEvent.set(rec.eventKey, completedBefore + 1);
  }
}
```
This requires **no harness or sidecar schema change** — it is a pure post-hoc read of already-recorded data. The rank-vs-team-count half of D-07 is NOT derivable this way (no sidecar field carries design-matrix rank) and needs a small new script re-reading the corpus directly, mirroring `identifiability.ts`'s existing pattern of an independent, purpose-built design-matrix construction.

   - What we know: season-pooled OPR's cost is measured (~131ms/update at ~3,700-team scale); the new design does many more, much smaller solves (one SVD per event per match, ~39x39 typical, versus one incremental O(n²) update at n up to ~3,700).
   - What's unclear: whether re-solving the whole event's design matrix on every single match within that event (rather than truly incrementally) is the intended implementation — CONTEXT.md's Claude's Discretion section leaves "the exact file/module decomposition" open, which includes whether each `update()` call re-runs a full per-event SVD (simple, and still cheap given the ~39-team scale) or something smarter.
   - Recommendation: implement the simple version first (full per-event re-solve on every match) — at ~39×39, even hundreds of re-solves per event costs low milliseconds total, several orders of magnitude below the old cost. Do not add incremental machinery back in without first measuring that the simple version is actually a bottleneck.

2. **Whether `opr.ts`'s rewritten module needs a version-string bump beyond `2.0.0+baseline`**
   - What we know: `buildArtifact` requires `{codeVersion}+{paramSetName}` with a non-empty string on each side of exactly one `+` (`[VERIFIED: packages/harness/artifact.ts:128-143]`) — any non-empty pair works, and `applyPromotedOverrides`/`warnIfNewerPromotedSigma1` never touch OPR (Sigma1-only).
   - What's unclear: whether the phase should bump `codeVersion` (e.g. `3.0.0+baseline`) to signal a semantically different algorithm, per D-13's project-wide version-identity convention referenced in Canonical References.
   - Recommendation: bump `codeVersion` — a reader of `data/algorithm-versions/` or any published artifact should not see `"2.0.0"` used for two structurally different algorithms across the D-13 retired-baseline fingerprint and any future artifact. This is Claude's Discretion territory per CONTEXT.md but worth flagging explicitly since it's easy to leave unchanged by default.
