# Phase 06.1 Learnings: match-and-event-data-enrichment

## Decisions

### Per-event metric percentiles rank against the season-final distribution, never a per-match-index pool
Every history-row percentile (`percentileAgainstSortedPool`) ranks a mid-season value against the
metric's **season-final** sorted pool — "where this team stood at that point, against the final
field" — not against the field as it stood at that point in the season. The rejected alternative
(rank against the pool as of that match index) was not built, sketched, or left as a TODO anywhere.

**Rationale:** A mid-season field is a moving target; ranking against it would make two events'
tier colours incomparable across a season. This was a user-locked decision (D-06.1-A) made at
planning time, not re-litigated by any of the eight plans.
**Source:** 06.1-01-PLAN.md `<locked_decisions>`; 06.1-03-PLAN.md `<locked_decisions>`; 06.1-05-PLAN.md `<locked_decisions>`.

---

### Offseason events are in scope for the event_rankings ingest
TBA's `/event/{key}/rankings` is fetched for offseason events too, not just in-season official
events.

**Rationale:** TEAM-04's "attended event" wording is not scoped to in-season; the team page already
renders event sections for offseason events; 553 of 1,581 corpus events (later measured as 368 of
1,690) are offseason, so excluding them would silently rank-less a third of all event cards; TBA
computes these rankings itself from official match results, a materially different trust boundary
from the self-reported `score_breakdown` Phase 3's RP fold excludes. Cost delta was ≈1 minute of
ingest time.
**Source:** 06.1-01-PLAN.md `<planner_decisions>` PD-01; 06.1-04-PLAN.md/COVERAGE.md (settled as an explicit row, not left as an assumption).

### A null TBA response body and an empty rankings array both store zero corpus rows; the distinction lives only in the ingest run's own counters
The corpus's `event_rankings` table cannot represent "checked, found nothing" differently from
"never checked" when the answer is zero rows either way. The two absent cases (`null` body vs
empty `rankings: []`) are counted separately in the ingest run's log output instead.

**Rationale:** A per-(event,team) fact table has no natural place to park a "we looked" marker when
there are zero facts. The honest record of the distinction lives where it is actionable — the
ingest run's own tally — not in a schema contortion. Later measured for real: 50 null-body vs 165
empty-rankings events across the four freshly-fetched 2022-2026 seasons, confirming the distinction
is real rather than theoretical.
**Source:** 06.1-01-PLAN.md `<planner_decisions>` PD-02; 06.1-04-SUMMARY.md.

---

### Per-bonus probabilities/flags travel as a positional array aligned to the season's bonus-name order, not a keyed Record
`RpPmfResult.redBonusProbabilities`, `Prediction.redBonusRp`, and the published
`TeamSeasonMatchSchema.redBonusRp`/`actualRedBonusRp` are all arrays indexed against
`RpRuleModule.bonusNames`, deliberately diverging from RESEARCH.md's and PATTERNS.md's own sketch of
a `Record<string, number>`.

**Rationale:** Two measured reasons. (1) Consumer fit: `BonusRpDots` already indexes positionally,
and an existing passing test (`bonusRp.test.ts`) already pins that the client's order matches
`bonusNames` exactly. (2) Payload budget: on the budget-critical `frc118/2024/sigma1` artifact, the
record form cost ≈238 bytes/match row vs the array form's ≈124 — a ≈33,000-byte difference against
only 70,138 bytes of total headroom, budget the phase also needed for percentiles. Rated
**costly** (not one-way): undoing it needs another full republish plus a client change, but breaks
no contract.
**Source:** 06.1-02-PLAN.md `<planner_decisions>` PD-04; 06.1-05-PLAN.md `<planner_decisions>` PD-04 (restated).

### Absence, null, and a real array are three distinct published states for a per-bonus field, and none is ever coerced to another
A key entirely absent means "this artifact predates the field, or the season has no registered
bonus vocabulary." An explicit `null` means "the pipeline looked and the fact is not derivable"
(no score breakdown, unparseable breakdown, RP-ineligible event type). A populated array is a real
answer. An empty array and an all-false array are both prohibited representations of absence.

**Rationale:** Collapsing null to an all-false array would assert every bonus was missed — a
positive claim the data does not support — mirroring `actualRedRp`'s pre-existing null contract
exactly. This three-state contract is what G-06.1-26 (see Lessons) later exposed as *inconsistently
implemented* rather than wrong in principle.
**Source:** 06.1-05-PLAN.md `<planner_decisions>` PD-10.

### The history-row percentile allowlist is capped to four metric names, single-sourced from core
`HISTORY_PERCENTILE_METRIC_KEYS` is exactly `COMPONENT_GROUP_METRIC_KEYS` (3 values) plus
`TOTAL_METRIC_KEY`, imported from `packages/core/algorithms/breakdown/index.ts`/`types.ts` — never
re-declared as string literals in the harness.

**Rationale:** Measured payload cost. The budget-critical artifact had 70,138 bytes of headroom; a
sigma1 2024 row's `metrics` record holds 17 possible names, and publishing a percentile on all 17
across 292 match rows would cost ≈89,000 bytes — more than the entire headroom before this phase's
other fields spent any of it. The four-name allowlist costs ≈21,000 bytes, which fits alongside the
per-bonus arrays. Single-sourcing from core (not `apps/web`) keeps the pipeline from learning
anything about the UI.
**Source:** 06.1-03-PLAN.md `<planner_decisions>` PD-06.

---

### Actual per-bonus flags are computed once per season, outside the per-algorithm loop, and threaded in as a parameter
`actualBonusFlagsForSeason` runs once per season in `publish.ts`'s per-season preamble, not once per
algorithm and not inside any `AlgorithmModule`.

**Rationale:** The flags describe the match, not a prediction, so they are algorithm-independent by
definition. Computing them inside the per-algorithm loop would re-run `ruleModule.parse` three times
per match for an identical result; computing them inside an `AlgorithmModule` would make real bonus
data visible only on Sigma1 pages — the same reasoning `actualRedRp` already established by being
sourced from the ingest-level match record rather than any one algorithm's internal state.
**Source:** 06.1-05-PLAN.md `<planner_decisions>` PD-09 (citing RESEARCH.md Pattern 1).

---

### A predicted per-bonus probability of exactly 0.5 renders as earned; the dot's label carries the real percentage
`PREDICTED_BONUS_THRESHOLD = 0.5`, and the boundary itself resolves to earned (not missed).

**Rationale:** A three-state dot vocabulary cannot express a continuous probability, so a threshold
is unavoidable once a probability drives a two-state mark. Half-up-to-earned matches the codebase's
existing half-away-from-zero rounding convention and `sigma1/index.ts`'s own tie-to-red handling at
`pRedWin === 0.5`. Because a binary mark still loses information, the dot's tooltip/`aria-label`
(one shared function, `bonusDotLabel`) carries the actual percentage so the visual stays binary
while the accessible text stays honest.
**Source:** 06.1-06-PLAN.md `<planner_decisions>` PD-11, PD-12.

---

### The gap-closure republish was deliberately skipped; a required client-side prop is what makes that safe
Plan 06.1-08 fixed the publish pipeline's qualification-only gate but did **not** spend a republish
to correct the ~54,671 already-published artifacts, which still carry stale playoff bonus arrays in
their raw JSON.

**Rationale:** A full republish costs ~23 minutes and rewrites every object — and the *previous*
republish (06.1-07) had already shown that "spend the republish" sweeps in unrelated
committed-but-unpublished work and can blow a payload ceiling. Repeating that risk to fix a defect
the client can already refuse to render was judged worse than deferring. `BonusRpDots.applicable` is
a **required** (non-optional) boolean prop specifically so a call site that forgets to gate it fails
`pnpm typecheck` rather than silently shipping a false claim; with it in place, the stale published
arrays are structurally never read. The deferred republish was recorded as a tracked todo file
rather than left as tribal knowledge.
**Source:** 06.1-08-PLAN.md `<planner_decisions>` PD-16, PD-17, PD-18; 06.1-08-SUMMARY.md.

---

### Over-eager de-duplication of a shared literal is itself a load-bearing prohibition
`packages/core/algorithms/opr.ts` and `packages/harness/score.ts` also compare `compLevel` against
`"qm"`, but plan 06.1-08 explicitly did **not** rewire either to the new shared
`isBonusRpCompLevel` predicate, and made an empty `git diff` on both files an acceptance criterion.

**Rationale:** OPR's comparison decides which matches feed its statistical fit; `score.ts`'s decides
a scoring view filter. Both happen to share a literal with the bonus-RP eligibility rule, but they
are different rules answering different questions. Unifying them under one predicate because they
look the same today is exactly how the *next* silent-drift bug gets created — the same failure mode
that produced G-06.1-26, just inverted.
**Source:** 06.1-08-PLAN.md `<planner_decisions>` (Task 2 action, "Prohibition, load-bearing"); 06.1-REVIEW.md (confirmed both files' diffs empty).

## Lessons

### One rule expressed as two independent literals drifted apart and shipped a false claim to users
The qualification-only bonus-RP rule (FRC awards bonus ranking points in `qm` matches only) was
implemented as a literal `compLevel !== "qm"` check on the *predicted* side (`distribution.ts`,
plan 06.1-02) but was **never gated at all** on the *actual* side (`actualBonusFlagsForSeason`,
plan 06.1-05). Every published artifact ended up asserting real earned/missed bonus dots on playoff
rows — a ranking-point fact FRC does not award there — while the predicted side correctly showed
nothing. The bug shipped through verification and was only caught by a human clicking a live team
page during UAT.

**Context:** What now structurally prevents this class of bug: (1) one exported predicate,
`isBonusRpCompLevel` in `packages/core/algorithms/sigma1/rp/constants.ts`, is the single source
consulted by all three gates (predicted, actual, and a fourth artifact-assembly defence-in-depth
layer) plus the client; (2) `BonusRpDots.applicable` is a *required* prop, so a future call site
that omits the gate fails `pnpm typecheck` instead of shipping silently; (3) the regression test is
written as an invariant over the *whole comp-level set* (`qm`/`ef`/`qf`/`sf`/`f` in one mixed
stream, asserting map size 1 against stream length 5) rather than as a single `sf` fixture, so a
future comp level or a reintroduced ungated form fails loudly rather than passing by accident.
**Source:** 06.1-08-PLAN.md `<assumption_delta_decision>`; 06.1-UAT.md gap G-06.1-26 (`root_cause`); 06.1-08-SUMMARY.md.

---

### A threat register's `accept` disposition can be correct at the moment it's written and wrong an hour later, inside the same phase
Plan 06.1-06's threat register filed T-06.1-26 (elimination-match dots) as `accept`, reasoning that
"those dots stay unknown — today's behaviour, unchanged (PD-13)." That premise was already false: an
*earlier* plan in the same phase (06.1-05) had shipped the actual-side publish code that put real
earned/missed data on playoff rows. Plan 06.1-06's own author apparently did not re-derive "today's
behaviour" from the code plan 06.1-05 had just landed, but from the pre-phase mental model.

**Context:** A disposition is only as good as the fact it's conditioned on, and that fact can rot
*within a single phase* as earlier plans in the same wave sequence land. The general lesson: before
accepting a risk with a premise like "X is unchanged" or "this is already true," re-verify against
the current code, not against what was true when the phase started — especially in a multi-plan
phase where sibling plans are actively changing the exact surface the premise depends on. The fix
was not to relitigate the acceptance from scratch; it was to re-derive the disposition against
current fact, which flipped it to `mitigate`.
**Source:** 06.1-08-PLAN.md `<assumption_delta_decision>` ("Why the earlier accept was wrong, recorded so it is not repeated"); 06.1-06-PLAN.md `<threat_model>` T-06.1-26.

### Verification passed 8/9 and UAT still found a major defect — because no automated test asserted cross-plan agreement
The initial `06.1-VERIFICATION.md` pass checked each plan's own claimed truths and each plan's own
tests, all of which were internally consistent and green. What no test checked was the thing that
actually broke: that the predicted-side gate and the actual-side gate agreed on the *same*
qualification-only rule. Each side was tested against its own plan's fixtures in isolation; nothing
asserted the two guards' agreement as a single invariant until plan 06.1-08 added one.

**Context:** Per-plan verification (and even goal-backward phase verification) can be blind to a
defect that only exists in the *seam* between two plans' outputs, especially when both plans'
individual tests pass and the seam is a semantic rule (not a type, not a schema) duplicated as two
literals in two files nobody cross-referenced. A human manually exercising the live UI (UAT test 26)
is what actually found it, in under a suggested few minutes of clicking. The corrective pattern
(see Patterns: comp-level-set invariant) generalizes: whenever a rule is expressed twice, plan for a
test that asserts the two expressions produce identical output, not just that each expression is
individually correct.
**Source:** 06.1-VERIFICATION.md frontmatter (`reopened`, `reopened_reason`); 06.1-UAT.md test 26.

### A "measure before you spend the republish" gate that only checks the current phase's own target artifact can still be blindsided by unrelated unpublished work
Plan 06.1-07's Task 1 dry-run projection checked only the `team/{teamKey}/{year}` artifact (the one
this phase's own fields land on) across all five seasons, and it was accurate for that artifact.
But the real republish also moved `teams/{year}` and `event/{eventKey}` — both untouched by this
phase's code — because two *Phase-6* commits (`06f468ad`, `bf1e3228`) had landed the day before and
had never been republished. The republish, being the first one since, swept them in unannounced,
and `teams/{year}` came out over its own committed budget ceiling.

**Context:** A payload-budget projection scoped to "what this plan changes" is necessarily blind to
"what has accumulated, unpublished, since the last time anyone actually spent a republish." The
"one authorized republish per phase" discipline that made this phase efficient is exactly what let
two unrelated commits' cost go unmeasured until republish time — sequencing efficiency and
cost-visibility trade off against each other. The corrective is not "always republish immediately,"
which was explicitly rejected elsewhere in this phase's threat model as risky/wasteful — it's that
a pre-republish projection needs to ask "what changed since the *last* republish," not "what did
*this phase* change."
**Source:** 06.1-07-SUMMARY.md `key-decisions` and Deviations §1; `.planning/WINDOWS.md` ledger #11 (referenced in 06.1-07-SUMMARY.md and 06.1-VERIFICATION.md).

### When a plan's descriptive prose and its own reference implementation disagree, the acceptance criteria — not the prose — is the authoritative contract
Plan 06.1-03's `<behavior>` prose asserted a query strictly below every pool member must return "a
percentile strictly greater than 0." But the plan's own instruction was to reuse
`percentileRanks`'s formula "verbatim," and that formula (and RESEARCH.md's/PATTERNS.md's own worked
examples of it) produce exactly `0` for that case. The executor implemented the literal formula
(yielding `0`) rather than forcing a different, prose-matching behavior, because the plan's actual
`<acceptance_criteria>` — the real grading gate — never tested the ">0" claim specifically.

**Context:** A plan's narrative behavior description is a summary written by a human/LLM planner and
can drift from what the plan's own cited reference implementation actually does; the
`<acceptance_criteria>` block is what a plan is graded against and is the more carefully
cross-checked artifact. When the two disagree and changing the code to match the prose would
contradict an explicit "reuse verbatim" instruction, resolving in favor of the reference
implementation plus the literal acceptance criteria — and documenting the reconciliation — is
correct.
**Source:** 06.1-03-SUMMARY.md "Decisions Made" §1.

### Removing a caption's visible text can silently delete an attribute (the tooltip) that lived on the same DOM element, un-mitigating a threat nobody re-examined
G-06.1-28 asked to remove the visible "vs season-final field" caption text. The caption's `title`
attribute — the hover tooltip carrying the *full* explanation — lived on the exact same `<span>`.
Deleting the span for the visible-text reason also deleted the only remaining explanation of what
the tier colours mean, anywhere on the site, reversing a prior decision (PD-14: "visible text, not a
hover title alone") and un-mitigating a high-severity threat (T-06.1-24) that the caption existed
specifically to cover — without anyone having explicitly decided to accept that consequence.

**Context:** The gap-closure plan's own author caught this before executing ("CORRECTION found by
the planner") and escalated it as a blocking, first-run checkpoint decision rather than silently
absorbing the caption removal. The general lesson: a UI element's visible content and its
accessibility/tooltip content are easy to conflate as "the same thing" when they are literally one
DOM node, and a request to remove "the text" needs an explicit check for what else rides on the same
element before treating removal as purely cosmetic.
**Source:** 06.1-UAT.md gap G-06.1-28 `missing` list ("CORRECTION (found by the planner, 2026-08-27)"); 06.1-08-PLAN.md Task 1 `<context>`.

## Patterns

### Tracer-first plan shape: prove the longest, least-proven path end-to-end before widening
Plan 06.1-01 wired TBA's rankings endpoint through every layer (API → ingest → corpus → publish →
schema → rendered line) for exactly one season before any other plan started, rather than building
per-bonus RP or percentiles first (both of which start with data already in-process).

**When to use:** When a phase has multiple features of different "path length" through the system,
build the one that crosses the most trust boundaries and touches the most files first, in
production-quality form, on the smallest possible scope. An architectural dead end at any boundary
then surfaces after one commit instead of after every feature is already half-built.
**Source:** 06.1-01-PLAN.md `<tracer_rationale>`.

---

### Pin an invariant over the whole relevant enum set, not one representative fixture
Rather than asserting "an `sf` match doesn't get a bonus dot," the regression test builds one stream
containing all five `CompLevel` values (`qm`/`ef`/`qf`/`sf`/`f`) and asserts the actual-flags map has
exactly one entry (`qm`'s), non-vacuously checked against stream length 5.

**When to use:** Whenever a rule partitions a small, closed, named set (comp levels, algorithm ids,
registered seasons), write the test as a loop or single assertion over the *whole* set rather than
one member. A single-fixture test only proves the rule holds for the case someone thought to check;
a whole-set test catches both a currently-missed member and a future member added to the enum.
**Source:** 06.1-08-PLAN.md `<assumption_delta_decision>` ("Generalized invariant"), Task 3 `<behavior>`; also used in 06.1-02-PLAN.md Task 3 (per-season bonus-array-length invariant over `RP_REGISTERED_SEASONS`).

---

### `not.toHaveProperty` for genuine absence; conditional spread (never `key: undefined`) is what makes that true
A field must be tested absent with `not.toHaveProperty`, not `toBeUndefined` — because Zod's object
parse keeps a key present-with-`undefined`-value when the candidate object literally carries that
key. Achieving genuine absence in the parsed output requires the row-assembly code to use a
conditional spread (`...(cond ? { field: value } : {})`) rather than a direct assignment
(`field: value`).

**When to use:** Any time a published/parsed schema must represent "this fact does not exist" as
key-absence rather than a null/undefined value, and especially when a field is populated from a
caller-supplied source that might itself carry `undefined`. Direct-assignment fields get
`toBeUndefined` tests; conditionally-spread fields get `not.toHaveProperty` tests — the two are not
interchangeable, and using the wrong assertion for a field's actual construction will pass even when
the underlying representation is wrong.
**Source:** 06.1-01-SUMMARY.md `key-decisions`; 06.1-05-PLAN.md Task 1/2; 06.1-05-SUMMARY.md `patterns-established`; 06.1-08-SUMMARY.md Rule 2 deviation (re-applied to `redBonusRp`/`blueBonusRp`).

---

### Corpus-gated end-to-end tracer test: existsSync guard, named skip message, deterministic pair selection
An end-to-end test that needs the real (gitignored) corpus guards on `existsSync` of the corpus
path and, when absent, calls `it.skip` with an explicit message naming the missing path — never a
silent pass. When present, it picks a deterministic (event, team) pair by sorting map keys and
taking the first, so the assertion is stable across runs regardless of SQLite's row order.

**When to use:** Any integration test that needs a large, environment-specific, gitignored data
source (a local corpus, a fixture directory) to make a real assertion, in a project where CI or a
teammate's machine might not have that data. Never let "data not present" collapse into a silent
pass; make the skip loud and name what's missing.
**Source:** 06.1-01-SUMMARY.md `patterns-established`; mirrored in 06.1-05-PLAN.md Task 3 (corpus-backed percentile invariant) and `packages/harness/digest.test.ts` (see next pattern).

---

### A reproducibility gate falls back to a committed fixture so it still runs in CI where the gitignored corpus never exists — and separately asserts the fixture isn't stale
`packages/harness/digest.test.ts` only skips when *neither* the real corpus *nor* a committed
`fixtures/digest-slice.json` is available. When only the fixture is available it still runs for
real against that fixture, and a dedicated case (`"corpus-derived and fixture-derived slice match
lists are identical"`) independently proves the committed fixture hasn't gone stale relative to the
live corpus, whenever both happen to be present at once.

**When to use:** Any gate whose full-strength form needs a large local-only data source, but whose
existence as a *gate at all* matters even in environments (CI) that will never have that source. A
skip-when-both-are-absent policy, plus a from-time-to-time staleness check between the fixture and
the real source, avoids the common failure mode of "the CI job always skips this, so nobody notices
when it would fail."
**Source:** `packages/harness/digest.test.ts` (module header, `CORPUS_AVAILABLE`/`FIXTURE_AVAILABLE`, T-03-17 staleness case); referenced in 06.1-02-PLAN.md Task 3 read_first.

---

### Record a fixed-seed/pre-edit golden value before widening a shared computation, so the widening's blast radius is measured, not assumed
Before adding a per-bonus tally to `rpPmfForMatch`'s existing Monte Carlo loop, plan 06.1-02 Task 1
first ran the *unmodified* production code against a fixed seed, captured the exact `redPmf`/
`bluePmf` arrays it produced, and committed that as a literal-array test case — before making any
production edit. After the widening, the same case had to still pass byte-identically.

**When to use:** Whenever a change is supposed to be "purely additive" alongside an existing
computation (reading data a loop already produces, without changing the loop's control flow or its
consumption of randomness/state). Recording the golden value *after* the edit only proves the new
code is internally consistent with itself; recording it *before* is what actually proves nothing
about the pre-existing computation moved.
**Source:** 06.1-02-PLAN.md Task 1 `<action>` ("Record the golden first"); 06.1-02-SUMMARY.md.

---

### Single-source a payload-budget-driven publish allowlist from core constants, never as re-declared literals in the harness
`HISTORY_PERCENTILE_METRIC_KEYS` is built by importing `COMPONENT_GROUP_METRIC_KEYS` and
`TOTAL_METRIC_KEY` from `packages/core`, with a lint-style grep acceptance criterion
(`grep -c 'phase[ATE]'` outside comments returns 0) proving no group-key string literal was
re-declared in `packages/harness/percentiles.ts`.

**When to use:** Any time a publish-time decision ("which metric names get this expensive field")
needs to agree with a domain vocabulary defined elsewhere (core algorithm metric names, registered
seasons, bonus names). Importing the canonical list and enforcing it with a grep-based "no literal
re-declaration" check is cheaper than a runtime cross-check and prevents the exact
two-independent-copies drift that caused this same phase's central defect (see Lessons).
**Source:** 06.1-03-PLAN.md PD-06 and Task 1 acceptance criteria; 06.1-03-SUMMARY.md.

---

### Extend the browser-safe-entry-point scan for every new module that reaches the client, rather than trusting a broad existing case
Each time a new core module became reachable from `apps/web` (`metricHistorySchema.ts` in
06.1-03, `rp/constants.ts` in 06.1-08), `browserSafeSchemas.test.ts` gained a *named* assertion
scoped to that specific file, mirroring the existing `BREAKDOWN_ENTRY_POINT` pattern — checked for
Node-builtin imports specifically, with its own non-vacuity check.

**When to use:** Any project that maintains a browser/server import-graph boundary via a test rather
than a bundler-enforced rule. A broad, generic "no Node imports anywhere in `apps/web`'s graph" case
can pass by accident (nothing new got imported yet) or fail unhelpfully (which new import broke it?)
— naming each new entry point explicitly means a future violation fails at the specific file's own
test, close to the cause.
**Source:** 06.1-03-PLAN.md Task 2 (`browserSafeSchemas.test.ts` extension); 06.1-08-PLAN.md PD-19 and Task 3 step 3.

---

### A client-side guard is defense-in-depth that can make a pipeline fix effective against already-published data without spending a republish
`BonusRpDots.applicable` (required prop) forces every dot to the `unknown` state for a
non-qualification comp level *regardless of what the artifact's JSON contains* — proven directly by
constructing a test fixture shaped exactly like the live, already-published (stale) 2024/2026
artifacts and asserting the guard still produces the correct render.

**When to use:** When a pipeline-side fix cannot practically be back-published to already-shipped
data (cost, risk of sweeping in unrelated unpublished changes — see Surprises), and the affected
data is read by a small, identifiable number of client surfaces. Making the client refuse to trust a
stale-but-still-present field, and proving that refusal against the *actual* stale shape rather than
a synthetic best case, buys time to defer the republish safely.
**Source:** 06.1-08-PLAN.md PD-18; 06.1-VERIFICATION.md "Data-Flow Trace (Level 4)" (traced against the exact live-production shape).

---

### Place a blocking decision checkpoint FIRST in an autonomous gap-closure plan, before any implementation task
Plan 06.1-08's Task 1 was a `checkpoint:decision` (not an implementation task) asking which of three
options replaces a removed UI caption's explanation — deliberately sequenced before Tasks 2-4 so the
answer could be given once, at launch, and the remaining tasks then run unattended to completion
rather than stalling mid-plan.

**When to use:** Any plan containing exactly one decision that only a human can make (a design
trade-off, an accepted-risk sign-off) alongside otherwise-mechanical implementation work. Sequencing
the human decision first turns "ask partway through and wait" into "ask once, then execute
autonomously" — valuable specifically when the plan is meant to run unattended after that one
answer.
**Source:** 06.1-08-PLAN.md PD-20; Task 1 (`type="checkpoint:decision" gate="blocking"`).

## Surprises

### TBA reports rankings for synthetic "second-robot" team keys that TBA's own /team endpoint 404s on
Some 2024 remote-league events (`2024azrl1`..`5`) report rankings for team keys like `frc1165B`,
`frc7755B` that have no corpus `teams` row at all — confirmed live, `/team/frc1165B` itself 404s on
TBA. The plan's literal schema (`team_key TEXT NOT NULL REFERENCES teams(team_key)`) failed the
*entire event's* upsert with a foreign-key violation on first contact with real data.

**Impact:** Required an unplanned Rule-1 fix mid-Task-1: skip (and separately count) a ranking row
for any team key outside the corpus's known team-key set, rather than fail the whole event or

**Source:** 06.1-01-SUMMARY.md "Deviations from Plan" §1.
