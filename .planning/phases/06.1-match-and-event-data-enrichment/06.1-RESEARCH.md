# Phase 06.1: Match and event data enrichment - Research

**Researched:** 2026-08-26
**Domain:** Offline data pipeline (packages/core, packages/ingest, packages/corpus, packages/harness) — no new UI, no new external library
**Confidence:** HIGH for priorities 1, 3, 4 (all settled by reading the actual source this session); MEDIUM-HIGH for priority 2 (TBA response shape confirmed live against the real API this session, but the community-doc citations for field-level nullability are MEDIUM confidence)

## Summary

This phase is pure pipeline plumbing: three published-data gaps in an already-built UI, landing in
one republish. None of the three needs a new algorithm, a new npm package, or a schema migration
tool — the corpus has no migration framework at all (`schema.sql` is applied idempotently via
`CREATE TABLE IF NOT EXISTS` on every `openCorpus()` call; see Pitfall 4), so a brand-new table
(`event_rankings`) is a zero-ceremony addition, identical in shape to Phase 6's own `team_media`
precedent.

**The single biggest open question going in — does F-06-1 require a new promoted algorithm
version under D-15's bitwise-reproducibility gate — is answered definitively by reading
`packages/harness/promote.ts` this session: `computePredictionStreamDigest` hashes exactly
`[matchKey, pRedWin, redScore, blueScore]` per prediction, nothing else.** Per-bonus RP data (both
the predicted probabilities and the actual achieved flags) touches none of those four fields and
does not change the Monte Carlo draw sequence that produces them (`rp/distribution.ts`'s
`buildJointModel`/`drawJoint` run identically before and after; only the *bucketing* of an
already-computed `predictThresholds()` result changes). **F-06-1 is therefore a pure additive
publish-time change — same promoted version, same digest, republish only.** This resolves the
plan's single biggest branch point before planning starts.

The second-biggest unknown — TBA's `/event/{key}/rankings` response shape — was verified live
against the real API this session (7 real events across 2022–2026, one district championship, one
not-yet-played future event, one offseason event already underway). Confirmed: the endpoint can
return HTTP 200 with a **`null` body** (an event with no ranking structure set up at all,
`2026scsc`), HTTP 200 with an **empty `rankings: []`** array (a scheduled event whose quals have
not yet run, `2026azscor`), and HTTP 200 with a populated array (every finished event tried,
including an offseason one). `sort_order_info`'s field *names* do differ by season (confirmed:
2022's four names differ from 2024's five, from 2026's three), but the phase's own success
criterion only needs `rank` and `rankings.length` — the named sort-order columns can be ignored
entirely for "Rank N of M."

F-06-3's ranking scheme is locked (season-final distribution) and its implementation site is
concrete: `packages/harness/publish.ts`'s per-`(algorithm, season)` loop already holds
`metricsByTeam` (the season-final value pool `withPercentiles` ranks) and
`metricHistoryForAlgo`/`metricHistoryByAlgoTeam` (the per-match history rows) in scope
*simultaneously*, in the same loop iteration, before either is written into an artifact. Nothing
needs to be threaded across a function boundary that does not already exist.

**Primary recommendation:** implement all three as pure functions inside the existing
per-`(algorithm, season)` publish loop, add one new corpus table for rankings (no migration
tooling needed), extend `packages/ingest` with one new TBA capability following the `media.ts`
pattern exactly, and republish. No new algorithm version, no new npm dependency, no schema
migration framework.

### Pattern 1: Algorithm-independent "actual" facts computed at publish time, not inside any AlgorithmModule

**What:** `actualRedRp`/`actualBlueRp` (Phase 6, D-02) are already populated from
`MatchResult.redRpEarned`/`blueRpEarned` — ingest-level facts, read the same way regardless of
which algorithm's artifact is being built. F-06-1's *actual* per-bonus flags should follow the
identical pattern: computed once from `match.scoreBreakdownRaw` + `rpRuleModuleForSeason(season)` +
`isRpEligibleEventType(match.eventType)`, independent of whether the artifact being built is
`opr`, `epa`, or `sigma1`.

**When to use:** any published fact that describes the match itself (not a prediction).

**Example (existing code establishing the pattern):**
```typescript
// Source: packages/harness/publish.ts:416-419 (read this session)
if ("winner" in match) {
  return {
    ...row,
    actualWinner: match.winner,
    actualRedScore: match.redScore,
    actualBlueScore: match.blueScore,
    // D-02 (Phase 6): never coerced null -> 0 — see TeamSeasonMatchSchema's
    // actualRedRp/actualBlueRp doc comment for the full null contract.
    actualRedRp: match.redRpEarned,
    actualBlueRp: match.blueRpEarned,
  };
}
```

**The same call already exists inside Sigma1, discarded.** `packages/core/algorithms/sigma1/index.ts`
lines 872–877 (read this session) already computes exactly the values F-06-1's actual flags need,
but only as an intermediate used to fold RP state — never returned:
```typescript
// Source: packages/core/algorithms/sigma1/index.ts:872-877
if (usedFallback || !isRpEligibleEventType(result.eventType)) {
  rpSkippedMatchCount += 1;
} else {
  const rawJson: unknown = JSON.parse(result.scoreBreakdownRaw!);
  const redRpParsed: RpParsedResult = ruleModule.parse(rawJson, "red", result.eventType);
  const blueRpParsed: RpParsedResult = ruleModule.parse(rawJson, "blue", result.eventType);
```
`redRpParsed.bonusFlags`/`blueRpParsed.bonusFlags` (the exact per-bonus booleans F-06-1 needs) are
computed right here and never surface. **Recommendation: do not thread this out of Sigma1's
`update()`.** Compute it independently at publish time (mirrors `actualRedRp`'s own precedent) so
OPR/EPA team pages also get real actual-bonus data, not just Sigma1's.

### Pattern 2: Widen an already-in-scope Monte Carlo loop rather than adding a second pass

**What:** `rp/distribution.ts`'s `rpPmfForMatch` already calls
`ruleModule.predictThresholds(redValues, eventType)`/`(blueValues, eventType)` inside its per-draw
loop (lines 371–372, read this session) and immediately discards everything except the outcome-RP
bucket:
```typescript
// Source: packages/core/algorithms/sigma1/rp/distribution.ts:371-386 (read this session)
const redPrediction = ruleModule.predictThresholds(redValues, eventType);
const bluePrediction = ruleModule.predictThresholds(blueValues, eventType);
...
const redTotalRp = Math.min(ruleModule.maxRp, redOutcomeRp + redPrediction.totalRp);
const blueTotalRp = Math.min(ruleModule.maxRp, blueOutcomeRp + bluePrediction.totalRp);
redBuckets[redTotalRp]! += 1;
blueBuckets[blueTotalRp]! += 1;
```
`redPrediction.bonusFlags`/`bluePrediction.bonusFlags` (a `Record<string, boolean>` keyed by
`ruleModule.bonusNames`) are available on every iteration of this already-running loop. Tallying
them costs one increment per bonus per draw — no new draws, no new RNG consumption, no change to
`redScore`/`blueScore`/`pRedWin` (computed earlier in `predict()`, untouched by this addition).

**When to use:** exactly this case — a value already computed inside an existing deterministic
loop, needed in aggregate.

**Recommended shape for `RpPmfResult`:**
```typescript
export interface RpPmfResult {
  readonly redPmf: readonly number[];
  readonly bluePmf: readonly number[];
  /** NEW (F-06-1): bonus name -> P(bonus achieved), tallied from the SAME draws that produced redPmf. Keyed by ruleModule.bonusNames, so a caller iterating BONUS_RP_BY_SEASON's key order finds every entry. Omitted entirely (mirrors redPmf/bluePmf's own convention) when params.rpMonteCarloDraws === 0 or compLevel !== "qm". */
  readonly redBonusProbabilities?: Readonly<Record<string, number>>;
  readonly blueBonusProbabilities?: Readonly<Record<string, number>>;
}
```

### Pattern 3: The percentile pass and the metric-history pass already coexist in one loop iteration

**What (F-06-3 implementation site):** `packages/harness/publish.ts`'s `for (const algorithm of
options.algorithms)` loop (starting line 1044, read this session) computes `metricsByTeam` (line
1047) and `metricsByTeamWithPercentiles = withPercentiles(metricsByTeam, teamsThisSeason)` (line
1056) — the season-final value pool and its percentile ranking — in the SAME iteration where
`metricHistoryForAlgo = metricHistoryByAlgoTeam.get(algorithm.id)!` (line 1059) is read and later
assigned onto `metricHistory: metricHistoryForAlgo.get(teamKey) ?? []` (line 1229) when building
each team's artifact. **Nothing needs to be threaded across a function boundary — both values are
simultaneously in scope.**

`packages/harness/percentiles.ts`'s existing `percentileRanks(values)` (lines 59–83) computes
percentiles for members of the *same* array it is given — it cannot rank an **external** value
(a mid-season history-row value) against that array, because it does not expose the sorted array
itself, only the resulting per-member percentiles. **A new function is needed**: given a metric's
season-final values (sorted once), compute the mid-rank percentile of an arbitrary query value
(the exact D-06.1-A operation — "where does this earlier value fall in the season-final
distribution"), via binary search (the sorted array already supports O(log n) insertion-point
lookup):

```typescript
// Recommended addition to packages/harness/percentiles.ts, alongside percentileRanks.
// Given `sortedValues` (ascending, the same season-final pool percentileRanks/withPercentiles
// already build), returns the mid-rank percentile of an ARBITRARY value against that pool —
// the D-06.1-A operation: "where did this team's value at match N fall against the SEASON-FINAL
// field", not "rank this value among its own peers."
export function percentileAgainstSortedPool(sortedValues: readonly number[], value: number): number {
  const n = sortedValues.length;
  if (n === 0) return 0; // no pool to rank against — caller must not call this with an empty pool
  // countStrictlyBelow: binary search for the first index >= value (lower bound)
  let lo = 0, hi = n;
  while (lo < hi) {
    const mid = (lo + hi) >>> 1;
    if (sortedValues[mid]! < value) lo = mid + 1; else hi = mid;
  }
  const countStrictlyBelow = lo;
  // countEqual: how many entries exactly equal value, starting from countStrictlyBelow
  let hi2 = countStrictlyBelow;
  while (hi2 < n && sortedValues[hi2] === value) hi2++;
  const countEqual = hi2 - countStrictlyBelow;
  return roundTo(((countStrictlyBelow + 0.5 * countEqual) / n) * 100, ROUNDING_RULE.percentile);
}
```

This reuses `percentileRanks`'s exact mid-rank formula (`(countStrictlyBelow + 0.5*countEqual)/n *
100`) so a history row's LAST value (the end-of-season row) computes to the *same* percentile
`withPercentiles` already publishes on `seasonStats.metrics` for that team/metric — a testable
invariant the planner should assert (last `metricHistory` row's percentile === `seasonStats
.metrics[name].percentile`, when both are defined).

**Build the sorted pool once per `(algorithm, season, metricName)`,** not once per history row —
the pool is exactly what `withPercentiles` already iterates (`teamsThisSeason` × `metricsByTeam`),
so a `Map<string, number[]>` (metric name -> sorted season-final values) built once per algorithm
right where `metricsByTeamWithPercentiles` is already computed, then reused for every team's every
history row, is the cheap shape (O(teams log teams) once, not per history row).

### Anti-Patterns to Avoid

- **Re-querying "the pool at that match index" despite D-06.1-A rejecting it.** 06-UAT.md's own
  text already names this the expensive alternative ("needs every team's state at every index").
  D-06.1-A is locked; do not plan for it.
- **Threading Sigma1-internal RP state out to make actual-bonus-flags work.** Would make the
  feature algorithm-specific for no reason — see Pattern 1.
- **A second Monte Carlo pass for per-bonus data.** See Pattern 2 — the existing draws already
  carry this information.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Binary search for percentile-against-pool | A custom linear scan per history row | The `percentileAgainstSortedPool` sketch above (O(log n) per lookup) | At ~3,700 teams/season and up to 292 history rows/team, a linear scan per row is O(n) per row vs O(log n); cheap either way at this scale, but the binary-search form is the natural generalization of `percentileRanks`'s own sorted-array approach already in the codebase |
| SQLite migration tooling for `event_rankings` | A migration framework, a versioned schema table | `schema.sql`'s existing `CREATE TABLE IF NOT EXISTS` idempotent-apply pattern | The corpus already has zero migration tooling by design (`db.ts`'s `openCorpus` header note); `team_media` proved a brand-new table needs nothing beyond this |
| TBA rankings HTTP client | A bespoke fetch wrapper for this one endpoint | `tbaClient.ts`'s existing `tbaFetch`/`TbaClientContext`/ETag pattern, extended with one new exported function (`fetchEventRankings`) | Exactly the pattern `fetchTeamMedia` already establishes for Phase 6's media endpoint |

**Key insight:** every piece of this phase is additive within an existing, already-proven pattern
(new table via the existing idempotent schema-apply, new TBA capability via the existing client
shape, new derived field via the existing publish-time percentile/rounding machinery). Nothing here
justifies a new abstraction.

## Common Pitfalls

### Pitfall 1: Assuming per-bonus predicted probabilities change the D-15 digest

**What goes wrong:** A planner might assume any change touching `Prediction`/`RpPmfResult` requires
a new promoted algorithm version (following 03.1-CONTEXT D-13's "a committed digest is never
hand-edited; if a change alters a prediction stream the result is a new promoted version" rule).

**Why it happens:** The RP pmf and the per-bonus data share the same Monte Carlo loop, so it looks
plausible the change is "in the prediction stream."

**How to avoid:** Read `packages/harness/promote.ts`'s `computePredictionStreamDigest` (lines
97–103, read this session) — it hashes `[matchKey, pRedWin, redScore, blueScore]` only. Neither
`redRpPmf` nor any per-bonus field is part of the digest today, and this phase's addition does not
change any of the four hashed fields (the score/win-probability computation in `predict()` runs
*before* the RP Monte Carlo step and is untouched). Verify this with a direct read of
`promote.ts` before planning a version bump — do not assume from the file's proximity to the pmf
code.

**Warning signs:** if a future addition DOES touch `pRedWin`/`redScore`/`blueScore`, THAT change
needs a new version; the per-bonus counters proposed here do not.

### Pitfall 2: Coercing a `null` rankings response body to an empty structure silently

**What goes wrong:** TBA's `/event/{key}/rankings` can return HTTP 200 with a **`null` body**
(confirmed live this session against `2026scsc`, a real event key with no ranking structure set up
at all) — not just an empty `rankings: []` array (confirmed live against `2026azscor`, a scheduled
event whose quals had not yet run). A Zod schema that assumes the top-level object always exists
(`z.object({...})` without `.nullable()`) throws on the `null`-body case; a schema that silently
defaults to an empty structure on parse failure hides the distinction between "TBA has this event
but no rankings yet" (rankings will appear later) and "checked, genuinely nothing" the same way
`team_media`'s `imageUrl: null` deliberately records "checked, none found" rather than leaving the
row absent.

**Why it happens:** Every other TBA endpoint this project ingests (events, matches, team detail)
always returns a real JSON object or array — this is the first endpoint observed to return a bare
`null` body with HTTP 200.

**How to avoid:** model the top-level response as `tbaEventRankingsResponseSchema =
z.object({...}).nullable()`, and treat `null` the same way `team_media` treats "no eligible photo"
— store a real row recording "checked, nothing there yet" (or skip the upsert and rely on absence,
whichever the planner picks, but pick deliberately and document which).

**Warning signs:** a `.rankings.length` TypeError at ingest time against a real not-yet-active
event is the symptom of skipping this.

### Pitfall 3: Treating `sort_order_info` names as stable across seasons for any purpose this phase needs

**What goes wrong:** `sort_order_info`'s field names genuinely differ by season — confirmed live
this session: 2022 (`Ranking Score, Avg Match, Avg Hangar, Avg Taxi + Auto Cargo`), 2024 adds a
5th (`Avg Coop`), 2026 uses different names again (`Avg Auto Fuel, Avg Tower`). A planner tempted to
surface a named sort-order column (e.g., a future "Ranking Score" display) must not hardcode a
season-specific name or assume a fixed array length.

**Why it happens:** looks like season-specific game-manual vocabulary the same way RP bonus names
already are (`bonusRp.ts`'s `BONUS_RP_BY_SEASON`), so it's tempting to build a similar per-season
table.

**How to avoid:** **this phase's own success criterion 2 ("Rank N of M") does not need any named
sort-order column at all** — `rank` and `rankings.length` are sufficient and season-stable in
shape (always present, always integers). Do not build a `sort_order_info` name table unless a
future phase actually asks to display a named ranking metric.

**Warning signs:** none for this phase specifically — this is a scope-creep trap to flag, not a
bug to hit.

### Pitfall 4: Assuming a corpus schema change needs a migration guard like `winner_imputed`'s

**What goes wrong:** `packages/corpus/db.ts`'s `openCorpus` (read this session, lines 163–169)
throws a loud, explicit error if an existing corpus predates the `winner_imputed` column — a
rebuild guard for a column ADDED TO AN EXISTING TABLE with data already in it. A planner unfamiliar
with the corpus's two different precedents might over-engineer a similar guard for
`event_rankings`.

**Why it happens:** `winner_imputed`'s guard is the more memorable/visible precedent in the
codebase (it throws with a long explanatory message).

**How to avoid:** `event_rankings` is a **brand-new table**, not a new column on an existing table
with rows already in it — this matches `team_media`'s precedent (schema.sql comment: "Additive
CREATE TABLE IF NOT EXISTS, matching the EVNT-01 columns' precedent, not `winner_imputed`'s rebuild
guard: an existing corpus gains this table on its next `openCorpus` with no rebuild"). No guard is
needed; a plain `CREATE TABLE IF NOT EXISTS` is sufficient and consistent with the established
pattern.

**Warning signs:** if the plan proposes throwing an error for a corpus predating `event_rankings`,
that is over-engineering relative to the established precedent.

### Pitfall 5: Fetching rankings per-team instead of per-event

**What goes wrong:** Phase 6's media endpoint is genuinely per-(team, year) — 17,231 requests
across 2022–2026 (COVERAGE.md, measured). A planner pattern-matching that precedent might assume
rankings also needs a per-team loop. It does not: `/event/{key}/rankings` returns every team's
standing for that event in ONE response.

**Why it happens:** superficial similarity to the media-endpoint ingest shape (`cli.ts`'s
`--media-only` mode iterates team keys).

**How to avoid:** iterate **event keys**, not team keys — one TBA request per event, ~1,581 total
across 2022–2026 (measured from the live corpus this session: 288/309/324/350/310 events per season
2022–2026), an order of magnitude cheaper than the media endpoint. This should follow
`ingestSeasonEventsOnly`'s iteration shape (loop over the corpus's own `events` table for the
season), not `ingestSeasonMediaOnly`'s (loop over `selectTeamKeysForYear`).

export function computePredictionStreamDigest(records: readonly PredictionRecord[]): string {
  const lines = records.map((r) =>
    JSON.stringify([r.match.matchKey, r.prediction.pRedWin, r.prediction.redScore, r.prediction.blueScore])

## Open Questions

1. **Should offseason events be included in the `event_rankings` ingest scope?**
   - What we know: TBA computed and returned real rankings for a live offseason event this
     session (`2026wvrox`, 30 teams). The corpus's `is_offseason` flag already exists and other
     ingest passes (`ingestSeasonMediaOnly`, RP folding) selectively exclude offseason data for
     specific, stated reasons (self-reported `score_breakdown` schema risk).
   - What's unclear: whether TBA's ranking computation for an offseason event carries the same
     "self-reported, not guaranteed to match schema" risk profile RP folding excludes, or whether
     it's computed identically to an in-season event's rankings (this session's one sample
     suggests the latter, but one sample is not a verification).
   - Recommendation: default to INTEGRATE (include offseason events) since the request-count cost
     difference is negligible (1,581 vs 1,028 events) and the team page already shows the team's
     event section for offseason events it attended (TEAM-04's "attended... event" is not scoped
     to in-season only) — but record this as a COVERAGE.md-style capability decision during
     planning, not an assumption.

2. **Where exactly should the actual-bonus-flags computation live to avoid 3x redundant `parse()`
   calls (once per algorithm × per match)?**
   - What we know: `ruleModule.parse()` is pure and deterministic given the same raw JSON; calling
     it 3 times (once per algorithm's `buildTeamSeasonArtifact` pass) for the same match produces
     identical results, just wasted CPU.
   - What's unclear: whether the wasted CPU is worth avoiding given the harness already re-walks
     the full `stream` once per algorithm for prediction purposes (this may already be
     dwarfed by that cost).
   - Recommendation: compute a `Map<matchKey, {redBonusFlags, blueBonusFlags} | null>` once, outside
     the per-algorithm loop (alongside `stream`'s own construction), and pass it into
     `buildTeamSeasonArtifact` as a new param mirroring `sortTimeByMatchKey`'s existing shape. This
     is a performance/clarity choice, not a correctness one — the planner can defer this to actual
     measurement if publish wall-clock time doesn't move.
