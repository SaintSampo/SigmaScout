## Summary

This phase wires three genuinely new data surfaces end to end — TBA event standings
(`event_rankings`), predicted/actual per-bonus RP marginals, and season-final history-row
percentiles — from ingest through the corpus, the publish boundary, and into the team-page UI.
I read every file in scope directly (not just the SUMMARY narration) and traced the specific
classes of defect this project cares about most: silent data fabrication, falsy-zero coercion on
legitimate zero values, vacuous corpus-gated tests, secret exposure in the TBA client/CLI, and
rounding calls reaching integral rank/totalTeams fields.

**None of those five defect classes are present.** Specifically:

- Every optional-field presence check in the reviewed code (`event.rank`, `event.totalTeams`,
  `tile.metric.percentile`, `probability`, `metric.percentile`, `flags`) uses `=== undefined` /
  `!== undefined` / `=== null`, never `!value`, `value ||`, or `?? <nonzero-implying default>`.
  A percentile of `0`, a bonus probability of `0`, and a `rank`/`totalTeams` boundary value all
  render correctly as real data rather than being coerced to "absent."
- No fabricated standing: `EventSection.tsx`'s "Rank N of M" line renders only when **both**
  `rank` and `totalTeams` are defined (`event.rank !== undefined && event.totalTeams !== undefined`),
  matching the phase's explicit prohibition. `publish.ts` uses conditional-spread
  (`...(e.rank !== undefined ? { rank: e.rank } : {})`), verified by the `not.toHaveProperty`
  tests in `pageArtifacts.test.ts`/`publish.test.ts`, so an absent ranking is genuinely absent
  from the parsed artifact, not present-with-`undefined`.
- The two corpus-gated tests I read in full (`eventRank.tracer.test.ts`,
  `publish.test.ts`'s `withHistoryPercentiles — real-corpus season-final agreement invariant`)
  both skip with an explicit, named message identifying the missing path — never a silent pass —
  and the non-skip path asserts a non-vacuity floor (`>= 50 teams`, `>= 250 events`) rather than
  merely "did not throw."
- `packages/ingest/tbaClient.ts` never logs, echoes, or returns the API key: `apiKey` flows only
  into the `X-TBA-Auth-Key` request header; every `console.log` call site in `cli.ts` prints only
  URLs, counts, and status codes. `docs/publish-budget.md` and every SUMMARY confirm no secret
  value appears in any command or file this phase produced.
- `rank`/`totalTeams` never pass through `roundTo`/`ROUNDING_RULE` anywhere in `publish.ts`,
  `db.ts`, or the ingest layer — they are copied verbatim from `event_rankings` through to the
  published artifact, and the publish-side schema enforces `z.number().int().positive()`.

The Monte Carlo per-bonus tally (`rpPmfForMatch` in `distribution.ts`) correctly reuses the
existing per-draw loop with no second RNG stream, matching the SUMMARY's claim exactly; the
short-circuit branches (non-`qm` compLevel, zero draws, RP-ineligible event type) all omit the
new `redBonusProbabilities`/`blueBonusProbabilities`/`redBonusRp`/`blueBonusRp` fields entirely
rather than publishing a fabricated all-zero array. `withHistoryPercentiles`/`sortedPoolsByMetric`
are correctly scoped once per `(algorithm, season)` inside the per-algorithm loop, built from
that algorithm's own `metricsByTeam` — no cross-algorithm state leakage.

The one **Warning** and two **Info** items below are real but narrow — none block shipping this
phase, and none touches the five priority defect classes above.

## Warnings

### WR-01: `tbaEventRankingSchema.rank` is not integer-constrained, unlike every other integer boundary this field crosses

**File:** `packages/ingest/schemas.ts:120-121`
**Issue:** `tbaEventRankingSchema` declares `rank: z.number()` (no `.int()`), while the value's
every other boundary in this codebase treats it as strictly integral: the corpus column
(`packages/corpus/schema.sql:104`, `rank INTEGER NOT NULL`) and the published artifact schema
(`packages/harness/pageArtifacts.ts:551`, `rank: z.number().int().positive().optional()`). If TBA
ever returned a non-integer `rank` (a live-data drift this schema's own header comment says should
"throw per this file's header policy, never a silently coerced default"), this schema would accept
it silently at the ingest boundary. `normalizeEventRankings` would pass it through unchanged, and
`upsertEventRanking` would write it into a SQLite column with `INTEGER` affinity — SQLite does not
coerce a non-integral `REAL` value into that affinity, so it would be stored as-is. The defect
would only surface much later, at publish time, when `TeamSeasonEventSchema.rank`'s `.int()`
refinement throws — failing loudly, but at the wrong boundary, and only for whichever team/season
artifact happens to include that event, rather than at the ingest run that actually saw the
drifted value.
**Failure scenario:** A future TBA response shape change (or a malformed proxy/cache response)
returns `rank: 3.5` for one event. `pnpm ingest:rankings` completes with exit 0, silently persists
the fractional rank, and the defect is only discovered when a later, unrelated `pnpm publish:seasons`
run throws deep inside `buildTeamSeasonArtifact` for that event's team artifacts — far from the
ingest run that actually observed the drift, and after the corpus already holds the bad value.
**Fix:**
```ts
export const tbaEventRankingSchema = z.object({
  rank: z.number().int(),
  team_key: z.string(),
  // ...
});
```

### IN-02: `EventSection.test.tsx` has no test asserting a metric tile at exactly percentile 0 renders the (correctly) untiered/Common state

**File:** `apps/web/src/components/team/EventSection.test.tsx`
**Issue:** `packages/harness/percentiles.test.ts` explicitly tests `percentile: 0` and
`percentile: 100` as legitimate boundary values (`"accepts a percentile of exactly 0 and of
exactly 100"`), and `tierForPercentile`'s own implementation (`apps/web/src/lib/tiers.ts:58-62`)
correctly treats `0` as defined data (`percentile === undefined` is the only early return, so `0`
falls through to `publishedTierForPercentile(0) ?? "common"`). This is provably not a bug — the
guard is correct. However, `EventSection.test.tsx`'s own per-event-tier `describe` block
(`"per-event metric tiers and basis caption"`) tests percentiles of 20, 80, and 97, but never 0
specifically, so there is no test in this file that would catch a future regression where someone
changes `EventSection.tsx`'s tile-rendering logic to use `tile.metric.percentile ?? undefined` (a
falsy-looking but actually-safe pattern) or accidentally introduces a `!tile.metric.percentile`
check that would misrender a real 0th-percentile tile as untiered in a way that's indistinguishable
from "no percentile published at all."
**Fix:** Add one case to `EventSection.test.tsx`'s tier `describe` block asserting that a metric
history row with `percentile: 0` still renders a (Common, unboxed) `MetricValue` with the value
text present — mirroring the boundary discipline `percentiles.test.ts` already applies one layer
down.
