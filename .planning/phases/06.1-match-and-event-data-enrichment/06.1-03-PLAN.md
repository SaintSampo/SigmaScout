<objective>
Add the two pure functions F-06-3 needs and widen the history-row metric schema to carry a
percentile — leaving the publish-time wiring to plan 06.1-05.

Purpose: `packages/harness/percentiles.ts`'s existing `percentileRanks(values)` computes percentiles
for members of the array it is given. It cannot rank an **external** value — a mid-season history-row
value — against that array, because it never exposes the sorted array, only the resulting per-member
percentiles. D-06.1-A's operation ("where did this team's value at match N fall against the
SEASON-FINAL field") needs exactly that: a sorted pool built once, queried many times.

Output: `percentileAgainstSortedPool`, `sortedPoolsByMetric`, `HISTORY_PERCENTILE_METRIC_KEYS`, and
an optional bounded `percentile` on `MetricValueSchema` — all leaf-level, all pure, none of them
touching `publish.ts`.
</objective>

<planner_decisions>
- **PD-06 — The history-row percentile is published only for the metric names the per-event line
  actually renders, single-sourced from core.** `HISTORY_PERCENTILE_METRIC_KEYS` is the three
  values of `COMPONENT_GROUP_METRIC_KEYS` plus `TOTAL_METRIC_KEY`, imported from
  `packages/core/algorithms/breakdown/index.js` and `packages/core/algorithms/types.js` — never
  re-declared as literals, and never derived from anything in `apps/web`, so the pipeline learns
  nothing about the UI.

  **Why not every metric — the measurement.** `docs/publish-budget.md` records the budget-critical
  artifact as `v1/team/frc118/2024/sigma1@2.0.0+tuned-2026-08.json` at 304,862 bytes under a
  375,000-byte ceiling: **70,138 bytes of headroom**. That team-season carries 292 matches, so 292
  `metricHistory` rows. A sigma1 2024 row's `metrics` record holds 17 names (13 season components,
  `total`, and the three phase groups). A published percentile key costs roughly 18 bytes. All 17
  names on all 292 rows is roughly **89,000 bytes — more than the entire remaining headroom, before
  this phase's per-bonus fields spend any of it**. The four-name set costs roughly **21,000 bytes**,
  which fits alongside them.

  This is the same trade `publish.ts` already documents for the teams artifact, where publishing
  `percentile` measured +42% gzipped against `tier`'s +10% and the cheap representation won because
  page-load speed is the project's top stated UX priority. **Reversibility: costly** — widening the
  set later needs another full republish, but nothing breaks and no migration is needed. Plan
  06.1-07 Task 1 re-measures this projection against the real corpus before the republish is spent,
  and carries a pre-approved mitigation ladder if the projection lands over.
- **PD-07 — `sortedPoolsByMetric` omits a metric name entirely rather than mapping it to an empty
  array.** An empty pool has no defensible percentile, and a caller that has to distinguish "empty
  array" from "absent" is one refactor away from treating an empty pool as rank zero. Absence is
  the honest representation, matching `withPercentiles`'s own "a team with no value for a metric
  receives no percentile key at all — never a coerced zero" rule. **Reversibility: reversible.**
</planner_decisions>

`percentileAgainstSortedPool(sortedValues: readonly number[], value: number): number` — given an
ascending pool, returns the mid-rank percentile of an arbitrary query value against it, via a lower-
bound binary search for the count strictly below plus a forward scan for the count of exact equals,

rounding call verbatim rather than re-deriving them is what makes the last-history-row equals
season-final invariant hold exactly rather than approximately. Throw a named error class for an
empty pool rather than returning zero — an empty pool has no defensible percentile, and a zero here
would read downstream as bottom-of-field. The doc comment must state D-06.1-A's semantics in words:
this ranks a value from an earlier point in the season against the SEASON-FINAL distribution, which
reads as "where this team stood at that point, against the final field", and is deliberately not
"the field as of that match index".

`sortedPoolsByMetric(metricsByTeam: TeamMetrics, teamKeys: readonly string[]): Map<string, number[]>`
