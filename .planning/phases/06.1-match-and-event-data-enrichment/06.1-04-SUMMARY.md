### Documented (not auto-fixed) discrepancy

**1. Task 2's stated acceptance criterion ("at least 250 distinct events per season") does not literally hold for three of five seasons**

- **Found during:** Task 2, verifying the live ingest run's corpus state with the required read-only queries.
- **What was expected:** the plan's own Task 2 acceptance criteria stated "A read-only corpus query confirms every season 2022 through 2026 has at least 250 distinct events with rows in `event_rankings`."
- **What was measured:** 2022: 236 events; 2023: 249 events; 2024: 280 events; 2025: 311 events; 2026: 246 events. Three of five seasons (2022, 2023, 2026) fall short of 250.
- **Why:** this is not a bug, a partial run, or a code defect — it is accounted for entirely by real TBA responses correctly handled and correctly tallied: 2022 had 52 events return an empty `rankings: []` array (scheduled/not-fully-run) with 0 null-body; 2023 had 58 empty + 2 null; 2026 had 24 empty + 40 null, the latter concentrated in 2026's still-ongoing offseason (today's date, 2026-08-26, is mid-fall-offseason for the 2026 game per `PROJECT.md`, so a meaningful share of 2026's offseason events genuinely have not been played yet). The ingest correctly stored zero rows for each of these (per PD-02, a row is only ever written for a real populated TBA response), so a lower-than-250 count is the honest, correct outcome of the real data, not a shortfall to fix.
- **Why not fixed:** there is nothing to fix — fabricating additional rows to hit an arbitrary threshold would violate the exact repudiation-resistance discipline (T-06.1-16) this plan itself requires: "verify the corpus with a fresh read-only query rather than trusting the run's own tally." The plan's actual `must_haves.truths` — rows exist for every season, and every stored row satisfies `rank >= 1 AND total_teams >= 1` — both hold exactly as measured, with zero invariant violations across all 47,695 rows.
- **Files modified:** none (documentation-only; recorded in `COVERAGE.md`'s "Acceptance-threshold note" and here).
- **Verification:** `SELECT e.year, COUNT(DISTINCT er.event_key) FROM event_rankings er JOIN events e ON e.event_key = er.event_key GROUP BY e.year` — read-only, run against the live corpus post-ingest.
- **Committed in:** `097f9756` (Task 2 commit).
