<planner_decisions>
- **PD-04 (restated, decided in plan 06.1-02) — per-bonus data is a positional array aligned to the
  season's bonus-name order, not a keyed record.** The schema in Task 1 follows that shape. Measured
  reason: on the budget-critical artifact the record form costs roughly 238 bytes per match row
  against the array form's roughly 124, a difference of about 33,000 bytes against 70,138 bytes of
  total headroom. **Reversibility: costly.**
- **PD-09 — Actual per-bonus flags are computed once per season, outside the per-algorithm loop, and
  threaded in as a parameter.** RESEARCH.md's Open Question 2 left the placement to measurement.
  Deciding it now rather than deferring: the flags are algorithm-independent by definition (they
  describe the match, not a prediction), so computing them inside the loop would run
  `ruleModule.parse` three times per match for an identical result, and computing them inside an
  `AlgorithmModule` would make real bonus data appear only on Sigma1 pages — contradicting the
  precedent `actualRedRp` already set by being sourced from the ingest-level match record.
  **Reversibility: reversible** — it is an internal placement, invisible in the published output.
- **PD-10 — Absence and null are different published states and both are kept.** A key absent
  entirely means "this artifact predates the field, or the season has no registered bonus
  vocabulary"; an explicit null means "this project looked and the data is not derivable". Neither
  is ever an empty array and neither is ever an all-false array. This mirrors `actualRedRp`'s
  existing null contract exactly. **Reversibility: costly** — it is a published-shape decision.
</planner_decisions>
