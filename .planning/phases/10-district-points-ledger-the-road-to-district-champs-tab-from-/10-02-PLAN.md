Three things make this plan load-bearing rather than routine:

1. **The browser prices nothing today, and the design contract says it does.** The sketch 021 README's Feasibility section claims SPR already prices any three-robot alliance against any other in the browser. It does not: the embedded state block that priced upcoming matches client-side was built by quick task 260915-isq and DELETED by 260923-3w6 on 2026-09-23, eight days before the sketch session, because Workers Paid made Worker-side pricing affordable again (memory `project_workers_paid_rearchitecture_decisions`). 10-CONTEXT.md's "Corrections from research" block supersedes the README on exactly this point. `apps/web/src/lib/simulationInputs.ts` and `simulation.worker.ts` consume only precomputed per-scheduled-match pmfs; no code path in the repo takes two arbitrary rosters and returns a win probability. This plan builds that path. Any task phrased as "call the existing alliance pricer" is wrong (10-RESEARCH.md Pitfall 1).

2. **The new formula is a THIRD instance of "which variance am I actually using", and the first two were bugs.** `packages/harness/pageArtifacts.ts`'s own header enumerates three structurally different quantities SPR publishes — a team's rating spread `√(pL + pS)`, an alliance's calibrated own predictive variance, and the Match Band's `rosterSize × Σ Sigma²` — and states that `pRedWin` is computed from none of them but from the raw uncalibrated figure. `Prediction.variance`'s own doc comment goes further: reconstructing a win probability from that published field would DISAGREE with `pRedWin`. So no control arm can reproduce the published number from published fields, which is precisely why the substitution has to be measured end to end instead of reasoned about. `uncertainty-display.md` records this class of mistake landing twice on this project already.

3. **The award table's leak boundary has two halves and the obvious test only covers one.** The bucket feature must not see the scored season's awards, and the rates themselves must not either. `scripts/measureAwardPredictability.test.ts` pins the first half twice (once on the feature builder, once end to end) because this project's failure log is a log of measurements that looked like answers. The second half — fitting season Y's table on seasons before Y — is the larger surface here, since the table is the thing 10-04 and 10-06 ship.

Purpose (SC-2, SC-6): SC-2 requires every blue cell to come from one joint per-run simulation whose bracket is priced by SPR; without a measured pricer that requirement has no floor. SC-6 requires the selection model's pick-order agreement and the award base-rate tables to be measured walk-forward, pinned by tests, and stated on the methodology page in its voice.
