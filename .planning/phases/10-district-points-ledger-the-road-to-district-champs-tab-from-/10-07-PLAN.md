<committed_facts_verified_during_planning>
Measured while writing this plan, against the committed code and the real
`data/fixtures/phase10/district-2026pnw.json`. Two of them correct assumptions a reader of the
sketch README would otherwise make. Reproduce them in the tests named below rather than trusting
this block blindly, but do not spend budget re-discovering them.

**Fact A — `insights.districtLockedCount` counts `locked` ONLY, never `lockedAward`.**
`scripts/publishDistricts.ts` builds it as `districtLocks.filter((r) => r.status === "locked").length`.
On `2026pnw`: `districtLockedCount` 42, `districtEliminatedCount` 76, and the actual verdict census
is `locked` 42, `lockedAward` 8, `eliminated` 76 over 126 teams with `dcmpSlots` 50. The sketch
README's "reproduces the artifact's 50 locked" refers to the CHIP count (42 + 8 = 50 = the slot
count), which is a different number from the artifact field. SC-3's acceptance is on the two
artifact fields, per verdict status.

**Fact B — the shipped district lock uses the team's WHOLE `pointTotal`, with a district-tier-only
`maxRemaining`.** `publishDistricts.ts` pass 1 passes `pointTotal: t.ranking.pointTotal` (which
includes any dcmp-tier points) and `maxRemaining: t.maxRemainingDistrict` (regular-tier remaining
events only). The browser recompute must reproduce those two inputs at the "now" position or SC-3's
count equality cannot hold. That is why the floor at a rewound position is derived by SUBTRACTING
reopened earned points from `team.pointTotal`, never by re-summing categories from scratch:
re-summing would silently drop the rookie bonus, the adjustments and TBA's own arithmetic.

**Fact C — a team's `eventPoints` can carry a dcmp-tier row.** `2026pnw`'s top team has three
entries: `2026wabon` (district, week 0), `2026wasam` (district, week 2) and `2026pncmp` (dcmp, week
5). This tab is the road to the district championship, so it renders district-tier rows only; the
dcmp row belongs to Champ Locks. Combined with 10-04's corpus Fact 3 (0, 1, 2, 3 and 4 event counts
all occur), "two rows per team" is the common case and not the rule.

**Fact D — `simAxis.ts`'s `x()` is slot-centred, which makes the points-axis reuse exact.**
`x(rank, teamCount, plotW) = ((rank - 0.5) / teamCount) * plotW`. A points histogram over `0..m`
has `m + 1` slots, so point value `v` is slot `v + 1` of `m + 1`. Substituting those two
expressions into every `simAxis` function reproduces the slot-centred convention exactly, including
the `[0.5, N + 0.5]` band-edge domain that its own comments prove the clamps never engage inside.
No second geometry module is needed and none may be written.

**Fact E — the existing red status token pair already exists and needs no palette addition.**
`apps/web/src/styles/theme.css` carries `--lock-status-eliminated-bg` / `--lock-status-eliminated-fg`
(rose) and `--lock-status-prequalified-bg` / `--lock-status-prequalified-fg` (purple) and
`--lock-status-locked-bg` / `--lock-status-locked-fg` (green). The Locked out chip reuses the rose
pair; In range and Out of range are outline-only chips built from `--color-text-primary`,
`--color-text-muted` and `--color-border`. So this plan adds NO palette entry, and the dataviz
palette validator therefore has nothing to validate — state that in the SUMMARY rather than running
it against an unchanged palette.

**Fact F — the mock-Worker technique is already shipped and exact.**
`apps/web/src/components/event/SimulationTab.test.tsx` installs the REAL protocol as the double's
script: `const realRunScript: MockWorkerScript = (message, ctx) => runSimulationJob(message, ctx.post);`
then `installMockWorker({ script: realRunScript })`, per test, with `restore()` in a `finally`.
`mockWorker.ts` routes every message through `structuredClone`, so a function smuggled into a
request fails in the suite rather than only in a visitor's browser.
