  <action>
Create `packages/harness/identifiability.ts` as a standalone runnable script following `cli.ts`'s shape: `parseArgs`, `async function main()`, and `main().catch(err => { console.error(...); process.exit(1) })`. Add an `identifiability` script to `package.json` invoking it via `tsx`, matching how `harness` and `ingest` are declared.

What it computes, per season, per component: build the alliance-sum design matrix for that component — one row per rating-eligible alliance observation, a 1 in each participating team's column, the observed component value as the target — exactly the structure `solveRidgeOpr` already regresses. Then run `ml-matrix`'s `SingularValueDecomposition` on it and report the rank, the largest and smallest non-negligible singular values, and the condition number. Do not hand-roll a rank check; `opr.ts`'s own comment gives the reason ("a bespoke Gaussian elimination is exactly the kind of code that looks finished until one team's row makes it diverge") and RESEARCH.md's Don't Hand-Roll table makes it explicit.

At full season scale the design matrix is roughly 36,000 rows by 3,700 columns and a dense SVD on it is not tractable — `opr.ts` measured a dense solve at n=1,500 taking about 21 seconds with cubic scaling. Sample instead: take a fixed, seeded subset of events per season (large enough to include teams that attended multiple events, since cross-event overlap is what makes the system connected at all) and report the sampled scale alongside every number, so a reader can see what was measured rather than assuming a full-season result. State the sampling design in the script's header comment; an identifiability claim whose sample is undisclosed is the kind of undocumented reasoning this project's failure log is about.

Report, additionally, per season per component:
- the fraction of alliance observations where the component is non-zero (a component observed in 3% of matches is not identifiable regardless of what the condition number says)
- the number of distinct teams with at least 5 non-zero observations

Break out the `foulsCommitted` component separately and prominently. D-04 names it the weakest member of the set and the corpus confirms why: the fraction of matches with any foul recorded is 63.2% (2022), 65.1% (2023), 36.5% (2024), 30.3% (2025), 36.9% (2026), and 2026 records fouls under entirely different field names. Report each season's foul figures individually — a pooled number would average away exactly the per-season structure that matters.

Emit a machine-readable JSON result alongside the console output (path via `--identifiability-out`, default `reports/identifiability.json`) so the write-up in Task 2 quotes numbers rather than retyping them.

Define and apply an explicit pass/fail threshold in the script — do not leave it to prose. Choose a condition-number ceiling and a minimum non-zero-observation fraction, justify both in the header comment, and have the script print a per-component verdict. A component that fails is not automatically a defect; it is a finding to record. What is a defect is a script that reports numbers without ever stating what would have counted as a failure.
  </action>

Then write `docs/models/epa-divergences.md`, which D-13 requires: every deliberate divergence from Statbotics, each with what Statbotics does, what this project does instead, and why. At minimum:
- Elimination matches: Statbotics applies a one-third weight and does not increment its match counter; this project learns from elims at full weight and counts them (D-08).
- Fouls: Statbotics multiplies a no-foul predicted score by a season-level foul rate; this project models a per-team `foulsCommitted` component so a predicted total includes the opponent's expected foul contribution (D-04).
- Per-season post-processing: Statbotics applies year-specific transforms including a 2018 switch/scale sigmoid and per-year clamps; this project applies none (D-13).
- Win-probability scale: Statbotics uses a season-level `score_sd`; this project uses an expanding-window standard deviation, because a season-batch constant applied to a week-1 match is outcome leakage (Pitfall EPA-1).
- Variance: Statbotics' `EPARating` carries a mean only and its docstring states it does not handle covariance between variables; Sigma1 carries variance on every component, which is the entire thesis of the algorithm.
- Component extraction: this project's own per-season maps rather than Statbotics' `all_keys[year]` grouping, with the granularity choices from plan 02-02 listed.
