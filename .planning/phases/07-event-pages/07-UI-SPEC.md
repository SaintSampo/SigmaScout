## Data Dependencies (blocking — read before planning)

This contract is written against the **post-D-18 published schema**, not the schema on disk today (verified by direct read, 2026-08-27). `packages/harness/pageArtifacts.ts`'s `EventArtifactSchema`/`EventMatchSchema`/`EventUpcomingMatchSchema`/`EventTeamSchema` do **not yet** carry:

1. **Event identity** (D-18 item 8) — no `name`/`startDate`/`location`/`week` on `EventArtifactSchema`. The page header has nothing to render from its own fetch until this lands (or the planner chooses the events-list-artifact fallback named in Claude's Discretion below).
2. **Official event rank + record + RPs** (D-18 item 6) — no field on `EventTeamSchema` carries TBA's `rank`, `record` `{wins, losses, ties}`, or the RP entry from `sort_orders`. Blocks the entire Insights tab (EVNT-02).
3. **Per-alliance own predicted-score variance on played AND upcoming event matches** (D-18 item 3) — `EventMatchSchema` has no `redScoreVarianceOwn`/`blueScoreVarianceOwn` equivalent (unlike `TeamSeasonMatchSchema`, which got this in Phase 6 D-01). Every Quals/Elims band in this contract is drawn from this field; it does not exist yet.
4. **`TeamMetric.spread` redefinition** (D-01/D-02) — today `spread` is D-09 consistency; this contract's Insights/Breakdown tier-boxed cells and Alliances combined-value math both assume the redefined `√(P+R)` value. No component change is needed for this — `MetricValue` already renders whatever `spread` contains — but the pipeline change is a hard prerequisite for this contract's numbers to be honest.
5. **As-of-event metric snapshots** (D-10) — `EventTeamSchema.metrics` today (once item 2 lands) would be season-final values; D-10 requires the walk-forward state AS IT STOOD when that event ended. This is a `publish.ts` structural change (`buildEventTeamsStanding` currently runs once per algorithm per season), not a field addition.
6. **Alliance data** (D-18 item 7) — nothing exists: no corpus table, no `EventArtifactSchema` field, no ingest call to `/event/{key}/alliances`. Blocks the entire Alliances tab (EVNT-05).
7. **Percentile on `EventTeamSchema.metrics`** — needed for tier boxes on Insights/Breakdown; carried by the same `TeamMetricSchema` `percentile`/`tier` fields already used elsewhere, but the AS-OF-EVENT vs SEASON-FINAL split (D-10: value as-of-event, percentile still season-final) means the publisher must NOT simply copy season-final `metrics` wholesale — it needs the as-of-event value paired with the season-final percentile, two different computations merged into one `TeamMetric`.
8. **Playoff bonus-RP array cleanup** (D-18 item 4) — `EventMatchSchema`/`EventUpcomingMatchSchema` are not the direct target of the `06.1-08` gate fix (that landed on `TeamSeasonMatchSchema`), but the same stale-key pattern (`actualRedBonusRp`/`actualBlueBonusRp` present-but-meaningless on playoff rows) must not be reintroduced when this schema gains bonus-RP fields for the Quals tab.

None of this blocks writing the contract below — every display rule is specified against the field names D-18 names or implies, flagged `(exact field name TBD by planner)` where CONTEXT.md did not commit to one. It blocks BUILDING until the publish-side plan wave lands. **The planner must sequence the schema/publisher/ingest/republish work before any tab component that reads these fields — this mirrors Phase 6's own "Data Dependencies" gate exactly.**

| md | 16px | Default element spacing, table cell horizontal padding, event-header stat-row gap |
| lg | 24px | Section padding, page-header-to-tabs vertical rhythm |
| xl | 32px | Layout gaps between major page regions |
| 2xl | 48px | Major section breaks |
| 3xl | 64px | Page-level spacing |

**Exceptions:**

- **44×44px minimum tap target**, inherited — applies to every tab trigger in the 5-tab strip, the algorithm/year dropdowns, and the mobile horizontal-scroll affordance on Insights/Breakdown/Quals/Elims.
- **Chart/match-table geometry constants are locked pixel values, not on the 4px base scale** — carried verbatim from `chart-craft.md`/`uncertainty-display.md`/06-UI-SPEC.md, reused unchanged for Quals and Elims: `BAND_H = 8`, `DOT_H = 12`, `TICK_H = 14`, `PLOT_H = 44`, `Y_RED = 12`/`Y_BLUE = 24`, plot width `PLOT_W = 470`. **Every derived `top` comes from one computed source** (`allianceMarkPositions` in `matchAxis.ts`) — do not hand-tune a second copy for the event-scoped table.
- **Tab strip on mobile is a horizontally scrollable row, not a wrapping grid** (Claude's discretion, resolving CONTEXT.md Open Question 5). Five short single-word labels (`Insights`, `Breakdown`, `Quals`, `Alliances`, `Elims`) at Label 12/600 each comfortably clear 44px width at mobile scale without truncation; wrapping to two rows was rejected because it pushes tab content down inconsistently as tabs are added (Phase 8 adds a sixth, `Simulation`) and a horizontal scroll region is already the established pattern for this app's mobile-width-constrained tables (Phase 5/6 precedent), so the tab strip reuses a gesture the user has already learned rather than introducing a new one. No visible scrollbar; `overflow-x-auto` with `scrollbar-width: none` (already the convention the match-table pinned-column region uses).

## Visual Hierarchy

**Primary focal point — the event name**, Heading 20/600 in the page header. A visitor arriving from the Events list or a deep link should confirm "yes, this is [event name]" before reading anything else. Unlike the team page, there is no Display-scale hero numeral here — the event NAME is the identity anchor, not a number.

**Secondary — the tab strip and its active indicator.** Five tabs represent five genuinely different views of the same event; the active-tab underline (accent) is the only accent-colored element on first paint besides the header link, so it reads clearly as "you are here."

**Tertiary, per tab:**
- Insights: the Rank column (leftmost, pinned) — it is the tab's entire reason for existing (D-07).
- Breakdown: no single focal column — deliberately flat, since VPR rank determines row ORDER but is not itself displayed as a numbered rank (D-11: "carrying no event rank at all").
- Quals/Elims: the shared-axis plot column — the band/tick/dot marks carry the content, matching 06-UI-SPEC.md's "deliberately quiet match table rows" precedent exactly.
- Alliances: the combined-value column, since "which alliance is strongest" is the tab's stated purpose (per the discussion log).

**The accent never marks a focal point** — it marks interactivity/active-state only (the reserved-for list above), same rule as every prior phase.

## Tab-by-Tab Contract

### Page header (all tabs)

Identity block, secondary-surface (`--color-bg-surface`) card, matching the team page's header treatment:

- Event name — Heading 20/600, truncates with ellipsis + `title` for long names (same rule as the Events list)
- Metadata line — Body 14/400 muted: `{startDate formatted} · {location or —} · Week {week, or "Offseason"/"—"}` (location and week both render em-dash when null, same null-handling rule as the Events list's `locationText`/week-badge)
- "View on TBA" — accent-styled external link, `https://www.thebluealliance.com/event/{eventKey}`, `target="_blank" rel="noopener"`, same construction as the team page's TBA link (Claude's discretion, resolving CONTEXT.md's open header-identity question in favor of the established per-entity TBA-link pattern rather than inventing a new element)

### Insights tab (EVNT-02, D-07…D-10)

A table, official-TBA-rank-ordered (or VPR-fallback-ordered per D-08), columns:

| Column | Content | Notes |
|---|---|---|
| Rank | Integer, pinned leading column | From `event_rankings`; VPR Total rank when no official ranking exists (D-08) |
| Team # | Links to `/team/{teamNumber}`, same search-param-threading pattern as `teams-table/columns.tsx` | pinned |
| Nickname | Truncates + `title`, same as every other team-name cell in the app | pinned |
| Record | `W-L-T` string, TBA's authoritative record (D-18 item 6), not counted client-side | |
| RP | Numeric, TBA's `sort_orders` RP entry (D-18 item 6) | tier-boxed like any other metric IF a percentile is ever published for it; otherwise bare (Claude's discretion: RP is a raw competition stat, not a modeled metric, so no percentile is expected — the column renders as a plain `numeric-cell`, not through `MetricValue`) |
| Auto | `MetricValue` for `phaseAuto`, as-of-event value / season-final percentile (D-10) | tier-boxed |
| Teleop | `MetricValue` for `phaseTeleop`, same D-10 split | tier-boxed |
| Endgame | `MetricValue` for `phaseEndgame`, same D-10 split | tier-boxed |

**D-08 fallback notice** (Claude's discretion on placement/wording): a single-line banner directly above the table, secondary-surface background, muted body text, small `Info` lucide icon (muted, `aria-hidden`) — never accent, never destructive:

> "This event has no official TBA ranking. Teams below are ordered by {selected algorithm label}'s rank instead."

Shown ONLY when the event's ranking data is absent (259/1,581 corpus events, per D-08's measurement) — never shown alongside real rank data, never a dismissible toast (it describes the table's current state, not a one-time event).

**Tier key row** (`TierKeyRow`, reused verbatim) renders once above the table, same as the team page.

### Breakdown tab (EVNT-03, D-11)

A table, VPR-rank-ordered (or the selected algorithm's rank — same fallback framing does NOT apply here, since D-11 is inherently "sorted by the selected algorithm's rank" with no official-rank concept at all), columns:

| Column | Content | Notes |
|---|---|---|
| Team # | Links to `/team/{teamNumber}` | pinned |
| Nickname | Truncates + `title` | pinned |
| {one column per `metricKeysFor(algorithmId, season)` key} | `MetricValue`, tier-boxed, including the algorithm's Total | Same key list, same order, as the Teams table and the season-header grid — never a Breakdown-specific list |

**No Rank column exists on this tab at all** — D-11 is explicit ("carrying no event rank at all"). Row order is the only signal of VPR standing; there is no numbered rank cell to read it from.

**Model-estimates caption** (Claude's discretion on exact wording, D-11's binding constraint that the tab "must not imply otherwise"): a single Body 14/400 muted line beneath the tier-key row:

> "Estimated per-team components — TBA publishes score breakdowns per alliance, not per team. These are {selected algorithm label}'s modeled per-team contributions."

**Tier key row** renders once above the table, same as Insights.

### Quals tab (EVNT-04, D-12…D-13)

Generalized `MatchTable` — same column set as the team page's match table (Match / shared-axis plot / Confidence / Predicted Score / Actual / Call), with two differences from the team-page version:

- **No team is bold-highlighted** — the team page bolds "this team's" three numbers per row; an event page has no privileged team, so every team-number cell renders at the same weight (Body 14/400, `numeric-cell`).
- **The shared axis domain is computed over THIS TAB's played-and-scheduled matches only** (D-12) — a fresh domain, not reused from the team page's per-team-per-event domain and not shared with the Elims tab's own domain.

Rows are qualification matches only (`compLevel === "qm"`), **played and upcoming merged client-side into one chronological list** (D-13) — the artifact's `matches[]`/`upcoming[]` stay separate on the wire; the browser interleaves by `sortTime`/`matchNumber`. An upcoming row draws both alliance bands and ticks at full weight with no actual dot, per D-13/06-CONTEXT D-08's shipped treatment, and the scheduled-time string (`Sat 10:32 AM`) in the Actual column with an em-dash Call.

Bonus-RP dots (`BonusRpDots`) render on every quals row, gated `isBonusRpCompLevel(compLevel)` (always true for `qm`).

### Elims tab (EVNT-06, D-14)

Same generalized `MatchTable` anatomy as Quals, with:

- **A flat chronological list, no bracket grouping** (D-14) — every playoff match (`compLevel` in `ef`/`qf`/`sf`/`f`) in one list, ordered by `sortTime`, with the round labelled per row via `matchLabel()`'s existing output (already produces `Semifinal 3-2`, `Final 1-1`, etc. — no new formatting needed).
- **Its own shared axis domain**, independent of the Quals tab's (D-12) — elimination alliances (best three from the draft) typically outscore qualification alliances, so a shared cross-tab axis would misrepresent both.
- **Bonus-RP dots never render** — playoff matches award no bonus RP (measured 0/N across the full corpus, per Phase 06.1's amended SC-1 wording); every dot slot renders `unknown`/greyed via `isBonusRpCompLevel` returning false, matching the team page's existing treatment for these same compLevels.
- Played and upcoming merge client-side, same D-13 rule as Quals.

### Alliances tab (EVNT-05, D-15…D-17)

A table, one row per alliance (1–8, ascending, TBA's own seed order), columns:

| Column | Content | Notes |
|---|---|---|
| Alliance # | `1`–`8` | |
| Captain | Team # + nickname, links to team page | first pick |
| Pick 2 | Team # + nickname, links to team page | |
| Pick 3 | Team # + nickname, links to team page | |
| Backup | Team # + nickname if TBA lists one, else `—` | Displayed, but its metrics NEVER enter the combined column (D-16) — a visual note (Claude's discretion: a small `Label` 12/600 muted `"(backup)"` suffix beside the number, not a separate styled chip — low-frequency enough not to need its own token) |
| Combined Total | `MetricValue` (no tier prop — see Color section) | `σ_alliance = √(σ₁² + σ₂² + σ₃²)` over the first three picks only, per D-15/D-16's exact arithmetic |

**No percentile, no tier box on any Alliances column** — there is no published percentile for a three-team sum (Color section, above).

**Independence-assumption caveat, stated once, visibly, not buried** (D-15's own binding instruction): a Body 14/400 muted caption line beneath the table:

> "Combined values assume each robot's performance is independent of its alliance partners. Real alliances are not fully independent, so the true uncertainty is likely larger than shown."

**When the event has no alliance data (D-17):** the tab trigger itself is `disabled` (plain-greyed, unclickable, no tooltip) — the tab is never entered, so this caveat and the empty table it would show never render at all.

## Copywriting Contract
