## What was measured for this plan, and when

Everything in this section was measured live on 2026-08-27 during planning, against
`data/corpus.sqlite`, the live TBA API and the live published artifacts at `data.sigmascout.org`.
It is recorded here so no task below rests on an assumption, and so a later reader can tell a
measured contract from a defensive one.

**1. The corpus-wide `picks` length histogram — the finding 07-05 routed to this plan, answered.**
All 1,581 corpus events were queried against `/event/{key}/alliances`. The three-state tally closes
exactly: 1,355 populated + 51 empty arrays + 175 null bodies + 0 not-found = 1,581. Across the
10,290 alliance rows those populated events contain:

| `picks` length | rows |
|---|---|
| 2 | 10 |
| 3 | 8,353 |
| 4 | 1,927 |

No row has length 0, 1, or 5 or more. **A sub-three-pick alliance is real**, so D-16's first-three
sum genuinely receives one as input and this plan states its contract rather than assuming it away.
All ten two-pick rows sit at exactly two events — `2022vabrb` and `2024vabrb`, both "Blue Ridge
Brawl", both offseason (`event_type` 99) — and at each of them **every** alliance has exactly two
picks and no `name` key at all. It is an event-level format, not one ragged alliance. Both events
also carry **zero** `event_rankings` rows, so they are simultaneously D-08 fallback events, and
neither publishes an artifact today (both 404 against R2) because they are offseason and reachable
only once 07-09 wires the offseason publish flag.

**2. A pick whose team has no row in the artifact's `teams` array — a second real case, at a
position inside D-16's sum.** Across a 226-event sample covering 4,685 picks, 23 picks (0.49%)
reference a team with no match at that event at all, and a further 76 reference a team that played
only playoff matches. The structural case is the Championship Finals: an Einstein alliance is a
division-winning alliance, so its members qualified at a division event rather than at `cmptx`.
Verified end to end against live data for `2024cmptx`:

- TBA publishes 8 alliances there, all named, all with 4 picks. Alliance 3 ("Daly") is
  `["frc1690","frc4522","frc9432","frc321"]`; alliance 7 ("Milstein") is
  `["frc604","frc9483","frc1058","frc78"]`.
- The live published artifact carries 25 entries in `teams`, and **`frc9432` and `frc1058` are not
  among them** — each sits at `picks[2]`, the third pick, which is INSIDE D-16's three-term sum.

So two of that event's eight alliances cannot produce a complete combined value, and six can. This
is the case Task 2's all-or-nothing rule exists for, and it is live today rather than hypothetical.

**3. The D-17 disabled-trigger rate is roughly double what the research sample suggested.**
07-RESEARCH.md's 40-event probe found 1 null body, 2 empty arrays and 37 populated. Corpus-wide the
same three states are 175, 51 and 1,355 — so **226 of 1,581 events (14.3%)** carry a disabled
Alliances trigger, not the 7.5% the sample implied. D-17's treatment is therefore load-bearing on
about one event page in seven, which is worth knowing before choosing to give it no explanatory copy
at all. The decision stands; the frequency is recorded so it was chosen with the real number visible.

**4. Reproduction.** Every figure above is re-derivable. The TBA calls need the API key and must
follow `.claude/CLAUDE.md`'s secrets convention — load it with `set -a; . ./.env; set +a` and pass
`"$TBA_API_KEY"` unexpanded in the `X-TBA-Auth-Key` header. Never read, print, echo or interpolate
the file or the value.

## Decisions this plan makes (Claude's Discretion, recorded not assumed)

CONTEXT.md's `### Claude's Discretion` covers "the fallback treatment for teams or events with
missing data on any tab" and "the visual treatment of the disabled Alliances tab (D-17)". Decisions
1 through 4 are that discretion applied; decision 5 goes one step beyond a UI-SPEC dismissal and is
flagged as such.

1. **The Combined Total is all-or-nothing over exactly three resolved terms — never a partial sum.**
   This is the contract 07-05's census routed here, and it answers both measured absence cases with
   one rule rather than two branches. The rejected alternative was summing whichever of the first
   three picks resolve and marking the cell somehow. It was rejected because a two-term sum renders
   in the identical shape, column and precision as a three-term one while being roughly a third low,
   and because D-16's own stated purpose — keeping the column comparable across rows — is precisely
   the property a variable-arity sum destroys. A marker would have to be strong enough to stop a
   reader comparing two numbers side by side, which is a stronger signal than an em-dash, not a
   weaker one. The em-dash is also already this application's established answer for "the pipeline
   legitimately has nothing here", so the rule adds no new vocabulary. A sub-three-pick alliance then
   needs no special case at all: it has no third position, so the third position does not resolve.
   — <reversibility rating="reversible">One predicate in one pure function, covered by its own test
   cases for both measured causes.</reversibility>

2. **The value's absence and the spread's absence are two independent rules over the same cell.**
   All three positions must resolve for a value to render at all. Given a value, the ± renders only
   if all three of those resolved metrics publish a `spread`; if any does not, the summed value
   renders bare. The rejected alternative was suppressing the whole cell when a spread is missing,
   which would blank the Combined Total for every OPR-selected event even though the sum of means is
   perfectly well defined there. This mirrors `07-07-PLAN.md`'s PD-04, which established at the
   schema boundary that conflating two kinds of absence is how an artifact silently loses a fact, and
   it needs no new component code — `MetricValue`'s existing no-spread path already renders a bare
   value, exactly as it does for the OPR rows 07-01 measured.
   — <reversibility rating="reversible">A second predicate beside the first, in the same function.</reversibility>

3. **When at least one alliance has no combined value, one muted line beneath the table says so and
   says why.** D-17 gets no explanatory copy because a disabled tab is a whole-tab state the reader
   can see is deliberate. An em-dash sitting in a column of numbers is not: at `2024cmptx` two of
   eight rows would be blank with nothing on the page accounting for them, and at `2024vabrb` all
   five would be. That is the "silently" D-08 explicitly refused on the sister tab, and 07-11 already
   minted the construct for it — a static muted line, no `role`, no dismiss control, an
   `aria-hidden` icon, the sentence carrying the whole meaning. This reuses that construct rather
   than inventing a second one. UI-SPEC's Copywriting Contract has no row for this sentence, so it is
   minted here under the discretion clause and recorded rather than assumed. It is pluralized
   properly, and both forms are tested, because a shipped grammar bug in a line that exists to
   explain missing data reads as carelessness precisely where care is being claimed.
   — <reversibility rating="reversible">One conditional line and one string builder.</reversibility>

4. **The trigger's disabled state is computed only from a genuinely resolved artifact for this event
   key, and a disabled tab id resolves to the default without navigating.** Disabling is itself a
   claim about this event's data, and 07-01's route uses `placeholderData: keepPreviousData`, so
   during a navigation `data` can still be the PREVIOUS event's artifact. Deriving the disabled state
   from it would let one event's alliance array decide another event's trigger. The predicate
   therefore consults the query's placeholder flag as well as the data. Separately, a shared
   `?tab=alliances` link to a disabled event resolves to `DEFAULT_EVENT_TAB` for rendering only —
   extending 07-01's existing `REGISTERED_EVENT_TABS` narrowing rather than adding a second
   mechanism, and without navigating, so the URL stays shareable and adds no history entry. This
   resolution is what makes UI-SPEC's E7 `empty` dismissal true rather than merely asserted.
   — <reversibility rating="reversible">A boolean and one term in an existing resolution expression.</reversibility>

5. **The table gets a horizontal scroll region even though UI-SPEC dismisses E7 `overflow`.**
   Recorded as a deliberate step beyond the contract rather than a silent addition. The dismissal's
   reasoning is "fixed 6-column table, at most 8 rows — no horizontal or vertical density problem",
   which measures density by row count; but four of those six columns each carry a team number AND a
   nickname, which is the widest cell content on any tab in this phase. If that table exceeds a
   390px viewport with no scroll region of its own, the overflow escapes to the page and breaks the
   three-sibling-scroll-regions invariant 07-RESEARCH.md's Open Question 5 established and every
   other tab upholds. Adding the region is strictly additive, costs nothing when the table fits, uses
   the identical class set the sibling tabs use, and cannot make any case worse. It does NOT re-open
   the dismissed row: 07-20 is not asked to add a backstop test for it.
   — <reversibility rating="reversible">One wrapper element and one class string.</reversibility>
