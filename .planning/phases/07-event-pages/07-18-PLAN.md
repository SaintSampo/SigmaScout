## The safety property, stated once so no task has to re-derive it

This plan is the second of three hinges in the phase's rename sequencing (outline assumption 7), and
its correctness argument is entirely about ORDER. Stated plainly:

1. **07-10** published an enriched subset under the pre-rename keys, which the deployed client read
   immediately.
2. **07-16** moved everything that determines what the publisher *writes*, and deliberately nothing
   the browser reads. Two id constants, two true statements.
3. **07-17** wrote every artifact under the new prefix and reseeded D1 under the new id, while the
   old prefix stayed present and stayed what the deployed browser read. Purely additive.
4. **This plan** moves the reader. Both prefixes now exist in R2; the browser switches from one to
   the other. This is the only wave in which anything the client requests changes at all.
5. **07-19** deletes the old objects and the old D1 row, which is safe precisely because step 4
   already happened.

The hazard this ordering exists to avoid is 07-16's `T-07-16-02`, and this plan is where it either
fires or does not. If the new keys and the new manifest entry are NOT live when this commit lands,
`useAlgorithmVersion` finds no entry for the renamed id, every artifact query on every route stays
disabled behind its version gate, and the site renders skeletons everywhere. Because
`.github/workflows/deploy.yml` deploys on every push to `main`, that outage would be live within
minutes of the commit and would persist until someone reverted or republished.

That is why Task 1 carries a **precondition, not an assumption**: two unauthenticated public GETs
against the artifact origin, run before any edit, that establish the new manifest entry and at least
one new object actually exist. It is a read-only check requiring no credential and no `.env`.

**The reverse direction is also load-bearing.** This entire plan is undone by `git revert` — the
deployed site would go back to reading the old prefix, which is still fully populated — *as long as
07-19 has not run*. That is exactly why the deletion is gated separately and scheduled after. The
`<reversibility>` element on each task states this in the same terms.
