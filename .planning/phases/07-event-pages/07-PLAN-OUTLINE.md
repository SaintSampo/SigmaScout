## Notes

### COVERAGE.md ownership

**07-03** owns `.planning/phases/07-event-pages/COVERAGE.md`. It is the plan that adds the never-before-called TBA capability (`/event/{key}/alliances`), so the subtraction record belongs with it. It must enumerate TBA's full event-scoped capability surface (alliances, rankings, awards, district_points, insights, oprs, predictions, matches, teams, simple, keys, …) with `INTEGRATE` as the default and a one-line reason on **every** `OPT-OUT`. A malformed or absent matrix blocks the phase seal at `verify:pre`.

### Plans carrying `checkpoint:decision` for a one-way door

- **07-17** — authorizes the full republish write pass. This is where D-01/D-02's `spread` redefinition and D-04/D-05's algorithm-ID rename stop being git-revertible code and become the published contract browsers read.
- **07-19** — authorizes the destructive half: ~18,222 `sigma1@…` R2 object deletions plus the D1 `algorithm_state` row delete. Recovery from here costs a third full republish.

**Gate-placement decision (deliberate, not an omission):** CONTEXT.md rates D-01/D-02 (07-06) and D-05/D-06 (07-16) as `one-way`, and both plans carry that `<reversibility rating="one-way">` annotation. Neither carries its own `checkpoint:decision`, because at their own commit both are ordinary source edits that `git revert` undoes completely — irreversibility is only realized at the publish/delete moment, which 07-17 and 07-19 each gate. Two gates at the real points of no return beat four gates where three of them re-litigate an already-locked decision.

**07-10 (subset publish) carries no gate** even though it writes to production R2: it overwrites a dozen-odd existing keys in place under the naming the deployed client already reads, adds no new key, deletes nothing, and is idempotent — re-runnable to correctness at any point. It is a refresh, not a door.

### Assumptions made

1. **Tracer tab = Breakdown.** Chosen because it is the only tab whose complete UI-SPEC contract renders from fields `EventArtifactSchema` publishes *today*; every alternative would have required a stub, which a tracer must never contain. Its position is unchanged by the subset-publish decision, for exactly that reason — it needs nothing 07-10 publishes.
2. **New `EventArtifactSchema` fields land optional/nullable (07-07).** This keeps the tracer green through the pipeline waves while pre-subset artifacts are still in R2, and every one of them is independently optional for a real reason anyway (D-08's absent rank, D-17's absent alliances, OPR/EPA rows carrying no variance, null location/week). No `PAGE_ARTIFACT_SCHEMA_VERSION` bump, per D-02.
3. **The page header (E1) is not in the tracer.** It consumes D-18 item 8's identity fields, which do not exist until 07-07 and are not published until 07-10 — so it is owned wholly by 07-15 rather than shipped thin in 07-01 and replaced later.
4. **`EVENT_TABS` is defined with all five tabs in 07-01**, but 07-01's route registers only the Breakdown trigger; each expansion plan adds its own trigger and content. Between waves, an unbuilt `?tab=` value resolves through the same `.catch(DEFAULT)` primitive `searchParams.ts` already uses for `?algorithm=`. The default tab stays `breakdown` until **07-18** flips it to `insights` — moved out of the Insights plan deliberately, see assumption 6.
5. **Both binding instructions are honored: subset-publish early, full republish last.** `07-UI-SPEC.md` requires the publisher/schema/ingest/republish work to precede any tab component reading the new fields; the phase's own sequencing rule requires the republish — a one-way write→verify→delete — to come last. The conflict was surfaced rather than silently resolved, and the user chose a third path neither instruction contained. `.github/workflows/deploy.yml` deploys to Cloudflare Pages on every push to `main`, so the cost UI-SPEC's rule was really guarding against was **waves of visibly degraded tabs on the live site** — Quals/Elims with no variance bands, Insights showing D-08's fallback on every event, Alliances disabling itself. `publish.ts`'s existing `--event <key>` single-event mode makes that avoidable for a few dozen PUTs. So 07-10 publishes a small real subset after the content-determining pipeline code (07-08, 07-09) is correct; tab plans 07-11…07-15 depend on it and are built and verified against real published data; and the full republish still runs last, gated, at 07-17/07-19. UI-SPEC's intent (tabs never read fields that no artifact carries) and the phase rule (the destructive pass is the end of the phase) are both satisfied.
6. **The default-tab flip moved from Insights to the client-cutover plan, to break a cycle.** 07-16's rename sweep touches `searchParams.ts`, so it must not share a wave with any plan editing that file; Insights previously owned the `breakdown → insights` default flip, which would have made 07-16 depend on 07-11, while 07-11 now depends on 07-10, which must precede 07-16. Moving the one-line flip to 07-18 — which owns `searchParams.ts`'s other cutover edit anyway — removes the cycle and keeps all `searchParams.ts` changes in exactly three plans (07-01 creates, 07-16 renames the pipeline-visible ids, 07-18 cuts the client over).
7. **The rename is split by tier, not scheduled as one block — this is what yields a single clean naming transition.** The hazard is symmetric: whenever the *client* rename lands, the browser starts asking for `vpr@…`, and if no `vpr@` key exists yet every page 404s on a site that deploys on every push. Moving the rename earlier relocates that window rather than closing it. The resolution extends D-06's own write→verify→delete discipline to the client: **07-10 publishes the subset under the current `sigma1@` keys** (pre-rename, so the deployed client reads it immediately); **07-16 renames only the pipeline** (what the publisher writes); **07-17 writes every `vpr@` key while `sigma1@` is still present and still what the browser reads**; **07-18 flips the client to `vpr@`, which by then exists**; **07-19 deletes `sigma1@`, after the client has left it.** The result is one artifact-naming transition instead of two, and no wave in which the client reads a prefix nothing has written. The alternative — renaming before the subset publish — would have forced the subset to write `vpr@` keys the deployed client could not yet request, breaking the live site for the entire tab-building stretch.
8. **Degradation between 07-10 and 07-17 is bounded to events outside the subset, and is by design rather than breakage.** Because the new schema fields are optional (assumption 2), a non-subset event renders its existing correct content and simply omits the new affordances; D-17's disabled Alliances tab and D-08's fallback banner are the *designed* absent-data treatments, not error states. The live site is therefore incrementally enriched through these waves and fully enriched at 07-17 — never broken. Recorded explicitly so a later reader does not mistake the window for an oversight.
9. **The `--include-offseason` fix is folded into 07-09**, not given its own plan, because it is a small `parseArgs`/`runSeasonsCliMode` thread through the same file 07-09 is already restructuring. It is a hard prerequisite for **both** publish plans — without it neither 07-10's offseason subset event nor 07-17's full pass reaches any of the 259 events D-08 was measured against.
10. **The D1 old-row cleanup, Worker deploy, `docs/publish-budget.md` re-measure, and the D-19 ROADMAP re-confirmation are folded into 07-19**, so every irrecoverable operation sits behind a single gate rather than scattered across the phase. The `vpr` D1 *reseed* belongs to 07-17 instead, since state seeding is part of the `publishSeasons` run itself.
11. **07-02/07-08's split of `event_alliances` writes vs reads is intentional.** 07-08 can be built and unit-tested against a seeded in-memory corpus before 07-05's live ingest populates the real table, which is why it depends on 07-02/07-07 rather than on 07-05. 07-10, which publishes real artifacts, does depend on 07-05.
12. **The four expansion tab plans are serialized (waves 6–9) rather than parallel**, because each registers its own trigger and `<TabsContent>` in `routes/event.$eventKey.tsx`. That file is a genuine shared coordination point; Elims additionally depends on Quals for `EventMatchTable.tsx`/`eventMatchAxis.ts`, which is a real dependency and not merely a file conflict. A tab-registry indirection would parallelize them but adds a layer of misdirection this app has no other use for.
13. **D-19 is already satisfied.** ROADMAP.md's Phase 7 Success Criterion 1 already carries the amended wording ("…falling back to the selected algorithm's own ordering, with that stated on the page…", annotated *Amended 2026-08-27 during Phase 7 discussion, D-19*). No plan needs to make the edit; 07-19 re-confirms it is present in the tree before the phase claims verification against it.
14. **The 17 probe edges, the recalled prohibitions, and the 7 UI-SPEC backstop rows are authored into per-plan `must_haves` at plan-writing time**, not at outline time — this file carries no `must_haves`.
