<planner_decisions>

- **PD-01 — `location` is ONE nullable display string, single-sourced through an exported
  `composeEventLocation`, rather than a nested `country`/`stateProv` pair.** The competing option was
  to mirror `EventsListRowSchema`'s two raw nullable columns and let the client compose. Rejected,
  for three reasons that point the same way. First, `pageArtifacts.ts` already contains this project's
  answer to exactly this class of problem: `publishedTierForPercentile` is exported from this file
  precisely so "the tier the pipeline publishes and the tier the client derives from a percentile can
  never disagree." A composed location has the same shape of risk and gets the same treatment.
  Second, 06-RESEARCH.md Pitfall 1 records `eventName: eventKey` as a shipped instance of the
  re-derive-in-the-client failure class, and Phase 6's own fix was to publish the display value
  directly. Third, `07-UI-SPEC.md` requires the header's null handling be "the same null-handling
  rule as the Events list's `locationText`/week-badge (reused, not reinvented)" — an exported
  composer is a mechanism for that reuse, whereas two raw fields is a hope for it.
  **Reversibility: costly** (a published field; removing it costs a republish).

- **PD-02 — `EventAllianceSchema` declares no field for the alliance leader and none for a fourth or
  reserve robot.** `07-PATTERNS.md` sketched `{ allianceNumber, picks: string[], captain, name?: string }`;
  that sketch is a pattern map, not a decision, and it is superseded here. 07-02's binding read shape
  `EventAllianceSelection` is `{ allianceNumber, name: string | null, picks: string[] }`, and its
  `picks` doc records that entry 0 is the alliance leader, entry 3 is the fourth robot where one
  exists, and that TBA's raw response has no separate field for either (RESEARCH.md Q2, verified live).
  A parallel field would be a copy of `picks[0]` that can drift from it, and this project's failure
  log already names documentation-that-drifts-from-code as a realized failure.
  **Reversibility: reversible** (the field does not exist; adding one later is additive).

- **PD-03 — one new `ROUNDING_RULE` key, one documented reuse, and four documented no-entries.** The
  instruction is "the matching `ROUNDING_RULE` entries for every new numeric field", and "matching"
  is doing real work here, because this file already contains both dispositions:
  - `redScoreVarianceOwn`/`blueScoreVarianceOwn` **REUSE `ROUNDING_RULE.variance`**. `rounding.ts`
    already states this explicitly for Phase 6's identical pair — "same physical quantity, so no new
    rounding rule is added for them" — and an event match row's own-variance is the same physical
    quantity as a team match row's. A second key for it would be drift wearing documentation's
    clothes. Task 1 extends that existing paragraph to name the event pair too.
  - `rp` gets a **NEW `ROUNDING_RULE.rankingPoints = 2`**. It is genuinely a new field class: not a
    model output like `metric`, but TBA's own reported per-match ranking-point average. Two decimals
    matches TBA's own published precision. Giving it its own key rather than borrowing `metric` means
    a future change to model-display precision cannot silently move a number TBA reported.
  - `rank`, `record.wins`/`losses`/`ties`, `week` and `allianceNumber` get **no entry at all** —
    integral by construction, exactly as `TeamSeasonMatchSchema.actualRedRp` already is ("integral by
    construction ... no `ROUNDING_RULE` entry for RP either") and as `buildEventsArtifact` already
    documents ("every value is an integer count or a nullable week index — nothing to round").
  Adding a key is not free: `rounding.test.ts` carries an **exhaustive** `Object.keys(ROUNDING_RULE)`
  assertion, so Task 2's new key makes that case go red first. That is the intended signal and the
  reason a new key is a decision rather than a keystroke. **Reversibility: costly** (07-08 rounds
  through it; changing precision later moves published numbers).

- **PD-04 — every new field is optional, and TWO DIFFERENT kinds of absence are used deliberately.**
  Conflating them is how an artifact silently loses a fact, so each field's doc comment states which
  kind it carries:
  - **optional but never null** — `name`, `startDate`. TBA has both for any real event, and 07-08
    falls back to the event key exactly as `buildEventsArtifact` already does for the events list.
    `undefined` here can only ever mean "this artifact predates the field."
  - **optional AND nullable** — `location`, `week`. `undefined` means the same as above; `null` is the
    honest published answer for an event with no recorded location or no derivable competition week.
    This is precisely `EventsListRowSchema`'s own shape for the same two source columns, plus the
    optionality the pre-republish window needs.
  - **optional, absence-only** — `rank`, `record`, `rp`, both variance fields, `alliances`. Absence is
    the single representation for "no such data", matching this file's standing rule that absence,
    not emptiness, represents absent data.
  The blanket optionality is outline assumption 2 and it is what keeps 07-01's tracer green through
  waves 2 to 9. **Reversibility: costly** (making any of these required later needs a republish).

- **PD-05 — no cross-field `.refine()` for the `rank`/`record`/`rp` triple.** The nearest analog in
  this file, `TeamSeasonEventSchema.rank`/`totalTeams`, explicitly chose the same thing: "always
  appear together or not at all (enforced at the ingest/publish boundary, not by a schema-level
  `.refine()` here — the render layer additionally treats a half-present pair as absent)". Here the
  reason is stronger than precedent: the half-present state is **real**. An `event_rankings` row
  written before 07-04 widens the ingest carries a `rank` with a NULL record and a NULL ranking
  score, so a refine demanding all three would reject a legitimate published state. Each field is
  independently optional and 07-11 renders each column's absence independently.
  **Reversibility: reversible.**

- **PD-06 — two deliberate non-additions, recorded so they do not read as oversights.** No
  `totalTeams` on `EventTeamSchema`: it is an event-level quantity that would be duplicated across
  every one of ~40 rows, `07-UI-SPEC.md`'s Insights column list does not include a "of N" display,
  and `teams.length` is NOT a substitute (the ranked pool and the roster are different sets) — so if a
  later phase wants "Rank 5 of 40" it needs a new event-level field, not a per-row one. And no red+blue
  `variance` on either event match row: that field is the win-probability denominator, nothing on the
  event page renders it, and D-01's whole point is one uncertainty quantity per aggregation level.
  **Reversibility: reversible** (both are additive if ever needed).

- **PD-07 — no `checkpoint:decision` in this plan, deliberately.** CONTEXT.md D-18 rates items 3, 6, 7
  and 8 as **costly**, not one-way ("published-schema fields — removing one means another full
  republish and breaks any client already reading it"), and every task below carries that rating.
  The phase's two gates sit at 07-17 (the republish write pass) and 07-19 (the destructive delete
  pass) per the approved outline's gate-placement note. At THIS commit the change is an ordinary
  source edit that `git revert` undoes completely: no artifact is written, no key renamed, no object
  deleted, and the deployed browser still reads pre-republish objects that parse unchanged. A later
  reader finding no gate here should read this entry, not infer an omission.

- **PD-08 — this plan changes no published byte, and that is an asserted criterion rather than an
  assumption.** `packages/harness/publish.ts` is out of scope (07-08 owns filling these fields), so
  `payloadBudget.test.ts` must show exactly the recorded baseline failure and no movement. A payload
  measurement that moved during a schema-only plan would mean a publisher edit leaked in.

- **PD-09 — new doc comments must state the CURRENT contract and must not restate the superseded
  two-quantity rule.** 07-06 Task 3 rewrote three doc sites in this exact file and proves its sweep
  with greps over the old claim's own wording. A fresh doc comment written in this plan that quotes
  that wording back would make 07-06's own gate fire on this commit. Every new doc comment below
  names D-01 / D-18 and this plan instead, and one of Task 1's acceptance criteria re-runs 07-06's
  sweep grep to prove the file is still clean afterwards. **Reversibility: reversible.**

- **PD-10 — every new-field test asserts on the PARSED value, never on `.parse()` not throwing.**
  This is load-bearing and easy to get wrong. Zod object schemas strip unknown keys silently by
  default, so `expect(() => Schema.parse(fixtureCarryingTheNewField)).not.toThrow()` passes

  ship with zero of its fields declared. Asserting `parsed.matches[0]!.redScoreVarianceOwn` toBe the
  written value fails before the edit (as `undefined`, and as a `pnpm typecheck` error on the
  property access) and passes after. Both failure modes are the RED step and both must be observed.
  **Reversibility: reversible.**
