<objective>
Corpus storage for the two new TBA data shapes: `CREATE TABLE IF NOT EXISTS event_alliances` in `packages/corpus/schema.sql` (following `event_rankings`/`team_media`'s own precedent and doc-comment convention), plus an `EVENT_RANKING_RECORD_COLUMNS`/`hasEventRankingRecordColumns` additive nullable-column migration in `packages/corpus/db.ts` for `record_wins`/`record_losses`/`record_ties` and the RP `sort_orders[0]` column on `event_rankings` — the safe "new source field" case per that file's own `EVENT_LOCATION_COLUMNS` analog, never a derived value. (D-18.6 storage half, D-18.7 table.)

Purpose: every other Phase 7 plan that touches alliance or ranking data reads or writes through the two shapes this plan defines. 07-03's ingest writes into them, 07-04's rankings extension fills them, 07-05's full-corpus live run populates them for 2022–2026, 07-08 reads them into the published event artifact, and 07-11/07-14 render what comes out. The column set therefore has to be right *now*: after 07-05 spends a full-corpus live TBA pass over ~1,581 events, changing it costs that pass again.

The risk this plan actually carries is not the new table — that is a `CREATE TABLE IF NOT EXISTS` with no prior rows. It is the four `ALTER TABLE ADD COLUMN` statements landing on a real, populated, ~359 MB `data/corpus.sqlite` holding 47,695 `event_rankings` rows and 102,877 matches that no git operation can restore. A wrong migration here is data loss, and Task 3 exists to prove it did not happen.

**Execution constraint:** this plan must run in the **main working tree, not a git worktree.** `data/corpus.sqlite` is gitignored, is not copied into a worktree, and any migration applied inside one does not merge back. Task 3 cannot execute at all without the real corpus present.

Output: an `event_alliances` table and its typed accessors, four nullable columns on `event_rankings` behind a `hasEventRankingRecordColumns` guard, and a corpus-gated regression proof that the real corpus survived the migration intact.
