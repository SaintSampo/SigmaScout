<objective>
Elims tab (EVNT-06, D-14): `ElimsTab.tsx` reusing `EventMatchTable`/`eventMatchAxis` with a **flat
chronological list, no bracket grouping** — every `ef`/`qf`/`sf`/`f` match ordered by `sortTime` with
the round labelled per row via `matchLabel()`'s existing output. Computes its **own** axis domain
independent of Quals (elimination alliances outscore qualification alliances, so one shared axis would
squash both). Bonus-RP dots never render as true — playoffs award none. Same D-13 client-side
played/upcoming merge as Quals.

Purpose: this is the smallest of the four expansion tabs by construction, and that is the point —
07-12 built the event-scoped match plot as shared machinery precisely so this tab would be a filter, a
domain call and a registration rather than a second table. The plan's real work is therefore
**evidence and restraint**: proving that the shared machinery behaves correctly on elimination data
(which differs from qualification data in row count, comp-level spread, score range and bonus-RP
applicability), and holding the line against the three ways this tab would fork — a second comparator,
a second geometry set, and a second empty-state sentence.

**One deviation from the objective above is deliberate and is the plan's most important decision.**
The outline says `ordered by sortTime`. That field now exists (07-07 and 07-08 added it after 07-12
was written), but this plan orders by 07-12's `compareEventMatchRows` instead, so the Quals and Elims
tabs share exactly one order. What that costs is measured, bounded and surfaced rather than absorbed:
see `must_haves.truths` and flagged planner assumption 1.

Output: one tab component, its Wave 0 EVNT-06 test file, and a registered `?tab=elims` panel behind
the route's one shared page-state tree.
</objective>
