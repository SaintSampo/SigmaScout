# Phase 03.2: Code Review Report

**Reviewed:** 2026-08-21
**Depth:** standard
**Files Reviewed:** 10
**Status:** issues_found

## Summary

The core of this phase — `packages/core/algorithms/opr.ts`'s event-scoped, quals-only, no-ridge
rewrite — is well constructed. The per-event `ReadonlyMap` state shape, the explicit
`lastEventByTeam` most-recent pointer, the quals-only `update()` no-op, the finiteness guard, and
the surrogate/disqualification policy carried forward unchanged all read correctly against
locked decisions D-01/D-02/D-04/D-05/D-06, and the accompanying test suite exercises each
decision with a real (not merely asserted) behavioral proof — including the solo-vs-interleaved
equivalence test, which is a genuinely strong way to prove event isolation. I traced the
minimum-norm SVD solve, the surrogate-offset arithmetic, the finiteness guard's reachability, and
the cold-start path and found no correctness defects in `opr.ts` itself. I did not re-litigate
anything the domain context marks as intentional (no-ridge, Gram-matrix solve, SVD's built-in
threshold, literal-zero cold start).

The two Warning-level findings below are both in the newer `packages/harness/eventScopeDiagnostic.ts`
diagnostic script: a floating-point equality assumption in the multi-season pooling reconstruction
that the code's own doc comment claims is "exact" but is not, in general, bit-for-bit exact in
IEEE 754 arithmetic (it happened to round-trip cleanly for the five real committed values, but
that is not guaranteed on a future run); and a test-coverage gap where the pooling/reconciliation
arithmetic that finding depends on has zero direct unit tests, despite being exported and
load-bearing for a check (T-03.2-18) whose entire job is to fail loudly on any population
mismatch. Neither is a data-corruption risk — the worst case is a spurious loud failure, which is
this project's preferred failure mode over silent corruption — but both degrade the diagnostic
script's reliability on a future re-run. Info-level items are minor clarity/style notes.

## Warnings

### WR-01: `poolSlices`'s "exact, bit-for-bit" pooling reconstruction is not actually exact, and the reconciliation gate depends on it

**File:** `packages/harness/eventScopeDiagnostic.ts:145-181` (doc comment) and `:245-257` (`buildReconciliationEntry`)

**Issue:** `poolSlices` reconstructs a pooled Brier score as `squaredErrorSum / scoredCount` where
`squaredErrorSum` is accumulated as `slice.brierScore * slice.scoredCount` across one-or-more
slices. The doc comment (lines 146-151) claims this is "exact, not an approximation ...
bit-for-bit-equivalent to scoring the full pooled population directly." That claim does not hold
in IEEE 754 double-precision arithmetic in general: `(x * n) / n` is frequently **not**
bit-identical to `x`. A quick empirical check confirms this:

```
node -e "let mismatches=0,total=0; for (let n=1000;n<200000;n+=137){ total++; const x=Math.random(); if (x !== (x*n)/n) mismatches++; } console.log(mismatches,'/',total);"
# -> ~180/1452 (~12%) mismatches
```

This matters because `buildReconciliationEntry` (the T-03.2-18 gate, whose own comment says
"never merely 'close'") compares `unbucketed.brierScore` — which for a single season is exactly
this lossy `(x*n)/n` round-trip of the artifact's own `brierScore` — against `artifactResult.brierScore`
read directly from `artifact.json` with no round-trip, using strict `===`:

```ts
const matches =
  unbucketed.brierScore === artifactResult.brierScore &&
  ...
```

On the real committed run (`data/diagnostics/opr-event-scope-2026-08.json`) all five seasons
happened to round-trip cleanly (verified directly against the committed file), so this did not
manifest this time. But that is IEEE-754 luck tied to this run's specific `(brierScore, scoredCount)`
pairs, not a property the code guarantees. A future re-run — same script, different corpus state
or season range — could throw `eventScopeDiagnostic: reconciliation FAILED` on data that is
actually identical, because the pooling round-trip introduced a one-ULP discrepancy, not because
anything is actually wrong. That is an expensive false alarm: regenerating `reports/event-scoped-v1/`
alone was measured at ~9 minutes in this phase's own SUMMARY.

**Why it matters:** a load-bearing, explicitly-designed-to-fail-loudly correctness gate is
fragile to a floating-point assumption that is stated as guaranteed but is not. This is exactly
the kind of "measurement pipeline that quietly stops being trustworthy" concern this project's
own failure log cares about, just inverted (loud false failure instead of silent bad data).

**Fix:** For the reconciliation path specifically, avoid the multiply/divide round-trip — compare
against the *unpooled* single slice's own `brierScore`/`winnerAccuracy` directly when only one
season is involved, or relax the reconciliation equality to a tolerance (e.g.
`Math.abs(a - b) < 1e-12`) rather than strict `===`. Alternatively, correct the doc comment to
stop claiming bit-for-bit exactness and note the known rounding risk, so a future reader
investigating a reconciliation failure doesn't waste time assuming it must be a real data bug.

### WR-02: `poolSlices`/`poolPredictions`/`buildReconciliationEntry`/`computeAccuracyBuckets`/`summarizeCheckpoint` have no direct unit tests

**File:** `packages/harness/eventScopeDiagnostic.ts` (exported functions at lines 155, 177, 245,
284, 413) — none appear in `packages/harness/eventScopeDiagnostic.test.ts`

**Issue:** `eventScopeDiagnostic.test.ts` covers checkpoint assignment/tagging (`assignCheckpointBucket`,
`tagRecordsWithCompletedQuals`), the design-matrix checkpoint slicing (`buildCheckpointRows`), and
the warm-cut partition (`computeWarmCut`/`assertWarmCutPartition`) — 11 tests total, matching the
SUMMARY's own count. But the actual pooling/reconstruction arithmetic — `poolSlices` (the function
WR-01 is about), `poolPredictions`, `buildReconciliationEntry` (the T-03.2-18 gate itself), the
per-bucket aggregation `computeAccuracyBuckets`, and the rank-checkpoint statistics
`summarizeCheckpoint` (mean/median/ratio/full-rank-fraction) — are all exported but never
exercised by a synthetic fixture. A test pooling two synthetic `ScoreSlice`s with deliberately
chosen Brier scores and counts would have been the natural place to catch WR-01's floating-point
fragility before it reached production data.

**Why it matters:** this is the arithmetic behind the phase's headline finding (the accuracy-by-
checkpoint curve and the D-09 warm cut), and it is currently verified only by "it happened to
produce numbers that looked right on one real run," not by a repeatable, deterministic proof —
weaker coverage than the file's other, well-tested halves.

**Fix:** add a unit suite for `poolSlices` (at minimum: pooling 2+ synthetic slices with known
counts/scores and asserting the weighted-mean identity; a slice with `brierScore: null`
contributing nothing; a slice with `winnerAccuracy: null` excluded from the accuracy denominator)
and a `buildReconciliationEntry` test that asserts `matches: true` for a synthetic
identical-population case and `matches: false` for a synthetic mismatch.

## Info

### IN-01: `OprState`'s `lastEventByTeam` doc comment reads ambiguously on first pass

**File:** `packages/core/algorithms/opr.ts:50-54`
**Issue:** "`lastEventByTeam` (D-04): explicitly tracked, not inferred from insertion order — a
team's FIRST event, not its MOST RECENT one." As written, this sentence can be misread as
describing what `lastEventByTeam` itself holds (which would be backwards — the map explicitly
tracks the MOST RECENT event, per D-04 and the code's own `next.set(team, eventKey)` on every
update). The intended reading — "insertion order would record a team's first event, not its most
recent one, which is why explicit tracking is needed instead" — only resolves after cross-checking
against the field's actual runtime behavior and the `teamMetrics` doc comment two functions below.
**Fix:** reword for one-pass clarity, e.g.: "`lastEventByTeam` (D-04): explicitly tracked. Map
insertion order alone would record a team's FIRST event, not its MOST RECENT one — wrong once two
events interleave — so this field is written explicitly on every `update()` call instead."

### IN-02: Magic number `3` for alliance size in the surrogate cold-start fallback

**File:** `packages/core/algorithms/opr.ts:150`
**Issue:** `currentLeagueMeanPerTeamShare`'s degenerate-case fallback is
`fallbackAllianceScore / 3`, with the `3` meaning "an FRC alliance has 3 teams." This is correct
for every FRC season 2022-2026 and is a pre-existing pattern in this codebase (no
`ALLIANCE_SIZE`/similar constant exists anywhere else either), so this is not a new defect — but
it is an unexplained literal at the one call site introduced by this phase's event-scoping of the
function (the doc comment explains the *fallback's* purpose but not why `3` specifically).
**Fix:** either a one-line comment ("3 teams per FRC alliance") or, if a shared constant is ever
introduced elsewhere for this purpose, reuse it here too. Not worth a standalone change today.

### IN-03: Sidecar line parsing has no defense against a truncated final line

**File:** `packages/harness/baselineFingerprint.ts:336-348` (`readSeasonRecordsBySidecar`) and
`packages/harness/eventScopeDiagnostic.ts:119-129` (`readSidecarRecordsForAlgorithm`)
**Issue:** Both functions' own doc comments describe a real, observed failure mode — a harness run
process killed mid-write leaves `predictions-<season>.jsonl` either 0 bytes or entirely absent —
and both handle the *entirely-missing-or-empty* case gracefully (an empty-line skip, and a
missing-file early return with a `console.warn`). Neither guards against a *partially written
final line* (e.g. the process is killed after `write()` flushed 40% of a JSON object but before
the trailing newline), which would make `JSON.parse(line)` throw a raw, unhandled `SyntaxError`
out of the `for await` loop. Given the doc comments already reason carefully about interrupted
writes, this is a plausible variant of the exact scenario they're written to defend against, left
uncovered.
**Fix:** wrap the `JSON.parse(line)` call in a `try/catch` that logs the offending line's season/
path and either skips the malformed line (consistent with the existing "loud warning, keep going"
treatment of a missing file) or re-throws with a clearer message naming the sidecar path and line
number, rather than surfacing a bare `SyntaxError: Unexpected end of JSON input`.
