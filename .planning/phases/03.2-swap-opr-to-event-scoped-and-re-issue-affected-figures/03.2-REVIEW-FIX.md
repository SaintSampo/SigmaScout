## Fixed Issues

### WR-01: `poolSlices`'s "exact, bit-for-bit" pooling reconstruction is not actually exact, and the reconciliation gate depends on it

**Files modified:** `packages/harness/eventScopeDiagnostic.ts`
**Commit:** `fd748f89`

**What changed:** Took the PREFERRED fix from the three options the reviewer offered — eliminated the lossy `(x*n)/n` round-trip on the path the reconciliation gate actually exercises, rather than loosening `buildReconciliationEntry`'s strict `===` to a tolerance. `poolSlices` now short-circuits when given exactly one slice (the single-season case `buildReconciliationEntry` pools every time, since `poolPredictions` groups by algorithm+season before calling `poolSlices`) and returns that slice's own `brierScore`/`winnerAccuracy`/`scoredCount` unchanged, with no arithmetic performed on them at all. For two-or-more slices (the real multi-season pooling case used by the accuracy-bucket and warm-cut aggregations), the original weighted-mean-of-group-means reconstruction is unchanged — it is mathematically exact in real-number arithmetic but not guaranteed bit-identical to a direct pooled computation, and no caller currently needs that guarantee for the multi-slice case.

Also corrected the doc comment (previously lines 145-153) that claimed the reconstruction is "exact, not an approximation ... bit-for-bit-equivalent" unconditionally. The comment now states the actual guarantee precisely: bit-for-bit exact for the single-slice case (the one that matters for the strict-equality gate), and an exact-in-real-arithmetic-but-not-bit-identical weighted mean for the multi-slice case, with the empirical ~12% mismatch rate from the reviewer's own repro cited as the reason a caller needing `===` must only ever pool a single slice.

**Why this approach:** The reviewer's guidance explicitly preferred this over loosening the gate's equality — it "keeps the strict `===` and the loud-failure discipline fully intact ... while removing the floating-point fragility entirely." Fixing it in `poolSlices` itself (rather than special-casing inside `buildReconciliationEntry`) benefits every current and future caller that happens to pool a single slice, not just the reconciliation path, and the fix is purely subtractive (removes arithmetic) so it cannot introduce a new numeric discrepancy.

**Frozen-data impact:** None. This is a source-code-only change; it was not run against the corpus or `reports/`, and no file under `data/baselines/` or `data/diagnostics/` was touched (verified: `git diff f53315d5 HEAD -- data/baselines/... data/diagnostics/...` is empty). The five already-committed reconciliation results in `data/diagnostics/opr-event-scope-2026-08.json` happened to round-trip cleanly before this fix (per the review), and the fix returns the identical underlying value for the single-slice case (same slice, now returned directly instead of round-tripped) — so this change is behavior-preserving with respect to every number already published.

### WR-02: `poolSlices`/`buildReconciliationEntry` (and related pooling functions) have no direct unit tests

**Files modified:** `packages/harness/eventScopeDiagnostic.ts`, `packages/harness/eventScopeDiagnostic.test.ts`
**Commit:** `235681c4`

**What changed:** Added a synthetic-fixture unit suite in `eventScopeDiagnostic.test.ts` covering exactly what the fix guidance specified:
- `poolSlices`: a single-slice pool returns the slice's own values unchanged — deliberately using `brierScore: 0.1, scoredCount: 3` (a value that provably mismatches under the old `(x*n)/n` round-trip: `(0.1*3)/3 !== 0.1` in IEEE 754 double precision, asserted directly in the test as a runtime sanity check before the real assertion). This is the exact round-trip fragility WR-01 identified, now under a regression test so it cannot silently reappear.
- Multi-slice pooling (2 synthetic slices with known counts/scores) asserts the weighted-mean identity for both `brierScore` and `winnerAccuracy`.
- A slice with `brierScore: null` contributes nothing to the pooled Brier numerator (population count still included, numerator does not).
- A slice with `winnerAccuracy: null` is excluded from the accuracy denominator entirely (not just from the numerator).
- `buildReconciliationEntry`: `matches: true` for a synthetic identical-population case and `matches: false` for a synthetic mismatch (mismatched `scoredCount`).

`buildReconciliationEntry` was previously a private (unexported) function; exported it so the test file can call it directly, matching the pattern already used for `poolSlices`, `assertWarmCutPartition`, `computeWarmCut`, etc. All fixtures are synthetic object literals — no corpus access, no `reports/` dependency, fully deterministic.

**Why this approach:** Followed the fix guidance precisely (poolSlices weighted-mean + null-handling cases, buildReconciliationEntry true/false cases) rather than expanding scope to the other functions the Issue section mentions (`poolPredictions`, `computeAccuracyBuckets`, `summarizeCheckpoint`) — the Fix section's "at minimum" list names only `poolSlices` and `buildReconciliationEntry`, and the orchestrator's guidance block reiterated exactly that scope.

**Frozen-data impact:** None — test-only and one `export` keyword addition; no data files touched, no corpus or `reports/` access.
