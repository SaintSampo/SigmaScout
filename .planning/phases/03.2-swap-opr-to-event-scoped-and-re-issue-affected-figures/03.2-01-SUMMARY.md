## Known Anomaly: Incomplete Sidecars on D-13's Final Run

The final run's prediction sidecars (`reports/retired-season-pooled/predictions-*.jsonl`) came out incomplete:

| File | Size | Status |
|---|---|---|
| `predictions-2022.jsonl` | 5,447,018 bytes | OK |
| `predictions-2023.jsonl` | 6,081,261 bytes | OK |
| `predictions-2024.jsonl` | 0 bytes | **EMPTY** |
| `predictions-2025.jsonl` | absent | **NEVER WRITTEN** |
| `predictions-2026.jsonl` | 6,872,635 bytes | OK |

This is a sidecar-*persistence* defect in this specific run's I/O, not a code-behavior change — `artifact.json`'s in-memory aggregation (which happens after all five seasons' replays complete) produced complete, exact metrics for every season including 2024 and 2025. The two are independent code paths (`writePredictionLine` per match vs. `aggregateScores`/`buildArtifact` at the end), and the metrics path was unaffected.

**Root cause not investigated** — this plan's scope is capturing the fingerprint, not debugging the harness's sidecar-write path, and the coordinator's guidance was explicit: do not re-run to try to fix it, do not let it block the plan, record it plainly. Filed as a finding for a future phase to investigate if it recurs; not itself a WINDOWS.md-tracked defect since it does not affect any of this plan's committed numbers (see the digest comparison table above for exactly which comparisons it does and does not affect).

**How `baselineFingerprint.ts` handles it (Rule 1 fix, see Deviations):** `readSeasonRecordsBySidecar` now tolerates a missing sidecar file, treating it as zero available records for that season and printing a loud warning rather than crashing. The affected seasons' `perSeason[].predictionStreamSha256` in the committed retired fingerprint are therefore the well-known SHA-256-of-empty-input hash (`e3b0c442...`), not real per-season digests — this is documented in the fingerprint's own `sourceNote` field and above.

## Background Process Handling (Infrastructure Note, Not a Deviation)

Two environment realities specific to this parallel-worktree execution, noted for provenance/traceability (no committed file is affected by either):

1. **`reports/tuned-v3/` and `data/corpus.sqlite` are gitignored** and therefore absent from this fresh worktree. Per this plan's own briefing, both were linked in read-only fashion from the main checkout: a directory junction (`reports/tuned-v3` → the main checkout's `reports/tuned-v3/`) and a hard link (`data/corpus.sqlite` → the main checkout's `data/corpus.sqlite`, opened exclusively via `openCorpusReadOnly`'s SQLite-level read-only flag by every script that touched it). Neither the main checkout's files nor any other worktree were written to.
2. **D-13's ~96-minute harness run required a detached OS-level process.** The first attempt, run via the standard backgrounded-Bash mechanism, was killed by the harness's own process supervision partway through (after ~3 of 5 seasons). It was restarted as a genuinely detached process (`Start-Process` with redirected output, independent of the Bash tool's process tree) and a separate lightweight polling wrapper watched for completion — this is what produced the incomplete-sidecar anomaly above (the first, killed attempt's partial output was cleared before the second attempt started via `rm -rf reports/retired-season-pooled`, so no data from the killed run leaked into the committed fingerprint; verified via `git diff --exit-code packages/core/algorithms/opr.ts` before the run and a fresh `--seasons 2022-2026` invocation for the second attempt).

## Decisions Made

- **`data/baselines/` un-ignored in `.gitignore`** (Rule 3 - blocking): `data/*` with only `!data/algorithm-versions/` as an exception meant `data/baselines/` was silently gitignored — `git add` refused the new fingerprint outright. Added `!data/baselines/` immediately after the existing exception line.
- **Narrow `ArtifactInputSchema` instead of the full `HarnessArtifactSchema`** (Rule 1 - bug): the surviving `reports/tuned-v3/artifact.json` predates plan 03.1's required `ExclusionCounts.quarantined` field and fails the current strict schema. A fingerprint generator whose entire purpose is reading *older* completed runs must not couple itself to whichever artifact shape is current — it reads only the handful of fields it actually needs (`schemaVersion`, `provenance.runTimestamp`/`.corpusIdentity`, `algorithms[].id`/`.version`, `slices[].{algorithmId,season,compLevelView,brierScore,winnerAccuracy,scoredCount}`), `.passthrough()` on everything else.
- **Missing/empty sidecar tolerance** (Rule 1 - bug, found running Task 2's real command): a missing `predictions-<season>.jsonl` now yields zero records for that season with a loud console warning, instead of crashing the whole generation. Documented above under "Known Anomaly."
- **`--run-dir` pointed at a directory junction / hard link rather than the literal plan-text relative paths**, since `reports/` and `data/corpus.sqlite` are gitignored and absent from a fresh worktree by construction — this is infrastructure, not a change to any committed artifact's content (see "Background Process Handling" above).
- **Requirements**: this plan's frontmatter lists `[ALGO-01, EVAL-01]`; both were already marked complete from Phase 1 (their current wording describes the season-pooled definition this very phase is replacing). `requirements.mark-complete` was run and confirmed a no-op (`already_complete`, no write) — no REQUIREMENTS.md change from this plan. Updating those requirements' *wording* to the event-scoped definition is out of this plan's scope (03.2-04/05/06's job per D-14/D-16).

Worked around by invoking `node_modules/.bin/tsx` directly (bypassing the `pnpm harness` script's `--env-file` flag) rather than creating or copying any `.env` content.
