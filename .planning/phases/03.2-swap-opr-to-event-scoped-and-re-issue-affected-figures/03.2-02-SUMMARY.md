## Accomplishments

- Rewrote `packages/core/algorithms/opr.ts`: `OprState` reshaped to `{ perEvent: ReadonlyMap<eventKey, PerEventOprState>, lastEventByTeam: ReadonlyMap<team, eventKey> }` (D-01/D-04); `update()` no-ops on every non-`"qm"` comp level (D-05); the ridge term is gone and the solve is renamed `solveEventOpr` (D-06); the finiteness guard on solved ratings survives as a per-event throw naming the eventKey and offending team (01-REVIEW WR-01, D-03); version bumped `2.0.0+baseline` -> `3.0.0+baseline`. `ratingEligibleTeams`/`allianceObservation` and their doc comments survive byte-for-byte (D-07, surrogate/DQ policy unchanged). - Rebuilt `opr.test.ts` around the new state shape: repointed at the new export surface, added a WalkForwardSimulator-driven tracer suite proving two interleaved events stay isolated end-to-end, and added six named behavioral suites (D-01/D-02/D-04/D-05/D-06 plus a rank-deficiency and a finiteness-guard suite) calibrated at the corpus-measured ~39-teams-per-event scale rather than the retired season scale.

- Ran the real single-season harness command (`--season 2024 --algorithm opr`) against the live corpus: completed in seconds (the per-event solve replaces the retired ~131ms/update season-pooled cost), producing a finite Brier/winner-accuracy pair and the expected `3.0.0+baseline` version string in `artifact.json`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `pnpm vitest`/`pnpm harness` triggered a failing `pnpm install` in this fresh worktree**
- **Found during:** Task 1, first attempt to run the test suite
- **Issue:** This worktree's `node_modules` was partial; invoking `pnpm vitest`/`pnpm harness` triggered pnpm's dependency-state check, which attempted a full reinstall. `better-sqlite3`'s `node-gyp rebuild` install step failed outright (no Visual Studio Build Tools on this machine), aborting the whole `pnpm install` and blocking every `pnpm`-wrapped command.
- **Fix:** Ran the already-present binaries directly instead of through the `pnpm` wrapper — `node node_modules/vitest/vitest.mjs run ...`, `node node_modules/typescript/bin/tsc --noEmit`, and `node node_modules/tsx/dist/cli.mjs packages/harness/cli.ts ...`. `better-sqlite3` needed no rebuild at runtime — it already ships a matching `prebuilds/win32-x64.node` that its own loader (`lib/win32-x64.js`) uses directly; the failing step was only the install-time rebuild attempt, never a real runtime capability gap.
- **Files modified:** None (environment workaround only, no committed file affected)
- **Verification:** Full suite (`pnpm test`'s equivalent) ran green at 676/676 tests across 44 files; the real harness run completed and produced a valid artifact.

**2. [Rule 3 - Blocking] `data/corpus.sqlite` absent from this fresh worktree**
- **Found during:** Task 1, before the required single-season harness run
- **Issue:** `data/corpus.sqlite` is gitignored (351 MB) and does not exist in a freshly created worktree, blocking the plan-required real `pnpm harness --season 2024 --algorithm opr` run.
- **Fix:** Created a hard link from this worktree's `data/corpus.sqlite` to the main checkout's read-only copy (`mklink /H`), mirroring 03.2-01-SUMMARY.md's own documented workaround for the identical constraint. Neither the main checkout's files nor any other worktree were written to — the corpus is opened read-only by every code path that touches it.
- **Files modified:** None (the hard link is itself gitignored, not a committed artifact)
- **Verification:** `git check-ignore -v data/corpus.sqlite` confirms it stays outside git's view; the harness run against it completed successfully with real, finite figures.
