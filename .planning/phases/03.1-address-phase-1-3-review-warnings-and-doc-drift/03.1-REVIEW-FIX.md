## Fixed Issues

### CR-01: OPR's Sherman-Morrison numerical-breakdown guard misses a non-finite `denom`

**Files modified:** `packages/core/algorithms/opr.ts`, `packages/core/algorithms/opr.test.ts`
**Commit:** d73d5aba
**Applied fix:** Widened the guard at `applyObservation` (opr.ts) from
`!Number.isFinite(residual) || denom <= 0` to
`!Number.isFinite(residual) || !Number.isFinite(denom) || denom <= 0`, so a
non-finite (`NaN`/`Infinity`) `denom` now trips the throw instead of walking
past it and corrupting every team's rating via `pu[r]/denom`. Detect-only
change — no rating arithmetic altered on the healthy path.

Added a regression test seeding an `OprState` whose `incrementalSolve.inverse`
is a duck-typed stub reporting `denom: Infinity` from `rank1Update` (the
private `IncrementalInverse` class can't be constructed directly from a test
file, and forcing genuine float-overflow through real match data isn't
practical at unit-test scale — this reproduces exactly what a corrupted
inverse would report). **Regression-proof, run in the worktree before the fix
was applied:** the test failed with `AssertionError: expected [Function] to
throw an error` — `Received: undefined` — confirming `opr.update` silently
returned instead of throwing under the old guard, exactly the silent-corruption
bug CR-01 describes. After the fix, `packages/core/algorithms/opr.test.ts`
passed 21/21 (was 20). `packages/harness/digest.test.ts` (bitwise digest
reproduction) also verified passing, confirming no prediction arithmetic
changed on the healthy path.

### WR-01: `acquireWriteLock`'s stale-lock reclaim path is not atomic

**Files modified:** `packages/corpus/db.ts`, `packages/corpus/db.test.ts`
**Commit:** 280b1e7e
**Applied fix:** The stale-lock reclaim branch no longer does a plain
`writeFileSync(lockPath, pid, "utf8")`. It now `unlinkSync`s the stale file
(ignoring `ENOENT`, in case a racing reclaimer already removed it) and
recursively retries `acquireWriteLock`, reusing the fast path's atomic `wx`
exclusive-create. At most one of two concurrent reclaimers wins the retried
write; the loser's retry hits `EEXIST` again against the winner's now-alive
pid and correctly falls through to the existing "already open" throw. The
module doc comment above `acquireWriteLock` was also updated — it previously
described only the fast path as atomic (the reviewer's own observation),
which no longer matched the reclaim path once WR-03's original fix landed.

Added a regression test mocking `unlinkSync` to simulate a competitor
recreating the lock (with a live pid) in the narrow window between this
process's unlink and its retry. **Regression-proof, run in the worktree
before the fix:** the test failed with the same `expected [Function] to
throw an error` / `Received: undefined` shape — the old plain-overwrite
reclaim let both simulated callers "win" silently. After the fix,
`packages/corpus/db.test.ts` passed 17/17 (was 16), and the full
`packages/corpus/` suite passed 22/23 with exactly the 1 expected skip
(the deliberately-stale `data/corpus.sqlite` integrity-check skip, unrelated
to this change). The pre-existing live-owner-throws test still passes
unchanged.

### WR-02: `makeSigma1` never validates `params` through `Sigma1ParamsSchema`

**Files modified:** `packages/core/algorithms/sigma1/index.ts`, `packages/core/algorithms/sigma1/sigma1.test.ts`
**Commit:** 11087dd8
**Applied fix:** `makeSigma1` now calls `Sigma1ParamsSchema.parse(options.params ?? DEFAULT_SIGMA1_PARAMS)` instead of passing the value through unchecked (also added `Sigma1ParamsSchema` to the module's import from `./params.js`, since it was previously only re-exported, not bound locally). This closes the runtime boundary `params.ts`'s "unconstructible" doc comment already claimed was closed — TypeScript's structural typing enforced the shape of `Sigma1Params` but not the schema's cross-parameter invariants (D-07, T-03-06, D-04).

Verified `DEFAULT_SIGMA1_PARAMS` parses cleanly through `Sigma1ParamsSchema` directly (a standalone script check) before wiring the call, confirming the change is a no-op for the untuned baseline. Added a regression test asserting `makeSigma1` throws when `params` violates the D-07 `processNoiseEventBoundary > processNoiseWithinEvent` invariant. **Regression-proof, run in the worktree before the fix:** the test failed the same way (no throw). After the fix, the full `packages/core/algorithms/sigma1/` suite passed 215/215, `packages/harness/` (which exercises `tune.ts`/`cli.ts`/`promote.ts`, the three call sites that already validate upstream) passed 252/252 — confirming the double-parse is a genuine no-op at every existing call site, not just the default.
