- `normalizeMatch` now derives a winner from the score comparison for a played, non-tied match TBA leaves `winning_alliance` empty (or any non-red/blue value) for, storing the derivation as one non-recomputed `winner_imputed` column (D-01/D-03, 01-REVIEW WR-06).

## Deviations from Plan

None — plan executed exactly as written. `vi.mock` for the WR-03 regression test is new test infrastructure for this codebase (no prior `vi.mock`/`vi.spyOn` usage existed), but it is scoped entirely to `packages/corpus/db.test.ts` and was necessary to produce a regression test that actually distinguishes the fixed code from the pre-fix code — the plan's acceptance criteria required a test that goes genuinely red against the pre-fix source, and a naive sequential "lock file already holds an alive pid" test does not (both old and new code throw correctly in that scenario, since JS's single-threaded execution has no real interleaving window without deliberately simulating one).

## Regression Proofs Observed (success criterion 1)

For each of the four warnings, the fix was temporarily reverted, the relevant test(s) were confirmed to fail, and the fix was restored before committing.

**WR-06 (D-01, `normalizeMatch`'s derivation branch removed):**
```
FAIL packages/ingest/normalize.test.ts > normalizeMatch — winner imputation (D-01, 01-REVIEW WR-06) > derives winner red and imputes when winning_alliance is empty and red outscored blue
  expected null to be 'red'
FAIL ... > derives winner blue and imputes when winning_alliance is empty and blue outscored red
  expected null to be 'blue'
FAIL ... > derives the winner from score comparison when winning_alliance is a non-red/blue/empty value on a played, non-tied match
  expected null to be 'red'
3 failed | 15 passed (18)
```

**WR-04 (D-02, `foreign_keys` pragma removed):** Removing the explicit `db.pragma("foreign_keys = ON")` line alone did **not** go red — this environment's `better-sqlite3` build defaults `PRAGMA foreign_keys` to `1` already (verified directly: `new Database(':memory:').pragma('foreign_keys')` → `1`). To produce a genuine regression signal, the pragma was instead explicitly set to `OFF`:
```
FAIL packages/corpus/integrity.test.ts > ... > reads back PRAGMA foreign_keys as enabled
  expected +0 to be 1
FAIL packages/corpus/integrity.test.ts > ... > throws when inserting a match whose event_key has no matching events row
  expected [Function] to throw an error
2 failed | 3 passed | 1 skipped (6)
```
This is recorded as a finding, not silently adjusted around: the explicit pragma is still the correct, future-proof code (01-REVIEW's own prescribed fix, and not dependent on a library default that could change across versions/environments), but "remove the line" is not itself a faithful regression-proof procedure here.

**WR-03 (`acquireWriteLock` reverted to probe-then-write):** A naive sequential test (pre-write an alive pid, call `openCorpus`, expect throw + unchanged contents) stayed green against the reverted code too — single-threaded JS has no real TOCTOU window without deliberately simulating one. A `vi.mock("node:fs", ...)`-based test forcing the `existsSync` probe to report "absent" while an alive owner's lock file genuinely exists reproduces the race deterministically:
```
FAIL packages/corpus/db.test.ts > openCorpus — atomic write-lock acquisition (WR-03) > TOCTOU regression proof: a race-simulated 'lock file absent' probe must not let acquisition silently clobber an alive owner's lock
  expected [Function] to throw an error
1 failed | 15 passed (16)
```
Restoring the atomic `wx`-based implementation returns this test (and all others) to green — the fixed success path never calls `existsSync` at all, so the mocked lie has no effect on it.

**WR-02 (`pnpm-workspace.yaml` glob):** No dedicated regression test — the fix is a one-line YAML config change verified structurally: `grep -c 'packages/\*' pnpm-workspace.yaml` returns 1, `grep -c 'apps/\*' pnpm-workspace.yaml` still returns 1, and `pnpm install --frozen-lockfile` completes without a lockfile change (no `packages/*` directory carries its own `package.json` today, matching the plan's stated expectation).
