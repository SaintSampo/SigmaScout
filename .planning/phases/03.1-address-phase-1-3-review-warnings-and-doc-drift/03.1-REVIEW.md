## Summary

This phase closes nine open code-review warnings from Phases 1 and 3, plus stale planning-doc
drift. Eight of the nine fixes hold up under adversarial re-reading: the OPR 5,000-match
incremental-vs-batch drift proof is real and exercised; the pnpm-workspace foreign-key/lock/
winner-imputation fixes are structurally sound and covered by targeted regression tests; the
`assertValidPRedWin` emission-time gate is wired at every `predict()` return site across
`opr.ts`/`epa.ts`/`sigma1/index.ts`; `Sigma1ParamsSchema`'s object-level `.check(...)` correctly
mirrors `isValidParamSet`'s five cross-parameter invariants (proven by an explicit agreement
test); `selectBestScreenRow` now throws a named error instead of a silent `rows[0]!` on a
fully-rejected grid; and `warnIfNewerPromotedSigma1` is a genuinely inert, defensively-coded
staleness warning that never changes which file is actually loaded.

One finding rises to Critical: the WR-01 numerical-breakdown guard in `opr.ts`'s
`applyObservation` — the guard whose entire job is to catch exactly this kind of silent
corruption at season scale — has an incomplete condition that lets a non-finite (`NaN`/`Infinity`)
`denom` bypass the throw, corrupting every team's rating in the returned state before the
run aborts one match later, misattributed to an unrelated observation. Three further findings
are Warnings: a residual (narrower) non-atomic race in the corpus lock's stale-reclaim path, a
Sigma1 parameter-validation boundary that the phase's own "unconstructible" claim does not
actually cover (`makeSigma1` never parses its `params` argument through the schema), and a
`pnpm-workspace.yaml` glob that still matches zero real packages under the current directory
layout.

## Critical Issues

### CR-01: OPR's Sherman-Morrison numerical-breakdown guard misses a non-finite `denom`, letting corruption through the exact check WR-01 added to catch it

**File:** `packages/core/algorithms/opr.ts:417`
**Issue:**

`applyObservation`'s guard reads:

```ts
if (!Number.isFinite(residual) || denom <= 0) {
  throw new Error(...);
}
```

`denom <= 0` is `false` whenever `denom` is `NaN` (or `+Infinity`), so a non-finite `denom` walks
straight past the guard instead of tripping it. This directly undermines the WR-01 fix's own
stated purpose (per this file's comment at the throw site): "aborts the run at the observation
that broke it, instead of silently folding a non-finite or sign-broken update into every rating
for the rest of the season."

Concretely, when `denom` is `NaN`:

- `rank1Update`'s own internal division (`factor = pu[r] / denom`) has already produced a
  corrupted `nextInverse` before the guard is even reached (`opr.ts:390`) — irrelevant when the
  guard *does* fire (the corrupted object is discarded because the function throws before it is
  returned), but load-bearing when it doesn't.
- The guard does not fire (since `NaN <= 0` is `false`), so execution falls through to:
  ```ts
  nextRatingsVector[r] = nextRatingsVector[r]! + (pu[r]! / denom) * residual;
  ```
  Dividing by `NaN` produces `NaN` for essentially every `r` in `nextRatingsVector`, not just
  the teams in this alliance's observation — the loop runs over the *entire* known-team range
  (`for (let r = 0; r < nextRatingsVector.length; r++)`), so one bad `denom` sets every team's
  rating to `NaN` in a single update.
- The corrupted `NaN`-filled state IS returned and becomes the live `OprState`.
- The corruption is *usually* caught one update later — the next `applyObservation` call for
  any alliance containing a previously-corrupted team computes `uX = sum(ratingsVector[idx])`,
  which is now `NaN`, so `residual = allianceScore - NaN = NaN` correctly trips
  `!Number.isFinite(residual)` and throws *then*. But the thrown error names the wrong match —
  the observation whose `allianceScore` is perfectly ordinary, not the one whose `denom` actually
  broke down — directly contradicting this guard's own documented diagnostic goal ("naming the
  offending score and the computed residual...so the failure is attributable without
  re-running").

This is exactly the class of failure the phase context calls out: "any guard that looks like it
enforces something but does not actually fire." The existing 5,000-match/400-team property test
(`opr.test.ts`'s "season-scale drift proof") never exercises this path (no test in the file
references `denom` at all — confirmed by search), so the gap is currently silent and untested.
Given the project's real target scale (~3,000-3,700 teams, ~15,000-18,000 matches/season, with
the guard's own comment explicitly disclaiming any periodic resynchronization "because
self-healing would move OPR's ratings"), accumulated floating-point error producing `Infinity`
or `NaN` in the maintained inverse over a full season is a plausible, not merely theoretical,
failure mode — precisely the regime WR-01 was raised against.

**Fix:**
```ts
if (!Number.isFinite(residual) || !Number.isFinite(denom) || denom <= 0) {
  throw new Error(
    `opr: incremental solve broke down applying an observation with allianceScore=${observation.allianceScore} — ` +
      `computed residual=${residual}, denom=${denom}. ...`
  );
}
```
Add a regression test alongside the existing `residual=NaN` case that forces `denom` to become
non-finite (e.g., by seeding an `IncrementalRidgeSolve` whose stored inverse already contains a
non-finite entry, or by driving the synthetic drift fixture with an adversarial/ill-conditioned
sequence) and asserts the throw fires on the *same* observation that produced the bad `denom`,
not a later one.


#### Resolution (2026-08-20)

**Status: Resolved.** Fixed in commit `d73d5aba` (`fix(03.1): CR-01 widen OPR breakdown guard to catch non-finite denom`), applied during phase 03.1's code-review gate.

The guard at `applyObservation` widened from `!Number.isFinite(residual) || denom <= 0` to `!Number.isFinite(residual) || !Number.isFinite(denom) || denom <= 0`, so a `NaN`/`Infinity` `denom` now trips the throw on the observation that produced it rather than walking past and corrupting every entry of `nextRatingsVector` via `pu[r]/denom`. Detect-only per D-08 — no rating arithmetic changed on the healthy path, and `packages/harness/digest.test.ts` still reproduces every committed digest bitwise (verified post-fix), with `data/algorithm-versions/` byte-identical to its pre-phase state.

The finding's core premise was independently confirmed before the fix was authorized: `NaN <= 0` and `Infinity <= 0` both evaluate to `false` in this runtime, and no test in `opr.test.ts` referenced `denom` at all. A regression test was added that seeds an `OprState` whose `incrementalSolve.inverse` is a stub reporting `denom: Infinity` from `rank1Update` (the private `IncrementalInverse` class cannot be constructed from a test file). Proven red against the pre-fix source — observed `AssertionError: expected [Function] to throw an error / Received: undefined`, i.e. `opr.update` silently returned under the buggy guard — then green after.

## Warnings

### WR-01: `acquireWriteLock`'s stale-lock reclaim path is not atomic, leaving a narrower version of the race WR-03 was meant to close

**File:** `packages/corpus/db.ts:67-76`
**Issue:** The WR-03 fix correctly replaces the "probe-then-write" TOCTOU on the *no-lock-file*
path with an atomic `wx`-flag exclusive create (`db.ts:57`). However, the *stale-lock reclaim*
path — reached when the lock file exists but its recorded owner PID is no longer alive — still
uses a plain, non-exclusive `writeFileSync`:
```ts
const ownerPid = Number(readFileSync(lockPath, "utf8").trim());
if (Number.isFinite(ownerPid) && isProcessAlive(ownerPid)) {
  throw new Error(...);
}
// Stale lock from a process that no longer exists (or unparseable contents) — reclaim it.
writeFileSync(lockPath, String(process.pid), "utf8"); // no { flag: "wx" }
```
Two processes that both encounter the same stale (crashed-owner) lock file at roughly the same
time will both pass the `isProcessAlive` check as `false` and both then overwrite the lock file
with their own PID — both believing they hold exclusive write access to the corpus, exactly the
scenario the single-writer lock exists to prevent. This is a narrower window than the original
WR-03 finding (it requires a crashed prior owner, not just ordinary concurrency), but the
comment on `acquireWriteLock` now describes "a single atomic exclusive-create syscall attempt,"
which is only true for the fast path, not the reclaim path.
**Fix:** Reclaim with the same atomic exclusive-create discipline used for the fast path, e.g.
`unlinkSync(lockPath)` guarded by a check that the file still names the same stale PID (or simply
attempt `writeFileSync(lockPath, ..., { flag: "wx" })` after unlinking and re-check for `EEXIST`),
so two concurrent reclaimers cannot both succeed.


#### Resolution (2026-08-20)

**Status: Resolved.** Fixed in commit `280b1e7e` (`fix(03.1): WR-01 make corpus stale-lock reclaim atomic`).

The stale-lock reclaim path now unlinks the stale lock and retries the same atomic `wx` exclusive-create used by the fast path, instead of a plain non-exclusive `writeFileSync`. Two processes that concurrently find the same crashed-owner lock can no longer both believe they hold it. The live-owner case still throws unchanged. Covered by a new regression test in `packages/corpus/db.test.ts`, proven red against the pre-fix source.

### WR-02: `makeSigma1` never validates `params` through `Sigma1ParamsSchema`, so the WR-01/03-REVIEW "unconstructible" guarantee does not hold at that boundary

**File:** `packages/core/algorithms/sigma1/index.ts:1086-1101`
**Issue:** `sigma1/params.ts`'s doc comment for `Sigma1ParamsSchema` states the fix makes "an
invalid `Sigma1Params` unconstructible rather than merely unbuilt-by-convention... on the schema
every construction path already parses through." In practice, `makeSigma1` — the actual runtime
factory that turns a `Sigma1Params` object into a live `AlgorithmModule` — does not call
`Sigma1ParamsSchema.parse` (or even `isValidParamSet`) on `options.params`:
```ts
export function makeSigma1(options: Sigma1Options): AlgorithmModule<Sigma1State> {
  const params = options.params ?? DEFAULT_SIGMA1_PARAMS;
  return { ... };
}
```
TypeScript's structural typing enforces the *shape* of `Sigma1Params` at compile time but not its
numeric ranges or cross-parameter invariants (D-07's boundary ordering, T-03-06's clamp ordering,
D-04's `[0,1]` weights) — those are exactly what the schema's `.check(...)` exists to enforce.
Today every call site that supplies custom `params` happens to validate first (`tune.ts`'s screen/
joint stages via `Sigma1ParamsSchema.parse`/`isValidParamSet`, `cli.ts`'s
`loadPromotedSigma1`/`loadSearchWinnerSigma1` via `PromotedVersionSchema`/`Sigma1ParamsSchema`,
`promote.ts` via `Sigma1ParamsSchema.parse`), so there is no live path producing a wrong published
number right now. But `makeSigma1` is an exported, public factory, and nothing in its own
signature or body prevents a future caller from passing an invalid `Sigma1Params` object directly
— contrary to the "unconstructible" claim.
**Fix:** Either have `makeSigma1` itself call `Sigma1ParamsSchema.parse(params)` before closing
over it, or narrow the doc comment's claim to name the specific parse boundaries that are
actually enforced (and add a `makeSigma1`-level test asserting it throws for a params object that
violates a cross-parameter invariant), so the code and the comment agree about where the
guarantee actually lives.


#### Resolution (2026-08-20)

**Status: Resolved.** Fixed in commit `11087dd8` (`fix(03.1): WR-02 validate makeSigma1's params through Sigma1ParamsSchema`).

Took the first of the two options the finding offered: `makeSigma1` now calls `Sigma1ParamsSchema.parse(params)` before closing over it, so the "unconstructible" claim in `params.ts`'s doc comment now genuinely holds at the runtime factory boundary rather than only at the upstream call sites that happened to validate. `DEFAULT_SIGMA1_PARAMS` was confirmed to parse cleanly, and the existing validating call sites (`tune.ts`, `cli.ts`, `promote.ts`) double-parse as a no-op. A `makeSigma1`-level regression test asserts it throws for a params object violating a cross-parameter invariant.

### WR-03: `pnpm-workspace.yaml`'s `packages:` glob still matches zero real packages under the current directory layout

**File:** `pnpm-workspace.yaml:1-3`
**Issue:** The workspace file declares:
```yaml
packages:
  - "apps/*"
  - "packages/*"
```
There is no `apps/` directory at all, and none of `packages/core`, `packages/corpus`,
`packages/harness`, or `packages/ingest` contains its own `package.json` — confirmed directly
(`ls packages/*/package.json` finds nothing). pnpm only recognizes a directory as a workspace
member if it has a `package.json`; as written, this glob currently resolves to an empty set of
workspace packages, and the single root `package.json` is the sole real package. This is
currently harmless (install/build/test all pass against the root package), but it means the WR-02
fix's premise — "glob did not match real package layout" — is only partially addressed: the glob
now points at plausible *future* directories rather than a typo, but it still does not describe
the actual present layout (a flat multi-directory single package, not a multi-package workspace).
**Fix:** Either add `package.json` files under `packages/*` (and `apps/*` once populated) to make
them genuine workspace members matching the glob's intent, or remove/comment the `packages:`
section until a real multi-package split happens, so the config states a fact about the repo
rather than an aspiration.


#### Resolution (2026-08-20)

**Status: Resolved.** Fixed in commit `c09b4b57` (`fix(03.1): WR-03 comment out unmatched pnpm-workspace.yaml package globs`).

Took the second of the two options the finding offered, deliberately. Converting `packages/core`, `packages/corpus`, `packages/harness`, and `packages/ingest` into genuine workspace members would require per-package manifests, dependency rewiring, and tsconfig path updates — a structural change out of scope for a review fix, and one the project already plans for a later multi-package split. So the `apps/*` and `packages/*` globs are commented rather than deleted, with an inline note recording why, making the file state a fact about the present repo instead of an aspiration. `allowBuilds` (required by `better-sqlite3` and `esbuild`) is untouched and still active. `pnpm install --frozen-lockfile` succeeds with `pnpm-lock.yaml` unchanged, verified post-fix.

**Superseded (2026-08-20, Phase 4 prep).** The commented-out state described above no longer matches HEAD. Because Phase 4 introduces `apps/worker` as a real package, the globs were uncommented so its `package.json` is not silently ignored; `pnpm-workspace.yaml` now lists `apps/*` and `packages/*` as live patterns with an inline comment recording why. `allowBuilds` remains active and unchanged, and `pnpm install --frozen-lockfile` was re-verified clean with no lockfile change. The accepted trade-off recorded above is therefore retired rather than carried forward.
