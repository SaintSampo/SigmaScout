<objective>
**One match, one outcome. The rank simulation stops drawing red's and blue's ranking points as two unrelated events and starts drawing the thing that actually happened — the match result — once.**

Today, `simulateRanks` draws red's total RP from `redRpPmf` and blue's total RP from `blueRpPmf` as two fully independent inversions of the shared `rng` stream. Both pmfs already fold the win RP into their domain, so a single draw can — and across 1,000 draws routinely does — hand the winning alliance's RP to red and to blue in the same simulated match. That is not a modelling simplification. It is a state the sport cannot produce, and every rank band the site renders is built on top of a thousand of them.

The fix is narrow, and D-15 states it in one sentence: draw the match outcome **once**, then bonuses per alliance. RESEARCH.md's assumption A3 flags that "draw the outcome once" has two defensible implementations and warns against leaving the choice implicit; the phase outline picks **approach (b)** so this plan does not re-litigate it. This plan implements (b): one three-outcome draw (red win / tie / blue win) from the shared stream, then one independent bonus-only draw per alliance, then the outcome RP added on — deterministic once the outcome is known.

Three things make this narrower than it first looks, and one thing makes it wider.

**Narrower.** The Monte Carlo stays (D-15, developer-confirmed). The `drawCategorical(pmf, rng)` primitive stays. The `rng` threading stays. The draw loop keeps its shape, its typed-array accumulators and its zero per-draw allocation. Only the *shape of what is drawn from* changes.

**Wider.** `rankSimulation.ts` does not compute pmfs — it receives them. So the bonus-only marginal 09-04 exports has to physically reach it, through two different transports: the offline baked path, which holds the `Prediction` object in hand, and the published event artifact, which the browser parses. Neither carries a bonus-only marginal today. That is the real work in this plan, and it is why the plan is three tasks rather than one edit.

Why the marginal is transported instead of recovered: the total-RP pmf *is* the convolution of outcome RP with bonus RP, so polynomial division would in principle recover the bonus half. On `roundPmf`-quantized published input that deconvolution is ill-conditioned and can return negative mass, which `drawCategorical` absorbs silently into a biased draw. The outline pins the source for exactly this reason — 09-04 separates the halves "specifically so you consume the bonus-only marginal rather than re-deriving it."

Purpose (D-15, deliverable 7, ROADMAP): *"Rank simulation: draw each match outcome **once** and then bonuses per alliance, replacing today's independent red/blue marginal draws where both alliances can win the same draw."*

Output: a coupled draw in the one shared simulation core, the decomposition carried to it over both transports as optional fields that degrade gracefully, and a test that makes the impossible state impossible to reintroduce.
</objective>
