Close **F5 / deliverable 6** — the live Worker never computes ranking points, so every live tick strips them.

Four pieces, in order, and the row-builder edit is the smallest of them:

1. `packages/harness/stateSnapshot.ts` gains a `sigmascoutRp` passenger pair and the shape version goes up by one.

Output: RP on live played rows, equal to what the publisher would have written, proven by a two-arm digest test rather than by presence; a gated, ordered, one-way seed-then-deploy decision; and a measured CPU number with its method stated and its limits named.

## Reversibility (REVERSIBILITY_GATES is on)

Two different ratings apply to two different things in this plan, and conflating them is how a plan either over-gates the code or under-gates the operation.

**The code is `costly`.** A `git revert` restores every source file exactly. What makes it costly rather than free is the shape constant: reverting after a seed has run leaves D1 holding rows one shape ahead of the deployed Worker, which is the same outage as being one shape behind, so a code revert after a seed obliges a re-seed too.

**The seed-then-deploy is `one-way`, and it is gated by Task 4's `checkpoint:decision`.** Not because either command is irreversible on its own, but because the pair has no safe intermediate state: a seed without a deploy and a deploy without a seed both take live folding down, and the recovery from either is *the other command*, which costs another pass against a 100k-row-write daily cap that roughly four passes exhaust. There is no revert that returns D1 to the previous shape without a second full publish run. The checkpoint therefore sits **before any network command is issued**, presents the sequencing, and takes the call.

`workflow.human_verify_mode` is `end-of-phase`, so there is no `checkpoint:human-verify` here. The one human judgement this plan's output feeds — "played rows carried RP during a real tick and `cpuTime` stayed off the pin" — is already recorded as a manual-only verification in `09-VALIDATION.md` and is collected by the phase's UAT during the next live event.

## A defect discovered during planning — reported, routed, NOT fixed here

**The D1 seed does not carry the Sigma Score beliefs, and has never carried them.**

`publish.ts`'s seed-emission block applies `withSwingBeliefs` and nothing else. `withSigmaBeliefs` and `withSigmaPopulation` are called in exactly one place in the repo — the Worker's own tick write path in `scheduled.ts` — and `SigmaScoutLayer` exposes no accessor for Sigma beliefs at all, so `publish.ts` could not seed them even if it tried. Quick task `260910-wg8` wired the resume-and-persist half and left the seed half unwritten; its SUMMARY says the remaining work is "seed-and-deploy", which reads as purely operational and is why this was easy to miss.

**The consequence:** a Worker resumed from a fresh seed cold-starts BPR's Sigma beliefs, computes every band from the flat prior until its own ticks have folded enough, and disagrees with the publisher while looking healthy — the exact failure the 10->11 bump was made to prevent, reintroduced through the seed rather than through the shape.

**Why this plan does not fix it:** it is a separate feature's seed wiring with its own verification (the band-stream digest, not the RP digest), and silently widening a Worker plan into a Sigma plan is how scope becomes untraceable. **What this plan does instead:** Task 2 files it as a pending todo with the evidence above, and Task 4's checkpoint briefing surfaces it, because 09-10's republish plus this plan's seed-and-deploy is precisely the event that would take it from latent to live.
