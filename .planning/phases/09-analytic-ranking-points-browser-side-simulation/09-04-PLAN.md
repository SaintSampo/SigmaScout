<objective>
**Delete the Monte Carlo. The distribution it was sampling has an exact closed form, and the code already proves it.**

`packages/core/rankingPoints/distribution.ts` builds a `2 + 2T`-dimensional joint Gaussian, Cholesky-decomposes it through `ml-matrix`, escalates a ridge ladder when the decomposition fails, clamps a cross-covariance term against its own Cauchy-Schwarz bound, and then draws 4,000 correlated samples per match to estimate a pmf. Every one of those machines exists to handle correlation. There is none. `empiricalMoments.momentsFor` returns a variance block that is diagonal by construction and a `scoreCrossCovariance` that is all zeros, and `buildJointModel` zeroes the cross-alliance blocks itself — so the Cholesky factor is a diagonal of standard deviations and the 4,000 draws are sampling independent normals. The closed form is therefore **exact, not an approximation**, and the Monte Carlo has been adding +/-0.008 of sampling noise to a quantity that can be computed.

This plan builds `packages/core/rankingPoints/analyticPmf.ts` — a zero-runtime-import browser-safe leaf (D-08) — that does the whole thing in four steps: fit one marginal per threshold variable (09-03's `fitAllianceMarginals`), group bonuses by shared threshold variable and enumerate each group's joint outcomes from marginal CDFs, convolve the groups into a bonus-RP pmf, and convolve that with the match-outcome RP. It replaces `rpPmfForMatch` behind the same call site — `#rpFieldsFor` in `packages/harness/sigmaScoutLayer.ts` — and takes `distribution.ts` with it: `CHOLESKY_RIDGES`, `clampCrossCovariance`, `CROSS_COVARIANCE_SAFETY_FACTOR`, `buildJointModel`, the module-local `mulberry32`/`boxMullerPair`/`fnv1a32`, the Monte Carlo config, and the `ml-matrix` import all go. `packages/core/algorithms/opr.ts` keeps `ml-matrix` for its SVD solve, so the dependency stays in `package.json` and nothing is installed or uninstalled.

The single highest-risk computation in the phase lives here. 2026's `energized` and `supercharged` both threshold `hubTotalCount`, and `SUPERCHARGED_THRESHOLD[tier] >= ENERGIZED_THRESHOLD[tier]` at every tier — so supercharged structurally implies energized, `P(both)` is `P(supercharged)`, and treating the pair as independent understates the joint while nothing downstream of a pmf can tell the difference. D-07 declined the one-time Monte Carlo equivalence check that would have caught this, and named hand-computed unit tests as the required mitigation. This plan pays that debt: expected values for each of the seven mechanism classes, computed from the closed form during planning and written into the task bodies, plus a dedicated non-vacuous case for the nested-threshold trap.

`RpLayerConfig = {winSource, tieModel, marginal}` (D-05) is introduced here at **inert defaults that reproduce today's model exactly** and threaded into both of `publish.ts`'s orchestrations. Every non-default value throws by name, pointing at 09-05, which owns all three changes (D-13's win source, D-14's tie model, D-01's marginal family). D-06 is what makes this scaffolding rather than architecture, and the file header says so: 09-06 collapses this to one hardcoded path and deletes the losing branches.

Purpose: this is deliverable 2, and the unblocking step for three later plans. 09-05 needs the config skeleton to hang its branches on. 09-07 needs the win/tie and bonus-only halves exported separately so its rank-simulation coupling fix draws from the same decomposition rather than a second one. 09-08 needs the RP path to be cheap enough and import-clean enough to run inside a Cloudflare Worker tick. D-10 ships the closed form unconditionally, so none of that is contingent on a measurement.

Output: one new leaf module and its two test files, one deleted module and its retired tests, four migrated call sites, a config threaded through both write paths, and a green D-12 gate proving `pRedWin`, `redScore` and `blueScore` are byte-identical against 09-01's frozen baseline after the whole swap.
</objective>

## The closed form, specified

This is the plan's transcription target. It is derived from reading `distribution.ts`'s draw loop at HEAD and from 09-RESEARCH.md's verified mechanism enumeration; **it is the executor's checklist, not a sketch.**

### Step 1 — one marginal per threshold variable

Call 09-03's `fitAllianceMarginals(moments, variables)` once per alliance, where `variables` is `ruleModule.thresholdVariables` with each entry's `marginalFamily` replaced by `resolveMarginalFamily(variable.marginalFamily, config)`. The mean comes from `moments.meanVector[i]`, the variance from `moments.varianceBlock[i][i]` — which is the diagonal `momentsFor` builds by construction, and the reason per-variable marginals are sufficient rather than an approximation. Keep the returned `FittedMarginal[]` on `AllianceBonusRp.marginals`: 09-03 deliberately separated `declared`, `resolved` and `fallbackReason` so a fit that silently degraded is countable, and collapsing that to a bare probability here would destroy the observability 09-06 depends on.

**`resolveMarginalFamily(declared, config)`** — the rule, stated once and documented in the function's own doc comment:

- `config.marginal === "gaussian"` (the inert default, and D-10's revert target): **every** variable is fitted Gaussian regardless of what it declares. One field change reverts the whole marginal swap without editing 34 declarations, which is exactly what D-10 promises ("a failed marginal swap reverts to Gaussian while everything else lands").
- `config.marginal === "negative-binomial"`: each variable is fitted with its **own** declared `marginalFamily`, so a variable that needs an exception keeps it — which is the entire reason D-02 put the family in the season module rather than deriving it from `unit`.

Today both sides agree (config gaussian, all 34 declarations gaussian), so the rule is inert and today's behavior is reproduced exactly. The second branch is unreachable in this plan because `assertSupportedRpLayerConfig` rejects it; it is written and documented now so 09-05 adds a value, not a semantics.

### Step 2 — group bonuses by shared threshold variable

Compute each `BonusPredicate`'s **variable footprint** — the set of threshold-variable names it reads:

| `kind` | Footprint |
|---|---|
| `singleThreshold` | `{variable}` |
| `nestedSameVariable` | `{variable}` |
| `linearCombination` | every `terms[].variable` |
| `conjunctionDistinct` | the union over `clauses[].terms[].variable` |
| `countOfIndicators` | the union over `indicators[].terms[].variable` |
| `dataDependentMixture` | `selector`, `whenSelectorTrue` and `whenSelectorFalse` term variables |
| `constant` | empty |

Bonuses land in the same group iff their footprints intersect — a connected-components pass over the footprint graph, computed, never a hardcoded season list. Groups are independent of one another (the variance block is diagonal and the cross-covariance is zero), so groups convolve.

**Across all ten registered seasons this produces exactly one multi-bonus group: 2026's `{energized, supercharged}`.** Everything else is a singleton. That fact is asserted by a test rather than assumed by the code, and the enumerator handles exactly two shapes:

- **Singleton group** -> the bonus's own probability `p`; contribution pmf `[1 - p, p]`.
- **Multi-bonus group where every member is `nestedSameVariable` over the same `variable` with the same `direction`** -> the interval enumeration below.
- **Anything else** -> **throw**, naming the season and the member bonus names, with the message stating that an exact joint form for that group shape does not exist in this module and that F4 (dependence between distinct threshold variables) is deliberately out of scope. A silent fallback to a product of independents is the one outcome this branch exists to prevent.

### Step 3 — the nested-threshold interval enumeration (D-07's named highest-risk case)

For a group of `nestedSameVariable` bonuses over one variable with `direction: "gte"`, resolve each member's threshold with `resolveRpThreshold(threshold, tier)`, sort the members by resolved threshold ascending (`T_1 <= T_2 <= ... <= T_n`), and let `q_k = probAtLeast(marginal, T_k)`. Then, because clearing `T_k` implies clearing every lower threshold:

- `P(exactly 0 of them fire) = 1 - q_1`
- `P(exactly k of them fire) = q_k - q_{k+1}` for `1 <= k < n`
- `P(all n fire) = q_n`

The contribution pmf over "how many of this group's bonuses fire" is therefore `[1 - q_1, q_1 - q_2, ..., q_{n-1} - q_n, q_n]`, which telescopes to 1 by construction. Each member's own marginal probability is its `q_k`. `probAtLeast` is monotone non-increasing in its threshold — an invariant 09-03 asserts rather than assumes — which is what makes every difference non-negative; assert non-negativity here anyway and throw if it is violated, because a negative probability reaching a published pmf is worse than a loud failure.

For 2026 at base tier (`T_energized = 100`, `T_supercharged = 360`): `P(both) = q_supercharged`, `P(only energized) = q_energized - q_supercharged`, and `P(supercharged AND NOT energized) = 0` structurally. **Never `q_energized * q_supercharged`.**

The `lte` direction has no nested group in the tree; if one ever appears, the sort order inverts and the same telescoping applies. Handle it or throw — do not silently assume `gte`.

### Step 4 — the per-bonus probability for a singleton group

One shared helper evaluates an `RpThresholdClause` to a probability, and every kind is expressed through it:

**`clauseProbability(clause, marginalsByName, tier)`** — build the clause's own marginal as the sum of its scaled terms. For the Gaussian family this is exact and closed: `mean = sum over terms of marginal.mean / (term.divisor ?? 1)` and `variance = sum over terms of marginal.variance / (term.divisor ?? 1)^2`, summed **left to right in declared term order**, then `fitMarginal(mean, variance, "gaussian")`. Compare with `probAtLeast(fitted, T)` for `direction: "gte"` or `probAtMost(fitted, T)` for `"lte"`, where `T = resolveRpThreshold(clause.threshold, tier)`. A single-term clause with no divisor reduces to the variable's own marginal and must produce the identical number — assert that rather than special-casing it.

Divide by `term.divisor ?? 1`; never multiply by a precomputed reciprocal. `linkPoints / 5` and `linkPoints * 0.2` are different doubles and a threshold comparison is the only place that difference decides anything, which is why 09-02 made `RpLinearTerm` carry a divisor and made term order part of the declaration.

Then, by `kind`:

| `kind` | Probability |
|---|---|
| `singleThreshold` | `clauseProbability` of its single implied clause |
| `nestedSameVariable` | handled by the group enumerator (step 3); its marginal is `q_k` |
| `linearCombination` | `clauseProbability` of its `{terms, direction, threshold}` clause |
| `conjunctionDistinct` | the **product** over `clauses` of `clauseProbability` — valid only because the clauses' footprints are pairwise disjoint and distinct variables are independent. Assert the disjointness; throw naming the bonus if it fails |
| `countOfIndicators` | `poissonBinomialAtLeast(indicators.map(clauseProbability), resolveRpThreshold(required, tier))` — valid only because the indicators' footprints are pairwise disjoint. Assert; throw if not |
| `dataDependentMixture` | `ps * p_true + (1 - ps) * p_false` where `ps = clauseProbability(selector)` and the two branch probabilities are unconditional — valid only because the selector's footprint is disjoint from both branches'. Assert; throw if not |
| `constant` | `value ? 1 : 0` |

**On 2022 `cargoBonus` specifically:** `autoCargoTotal` and `matchCargoTotal` are declared as distinct tracked variables and this model treats them as independent even though auto cargo is presumably part of match cargo. That is a known, measured, **deferred** flaw (09-CONTEXT `<deferred>`), and the disjointness assertion passes because the declared names are distinct. Reproduce it. Do not fix it.

**The `untrackedGate` on a predicate is metadata and must never be read.** 09-02 baked the conservative choice into *which threshold table the declaration names*, so there is nothing for this layer to decide. A gate this module could branch on is a gate a future edit could flip, and `rpConservativeBranch.ts`'s measured understatement table would silently stop describing the shipped model.

### Step 5 — convolve groups into the bonus-only pmf

`convolvePmf(a, b)[k] = sum over i of a[i] * b[k - i]`, plain polynomial multiplication over arrays of length at most 6. Fold every group's contribution pmf together, starting from `[1]`. The result has length `bonusNames.length + 1` and is `AllianceBonusRp.pmf` — **the bonus-only marginal 09-07 consumes.** Its per-bonus marginal probabilities, in `bonusNames` declaration order, are `AllianceBonusRp.bonusProbabilities`, which replaces the Monte Carlo tally that `redBonusRp`/`blueBonusRp` publish today. Order is a positional contract all the way to the rendered dots; read it from `bonusNames`, never from a record's key order.

### Step 6 — the outcome half

`matchOutcomeDistribution` under `winSource: "score-draw"` reproduces the deleted draw loop's `redScore > blueScore` comparison exactly. The two alliance scores are independent Gaussians (the cross-alliance block was zero), so the difference `D = redScore - blueScore` is Gaussian with `meanD = red.scoreMean - blue.scoreMean` and `varianceD = red.scoreVariance + blue.scoreVariance`:

- `varianceD > 0` -> `pRedWin = 1 - standardNormalCdf(-meanD / sqrt(varianceD))`, `pTie = 0` (the `continuous-equality` model: a tie needs exact float equality of two continuous draws, so its probability is exactly zero — F7's dead branch, reproduced not repaired), `pBlueWin = 1 - pRedWin`.
- `varianceD === 0` -> both draws are deterministic and every Monte Carlo draw would have been identical: `pRedWin = meanD > 0 ? 1 : 0`, `pTie = meanD === 0 ? 1 : 0`, `pBlueWin = meanD < 0 ? 1 : 0`.

The three always sum to exactly 1; assert it. Red's outcome-RP pmf is a length-`winRp + 1` array with `pRedWin` at index `winRp`, `pTie` at index `tieRp` and `pBlueWin` at index `0` (accumulated, since `tieRp` could in principle equal `0`); blue's mirrors it.

### Step 7 — the final pmf, and why no mass folds

`redPmf = convolvePmf(redOutcomePmf, redBonusPmf)`. Length is `(winRp + 1) + (bonusNames.length + 1) - 1 = winRp + bonusNames.length + 1`, and `maxRp === winRp + bonusNames.length` in **all ten** registered seasons (2016-2024 `winRp: 2`, 2025-2026 `winRp: 3`; every module writes `maxRp: <winRp> + BONUS_NAMES.length` literally), with `tieRp: 1 <= winRp` everywhere. So the deleted `Math.min(ruleModule.maxRp, outcomeRp + totalRp)` could never bind, the pmf lands at exactly `maxRp + 1` entries, and **no mass folding is needed**. Assert `maxRp === winRp + bonusNames.length` and `pmf.length === maxRp + 1` per season rather than carrying the claim forward as a comment.

### The two short-circuits, carried forward unchanged

- **Non-qualification comp levels:** `if (!isBonusRpCompLevel(compLevel)) return { redPmf: [1], bluePmf: [1] }` — the degenerate `P(RP=0)=1` pmf, no marginals fitted, exactly as `rpPmfForMatch` did. Keep the single shared `isBonusRpCompLevel` predicate; do not reintroduce a comp-level string comparison.
- **The zero-draws fast path is GONE.** It existed so `tune.ts`'s hyperparameter search could skip 4,000 draws per match. A closed form has no such cost and no draw count to set to zero. `analyticRpPmf` always computes. The one place that mattered is handled at its call site (Task 3).

### The independence precondition, asserted rather than assumed

`analyticRpPmf` is exact **because** the joint is diagonal. Assert that on entry for both alliances: every `scoreCrossCovariance[i]` is `0`, and every off-diagonal `varianceBlock[i][j]` (`i !== j`) is `0`. Throw naming the season and the violating index otherwise. This is not defensive padding — it is the one line that stops a caller supplying a learned correlation (sigma1's `predictAllianceRpMoments` does exactly that) and having it silently discarded by a function whose whole correctness argument depends on its absence.
