<objective>
Per-team data is currently stored in the rows meant for league-wide aggregates, and it has two
consequences: two of the three published algorithms cannot be seeded into D1 at all, and every tick
that does real work has to parse roughly 584 KB of JSON it does not need. Move the per-key data into
`scopeKind: "team"` rows, keep the handoff exactly lossless, and prove the fix by actually running
the seed and the import against the real database.

Purpose: `packages/harness/stateSnapshot.ts` serializes each algorithm's state into `StateRow`s
scoped `team`, `event`, or `league`. D-13's whole point — and plan 04-03's own stated must-have — is
that `league` rows hold small league-wide aggregates while per-key data lives in `team`/`event` rows,
so a tick reads only the keys it is folding. Three rows violate that, measured on 2026-08-22 against
the real corpus:

- **sigma1** `league` row is 253.1 KB. `priorSeasonRatings` alone is 245.8 KB of it — 97% of the row.
  The genuine aggregates (`league`, `allianceScoreStats`, `componentOrder`, and three scalars) come
  to about 7.1 KB.
- **epa** `league` row is 246.0 KB (251,995 bytes as a single SQL tuple), for the same reason —
  `SerializedEpaLeague.priorSeasonRatings` carries the same two per-team maps.
- **opr** `league` row is 84.9 KB, carrying `lastEventByTeam`, a map of every team to its last event
  key. OPR's per-event data is already correctly in `event`-scoped rows (209 of them).

D1's hard per-statement cap is 100,000 bytes, and a single row cannot be split across statements. So
`wrangler d1 execute --file` rejects the whole import with `statement too long: SQLITE_TOOBIG`. The
emitter's batching bound was fixed on 2026-08-22 (`DEFAULT_MAX_STATEMENT_LENGTH` was 4,000,000 —
forty times over the real limit — now 90,000) and `SeedRowTooLargeError` now fires at emit time
instead of producing a file that only fails at import. After that fix, **opr emits 28 statements,
longest 90,050 bytes, and imports cleanly into remote D1** (211 changes, 630 rows written; a
`GROUP BY` read-back confirms `opr event 209 rows`, `opr league 1 row`). **epa and sigma1 still throw
at emit time and cannot be seeded at all**, so `pnpm publish:seasons` exits 1 after uploading
artifacts, and plan 04-07's Task 2 precondition — a seeded D1 — cannot be met.

The second consequence is the read cost. `apps/worker/src/stateStore.ts`'s `readScopedState` always
fetches the `league` row alongside the named keys, deliberately, so it costs one subrequest instead
of two. That is the right design; it is only expensive because the league rows are full of data the
tick does not need. Measured idle-tick CPU on the deployed Worker (10 consecutive invocations,
version `5a8e0a6f`): median 7 ms, range 5–9 ms, cold start 14 ms, all `outcome: ok`. The idle path
loads no state, so a working tick starts from that 7 ms and then adds the 584 KB parse. Whether it
fits the documented 10 ms free-plan budget is unmeasured — and note plainly that the observed 14 ms
cold start returned `ok`, so the relationship between the documented figure and what the platform
actually enforces is itself unresolved. This plan does not settle that. It removes the parse and
records the numbers honestly; the working-tick measurement stays plan 04-07's job.

Output: league rows that hold only aggregates, three seed files that import, a regression test that
makes this shape defect fail on the commit that reintroduces it, and a budget doc that records what
was measured and by which run.
</objective>

    Reshape the three serializers so a `league` row holds only values whose size is a function of the
    season's components, not of its team count.

    For sigma1 and epa, the two per-team maps under `priorSeasonRatings` move onto the team rows. The
    team-row payload becomes a union: a team may have current-season state, a prior-season rating,
    or both, and the serializer must iterate the UNION of the team keys across all the per-team maps
    the algorithm holds — a team carrying only a prior-season rating still gets its own row. The
    existing defensive union in `serializeEpaState` over `teamComponents`/`teamMatchCounts` is the
    pattern to widen. `deserializeState` reassembles the three maps from those rows.

    fold this map into the event rows instead. That alternative looks attractive because an event row
    already knows its own teams, but it is wrong: a tick that folds a team's first match at event E
    cannot remove that team's stale entry from event D's row, because D is not loaded, so the team
    would end up claimed by two events and the union would be ambiguous. A team row is authoritative
    and gets overwritten in place.

    Add an exported snapshot shape version to every league payload and check it on the way in,
    throwing a named error (following `MissingLeagueRowError`'s existing shape and message style)
    when it is absent or does not match. This is what makes the currently-seeded rows in remote D1

    aggregate would be a worse failure than a red test.

    Keep the stable-serialization discipline intact: every Map still becomes a key-sorted array of
    pairs, every plain object still goes through `canonicalize`. That property is what lets
    `selectChangedRows` skip a write for an unmoved team, and the reshape must not weaken it.

    Write the tests in `stateSnapshot.test.ts` first, from the behavior block above, and watch them
    fail before touching the serializer.
