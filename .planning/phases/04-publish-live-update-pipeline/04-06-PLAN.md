<objective>
Write the tick: read what is live, ask TBA what changed, advance the state, rewrite the artifacts that
moved, and do all of it inside a 10 ms CPU budget and a 50-subrequest ceiling.

Purpose: this is the plan that makes DATA-04 true — a new match result reflected in published
artifacts within one to three minutes. Every piece it needs already exists. The manifests exist (plan
04-03), the state store and the budget exist (plan 04-05), the artifact schemas and keys exist (plan
04-02), and the prediction code has existed since Phase 2 and has been deliberately kept
Worker-importable that whole time. What is left is orchestration, and the orchestration has an order
that matters:

**update, then state write, then artifact write.** Never a different order and never in parallel.
State is the source of truth; a published artifact is a projection of it. If artifacts are written
first and the process dies between the two, the site shows a result the live state has not folded, and
the next tick's prediction is computed from stale state while the page already shows the newer outcome.
That is not a crash — it is a wrong number that looks fine.

The other thing this plan gets right by construction is the one D-14 will later measure: the Worker
imports the same `predict` and `update` from `packages/core` that the harness calls, and validates
against the same Zod schemas the offline publisher uses. Equivalence is not something to test into
existence afterwards; it is a property of not writing a second implementation.

Output: a cron tick that early-exits when nothing is live, polls politely, advances only what changed,
and never lets one bad event take the others down.
</objective>

**The sequence, in order, with the budget consulted before every step that costs a subrequest:**

1. **Read the manifests.** One or two binding calls. If `liveEventsAt(now)` is empty, return
   immediately with a result recording zero events and zero TBA requests. This is the overwhelmingly
   common case — ten months of the year — and it must be visibly the first branch, not a loop that
   happens not to iterate.
2. **Order the live events** with `rotate(sortedEventKeys, persistedOffset)` from the budget module.
   Not the manifest's own order: a stable order plus a cap means the tail is never reached.
3. **Per event, inside a try/catch:**
   a. Read the event cursor (`tba_etag`, `last_folded_match_key`).
   b. Poll TBA conditionally. 304 means nothing changed — record the poll and move on.
   c. Diff the returned match list against the cursor. Matches at or before `last_folded_match_key` in
      the event's own order are already folded; skip them. If nothing is new, move on.
   d. Read the state slice for the algorithms in the manifest and the scopes the new matches touch —
      one batched call, per algorithm. Rebuild each module: `opr` and `epa` imported directly,
      `sigma1` via `makeSigma1` with the manifest's parameters.
   e. For each new match in order: `predict` (through `toLeakProofUpcoming`), then `update`. The same
      two calls, on the same functions, in the same order the offline harness makes them.
   f. **Write state first.** One batched write per algorithm. If it rejects, log the event as failed
      and `continue` — do not write artifacts for this event this tick. The next tick retries from an
      unadvanced cursor, which is safe precisely because the batch is all-or-nothing.
   g. **Then write artifacts:** the event's own artifact, and the team-season artifact for each of the
      roughly six teams that played in each new match. Per D-16, and no more — the year-wide teams
      table and events list are not touched here.
   h. Advance the cursor.
4. **The slower cadence (D-16).** Rebuild `teams/{year}` and `events/{year}` when either at least
   `GLOBAL_REBUILD_INTERVAL_MS` (start at 10 minutes) has passed since the last rebuild, or an event
   just finished its last scheduled match. Both triggers, not one: the interval keeps the season
   ranking fresh enough that nobody notices, and the event boundary makes an event's completion show
   up in the season view immediately, which is when someone actually looks. Persist the last-rebuild
   timestamp in D1 alongside the rotation offset. Guard the whole rebuild behind `budget.tryConsume`
   for the puts it needs, so a busy tick defers the global rebuild rather than starving the per-event
   refresh that visitors are watching.
5. **Persist the rotation offset**, advanced by the number of events actually processed, and return a
   result object: events considered, events advanced, events deferred, events failed, TBA requests
   (from the counter), subrequests used, and whether the global rebuild ran.

**Error confinement.** Every per-event body is wrapped, and a caught error records the event as failed
and continues to the next one. That is D-15's requirement in its most literal form: one event's
problem is one event's problem. The only errors that abort the tick are the fixed-cost ones — a
manifest that will not parse means the tick has no idea what is live, and continuing would be guessing.

**Keep the CPU work honest.** Pitfall 4's point is that 10 ms is per invocation, not per event: each
event's work being individually cheap does not mean the sum across many events is. So do not do
anything per event that is not strictly needed — no full-state deserialization when a slice will do,
no re-serialization of unchanged rows, no rebuilding the algorithm modules once per event when once per
tick suffices. Hoist the module construction out of the event loop and say why in a comment.
