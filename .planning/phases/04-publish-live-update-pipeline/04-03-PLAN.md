<objective>
Build the three things that stand between the offline pipeline and the online Worker: the manifest
that tells the Worker what is live, the manifest that tells it which algorithms and which versions it
is allowed to advance, and the state snapshot that gives it something to advance from.

Purpose: D-12 makes a deliberate architectural choice that is easy to state and easy to get subtly
wrong — **the offline run is the authority, and the Worker only loads and advances.** That is what
keeps a mid-season team starting from its real accumulated rating instead of a cold prior, and what
keeps incremental drift correctable rather than compounding. It only works if the snapshot is
lossless and the Worker has no independent opinion about which algorithm version it is running.

This plan is also where the phase's second unresolved design question gets its answer in code. Plan
04-01 established that `packages/harness/cli.ts`'s `applyPromotedOverrides` cannot run in a Worker
(the file imports `node:fs`, `node:path`, `node:util`, `node:url`, `node:perf_hooks`). The answer is
not to reimplement it — that is the two-implementations-drifting anti-pattern the whole
`packages/core` boundary exists to prevent — but to carry its *answer* forward: the offline run
resolves the promoted version once, writes the resulting id, version string and parameter set into
the algorithms manifest, and the Worker rebuilds the module with `makeSigma1`, which does live in
`packages/core` and is Worker-importable.

Output: two manifest builders with schemas, a lossless state serializer, and the D1 table the Worker
will read.
</objective>

Create `packages/harness/stateSnapshot.ts` and `packages/harness/stateSnapshot.test.ts`. Tests first;
the round-trip assertions are the specification here.

**The row shape.** `StateRowSchema` is a Zod object: `algorithmId`, `algorithmVersion`, `scopeKind`
(the enum `"team" | "event" | "league"`), `scopeKey`, `stateJson` (a string), `generation`,
`computedAt`. `scopeKind` exists because the three shipped algorithms do not share a granularity, and
pretending they do would be the failure. Sigma1 and EPA accumulate per team; **event-scoped OPR
accumulates per event** (D-09 — its `OprState.perEvent` is keyed by `eventKey`, and its whole reason
for existing is that season-pooled OPR's state exceeded a Worker's memory outright). A `team_state`
table would have forced OPR's event-shaped state into a per-team column, so the table and the
serializer both say `scope` instead.

**Serialization.** Write one `toJson`/`fromJson` pair per algorithm. The unavoidable work is the
`Map` members — `JSON.stringify` turns a `Map` into `{}` with no error, so every one of them must be
converted explicitly to an array of `[key, value]` pairs on the way out and rebuilt with `new Map()`
on the way in. Enumerate them from the read-listed types rather than from memory:

- Sigma1: `teams` (Map, one row each), `league.componentMean`, `league.componentConsistency`,
  `league.rpVariableMean` (plain records), `priorSeasonRatings.lastSeason` and `.yearBefore` (Maps),
  plus the per-team `covariance` 2D array and `innovationStats`.
- EPA: `teamComponents` and `teamMatchCounts` (Maps, one row each), `priorSeasonRatings`' two Maps.
- OPR: `perEvent` (Map of eventKey to `{observations, ratings}`, where `ratings` is itself a Map — one
  row per event) and `lastEventByTeam` (Map, in the league row).

For stability, serialize every map as a **key-sorted** array of pairs and every record with sorted
keys. That is what makes re-serializing an unchanged team produce the identical string, which is what
lets the Worker skip a write for a team that did not move — a direct saving against the R2/D1 write
volume DATA-05 caps.

**Proving it is lossless.** The round-trip test must not settle for a deep-equal of two objects. Build
a small in-memory corpus fixture, replay a handful of matches through each algorithm with
`WalkForwardSimulator`, capture the final state, round-trip it, then replay a further few matches
through both the original and the round-tripped state and assert
`computePredictionStreamDigest` produces the same hash for both streams. That is the same standard
Phase 3 uses for "these two runs are the same run", applied to the offline-to-online handoff, and it
catches a lossy field that a shallow structural comparison would miss.

Also add the partial-load test: deserialize a league row plus two team rows and assert `predict()`
for a match between those two teams matches the full-state prediction. That property is what D-13's
per-team-granular-read requirement actually cashes out to, and it needs to be true before the Worker
is written, not discovered afterwards.
