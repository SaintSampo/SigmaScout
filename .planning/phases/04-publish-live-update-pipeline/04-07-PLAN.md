<objective>
Deploy the thing, prove it is as fast as the requirement says, prove it computes the same numbers the
harness does, and write down what it costs on the real platform.

Purpose: four of this phase's claims cannot be established by any amount of local testing, and
`04-VALIDATION.md` lists them explicitly as the items the automated suite does not cover — peak-tick
subrequest count, peak-tick CPU time, daily R2/KV write volume, and TBA request counts. They are
"measured and recorded", not green-or-red. That distinction is the whole reason this plan exists as
its own plan rather than as a footnote to plan 04-06: a green `pnpm test` says nothing about whether
this fits in a 10 ms budget, and letting it stand in for that would be the failure mode this project's
own log already records once.

The rig is dual-purpose by design (D-20 says so). The same recorded historical event pushed through the
deployed Worker gives both the freshness number and, compared against the same slice replayed through
`packages/harness`, the equivalence assertion D-14 asks for. One fixture, two proofs.

**The gap this plan records rather than hides.** Because the rig replaces TBA with recorded data, it
does not exercise real TBA latency or real Cloudflare cron jitter. `04-CONTEXT.md` D-20 accepts that
deliberately and says a live offseason event is an optional later confirmation, not a requirement for
closing the criterion. The next such events are `2026azscor` (2026-08-28) and `2026scsc`
(2026-08-29). Record the gap in plain words in the budget doc; do not describe the rig's number as if
it included latency it did not measure.

Output: a deployed Worker, a written operating procedure, a repeatable rig, and a budget doc with no
`pending` cells left in it.
</objective>
