<objective>
Answer this phase's two open empirical questions before anything is built on top of their assumed
answers: does the virtualized-plus-pinned table composition survive real touch input, and does a
2.7 megabyte artifact paint fast enough to leave D-03's search-index split deferred.

Purpose: `05-RESEARCH.md` is explicit that no official example proves the three-way combination of row
virtualization, column pinning and touch, and that deferring the first-paint measurement means a
"build the split" verdict would arrive after everything else was built assuming it was not needed.
Both risks are cheap to retire now — a throwaway spike and three Lighthouse runs — and expensive to
discover in wave 4 or at phase end.

Output: a running touch proof with a stated fallback, performance marks that separate network cost
from render cost, and a dated measurement record carrying the D-03 verdict.
</objective>

  <action>
Build the smallest thing that can fail, and make it fail visibly if the composition does not work.

**The spike component.** `src/spike/TableSpike.tsx` renders fabricated data only — about 50 rows and
12 columns, matching 2026's real column count, with the first three columns pinned left. It follows
the research's Pattern 2 exactly and nothing else: ONE native scrolling element scrolling on both
axes, which is also the virtualizer's scroll element; the table sized to the total column width so the
horizontal axis overflows naturally; the header row stuck to the top; pinned cells positioned sticky at
their computed left offset. Every pinned cell carries an opaque background token — the bleed-through
failure the research names is purely visual and will not show up in a scroll-position assertion, so it
needs its own check.

There must be exactly one element with an overflow rule in the whole component. A second overflow
region is the failure shape D-04 warned about, so if the implementation seems to want one, that is the
signal to stop and record it rather than to add it.

**The route.** `src/routes/spike.tsx` mounts the component at `/spike`. It fetches nothing and reads
no artifact — fabricated rows only. Plan 05-08 deletes both files; note that in the file header so a
later reader does not mistake it for shipped surface.

**The harness.** `playwright.config.ts` configures two projects using the built-in device descriptors
for a recent iPhone and a recent Pixel, with `hasTouch` enabled, and a `webServer` entry that builds
and serves the app locally so the spec is self-contained. Point `testDir` at `e2e/` and keep that
directory out of the Vitest include (plan 05-01 already excluded it).

**The proof.** `e2e/touch-scroll.spec.ts` asserts, on both devices:
- A vertical touch drag inside the table body advances the container's vertical scroll offset and
  leaves the horizontal offset unchanged.
- A horizontal touch drag across the unpinned region advances the horizontal offset and leaves the
  vertical offset unchanged.
- After a horizontal drag, the pinned columns' bounding boxes have not moved horizontally relative to
  the viewport, while an unpinned column's has.
- The header's bounding box top stays fixed after a vertical drag.
- Virtualization is real: the number of rendered row elements stays far below the total row count
  after scrolling, and the row content at the scrolled position differs from the content at the top.
- A pinned cell's computed background colour is not transparent.

Use touch drag primitives, not mouse wheel events — wheel scrolling does not exercise the gesture
arbitration this is testing.

**If it fails.** Do not improvise a redesign. Record which assertion failed on which device, and adopt
the named fallback: drop the horizontal-overflow-with-pinning composition for a fixed column set that
fits phone width with the remaining metric columns reachable through an explicit column-selector
control, keeping every column present per D-04's intent but not simultaneously on screen. Write the
failure and the fallback into the SUMMARY as a decision plan 05-06 must implement, and flag it to the
user — D-04 is a locked decision, so changing how it is delivered is a reportable deviation, not a
silent substitution.
