<objective>
Add the four location and calendar facts the Events page filters on — real name, competition week,
country, state/province, district — to the published `events/{year}` artifact, and republish.

Purpose: `05-UI-SPEC.md` names this a blocking cross-phase prerequisite, and reading the code confirms
it is worse than the UI-SPEC assumed. `EventsListRowSchema` already declares `name` and `week`, but
`publish.ts` feeds `name` the event key and hard-codes `week` to `null`, because the corpus `events`
table has neither column. `country`, `state_prov` and `district` are absent from the TBA ingest schema
entirely. So EVNT-01's four filter dimensions currently have zero backing data, and NAV-03's
"find an event by name" cannot work at all against what is published today.

This is a schema-and-refetch job, not new data gathering: TBA's event object already carries all five
values. The chain is ingest schema, normalizer, corpus column, upsert, publish query, artifact schema,
republish.

Output: five new fields flowing end to end, a cheap events-only refresh command, republished artifacts
verified live, and a re-measured payload budget.
</objective>

Widen the TBA event contract, the corpus, and the ingest path so the five facts exist locally.

**Ingest schema.** Add to `tbaEventSchema`: `name` as a required string; `week` as a nullish
integer; `country` and `state_prov` as nullish strings; `district` as a nullish object carrying
`abbreviation`, `display_name`, `key` and `year`. Required-vs-nullish is a deliberate split, and the
file header's loud-failure policy is why it needs stating: `name` is present on every TBA event, so a
missing one is real drift and should throw. The other four are legitimately absent for offseason,
preseason and non-district events, so `nullish` describes TBA's actual contract rather than coercing a
value. Record that reasoning in a comment on the schema.

**Normalizer.** `CorpusEvent` gains `name: string`, `week: number | null`, `country: string | null`,
`stateProv: string | null`, `districtKey: string | null`. `normalizeEvent` maps each from the TBA
event, collapsing `undefined` to `null` with `?? null` so the corpus never stores the difference
between "absent" and "null".

`districtKey` takes `event.district?.abbreviation` — the short form TBA itself uses (`ne`, `fim`,
`ont`), not `district.key`. This is a planner decision with a concrete reason to record in a comment:
`district.key` is year-prefixed (`2024ne`), and D-11 requires a year change to preserve active
filters, so a year-scoped identifier would silently invalidate every district filter on every year
switch. The abbreviation is stable across seasons and is what an FRC user recognizes.

**Corpus schema and migration.** Add `name TEXT`, `week INTEGER`, `country TEXT`, `state_prov TEXT`
and `district_key TEXT` to the `events` table in `schema.sql`, all nullable. Then add
`hasEventLocationColumns(db)` to `db.ts` — a `PRAGMA table_info(events)` scan mirroring
`hasWinnerImputedColumn` — and, in `openCorpus`, run an idempotent additive migration when it returns
false: one `ALTER TABLE events ADD COLUMN` per missing column, then re-check.

This deliberately diverges from the `winner_imputed` guard, which throws and demands a rebuild.
Document the distinction in the code comment, because a later reader will otherwise see an
inconsistency: `winner_imputed` is a *derived* value, so an existing row's value would be wrong until
recomputed from source, and only a rebuild can produce it. These five are *new source fields* that are
honestly NULL until the very refetch Task 3 runs, and a NULL here is already the schema's legitimate
value. The exception is scoped to additive nullable columns and must not become a general migration
framework.

**Upsert.** Extend `upsertEvent`'s INSERT column list, its `VALUES` bindings and its
`ON CONFLICT DO UPDATE SET` clause with all five, so a re-ingest of an existing event fills them.

**Events-only refresh path.** Add an `--events-only` boolean to `packages/ingest/cli.ts`'s
`parseCliOptions`. When set, the run fetches `/events/{year}` for each year in the requested range
with the cached ETag deliberately bypassed (the same bypass `--force` already performs — a 304 carries
no body, so a conditional request cannot deliver the new fields), upserts every event, writes the new
ETag, and returns without touching teams or per-event matches. Log the per-year event count. This is
what makes filling the new columns cost roughly one request per season instead of a full multi-season
match re-ingest.

**Tests.** In `normalize.test.ts`: a full TBA event maps all five through; an event with
`district: null` yields `districtKey: null`; an event with `week` absent yields `week: null`; a real
district event yields the abbreviation and not the year-prefixed key. In `db.test.ts`: `upsertEvent`
round-trips all five, and a second upsert with changed values overwrites rather than being ignored. In
`integrity.test.ts`: `hasEventLocationColumns` is true for a database created by the current
`schema.sql`, false for one created without the columns, and true again after `openCorpus` runs the
additive migration over that legacy database — proving the migration path, not just the predicate.
