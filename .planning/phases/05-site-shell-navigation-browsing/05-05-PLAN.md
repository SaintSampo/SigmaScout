<objective>
Build the shell every page in Phases 5-8 hangs off: the persistent ribbon, the two global dropdowns,
and the typed URL state that makes any view shareable.

Purpose: NAV-01, NAV-02 and NAV-05 are one mechanism, not three. The dropdowns write to the URL, the
URL is validated once at the root, and every page reads its slice from there — which is exactly why
`.claude/CLAUDE.md` picked a router with typed search params. Getting the shared schema and the
navigation form right here is what stops "the dropdown and the URL disagree" bugs from appearing one
page at a time later.

This plan also owns the one piece of derived logic the research flagged as easy to get half-right: the
sort-key fallback. D-13 names the algorithm switch as its trigger, but the metric-key set is
season-dependent as well as algorithm-dependent, so a plain year change can invalidate a sort too.
One function, both callers.

Output: a validated root search schema, a responsive ribbon, both dropdowns wired to the URL, the
season list, the metric-key derivation, and the shared sort-key resolver — all tested.
</objective>

<assumption_delta_decision>
**Signal:** `chosen` — the Teams table's sort column set stopped being derived from one fixed
algorithm and became chosen per `(algorithm, season)` pair. `05-RESEARCH.md` Pattern 3 establishes
that EPA and Sigma1 derive their component keys from `componentMapForSeason(season)` while OPR
publishes only `total`, so the valid key set varies along two axes, not one.

**The noun that is now primary:** the **metric-key set for an (algorithm, season) pair**. Not "the
algorithm's columns" — that phrasing is what makes the year-change trigger invisible.

**Decision: promote.** `metricKeysFor(algorithmId, season)` is the primary representation and takes
both axes; `resolveSortKey(currentSort, validKeys)` consumes the set rather than an algorithm id, so it
cannot know or care which axis moved. The algorithm-only reading is demoted to one input. The rejected
alternative was add-alongside — an algorithm-switch handler plus a separate year-switch handler — which
`05-RESEARCH.md` explicitly names as the drift risk, and which would have silently contradicted the
generalization by leaving two implementations of one rule.

**Invariant test (adopted):** `resolveSortKey.test.ts` covers both triggers against the same function,
including an EPA 2026-to-2022 year change dropping a component key that exists only in 2026 — the case
D-13's own text never names.
</assumption_delta_decision>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-02 | Tampering | `apps/web/src/lib/searchParams.ts` at the router boundary | medium | mitigate | Every param is parsed by a schema in `validateSearch` before any component reads it: year is coerced and constrained to the known season list, algorithm is an enum over the published ids, direction is an enum, and the sort key is validated against the resolved key set. A malformed or adversarial deep link therefore lands on a defined state or is rejected — it can never reach render logic as a raw string. |
| T-05-04 | Tampering | `apps/web/src/lib/api/manifests.ts` | medium | mitigate | The manifest is schema-parsed at the fetch boundary and merged over the build-time id constant, and an id the constant does not know is ignored rather than rendered — so a tampered or drifted manifest cannot introduce an unknown algorithm into the control or cause an artifact request for an id this phase never published. |
