Simulation tab that offers a picker and a Run button for a simulation that can never produce a rank.

<planner_decisions>

**PD-01 — `resolveActiveTab` takes a named-field options object rather than a second positional
boolean.** The function is module-private, has exactly one call site, and is imported by no test.
Adding `isSimulationDisabled` as a third positional parameter would put two adjacent same-typed
booleans in one call, where a transposition compiles cleanly, type-checks cleanly, and produces a
page that silently disables the wrong tab. The new signature takes `tab` plus one object with two
named fields, which makes a transposition a compile error instead of a rendering bug. The change is
contained to one function and one call site.
— <reversibility rating="reversible">One private function, one call site, no external importer.</reversibility>

**PD-02 — The VPR id is one exported constant, not two string literals in two files.** The route
needs `"vpr"` to derive its disabled boolean and the panel's own contract is defined in terms of the
same id. `publishedAlgorithms.ts` exports the id LIST but no name for the individual id, and
`searchParams.ts`'s `DEFAULT_ALGORITHM` is module-private. `SimulationTab.tsx` therefore exports
`SIMULATION_ALGORITHM_ID` and the route imports it beside the component, so the D-04 rule has one
spelling. This is deliberately not a `isSimulationAlgorithm()` helper — wrapping an inequality in a
function buys nothing the constant does not already give.
— <reversibility rating="reversible">A constant and one import.</reversibility>

**PD-03 — The panel does NOT re-derive the D-04 rule; it does not branch on `algorithmId` at all.**
Radix keeps every `TabsContent` mounted with `hidden`, so `SimulationTab` renders on an OPR event
page too, in a hidden panel the user cannot reach (the trigger is disabled AND `resolveActiveTab`
redirects `?tab=simulation`). A second algorithm check inside the panel would be a second home for
one rule, and two homes for one rule is how they come to disagree. The panel instead answers only
the question it can answer from its own input — does this artifact carry ranking-point
distributions — and renders its unavailable state in the hidden panel. `algorithmId` stays on the
props interface to mirror its four siblings' shape and because 08-11/08-13 will want it, but this
plan reads it for nothing.
— <reversibility rating="reversible">Adding a branch later is additive; removing one that shipped is not.</reversibility>

**PD-04 — The unavailable-state copy states the observable fact first and hedges the cause,
because the artifact cannot confirm the cause.** `EventArtifact` carries `eventKey`, `season`,
`name`, `startDate`, `location`, `week`, `matches`, `upcoming`, `teams` and `alliances` — and no
`eventType`. So the panel genuinely cannot distinguish "offseason, so the ranking-point model has no
rules for it" from any other reason the pmfs are absent. Naming offseason as a certainty would be a
claim the page cannot support; omitting it entirely would leave the reader with a bare refusal.
The copy therefore leads with what is true of the data in front of it and names offseason as the
usual reason, hedged — which is defensible on the population figure (368 corpus events) rather than
on this artifact.
— <reversibility rating="reversible">Copy constants, exported from one module.</reversibility>

**PD-05 — The pmf predicate reads the RAW artifact arrays, not the merged rows.**
`mergeEventMatches` is the right tool for the zero-`qm` branch and this plan uses it there, exactly
as `QualsTab` and `ElimsTab` do. But `EventMatchRow` deliberately carries no pmf pair, and widening
that shared Phase 7 type with a Phase 8 field three plans before any renderer reads it would put a
field on the row model for nobody. `hasSimulatableRankInputs` therefore walks
`artifact.matches`/`artifact.upcoming` directly. If 08-11's input assembly later needs the pmf pair
on the merged row shape, that is 08-11's call to make against its own consumer.
— <reversibility rating="reversible">A predicate over two arrays; widening the row type later is additive.</reversibility>

**PD-06 — The predicate tests the CLASS, not per-row completeness.** "Does any `qm` row across both
arrays carry both pmfs" answers "is this event in the pmf-bearing class at all," which is the only
question this panel's branch needs. Whether every remaining match after a chosen start match carries
one is a sharper question whose answer changes what the Worker receives, and that belongs to 08-11's
`simulationInputs.ts`. Making this predicate stricter here would move a decision into the plan that
cannot act on it, and would produce an unavailable state on an event where the simulation could
legitimately run over the rows that do carry pmfs.
— <reversibility rating="reversible">A predicate's quantifier; 08-11 can narrow its own.</reversibility>

**PD-07 — The shell holds no state.** No selected start match, no run result, no worker handle. The
picker's selection state arrives with the picker (08-11) and the run state with the run control
(08-13), each in the plan that has something to put in it. Scaffolding state three plans before a
consumer means guessing its shape, and a guessed shape is more expensive to unwind than to add.
What the shell DOES establish is the vertical layout stack in UI-SPEC's declared order — picker,
run control, rank table — with a stable testid, so each later plan mounts into a known place rather
than restructuring the panel.
— <reversibility rating="reversible">An empty container with a testid.</reversibility>

**PD-08 — This plan carries no `checkpoint:decision`.** Under `REVERSIBILITY_GATES` a `one-way`
decision earns a gate; nothing here is one-way. Growing a `z.enum` tuple is additive — removing
`simulation` later would make an already-shared `?tab=simulation` link fall through
`EventSearchSchema`'s own `.catch(DEFAULT_EVENT_TAB)` to Insights rather than break, which is the
same safety argument `searchParams.ts` already records for the retired pre-rename algorithm id. No
published contract, no key name and no stored data changes in this plan.

**PD-09 — The three tab-position assertions in `event.$eventKey.test.tsx` are UPDATED, not
deleted.** Two count triggers (`toHaveLength(5)` with a five-name `toEqual`) and one asserts
`tabs.at(-1)?.textContent` is `Elims`. That third one is the easy miss: appending `simulation`
makes Elims no longer last, and the test's own NAME says "appears LAST among the registered
triggers." Its intent — that a newly-registered tab lands in its declared position rather than
wherever the JSX happened to put it — is worth keeping, so it is rewritten to assert Simulation is
last and Elims is fifth, not weakened to drop the position claim.

</planner_decisions>
