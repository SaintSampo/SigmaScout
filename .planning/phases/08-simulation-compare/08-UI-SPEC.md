- **New locked geometry constants** (not on the 4px scale), living together in a new `apps/web/src/lib/simAxis.ts` — mirroring `matchAxis.ts`'s own "every derived position comes from one computed source" discipline (`chart-craft.md`):

  ```js
  var PLOT_W = 470;          // reused verbatim from matchAxis.ts — same visual language, same plot-cell width across the app
  var ROW_PLOT_H = 40;       // the rank-distribution plot cell's total height
  var HIST_BAR_MAX_H = 32;   // leaves 4px top/bottom padding within ROW_PLOT_H
  var MEDIAN_TICK_W = 2;     // solid vertical line width at the median rank
  var BAND_OPACITY = 0.18;   // the 10th-90th percentile overlay, translucent so it never hides the histogram bars underneath it

  function x(rank, teamCount) {
    return ((rank - 1) / (teamCount - 1)) * PLOT_W;   // rank axis: 1..N, N = this event's team count (up to 78 measured)
  }
  ```

  `x()` accepts a **continuous** rank value, not just an integer — the 10th/90th percentile edges it positions are interpolated quantiles (see Simulation Tab Contract section 3), so this function must not floor/round its input before mapping it to a pixel position.

  At the largest measured event (78 teams), each rank position is ~6px wide on a 470px plot — enough for a legible bar, but this MUST be rendered against the real largest event and looked at (`chart-craft.md`'s "render it and look at it" rule) before it ships; see the S3 overflow backstop row below.
- **Progress bar height locked at 8px**, matching the app's existing `BAND_H = 8` visual vocabulary from `uncertainty-display.md` — one more instance of "soft/thin bar = 8px" rather than a new number.
- **Tab strip on mobile stays a horizontally scrollable row** (Phase 7's established pattern, `overflow-x-auto`, `scrollbar-width: none`), now carrying 6 triggers instead of 5. `Simulation` (10 characters) is the longest label in the strip; see the S0 overflow backstop row below for why this still needs a real check rather than an assumption.

## Visual Hierarchy

**Simulation tab.** Primary focal point is the rank-distribution table once results exist — the histogram/band/median plot cells carry the content, matching Phase 7's "the shared-axis plot column carries the content" precedent exactly, generalized from a score axis to a rank axis. Before a run, the primary focal point is the start-match picker + the "Run simulation" button (the accent-colored CTA is the only accent element on the tab pre-run, so it reads clearly as "do this next"). During a run, the progress bar + live counter become the focal point; the picker and rank table both recede (picker becomes read-only/disabled while running, table stays in its pre-run placeholder).

**Compare page.** Primary focal point is the accuracy table — the bolded winner cells are the page's one piece of "look here" typographic emphasis, deliberately restrained (weight only, no colour, per the Color section above), and — per D-11 — **withheld entirely** where the published data cannot establish a real winner, so bold ink on this table always means something. The calibration section's own focal point is its **plain-language sentence, not its chart** (sketch 006, winner C) — the sentence renders at full body ink weight while the chart beneath it renders visually smaller and more muted, genuinely useful as supporting evidence but deliberately demoted because reading a reliability diagram unaided is a skill this audience mostly does not have (08-CONTEXT.md: "calibration is unfamiliar to most of this audience"). The data-coverage table is tertiary — it exists so COMP-01/EVAL-05/D-09's "surfaces everything" obligation is met, not because most visitors will read it first.

**The accent never marks a focal point** — inherited rule, unchanged. It marks interactivity/active-state only (the reserved-for list above).

## Simulation Tab Contract (EVNT-07, D-01…D-07)

### Tab-disabled state (D-04)

Exactly Phase 7 D-17's plain-disabled treatment, reused verbatim: `TabsTrigger disabled` when the selected algorithm is OPR or EPA — visible, greyed (`--color-text-muted`, no background tint, no accent underline), unclickable, **no tooltip, no explanation**. Same accepted cost as D-17: cannot distinguish "you haven't switched to VPR yet" from any other reason. This is deliberate consistency, not an oversight — the site now has exactly one rule for "tab you cannot use."

### Layout, top to bottom

1. **Start-match picker** (a bounded-height scrollable panel, `max-height: 320px`, internal `overflow-y-auto`)
2. **Run control** (button + progress/timer, directly beneath the picker)
3. **Rank-distribution table** (the tab's main content, beneath the run control)

### 1. Start-match picker

A compact, terser sibling of the full `MatchTable` — not the band/tick/dot plot (that would be visual noise for a picker whose only job is "which match"), just enough to identify each match:

| Element | Content |
|---|---|
| Row | One per qualification match, chronological order (reuses the same `compareEventMatchRows`-family ordering `matchAxis.ts` already established) |
| Match label | `matchLabel()` output (`Qual 47`) — same function, no new formatting |
| Teams | Red/blue team-number chips only (no nicknames — deliberately terse; the full roster is one tab away on Insights/Breakdown) |
| Status | A small `Played`/`Upcoming` label, Label 12/600, muted — not a full Call/score column, since the picker's job is "when," not "what happened" |
| Row state | Default (unselected), **selected** (accent left-border + accent-tinted background, per the Color section), and — while a run is in progress — the whole picker is inert (`pointer-events: none`, reduced opacity) so a click mid-run can't silently change the start match under a running simulation |

**Default selection:** the first genuinely-unplayed match, if the event has one (the exact, no-caveat D-01 case). If the event is fully played (the common case — 97% of corpus events per CONTEXT's measurement), **no row is pre-selected**; a hint line above the list reads "Pick a match to simulate from — matches after it are simulated 1000×." (Copywriting Contract.) This is a deliberate choice over defaulting to some arbitrary played match: a rewind default the user didn't choose would be a confusing, unexplained starting point.

**Selecting an already-played row** immediately shows the rewind-honesty caption (D-02) beneath the picker, before the user even presses Run — the caveat belongs to the choice, not just the result.

### 2. Run control

Three states, one region:

| State | Content |
|---|---|
| **Idle** (no run yet, or start match changed since the last run) | "Run simulation" button (disabled until a start match is selected), accent `default` variant |
| **Running** | Determinate progress bar (8px, accent fill, 0–100% mapped from completed/1000 draws reported by the Worker), a live counter (`347 / 1000 draws`) beside it, a ticking elapsed timer (`3.2s elapsed`) beneath it. **No streaming partial results** — the rank table stays in its pre-run placeholder for the full run; a partially-filled histogram would misrepresent an incomplete distribution as a real one, which this app's honesty premise cannot afford. This is a deliberate rejection, recorded so a future contributor doesn't "improve" it into a half-truth. |
| **Complete** | Progress bar and counter are replaced by the completion summary ("Simulated 1000 matches in 2.8s", full-ink weight per Typography) and a "Re-run simulation" button (same accent treatment, relabeled) |
| **Error** (Worker construction fails, or throws mid-run — this is the app's first Web Worker, so this path has no prior art to lean on) | Inline error text ("Simulation failed to run.") + a Retry affordance in the same region — never a silently-stuck progress bar |

**Elapsed-time capture obligation (SC-2):** the same completion-summary figure this UI shows the user is the number the plan must also write into the phase SUMMARY at execution time (08-CONTEXT.md D-07's planner note) — this UI-SPEC's job is only the on-page display; the SUMMARY capture is a plan-level obligation, noted here so it isn't lost between artifacts.

### 3. Rank-distribution table (D-05, D-06)

Columns:

| Column | Content | Notes |
|---|---|---|
| Team # | Links to `/team/{teamNumber}` | pinned |
| Nickname | Truncates + `title`, same rule as every other team-name cell | pinned |
| Median | Plain `numeric-cell` integer | Sort key — table is sorted by median rank, ascending |
| Distribution | The band+histogram plot cell (see Spacing Scale geometry) | The tab's entire reason for existing |

**No "probability of top 8" / captain column** — explicitly dropped (D-06), do not add one back.

**Band edges are interpolated (continuous), not integer-snapped — sketch 005's winning decision, binding.** Treat rank `r`'s probability mass as occupying `[r-0.5, r+0.5)`, spread uniformly inside, which makes the empirical CDF piecewise-linear and the 10th/90th quantile continuous (R's default type-7 estimator applied to the 1000 binned draws, not a bespoke smoothing curve). Reference implementation: `continuousQuantile()` in the sketch's `sources/005-rank-distribution/index.html` — port that algorithm (a new `apps/web/src/lib/simQuantile.ts` is a reasonable home), do not reinvent it. An edge is bounded by construction between `0.5` and `N+0.5`, so it can never imply a rank that doesn't exist.

Measured against real corpus data, integer snapping produced three concrete defects this contract exists to prevent:

| | Integer-snapped | Interpolated |
|---|---|---|
| A locked team (3467 @ 2023nhgrs) | `1–1`, width **0 — invisible** | `0.60–1.40`, width 0.80 |
| Team 95 @ 2023nhgrs | `2–3`, width 1 | `1.65–3.20`, width 1.55 |
| Team 4564 @ 2023nhgrs | `2–3`, width 1 | `1.80–3.49`, width 1.69 |

1. Locked teams vanish — a zero-width band is invisible on screen (2 of 39 rows at `2023nhgrs`, 3 of 42 at `2025flta`, drew a zero-width band under integer snapping).
2. Genuinely different distributions can render as identical integer bands (95 vs 4564 above), hiding a real difference between two teams.
3. Up to a full rank of quantization error at each edge.

**The distribution plot cell, one shared axis (rank 1..N) drawn once in a header row** (same "axis drawn once" rule as `uncertainty-display.md`'s match table):

- **Histogram bars** (`--sim-hist-bar` fill) — one thin bar per rank position, height proportional to how many of the 1000 draws landed there, capped at `HIST_BAR_MAX_H`. This is the layer that makes bimodality visible (08-CONTEXT.md D-05: "a team that either captains or misses entirely looks identical to a steady mid-pack team under summary statistics alone") — a team with two humps shows two humps.
- **10th–90th percentile band** (`--sim-band-overlay`, translucent, full `ROW_PLOT_H` height, spanning `x(p10)` to `x(p90)` where `p10`/`p90` are the **interpolated, non-integer** quantiles computed above, not integer bucket edges) — overlaid on top of the histogram, not beside it, so the reader sees "this is the middle 80% of that same distribution" in one glance rather than reconciling two separate marks.
- **Median tick** (`--sim-median-tick`, `MEDIAN_TICK_W` wide, full `ROW_PLOT_H` height) — the single reference line, drawn last so it's never obscured.
- **Never labelled with a `±` glyph anywhere** — the band's text label (beside the plot, Label 12/600 muted) reads `10th–90th: {p10}–{p90}`, one decimal place (e.g. `10th–90th: 1.7–3.2`), an explicit interpolated range, never `±N` and never rounded to an integer. This is D-05's binding constraint, restated here so it can't be missed by a component author reaching for the app's existing `MetricValue` primitive out of habit (that primitive prints `±` by construction and must NOT be reused for this column).
- **Never give the row its own scale** — one shared `1..N` axis for the whole table, drawn once in the header. Rejected outright by the user on sight in sketch 005 ("terrible"); the shared-scale rule already established in `uncertainty-display.md` for the match-prediction bands holds here too.
- **Do not clip the shared axis to "the union of occupied ranks."** Every one of the 1000 draws assigns each team to exactly one of the N ranks, so every rank column is always occupied by somebody — clipping the axis is a mathematical no-op that reclaims zero pixels on a full-field table (measured: exactly 1000 draws per rank, every rank, across all three sketch-tested events). It can only help on a genuinely partial roster (one team plus neighbours), which is a different feature, not this table.

**Mock-before-build obligation (`chart-craft.md`, carried forward from 08-CONTEXT.md's planner note and sharpened by sketch 005):** before this component ships, mock the histogram AND the interpolated-quantile calculation against a REAL 1000-draw distribution from a real event (not a synthetic/uniform-looking sample) — the same discipline that caught sketch 004's top-of-table tier problem. Sketch 005 found the real defects lived in the **edge-computation choice**, not just the chart's rendering, so the mock must exercise `continuousQuantile()` itself against real draws, not only eyeball the finished bars. A convenient, evenly-spread fake distribution will validate a layout that a real, often-lopsided one disproves. Also do not generalise from the top of the table alone — sketch 005's own session sampled the first 12 rows, wrongly concluded near-universal 1-rank spreads, and was off by a factor of three; measure every row.

### compLevel switcher

### Accuracy table (D-08, D-11)

One uniform table, 5 rows (2022–2026, ascending, no visual grouping by tune/holdout — D-08 is explicit that presentation must not tier or group by season label), column-grouped by algorithm — **season rows, algorithm columns**, the sketch-007 winning shape:

| Year | OPR Winner Accuracy | OPR Brier | EPA Winner Accuracy | EPA Brier | VPR Winner Accuracy | VPR Brier |
|---|---|---|---|---|---|---|

- Every numeric cell is a plain `numeric-cell`, Body 14/400.
- **No per-algorithm identity colour anywhere on this table** — inherited constraint, restated by sketch 007: the palette is already spent (alliance red/blue, rarity sky/purple/amber, percentile-tier teal/cyan/indigo/slate, win/loss green/rose). Labelled, spatially-separated columns disambiguate the three algorithms without a fourth hue.
- **Per row, the highest Winner Accuracy cell and the lowest Brier Score cell render at weight 600 — but only when a winner is real, per D-11.** Two tie tests, one per metric, both computed, never eyeballed:
  - **Brier Score:** compare the values as they will actually be *displayed* (4 decimal places). If the leading and next-best cells round to the same displayed digits (e.g. 2022 elimination: OPR `0.14721` vs VPR `0.14717`, both display `0.1472`), render both at plain weight — bolding one over a number that looks identical on screen reads as a rendering bug, not a result.
  - **Winner Accuracy:** compute each algorithm's naive standard error, `SE = sqrt(p·(1−p) / n)` where `p` is that cell's winner-accuracy fraction and `n` is that cell's `scoredCount`; combine the two leading cells' SEs as `sqrt(SE_a² + SE_b²)` (this treats the two algorithms as independent — a known simplification, not a paired test, and D-11 says so explicitly). If the gap between the leading and next-best cell is smaller than that combined SE, render both at plain weight. This is exactly the arithmetic behind D-11's own worked example — 2022/2024/2025 elimination gaps of 1.06pp/0.02pp/0.25pp, each inside a 1.10–1.20pp naive-SE band.
  - **Above both thresholds, exactly one cell bolds, as before.** A genuine display-precision tie (identical rounded values with zero computed gap) bolds both.
  - **Never grey a "losing" cell.** This app's existing rule (`chart-craft.md`: "grey the loser's number, never its mark") assumes a loser exists; D-11 is explicit that below threshold, the published data cannot establish one, so nothing on this table is ever greyed to imply defeat — only the bold/plain distinction moves.
- Brier's column header carries `(lower is better)` as part of the header text (Copywriting Contract) — this app's audience should not need outside knowledge of what a Brier score is to read the table correctly.
- **No `seasonLabel`/`headlineEligible` tiering, grouping, row-striping-by-tune-vs-holdout, or asterisk system anywhere on this table** — D-08's binding constraint. That distinction lives in the methodology note below, in prose, not encoded into the table's visual structure.
- **A short caption beneath the table (or folded into the methodology note) must state, in plain language, that the near-tie threshold is a judgement call, not a computed statistical-significance level** — D-11's binding requirement, so no reader mistakes "both cells plain" for "these are formally proven equal." Exact copy in the Copywriting Contract below.
- **Known and accepted, inherited from sketch 007 (winner A):** this table does not reflow at 390px; it scrolls horizontally inside the same `.tablewrap` pattern and scroll-arbitration guarantees Phase 7's e2e suite already established for every other wide table on this site (only the table pans, never the page) — reuse that wiring verbatim rather than reinventing scroll handling for this one table.

### Calibration section (D-09), plain-language-first (sketch 006, winner C)

- **Section heading:** "Calibration" (Heading 20/600, same weight as the page title's sub-sections — no Display scale).
- **Primary content is a single plain-language sentence, not the chart.** Sketch 006's winning treatment demotes the reliability chart to supporting evidence beneath the sentence, because judging distance from a 45° line is a learned skill this audience (FRC students, mentors, scouts) mostly does not have. Sentence template (Copywriting Contract): `"{Algorithm} predicted {predictedPct}%, and it was right {observedPct}% of the time across {count} matches."` — e.g. the case that justifies this whole section's existence: 2026 qualification, OPR predicted 85.3%, observed 52.8% across 395 matches, a 32.5pp overconfidence gap that OPR's headline accuracy (74.8%, only four points behind VPR) hides completely.
- **Which bin the sentence describes:** on load, the bin with the largest `|predicted − observed|` gap for the currently-selected algorithm/year/compLevel (ties broken by the higher sample count, so a one-match fluke never wins the headline over a well-populated bin). Hovering or clicking any point on the chart below replaces the sentence with that point's own fact — the chart becomes an explorable index into more sentences, not the primary reading surface.
- **Algorithm selection for the sentence:** the sentence describes one algorithm's line at a time; the existing `OPR`/`EPA`/`VPR` legend, made clickable, doubles as the switcher (no new control needed). Default to VPR, the algorithm most readers arrive already curious about.
- **Sparse-bin encoding is mandatory, not decorative.** Bin sample counts range from a single match to 5,950 in the corpus. Each chart point's radius scales with its own bin's sample count, so a single-match bin visibly shrinks rather than reading with the same visual authority as a 5,950-match bin — this is what keeps the chart truthful rather than decoration on top of the sentence. **Never hide a sparse bin** — shrink it, and let the sentence's printed `{count}` carry the rest of the honesty when that bin is the one selected.
- **Chart is visually secondary** — smaller and more muted than the sentence above it, per the Visual Hierarchy section — supporting evidence, not the section's headline.
- **Year selector:** a `Select`, local to this page (not the global ribbon dropdown — see the exception above), defaulting to the most recent year (2026). Reading all 5 years' calibration curves at once (5 years × 3 algorithms × 10 bins = up to 15 overlapping lines) would be unreadable spaghetti; a single-year, 3-line view stays legible while the selector still reaches every year D-09 requires to be "surfaced."
- **Chart:** Recharts line chart, x-axis = predicted-probability bin midpoints (10 bins), y-axis = observed frequency (0–100%), three lines (OPR/EPA/VPR), plus a dashed neutral diagonal reference line (`--color-border`, "perfect calibration"). Filtered by the shared compLevel state from the switcher above.
- **Series colors — fixed, sketch-validated (see Color section):** `--compare-algo-opr` (`#EA580C`), `--compare-algo-epa` (`#7C3AED`), `--compare-algo-vpr` (`#0D9488`).
- Legend: `OPR`/`EPA`/`VPR`, matching the ribbon's own algorithm labels (D-05 rename already in force site-wide since Phase 7); as noted above, the legend also serves as the sentence's algorithm switcher.
- **The concept-level plain-language explainer stays** (exact copy in the Copywriting Contract) — this audience is calibration-unfamiliar per 08-CONTEXT.md, so the explainer still earns its place, but it is now secondary framing beneath the concrete sentence, not the section's primary content.

### Data-coverage-per-year section (D-09)

- **Section heading:** "Data coverage per year"
- **Explainer**, Body 14/400 muted, carrying D-09's careful wording exactly (Copywriting Contract) — offseason matches feed the model but are excluded from scoring; this must never read as "offseason events are ignored."
