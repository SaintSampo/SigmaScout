**Exceptions:**

- **New locked geometry constants** (not on the 4px scale), living together in a new `apps/web/src/lib/simAxis.ts` — mirroring `matchAxis.ts`'s own "every derived position comes from one computed source" discipline (`chart-craft.md`):

  ```js
  var PLOT_W = 470;          // reused verbatim from matchAxis.ts — same visual language, same plot-cell width across the app
  var ROW_PLOT_H = 40;       // the rank-distribution plot cell's total height
  var HIST_BAR_MAX_H = 32;   // leaves 4px top/bottom padding within ROW_PLOT_H
  var MEDIAN_TICK_W = 2;     // solid vertical line width at the median rank
  var BAND_OPACITY = 0.18;   // the 10th-90th percentile overlay, translucent so it never hides the histogram bars underneath it

  function x(rank, teamCount) {
    return ((rank - 1) / (teamCount - 1)) * PLOT_W;   // rank axis: 1..N, N = this event's team count (up to 78 measured)
  }
  ```

  At the largest measured event (78 teams), each rank position is ~6px wide on a 470px plot — enough for a legible bar, but this MUST be rendered against the real largest event and looked at (`chart-craft.md`'s "render it and look at it" rule) before it ships; see the S3 overflow backstop row below.
- **Progress bar height locked at 8px**, matching the app's existing `BAND_H = 8` visual vocabulary from `uncertainty-display.md` — one more instance of "soft/thin bar = 8px" rather than a new number.
- **Tab strip on mobile stays a horizontally scrollable row** (Phase 7's established pattern, `overflow-x-auto`, `scrollbar-width: none`), now carrying 6 triggers instead of 5. `Simulation` (10 characters) is the longest label in the strip; see the S0 overflow backstop row below for why this still needs a real check rather than an assumption.

| Label | 12px | 600 | 1.3 |
| Heading | 20px | 600 | 1.2 |

Two weights only: 400 (regular) and 600 (semibold) — no 500 or 700 anywhere.

**This phase's usage additions:**

- **Compare table numeric cells:** Body 14/400, `numeric-cell` (tabular figures), matching every prior numeric table in the app — **except** the per-row winner (highest Winner Accuracy, lowest Brier Score) which renders at weight 600 within the same 14px size. This is the one place this phase uses weight, not colour or a new token, to surface a pattern — see Color section for why colour was rejected for this job.
- **Run-control live text** (`347 / 1000 draws`, `2.8s elapsed`): Body 14/400, `numeric-cell` for the numerals, `--color-text-muted` — same visual weight as every other secondary status line in the app (e.g. the team page's record/win-rate line).

## Color

Inherited unchanged from `05-UI-SPEC.md`'s 60/30/10 split — **no `--color-*`/`--accent`/`--alliance-*`/`--tier-*` VALUE changes this phase** (08-CONTEXT.md's binding constraint).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#F8FAFC` (slate-50) | Page background |
| Secondary (30%) | `#F1F5F9` (slate-100) | Section card backgrounds (run-control panel, Compare's calibration/data-coverage sections), disabled-tab background tint |
| Accent (10%) | `#4F46E5` (indigo-600, `--color-accent` = `--color-primary`) | See extended reserved-for list below |
| Destructive | `#DC2626` (red-600) | Error-state icon/text, retry-button border, S2's simulation-failure error state — never for the rewind-honesty caption (that is a method disclosure, not an error) |

**Accent reserved for (extends Phase 5/6/7's list — same token, no new hex, additive elements only):** the active tab indicator underline (now on a 6-tab strip), the "Run simulation"/"Re-run simulation" button (shadcn `Button`'s `default` variant, which is already `bg-primary` = `--color-accent` site-wide — this is the button's existing default treatment, not a new accent use invented for this phase), the progress bar's fill, the selected start-match picker row's left border + background tint, focus rings on every interactive control, the Compare page's active compLevel-switcher segment. **Never used for:** the rank-distribution band/histogram (see below — deliberately neutral, not accent, so it reads as data not as an interactive affordance), alliance identity, tier boxes, body text, or any static surface.

**Two locked color systems, unchanged, reused exactly as Phase 6/7 shipped them (no alliance or tier concept exists on either new surface, so neither actually renders on this page — listed only so the "no value changes" claim above is checkable):**

```css
--alliance-red:  #DC2626;   --alliance-blue: #2563EB;   --loser-ink: #94A3B8;
--tier-rare-bg:  #E0F2FE;   --tier-epic-bg:  #F3E8FF;   --tier-legendary-bg: #FEF3C7;
```

**New purpose-specific tokens, derived from existing neutrals (not new hues — "polish within the existing system," per 08-CONTEXT.md's explicit license), for the rank-distribution plot cell:**

```css
--sim-hist-bar:     color-mix(in srgb, var(--color-text-muted) 55%, transparent);
--sim-band-overlay: color-mix(in srgb, var(--color-text-muted) 18%, transparent);
--sim-median-tick:  var(--color-text-primary);
```

Rationale: the histogram/band/tick vocabulary generalizes `uncertainty-display.md`'s "soft band → solid tick" pattern from a score axis to a rank axis, but a rank distribution is not a win-probability comparison between two alliances — there's no "identity" to colour-code (unlike the red/blue match plot), so it deliberately stays in neutral ink rather than reaching for the accent or inventing a new hue. This keeps the accent's "marks interactivity only" rule (Phase 7's Visual Hierarchy rule, inherited) intact: nothing on this static distribution chart is clickable, so nothing on it is accent-colored.

**Calibration chart series colors (Compare page):** pull the three algorithm-identity line colors from the **dataviz skill's already-validated default categorical palette** (`references/palette.md`), not new hex values invented for this phase — that palette exists precisely to avoid clashing with domain colors (alliance red/blue) or the tier palette (sky/purple/amber), per `chart-craft.md`'s "chrome hues should avoid both so they never compete." **Binding obligation carried to the checker:** run the dataviz skill's `validate_palette.js` against the three chosen series colors AND confirm no collision with `--alliance-*`/`--tier-*` before this ships — do not hand-pick and eyeball it (`chart-craft.md`: "Colour is computable — compute it").

**Call-column-style bold-vs-plain distinction on the Compare table** (see Typography) is a weight change, deliberately not a color change — a "winner" tint would need a 4th semantic color this app doesn't have, and would collide with the existing "colour carries tier/confidence/win-loss/alliance meaning, never decoration" rule (`SKILL.md`), since a Compare-table cell has none of those four meanings.

## Visual Hierarchy

**Simulation tab.** Primary focal point is the rank-distribution table once results exist — the histogram/band/median plot cells carry the content, matching Phase 7's "the shared-axis plot column carries the content" precedent exactly, generalized from a score axis to a rank axis. Before a run, the primary focal point is the start-match picker + the "Run simulation" button (the accent-colored CTA is the only accent element on the tab pre-run, so it reads clearly as "do this next"). During a run, the progress bar + live counter become the focal point; the picker and rank table both recede (picker becomes read-only/disabled while running, table stays in its pre-run placeholder).

**Compare page.** Primary focal point is the accuracy table — the bolded winner cells are the page's one piece of "look here" typographic emphasis, deliberately restrained (weight only, no colour, per the Color section above). The calibration chart is secondary — genuinely useful but the audience-unfamiliarity risk (08-CONTEXT.md: "calibration is unfamiliar to most of this audience") means it earns a plain-language explainer rather than visual prominence. The data-coverage table is tertiary — it exists so COMP-01/EVAL-05/D-09's "surfaces everything" obligation is met, not because most visitors will read it first.

**The accent never marks a focal point** — inherited rule, unchanged. It marks interactivity/active-state only (the reserved-for list above).

## Simulation Tab Contract (EVNT-07, D-01…D-07)

### Tab-disabled state (D-04)

Exactly Phase 7 D-17's plain-disabled treatment, reused verbatim: `TabsTrigger disabled` when the selected algorithm is OPR or EPA — visible, greyed (`--color-text-muted`, no background tint, no accent underline), unclickable, **no tooltip, no explanation**. Same accepted cost as D-17: cannot distinguish "you haven't switched to VPR yet" from any other reason. This is deliberate consistency, not an oversight — the site now has exactly one rule for "tab you cannot use."

### Layout, top to bottom

1. **Start-match picker** (a bounded-height scrollable panel, `max-height: 320px`, internal `overflow-y-auto`)
2. **Run control** (button + progress/timer, directly beneath the picker)
3. **Rank-distribution table** (the tab's main content, beneath the run control)

### 1. Start-match picker

A compact, terser sibling of the full `MatchTable` — not the band/tick/dot plot (that would be visual noise for a picker whose only job is "which match"), just enough to identify each match:

| Element | Content |
|---|---|
| Row | One per qualification match, chronological order (reuses the same `compareEventMatchRows`-family ordering `matchAxis.ts` already established) |
| Match label | `matchLabel()` output (`Qual 47`) — same function, no new formatting |
| Teams | Red/blue team-number chips only (no nicknames — deliberately terse; the full roster is one tab away on Insights/Breakdown) |
| Status | A small `Played`/`Upcoming` label, Label 12/600, muted — not a full Call/score column, since the picker's job is "when," not "what happened" |
| Row state | Default (unselected), **selected** (accent left-border + accent-tinted background, per the Color section), and — while a run is in progress — the whole picker is inert (`pointer-events: none`, reduced opacity) so a click mid-run can't silently change the start match under a running simulation |

**Default selection:** the first genuinely-unplayed match, if the event has one (the exact, no-caveat D-01 case). If the event is fully played (the common case — 97% of corpus events per CONTEXT's measurement), **no row is pre-selected**; a hint line above the list reads "Pick a match to simulate from — matches after it are simulated 1000×." (Copywriting Contract.) This is a deliberate choice over defaulting to some arbitrary played match: a rewind default the user didn't choose would be a confusing, unexplained starting point.

**Selecting an already-played row** immediately shows the rewind-honesty caption (D-02) beneath the picker, before the user even presses Run — the caveat belongs to the choice, not just the result.

### 2. Run control

Three states, one region:

| State | Content |
|---|---|
| **Idle** (no run yet, or start match changed since the last run) | "Run simulation" button (disabled until a start match is selected), accent `default` variant |
| **Running** | Determinate progress bar (8px, accent fill, 0–100% mapped from completed/1000 draws reported by the Worker), a live counter (`347 / 1000 draws`) beside it, a ticking elapsed timer (`3.2s elapsed`) beneath it. **No streaming partial results** — the rank table stays in its pre-run placeholder for the full run; a partially-filled histogram would misrepresent an incomplete distribution as a real one, which this app's honesty premise cannot afford. This is a deliberate rejection, recorded so a future contributor doesn't "improve" it into a half-truth. |
| **Complete** | Progress bar and counter are replaced by the completion summary ("Simulated 1000 matches in 2.8s", full-ink weight per Typography) and a "Re-run simulation" button (same accent treatment, relabeled) |
| **Error** (Worker construction fails, or throws mid-run — this is the app's first Web Worker, so this path has no prior art to lean on) | Inline error text ("Simulation failed to run.") + a Retry affordance in the same region — never a silently-stuck progress bar |

**Elapsed-time capture obligation (SC-2):** the same completion-summary figure this UI shows the user is the number the plan must also write into the phase SUMMARY at execution time (08-CONTEXT.md D-07's planner note) — this UI-SPEC's job is only the on-page display; the SUMMARY capture is a plan-level obligation, noted here so it isn't lost between artifacts.

### 3. Rank-distribution table (D-05, D-06)

Columns:

| Column | Content | Notes |
|---|---|---|
| Team # | Links to `/team/{teamNumber}` | pinned |
| Nickname | Truncates + `title`, same rule as every other team-name cell | pinned |
| Median | Plain `numeric-cell` integer | Sort key — table is sorted by median rank, ascending |
| Distribution | The band+histogram plot cell (see Spacing Scale geometry) | The tab's entire reason for existing |

**No "probability of top 8" / captain column** — explicitly dropped (D-06), do not add one back.

**The distribution plot cell, one shared axis (rank 1..N) drawn once in a header row** (same "axis drawn once" rule as `uncertainty-display.md`'s match table):

- **Histogram bars** (`--sim-hist-bar` fill) — one thin bar per rank position, height proportional to how many of the 1000 draws landed there, capped at `HIST_BAR_MAX_H`. This is the layer that makes bimodality visible (08-CONTEXT.md D-05: "a team that either captains or misses entirely looks identical to a steady mid-pack team under summary statistics alone") — a team with two humps shows two humps.
- **10th–90th percentile band** (`--sim-band-overlay`, translucent, full `ROW_PLOT_H` height, spanning `x(p10)` to `x(p90)`) — overlaid on top of the histogram, not beside it, so the reader sees "this is the middle 80% of that same distribution" in one glance rather than reconciling two separate marks.
- **Median tick** (`--sim-median-tick`, `MEDIAN_TICK_W` wide, full `ROW_PLOT_H` height) — the single reference line, drawn last so it's never obscured.
- **Never labelled with a `±` glyph anywhere** — the band's text label (beside the plot, Label 12/600 muted) reads `10th–90th: {p10}–{p90}`, an explicit range, never `±N`. This is D-05's binding constraint, restated here so it can't be missed by a component author reaching for the app's existing `MetricValue` primitive out of habit (that primitive prints `±` by construction and must NOT be reused for this column).

**Mock-before-build obligation (`chart-craft.md`, carried forward from 08-CONTEXT.md's planner note):** before this component ships, mock the histogram against a REAL 1000-draw distribution from a real event (not a synthetic/uniform-looking sample) — the same discipline that caught sketch 004's top-of-table tier problem. A convenient, evenly-spread fake distribution will validate a layout that a real, often-lopsided one disproves.

## Compare Page Contract (COMP-01, EVAL-05, D-08…D-10)

### Global-dropdown exception (Claude's Discretion, resolved here)

The Compare page **does not filter by the ribbon's global year or algorithm dropdowns.** This is a deliberate, documented exception to NAV-02's usual "changing either re-slices the current page immediately" rule: D-08's entire point is showing every algorithm across every year at once, so there is nothing on this page for a single year/algorithm selection to slice. The ribbon dropdowns stay visible and functional (for navigating to other pages), but have no visible effect on Compare's own content. This is the same category of documented exception Phase 7 recorded for its own cross-cutting reaches — named outright rather than left to look like an oversight.

### Layout, top to bottom

1. Page title ("Compare", Heading 20/600)
2. compLevel switcher (Combined / Qualification / Elimination) — one shared filter driving both the accuracy table and the calibration section below it
3. Accuracy table (D-08, D-09)
4. Methodology note (D-08)
5. Calibration section (D-09)
6. Data-coverage-per-year section (D-09)

### compLevel switcher

Three segments, `Combined` (default) / `Qualification` / `Elimination` — a segmented control (three `Button`s in a `ButtonGroup`-style row, or `Tabs` styled as a switcher; either is fine, not prescribed further since no new visual language is needed). **One state, two consumers**: the accuracy table and the calibration chart both derive from the same selected compLevel, never two independent controls that could disagree (`chart-craft.md`'s "derive coupled geometry" principle, generalized here from pixel geometry to page state).

**Why this switcher earns its place, not just "more data":** in 2025, OPR beats EPA on elimination matches (Brier 0.1767 vs 0.1897) while losing badly on quals (0.2192 vs 0.1950) — a real, opposite-direction finding a combined-only table would erase (08-CONTEXT.md D-09). The switcher is how a reader finds that.

### Accuracy table (D-08)

One uniform table, 5 rows (2022–2026, ascending, no visual grouping by tune/holdout — D-08 is explicit that presentation must not tier or group by season label), column-grouped by algorithm:

| Year | OPR Winner Accuracy | OPR Brier | EPA Winner Accuracy | EPA Brier | VPR Winner Accuracy | VPR Brier |
|---|---|---|---|---|---|---|

- Every numeric cell is a plain `numeric-cell`, Body 14/400.
- **Per row, the highest Winner Accuracy cell and the lowest Brier Score cell render at weight 600** (see Typography/Color — a weight distinction, not a colour one). Ties render both cells at 600.
- Brier's column header carries `(lower is better)` as part of the header text (Copywriting Contract) — this app's audience should not need outside knowledge of what a Brier score is to read the table correctly.
- **No `seasonLabel`/`headlineEligible` tiering, grouping, row-striping-by-tune-vs-holdout, or asterisk system anywhere on this table** — D-08's binding constraint. That distinction lives in the methodology note below, in prose, not encoded into the table's visual structure.

### Methodology note (D-08)

A single Body 14/400 muted paragraph directly beneath the table (not a tooltip, not collapsed behind a disclosure toggle — D-08's "single methodology note" framing reads as always-visible):

> "VPR's hyperparameters were tuned only on 2022–2024 ('tune' seasons); 2025 and 2026 are true holdout seasons the tuning process never saw. If the fixed split were flattering VPR, holdout years would score visibly worse than tune years — they don't. Tune-season Brier: 0.1592 / 0.1687 / 0.1761. Holdout-season Brier: 0.1617 / 0.1501 — 2026, a holdout year, is VPR's single best season of the five."

(Exact figures per 08-CONTEXT.md D-08; if the numbers on record differ at implementation time because of a re-measurement, use the current committed artifact's numbers, not these — the sentence structure is what's contractual, not the literal digits.)

### Calibration section (D-09)

- **Section heading:** "Calibration" (Heading 20/600, same weight as the page title's sub-sections — no Display scale)
- **Plain-language explainer**, Body 14/400 muted, directly beneath the heading (Copywriting Contract has the exact text) — this is the section CONTEXT.md flags as needing to work for readers unfamiliar with the concept, so the explainer is not optional decoration.
- **Year selector:** a `Select`, local to this page (not the global ribbon dropdown — see the exception above), defaulting to the most recent year (2026). Reading all 5 years' calibration curves at once (5 years × 3 algorithms × 10 bins = up to 15 overlapping lines) would be unreadable spaghetti; a single-year, 3-line view stays legible while the selector still reaches every year D-09 requires to be "surfaced."
- **Chart:** Recharts line chart, x-axis = predicted-probability bin midpoints (10 bins), y-axis = observed frequency (0–100%), three lines (OPR/EPA/VPR, colors per the Color section above), plus a dashed neutral diagonal reference line (`--color-border`, "perfect calibration"). Filtered by the shared compLevel state from the switcher above.
- Legend: `OPR`/`EPA`/`VPR`, matching the ribbon's own algorithm labels (D-05 rename already in force site-wide since Phase 7).

### Data-coverage-per-year section (D-09)

- **Section heading:** "Data coverage per year"
- **Explainer**, Body 14/400 muted, carrying D-09's careful wording exactly (Copywriting Contract) — offseason matches feed the model but are excluded from scoring; this must never read as "offseason events are ignored."
- **Table**, 5 rows (2022–2026), columns: Candidate matches, Scored matches, Offseason excluded, Surrogate-affected excluded, Missing-result excluded, Quarantined excluded, Ties, No-calls — every field `exclusionCounts`/`candidateCount`/`scoredCount`/`tieCount`/`noCallCount` carries (D-09's "surfaces everything" obligation), filtered by the shared compLevel state.
