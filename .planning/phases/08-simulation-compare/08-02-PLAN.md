<planner_decisions>

- **PD-01 — `EventMatchSchema` becomes a refine-chained schema, and the refine pair is COPIED rather than
  written.** The two `isValidPmf` refines on `EventUpcomingMatchSchema` are reproduced with the identical
  predicate call, the identical message string and the identical `path` array. A second validator, or the
  same rule with a reworded message, would be two enforcements of one contract that can disagree about what
  a valid distribution is — and there would then be four of them in this repo, since `predictions.ts`'s
  `PredictionRecordSchema` carries its own deliberate copy for the sidecar. Verified safe: `EventMatchSchema`
  is not exported and its only reference anywhere in the repo is inside `z.array(...)` at
  `EventArtifactSchema.matches` (`pageArtifacts.ts:870`) — no `.extend()`, no `.shape` access, no `.pick()` —
  so the conversion from a bare object schema to a refine-chained one breaks nothing.
  **Reversibility: costly** (a published field; removing it costs a republish).

- **PD-02 — the pmf pair is mirrored UNGATED, and a playoff row's shape therefore DOES change.** The
  approved outline expected a playoff row to be unchanged. That expectation is corrected here on evidence,
  not overruled on preference. `rpPmfForMatch` short-circuits every non-qualification competition level to a
  degenerate one-entry distribution rather than to an empty array, and sigma1's `predict()` spreads any
  non-empty pmf onto the returned `Prediction` — so a playoff `Prediction` carries a real one-entry pmf, the
  `upcoming` builder has always published it ungated, and `buildTeamSeasonArtifact` publishes it ungated too.
  **Live-verified 2026-08-30** against `v1/team/frc254/2025/vpr@2.1.0+tuned-2026-08.json`: `2025cada_sf1m1`
  carries a single-entry red and blue pmf and a real integer zero on both actual-RP keys. Gating this one new
  site on the competition level would make the event artifact's played rows the only surface in the pipeline
  that omits what the model returned — a fourth convention where three already agree. Measured cost of NOT
  gating, at the largest event: **465 bytes**, 0.14% of the artifact and 6% of the remaining headroom. That is
  not a price worth a divergence. Note the deliberate contrast with `redBonusRp`/`actualRedBonusRp`, which ARE
  gated on the competition level in `buildTeamSeasonArtifact`: those are per-bonus claims about a ranking point
  FRC never awards in eliminations, whereas a one-entry pmf is the model's own honest statement that this match
  awards none. The existing distinction is preserved, not flattened. **Reversibility: costly.**

- **PD-03 — the actual-RP pair routes through `toIntegerRpOrNull`, and that is load-bearing rather than
  stylistic.** `MatchResult.redRpEarned` is sourced from corpus columns SQLite's loose type affinity does not
  enforce as integers. `.planning/WINDOWS.md` ledger **#14** records exactly this value class — Oregon
  BunnyBots' self-reported non-FRC ranking points at `2024orbb`/`2025orbb`, 30 rows — throwing
  `TeamSeasonMatchSchema`'s integer assertion and **blocking 07-17's `--include-offseason` full republish
  outright**. `08-05` runs the same command with the same flag against the same corpus. Reading
  `match.redRpEarned` raw here would reintroduce a known abort with a known trigger into a 23-to-25-minute
  run. The guard degrades to `null` — D-12's own "not derivable" value — rather than rounding a fabricated
  count into existence. **Reversibility: reversible** (a publisher-side guard; the field it feeds is not).

- **PD-04 — both actual-RP fields are assigned DIRECTLY, never conditionally spread, and that asymmetry with
  the `rank`/`record`/`rp` triple is deliberate.** `eventTeamRankingFields` uses conditional spreads because a
  team row genuinely may have no ranking entry at all, and an absent key is the honest representation.
  Here every row in `params.predictions` is a played match by construction — the builder already assigns
  `actualWinner`, `actualRedScore` and `actualBlueScore` unconditionally from it — so the fact always exists
  and the only question is whether it is derivable. A direct assignment publishes `null` when it is not,
  which means a post-republish played row ALWAYS carries both keys. That is what gives 08-11 a working
  discriminator: key absent means the artifact predates the field, key present with `null` means the pipeline
  looked and found nothing. A conditional spread would collapse those two into one indistinguishable state
  and give 08-11 no way to recover the difference. This mirrors `buildTeamSeasonArtifact`'s own played branch
  exactly. **Reversibility: costly** (changing this later changes published bytes).

- **PD-05 — no new `ROUNDING_RULE` key, and both no-entry dispositions are written into `rounding.ts`'s own
  enumeration.** The pmf pair reuses `ROUNDING_RULE.pmf` through the existing `roundPmf`; that rule's header
  table already names Phase 8's 1000-run simulation as the reason it sits at five decimals, so it was written
  anticipating this exact field and a second key would be drift wearing documentation's clothes. The actual-RP
  pair is integral by construction and published unrounded, exactly as `TeamSeasonMatchSchema`'s pair already
  is. Neither needs a key — but `rounding.ts`'s prose explicitly ENUMERATES the fields that get no entry, and
  an enumeration that silently stops being complete is the same drift class this project's failure log already
  names. Task 3 extends both paragraphs by name. Because no key is added, `rounding.test.ts`'s exhaustive
  key-set assertion stays green and that file is deliberately not in this plan's diff.
  **Reversibility: reversible.**

- **PD-06 — every new-field test asserts on the PARSED or BUILT value, never on `.parse()` not throwing.**
  Inherited verbatim from 07-07 PD-10 because the failure mode is unchanged: Zod object schemas strip unknown
  keys silently, so a not-throw assertion over a fixture carrying the new field passes identically before and
  after the field is declared — a vacuous green that would let this entire plan ship with nothing declared.
  Asserting the value read back off the parsed result fails before the edit both as `undefined` and as a
  `pnpm typecheck` error on the property access. Both failure modes are the RED step and both must be observed
  and quoted. **Reversibility: reversible.**

- **PD-07 — the schema-level refine failure is proven at the SCHEMA, and the publisher-level failure through
  the BUILDER, because they are different failures.** `roundPmf` unconditionally renormalizes any non-empty
  array so its rounded entries sum to exactly 1, adding the residual to the largest entry — so a pmf that does
  not sum to 1 cannot reach the refine through `buildEventArtifact` at all; it is renormalized into validity
  first. 07-08's own test block records this deviation, found RED-first. The non-summing case is therefore
  asserted by calling `EventArtifactSchema` directly with the unrounded value (Task 1's schema half), and the
  builder's own failure path is asserted with an EMPTY array, which `roundPmf` rejects by its own explicit
  guard. Writing a non-summing pmf into a `buildEventArtifact` test and expecting a throw would produce a
  passing artifact and a silently wrong test. **Reversibility: reversible.**

- **PD-08 — three doc sites in `pageArtifacts.ts` become false the moment Task 1 lands, and Task 3 corrects
  all three rather than leaving them to a future reader.** `EventArtifactSchema`'s doc closes its 04-04
  paragraph with a claim about the `matches` array's shape relative to the 04-01 tracer; that claim is
  falsified by this plan. `EventUpcomingMatchSchema`'s doc claims the upcoming shape is what this phase's rank
  simulation consumes; after 08-05, the simulation consumes played rows for every rewind start match, which is
  the overwhelmingly common case. And `EventMatchSchema`'s own header makes the sidecar-parity claim that
  D-03 finally makes true and should say so. A doc comment that describes a shape the code no longer has is
  precisely the failure this project's own log names as realized — the README that described a deleted model —
  so the sweep is an acceptance criterion with a grep gate, not a courtesy. **Reversibility: reversible.**

- **PD-09 — the schema-shape conversion reindents roughly 59 lines, and the review gate accounts for that.**
  Converting `EventMatchSchema` from a bare object schema to a refine-chained one moves the whole object
  literal one indent level deeper, so `git diff` will show nearly the entire schema as changed. A field
  retype, reorder or removal hidden inside that churn would be invisible to a reviewer scanning the diff.
  Task 1 therefore carries a `git diff -w` criterion: with whitespace ignored, the only changed lines in
  `EventMatchSchema`'s range are the four new field declarations, their doc comments, the object literal's
  closing punctuation, and the two appended refines. There is no formatter in this repo's root scripts, so
  the reindent is manual and this gate is the only thing that catches a slip in it.
  **Reversibility: reversible.**

- **PD-10 — no `checkpoint:decision` in this plan, deliberately.** `08-CONTEXT.md` rates D-03 and D-12 as
  **costly**, not one-way, and both tasks below carry that rating. Under `REVERSIBILITY_GATES`, `one-way`
  earns a gate and `costly` is flagged only. Beyond that rule, this commit writes no published byte: no R2
  object is created or deleted, no key is renamed, and the deployed browser still reads pre-republish objects
  that parse unchanged. `git revert` undoes it completely. The phase's irreversibility, such as it is, is
  realized at 08-05's republish — and even there the operation is additive under existing key names,
  overwrites in place, deletes nothing, and is idempotent, which is why the approved outline places a hard
  STOP (the byte gate) there rather than a gate. A later reader finding no checkpoint here should read this
  entry, not infer an omission.

- **PD-11 — this plan changes no published byte, and that is an asserted criterion rather than an
  assumption.** A payload measurement that moved during a source-only plan would mean a publish leaked in.
  `payloadBudget.test.ts` must show exactly the two recorded baseline failures and nothing else.
