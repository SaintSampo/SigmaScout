<objective>
**The one full republish — carrying D-03 and D-12 together, run exactly once, backgrounded from the first attempt, and gated on bytes rather than on a process exit code.**

08-02 declared four optional fields on `EventMatchSchema` and filled them in `buildEventArtifact`'s `matches` row builder. Today those fields exist only in unit-test fixtures: not one of the 4,143 published `event/{eventKey}` objects in production R2 carries `redRpPmf`, `blueRpPmf`, `actualRedRp` or `actualBlueRp` on a played row. This plan runs the single pass that changes that, and then proves it on real bytes read back from the origin the browser reads.

Three constraints are non-negotiable and each is an acceptance criterion below rather than advice:

1. **Backgrounded from the first attempt.** `pnpm publish:seasons` runs seventeen to twenty-five minutes. A foreground invocation has its outer wrapper killed by the executor tool's Bash timeout while the deep `tsx` child survives and keeps writing — the exact failure that produced a four-way concurrent-writer race against the live R2 bucket during Phase 7 plan 07-17, documented in `.planning/STATE.md`. `run_in_background: true` on the very first invocation, never as a retry after a timeout.
2. **The byte budget is a hard gate.** D-03 costs roughly 13,000 bytes and D-12 roughly 5,000 at the largest event, against 22,828 bytes of committed headroom. A breach of the 350,000-byte `event` ceiling at any event is a stop-and-report condition, never something to absorb by trimming another field or raising the ceiling.
3. **Secrets discipline.** The R2 credentials and TBA key are reached only by letting the tool read `.env` itself. Never `Read`, `cat`, `echo` or interpolate `.env` or any value from it.

Purpose: three plans downstream of this one build a Simulation tab that reads fields no published artifact carries today. `08-UI-SPEC.md`'s Data Dependencies gate is explicit that no tab component may be built before the artifacts carry the fields it reads, and the outline honors that gate strictly for everything that reads `redRpPmf`/`blueRpPmf` off a fetched artifact — 08-09, 08-11, 08-13 and 08-14 all sit at wave 3 or later, downstream of this plan. This is the plan that makes them buildable.

This plan also corrects a gate that could not fire. `packages/harness/payloadBudget.test.ts`'s internal-consistency test iterates all five page kinds inside one `it(...)`, and its first iteration (`teams`) has failed since WINDOWS.md ledger #11 opened — so the `event` ceiling assertion inside that same block has been unreachable the whole time. Running the file and seeing "the same failures as baseline" would therefore have proved nothing about the event page. The plan adds a dedicated, independently reachable `event` ceiling test before publishing anything, so the byte gate is real rather than ceremonial.

Output: an extended credential-free verifier carrying D-03/D-12 expectations, one dedicated byte-ceiling test, ~56,776 republished production R2 objects, an updated `docs/publish-budget.md` (narrative entry plus the committed machine-readable block), and a `## Republish ledger` in the SUMMARY that four sibling plans read a fact out of.

<planner_decisions>

**PD-01 — The byte gate gets its own reachable test, because the existing one cannot fire.**
`payloadBudget.test.ts`'s `is internally consistent: medianBytes <= p95Bytes <= maxBytes <= budgetMaxBytes for every page kind` iterates `PAGE_KINDS` in the order `teams, team, events, event, compare` inside a single `it(...)`. Its first iteration fails on ledger #11 and throws, so the `event` iteration has never executed while that ledger entry has been open. Running the file post-republish and observing "the same failures as baseline" would therefore have said nothing at all about whether D-03 plus D-12 breached 350,000 bytes. Task 1 adds one dedicated `it(...)` for the `event` page kind against a new `EVENT_PAGE_ABSOLUTE_MAX_BYTES` constant, mirroring the two existing per-kind absolute-ceiling tests, which are reachable precisely because each lives in its own `it`. That test is written and observed GREEN against the current committed block (327,172 <= 350,000) BEFORE the republish, so a post-republish failure is unambiguously about the new bytes.

**PD-02 — The existing internal-consistency block is NOT restructured here.** Splitting it per kind would make all five reachable, which is the right long-term fix, but it would also newly surface ledger #15's `team` breach as a separate failure and change the baseline failure count in the same execution that writes 56,776 production objects. Two signals moving at once is exactly how a real regression hides. The restructure is recorded as a finding for its own todo and is deliberately not done here.

**PD-03 — A pre-flight dry-run probe runs before the 25-minute pass.** `publish.ts`'s `--dry-run` path prints `[dry-run] Would publish "<key>" (<n> bytes) to bucket "<bucket>" — no upload performed.` (`publish.ts:2177`), so a single `--event <key> --algorithm vpr --dry-run` invocation measures one event's post-change artifact size in roughly the cost of one season replay, uploads nothing, and needs no new code. Probing the committed `largestKey` before committing to 56,776 PUTs converts "run it and find out" into "know before you pay". The probe predicts; it does not bound (see the second backstop truth), so the post-run measurement remains authoritative.

**PD-04 — Verification extends `scripts/verifySubsetPublish.ts` rather than adding a second verifier.** 07-10 built it with an extensible `PUBLISHED_SUBSET` table and an `--origin` override specifically so later publish work would extend one table; 07-17 and 07-19 both already did. Its `expectVariance: "present" | "absent"` check (check 8) is the exact structural analog of what D-03 needs — a positive assertion paired with a negative one on the arms that must NOT carry the field. Writing a second script would duplicate manifest resolution, cache-busting fetch, schema parsing and per-entry reporting to gain nothing. The outline named `docs/publish-budget.md` as this plan's file coordination point and did not name the verifier; adding it is recorded here as a decision. No other wave-2 plan touches it (08-06: `compare.tsx`/`compareTie.ts`/`compare.test.tsx`; 08-07: `workers/simulation.worker.ts`; 08-08: `scripts/measureRewindGap.ts` and `docs/models/`), so there is no same-wave file conflict.

**PD-05 — Pmf presence is expected per-entry from `isRpEligibleEventType`, not per-algorithm.** Reading `sigma1/index.ts:748` at planning time established that `predict()` returns `{ redPmf: [], bluePmf: [] }` for any event type absent from `EVENT_TYPE_TIERS`, and the publisher's conditional spread then omits the key entirely rather than writing an empty array. So a VPR artifact for an offseason event will carry `actualRedRp`/`actualBlueRp` on every played row and NO pmf on any row — while a VPR artifact for a regular event carries both. Encoding this as one blanket "VPR means pmfs present" expectation would produce eight false failures on the offseason entries and would hide the real property.
