<objective>
**The start match becomes a choice the reader makes, the simulation's inputs get assembled honestly
from it, and the page states what that choice costs.**

This plan ships three things that only make sense together. `StartMatchPicker.tsx` is the control
that turns "the start match" from an implicit boundary into a user-supplied parameter.
`simulationInputs.ts` is the layer that answers, from the artifact alone, the two questions 08-03's
pure core deliberately refused: which rows are remaining (D-13) and what each team has already
earned (D-12). And the rewind-honesty caption is what stops the first of those choices from being
made silently — it carries 08-08's measured figure, branches on 08-08's measured verdict, and
appears the moment the choice is made rather than after the run.

Purpose: this is where the phase's highest-consequence unit ambiguity is resolved. 08-03 stated it
in its own PD-02 and named this plan as the consumer: `SimTeamBaseline.earnedRpSum` is a TOTAL,
while D-12's preferred source, `EventTeamSchema.rp`, is a per-match average. A caller that forwards
the average unconverted mis-ranks the entire field by a factor of that team's match count, and no
test on either side of the boundary would catch it — 08-03's tests pass on self-consistent inputs
and a picker's tests pass on a plausible-looking map. The mitigation is that the conversion happens
here, once, in a tested pure function whose own assertions are computed from the published fields
rather than eyeballed.

Output: a chronological bounded-height picker with its default-selection rule, a pure input-assembly
module with the D-12 precedence and the D-13 selection under test, a caption that cannot outrun its
own measurement, and one new `color-mix`-derived theme token for the selected row's tint.
</objective>

<planner_decisions>

**PD-01 — D-12's precedence is applied to the quantity "RP earned in the played qualification rows
STRICTLY BEFORE the start match," which is what makes rule 1 correct where it is used and rule 2
the honest path everywhere else.** D-12's own opening sentence states the quantity: "A rewind start
match needs each team's accumulated actual RP **as of that match**." `EventTeamSchema.rp` is TBA's
end-of-event Ranking Score. It is a published value OF that quantity only when the prefix is the
whole played set — that is, when no played qualification row lies at or after the chosen start. When
one does, `rp` describes a different quantity entirely, and rule 1's "when present" condition is not
met for the quantity being computed, so D-12's own rule 2 applies. Reading rule 1 as
start-match-independent would have every rewind start add RP the simulation is simultaneously
re-drawing — a double count producing a plausible, well-formed, entirely wrong rank distribution. The
two named computations are used exactly as D-12 names them; what this decision fixes is which
question each of them is answering. **Runner-up, recorded rather than silently discarded:** anchor
on `rp x denominator` and subtract the per-match actual RP of the played rows at or after the start,
which would keep TBA's surrogate/DQ adjustment for the prefix. It is more accurate and it is a THIRD
arithmetic path D-12 does not name, whose surrogate exposure runs the wrong way (over-subtracting a
surrogate row TBA never counted yields a wrong number, where rule 2 yields a differently-defined
number D-12 already accepted in writing). Rejected on those grounds, not on difficulty.
— <reversibility rating="reversible">A branch in one pure function, no published contract, no stored data.</reversibility>

**PD-02 — The precedence-1 denominator is TBA's own record, not a count of appearances.** D-12
prefers rule 1 specifically because Ranking Score "already accounts for surrogate appearances and
disqualifications." That adjustment lives entirely in TBA's denominator, so multiplying by a
denominator this pipeline counted itself would discard the exact property the rule was chosen for.
`EventTeamSchema.record` is TBA's own reported record for this team at this event, required to come
from TBA rather than tallied from `matches[]` (Phase 7 D-18 item 6), so `wins + losses + ties` is
that denominator. It is independently optional, so a documented second fallback to the played-`qm`
appearance count exists and is recorded per team in `BaselineSource` — never silently. Verified on
live bytes 2026-08-30: `2025cada`/`frc254` has record 10-2-0 and twelve appearances, which agree,
and `2023nhgrs`/`frc5902` has record 3-5-0 and eight appearances, which also agree; the two
denominators are expected to agree on most events and the point of the decision is which one is
authoritative when they do not.
— <reversibility rating="reversible">A denominator choice inside one function, recorded per team.</reversibility>

**PD-03 — The product is rounded to the nearest integer, and that is a recovery with a proof, not a
tolerance.** `rp` is rounded once at the publish boundary to two decimals, so `rp x denominator`
carries an error of at most `0.005 x denominator`. Every per-match ranking-point value is a
non-negative integer (`actualRedRp` is `z.number().int()`), so the true total is an integer, and
nearest-integer rounding recovers it exactly whenever the error is under 0.5 — that is, for any
denominator below 100, which no FRC qualification schedule approaches. Passing the unrounded product
instead would leave a sub-0.005-per-match artifact in the starting average that could break a
genuine tie between two teams in a direction no data supports, which D-14's team-key tie-break exists
precisely to avoid. Rule 2 needs no such step: summing integers yields an integer.
— <reversibility rating="reversible">One call, removable without touching a caller.</reversibility>

**PD-04 — A `null` per-match value is excluded from the count as well as from the sum.** D-12 states
the numerator rule ("contributes nothing to the sum") and is silent on the denominator. Counting the
match in the denominator while omitting it from the numerator would depress that team's starting
average by exactly the RP the match is missing — which is D-12's own named rejection, "treating a
missing baseline as 0 with a caveat," applied one match at a time instead of one team at a time.
Excluding it from both computes the average over the matches actually known, which is the honest
estimate, and the team's key lands in `incompleteBaselineTeamKeys` so the page can say so.
— <reversibility rating="reversible">A branch in one loop, with the affected team keys already surfaced.</reversibility>

**PD-05 — A remaining qualification row with no usable pmf pair is excluded and counted, and D-13 is
not violated by that.** D-13 forbids filtering on a row's offseason, surrogate or quarantine STATUS,
because the artifact carries no such flag and inventing one would assert a distinction the data does
not make. A row carrying no ranking-point distribution is a different fact: there is nothing to draw
from. 08-03's `simulateRanks` performs an up-front shape validation and throws a named
`InvalidPmfError` on an empty or absent pmf (its PD-04), so passing such a row through would crash
the run rather than degrade it. Substituting a distribution is forbidden outright — 08-09's second
prohibition inherits Sigma1's own reasoning that a degenerate certain-zero pmf is a POSITIVE claim
that an alliance certainly earns no ranking points, and a fabricated pmf is pixel-identical to a real
one on screen. So: exclude, count, disclose. Expected to be rare on a reachable event, since 08-05
measured pmf presence as effectively all-or-nothing per event; the count is reported at execution
time rather than assumed to be zero.
— <reversibility rating="reversible">An exclusion list and a disclosure line.</reversibility>

**PD-06 — Selection is a `matchKey`, not an index, and it is resolved against the CURRENT rows on
every render.** This site's freshness target is one to three minutes during a live event, and
TanStack Query refetches the event artifact on that cadence. A match crossing from `upcoming[]` to

selection would silently re-point at a different match under a reader who had already chosen. The
same resolution handles the two other cases for free: a selected key absent from the current rows
resolves to no selection (the hint returns) rather than snapping to a neighbour, and navigating
between events cannot carry a stale selection into a roster it does not belong to.
— <reversibility rating="reversible">The state's type and one lookup.</reversibility>

**PD-07 — The default selection is computed once, in a lazy state initializer, and never re-applied.**
Recomputing it on every artifact change would move the reader's chosen start match out from under
them the moment the first unplayed match became played, mid-event, which is exactly when a reader is
most likely to be watching. Computing it once at mount gives the D-01 no-caveat case its correct
default and then leaves the choice alone. This is the same reason the default is absent rather than
arbitrary on a fully-played event.
— <reversibility rating="reversible">A state initializer.</reversibility>

**PD-08 — "Rewind" is defined as "at least one played qualification row lies at or after the start,"

absorbed results the simulation is pretending have not happened. The second misses a representable
shape — an unplayed row ordered before a played one, which `compareEventMatchRows` can produce, since
it sorts rows carrying `sortTime` ahead of rows without one and `sortTime` is optional on both
arrays. UI-SPEC's rule ("selecting an already-played row shows the caption") is a strict subset of
this one, so nothing the contract requires is lost.
— <reversibility rating="reversible">A predicate.</reversibility>

<assumption_delta_decision>

**Signal.** The orchestrator's assumption-delta scan fired on the term `chosen`, from the phase
goal's own wording — "rank simulation from a **chosen** match." The question the checkpoint asks is
whether a configuration decision has become a modeling decision. This is the plan where the start
match actually becomes user-chosen, so the call belongs here.

**Noun now primary: the start match — or more precisely, "the state of the event as of a chosen
match."** Before this plan, the phase's implicit noun was "now": a single boundary between what has
been played and what has not, readable straight off the artifact as the end of `matches[]`. That
noun needed no representation because there was only ever one instance of it, and every field it
would have carried (each team's earned RP, the remaining schedule) was already a published field or
a trivially derivable one. This plan replaces it with a parameterized family — one instance per
qualification row — and none of its fields are published. Each has to be assembled: the remaining
set is a slice, and each team's earned RP is a per-start-match computation with a branch that D-12
had to be written to resolve.

That is a genuine generalization, and it is not a prose coincidence. `EventTeamSchema.rp` exists
precisely because "now" was the only instance that needed a number; the fact that it answers the
wrong question for every other instance (PD-01) is the clearest evidence available that the noun
really did change shape.

**Decision: `add-alongside`.**

`SimulationInputs` is introduced as a named, tested value type representing the event as of a chosen
match — assembled in one place, with its provenance recorded per team in `BaselineSource` and its
two honesty gaps recorded in `excludedMatchKeys` and `incompleteBaselineTeamKeys`. It sits beside the
existing "read it off the artifact" path rather than replacing it: `EventTeamSchema.rp` keeps its
meaning and its published contract, every other surface on the site that reads a team's standing
keeps reading it, and precedence 1 still uses it wherever it is a value of the quantity being asked
for.

**Why not `promote`.** Promotion would mean making this noun a first-class published or persisted
entity — a schema, an artifact key, a publish contract. That is exactly the deferred
sidecar-checkpoint idea in `08-CONTEXT.md`'s `<deferred>` section, and D-02's measurement is its
stated trigger. Building it now would ship a published contract change this phase has no evidence it
needs, on top of a republish that is already sized against 22,739 bytes of headroom. Promoting
speculatively would also be the exact "manufacture a refactor to satisfy the checkpoint" the
capability contribution warns against.

**Why not `no-change`.** A defensible `no-change` would require the start match to be pure
configuration — a value that selects among behaviours without changing what has to be modelled. It
is not: it changed which quantity `EventTeamSchema.rp` is an answer to, and that change is what
forced D-12 into existence at planning time and PD-01 into existence here. Calling that
configuration would leave the highest-consequence unit decision in the phase unnamed.

**What would later force a promote.** Any one of: (a) D-02's measured gap turns out large enough to
justify the sidecar-checkpoint phase, at which point "event state as of match N" acquires an R2 key,
a Zod schema and a publish contract and must become a first-class model; (b) a second surface needs
the same as-of-a-match state — an as-of-match team page, or an elimination-bracket simulation —
making a browser-local assembly the wrong home for it; or (c) the assembly stops being derivable
from a single event artifact, which would happen the moment it needed frozen per-match model state,
since Phase 7 D-11 forbids reconstructing combined figures client-side.

**Advisory, not blocking.** This checkpoint gates nothing in this phase and no task above depends on
its outcome.
