## Decisions this plan makes (Claude's Discretion, recorded not assumed)

1. **No-calls become a three-column algorithm group; the other seven coverage fields stay one column each — decided on measurement, not preference.**
   The UI-SPEC's column list is flat: "Candidate matches, Scored matches, Offseason excluded,
   Surrogate-affected excluded, Missing-result excluded, Quarantined excluded, Ties, No-calls" against
   five season rows. Measured against all five live published artifacts this session, that shape is
   unrenderable for one of its own columns: `noCallCount` differs between OPR, EPA and VPR in **15 of
   15** (season, view) groups (2022 qualification is 982 / 248 / 245), while `candidateCount`,
   `scoredCount`, `tieCount` and all four `exclusionCounts` members differ in **0 of 15**. That split
   is not an accident of the data — a no-call is a prediction of exactly 50%, which is a fact about an
   algorithm's behaviour, while the other seven describe the match population it was scored on. The
   three available responses were: print one algorithm's no-call count under a population header (a
   lie by omission), sum the three (a number that means nothing), or give No-calls its own algorithm
   group. Only the third is honest, and it costs nothing new — it reuses the two-row grouped header
   08-01 built for the accuracy table.
   — <reversibility rating="reversible">Header markup and one row-model field; the pure model already returns per-algorithm values.</reversibility>

2. **A disagreement between the three algorithms on a shared column renders all three labelled values, never a silently-picked one.**
   The seven-field agreement above is an empirical property of today's published data, **not** a
   schema guarantee. `aggregateScores` computes `candidateCount`, `tieCount` and every exclusion count
   independently inside a per-algorithm loop, and `exclusionCounts.quarantined` is by construction an
   algorithm-specific verdict (`!isValidPRedWin(candidate.pRedWin)`) that merely happens to be zero
   everywhere today. So the collapse has to be conditional. Rendering the first algorithm's value
   would put an algorithm's own figure under a header claiming to describe the match population, and
   it would look exactly like a correct render. The cost of the honest branch is one discriminated
   union member in a pure function plus one render branch plus two constructed tests, which is
   proportionate for a page whose stated purpose is not printing numbers it cannot stand behind.
   — <reversibility rating="reversible">One union member; if the invariant is ever made structural upstream, the branch becomes dead code and is deleted in one edit.</reversibility>

3. **The table's header groups the four exclusion columns and separates Ties and No-calls from them.**
   Confirmed against source rather than inferred: `scoredCount`'s own declaration comments read "The
   Brier population for this slice (includes ties and no-calls)" and `candidateCount`'s read
   "`scoredCount + sum(exclusionCounts)`", and the identity holds exactly in 45 of 45 published
   slices. So the eight counts are two different kinds of fact — five that partition the candidate
   population, and two that are subsets of the scored part of it. Rendered as eight adjacent columns
   they read as one additive list, and a reader adding them gets a number with no meaning. A two-row
   header with a bordered `Excluded from scoring` group over the four exclusion columns, with Ties and
   the No-calls group outside that border, encodes the real structure at zero interaction cost.
   — <reversibility rating="reversible">Header markup over an unchanged row model.</reversibility>

4. **The Copywriting Contract's D-09 explainer ships verbatim, with a second authored sentence added beside it — not a rewrite.**
   The contract sentence carries D-09's binding offseason distinction correctly and is checker-approved
   copy, so it is not the planner's to edit (08-06's precedent with the near-tie caption). But it names
   two exclusion reasons — offseason, and matches without a recorded winner — while the table beneath
   it shows four columns, leaving Surrogate-affected and Quarantined standing unexplained beside a
   sentence that reads as though the exclusions are only the two it names. This is a gap, not the
   inversion 08-10 found in the calibration explainer, so the proportionate fix is additive: keep the
   contract sentence first and unedited, and follow it with an authored structural sentence covering
   the partition and the ties/no-calls placement. Nothing approved is amended and nothing contradicts.
   — <reversibility rating="reversible">One additional exported string constant.</reversibility>

5. **Counts render as bare integers with no locale grouping.**
   The web app contains no `toLocaleString` and no `Intl.NumberFormat` call anywhere today; every
   integer renders bare inside `numeric-cell`, whose job is tabular figures. Two reasons to keep it
   that way here rather than introducing grouping for five-digit counts: it matches every other number
   on the site, and grouped output is locale-dependent, which would make the fixture-derived parity
   assertions depend on the test runner's locale — a silent cross-machine flake in the one suite whose
   entire value is being trustworthy.
   — <reversibility rating="reversible">One formatter call site if grouping is ever wanted app-wide.</reversibility>

6. **The section lives in one file named for its table, per the outline.**
   The outline names `DataCoverageTable.tsx`. 08-10 split `CalibrationSection` from
   `CalibrationChart` because the chart sits behind a real dynamic-import seam; this section has no
   seam — it is a heading, two paragraphs and a table. One component file exporting
   `DataCoverageSection` (the mounted component), `DataCoverageTable` and
   `DataCoverageSectionSkeleton` keeps the section's spacing rhythm in one place. The pure row model
   still splits into `coverageRows.ts`, matching this phase's own `calibrationSeries.ts` precedent.
   — <reversibility rating="reversible">A file boundary with no data contract behind it.</reversibility>

7. **The pending branch's placeholders for the methodology note and the calibration section are declared in `compare.tsx`, not added to 08-06's and 08-10's components.**
   Both of those components render only in the populated branch by their own plans' design, and
   neither ships a skeleton sibling. Adding one to each would mean editing two files this plan
   otherwise has no reason to touch and that two other plans own. A small module-local composition in
   `compare.tsx` using the already-installed `Skeleton` primitive gives the pending branch the same
   footprint the populated page has, which is the whole point, without widening this plan's blast
   radius.
   — <reversibility rating="reversible">A local composition in one file; promoting either placeholder into its own component later is a move, not a redesign.</reversibility>

## Flagged planner assumptions

1. **The UI-SPEC's eight-column data-coverage table is not renderable as written, and this plan
   changes its shape on measurement.** `noCallCount` differs across the three algorithms in 15 of 15
   published (season, view) groups, so a single "No-calls" column has no single value to hold. This is
   a deliberate departure from a shape an approved design contract sketches, not an interpretation of
   it, and Decision 1 records the three options and why only the algorithm group is honest. The
   departure is contained: it adds three leaf columns and changes no other column, no row, no copy and
   no data contract. If the UI-SPEC is re-approved, its column list should be updated to match.

2. **C4's `overflow` row was dismissed on the premise of a "fixed 5-row x ~8-column table, same
   bounded size as C1", and this plan ships eleven leaf columns instead.** The dismissal's reasoning
   still holds in substance — the table is bounded, does not reflow, and inherits the same
   already-solved horizontal-pan pattern C1 uses, which sketch 007 confirmed for a table of this
   class — so this plan does not promote the row to a backstop and does not add work to 08-15. It is
   flagged because the row's stated premise moved and a reader deserves to see that it was rechecked
   rather than inherited. If a 390px render later shows eleven columns panning worse than seven, that
   is a C1-family finding and 08-15's C1 evidence is where it would surface.

3. **The Copywriting Contract's D-09 explainer names two of the four exclusion reasons, and this plan
   adds a sentence rather than editing it.** The contract sentence is correct about offseason
   exclusion — the one thing D-09 binds — but says "official-season matches with a recorded winner",
   which accounts for the offseason and missing-result columns while leaving Surrogate-affected and
   Quarantined standing unexplained beside it. This is a gap, not the factual inversion 08-10 found in
   the calibration explainer, so the response is additive (Decision 4) rather than corrective. Flagged
   so a copy reviewer sees a considered position.

4. **"Quarantined" is an opaque column header for this audience and this plan does not invent copy to
   fix it.** The column list is fixed by the UI-SPEC and the term is the artifact's own field name;
   authoring a plain-language gloss would be new copy on an approved contract for a column that is
   zero in all 45 published slices today. Recorded rather than silently accepted: if a reader-facing
   gloss is wanted, it is a one-row addition to the Copywriting Contract and a one-clause addition to
   `DATA_COVERAGE_EXPLAINER_STRUCTURE`, and it should be made in both.

5. **The agreement of the seven collapsible coverage fields is empirical, not structural, and the
   plan is built on the weaker claim.** `aggregateScores` computes them inside a per-algorithm loop
   and `exclusionCounts.quarantined` is by construction an algorithm-specific verdict, so nothing
   guarantees the collapse is always safe — it merely is, in 15 of 15 groups, today. The disagreed
   rendering path therefore exists as a real branch with real tests rather than as a theoretical one,
   and Task 3's fixture assertion checks the empirical claim on every run rather than trusting this
   session's measurement.

6. **Every wide table in this app renders inside two nested horizontal scroll containers, and this
   plan matches that rather than fixing it.** The `Table` primitive's own wrapper carries
   `overflow-x-auto`, and every existing caller adds the `min-w-0 touch-pan-xy overflow-x-auto
   overscroll-x-contain` set around it — `AlliancesTab`, `ElimsTab` and 08-01's `AccuracyTable` all
   do. Recorded because 08-01's must-have describes its scroll region as containing "no nested scroll
   region of its own", which is true of what that component authors and not of what the primitive
   brings. Deviating here would make this the one table on the page that scrolls differently, which is
   a worse outcome than inheriting a shipped quirk; changing the primitive is a cross-cutting change
   for a different plan.

7. **RESEARCH.md's Pattern 8 states "45 slices per year's file"; the real figure is 9.** 08-01 already
   measured and recorded this, and this plan is built on the measurement: each `v1/compare/{year}.json`
   carries nine slices for its own season across three algorithms and three views, which is why the
   coverage table reads five separately-fetched artifacts rather than one. Restated here only because
   this plan's own measurements are quoted per-slice and a reader checking them against RESEARCH would
   otherwise find a discrepancy that was already resolved.
