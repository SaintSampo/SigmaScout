<objective>
Model the FRC ranking-point rules for 2022-2026 as per-season modules whose thresholds are
tiered data, and discharge SC-4 two ways at once (D-12): the official manual is the authoring
source cited by section in every module, and a corpus-wide reconciliation test is the proof.

Purpose: ALGO-08 predicts ranking points "using each season's RP rules". Those rules are not
uniform — the win RP value changed from 2 to 3 in 2025, and four of five seasons raise bonus
thresholds at higher event tiers with a different tier-bump pattern per season. TBA already
records every bonus-achievement flag in `score_breakdown_raw`, so ground truth is free and a
manual misreading can fail a test instead of sitting in prose.

Output: `packages/core/algorithms/sigma1/rp/` — a dependency-free leaf, a dispatch table, five
per-season rule modules, and a corpus-wide reconciliation test.

This plan is an INDEPENDENT domain axis, not an expansion of plan 03-01's tracer slice: it
touches no file that plan touches and reads `event_type` straight from the corpus in its test,
so it needs nothing from the parameterization work. Wiring these rules into `predict()` is
plan 03-03's job.
</objective>

**`packages/core/algorithms/sigma1/rp/constants.ts` (new, dependency-free leaf).** Declare:

- `RpThresholdVariable` — one named scalar a season's RP rules threshold on, tracked in its own
  units. Name it "threshold variable", NOT "count": 2022's Hangar Bonus thresholds on
  `endgamePoints` (a point total) while its Cargo Bonus thresholds on `matchCargoTotal` (a raw
  count). D-09's discipline is that these live in a state vector kept SEPARATE from the score
  component vector — it is not a claim that every one of them is a count. Each variable carries
  `{ name: string; unit: "count" | "points" }` so a module cannot silently read a `*Points`
  roll-up where the manual's rule wants a raw `*Count`.
- `EventTier = "base" | "districtChampionship" | "championship"` and
  `EVENT_TYPE_TIERS: Readonly<Record<number, EventTier>>` mapping TBA's `event_type` values:

  (including `99` offseason, which is excluded from every RP population) rather than defaulting
  to `base` — a silent default here is exactly Pitfall 1's failure mode.
- `RpTieredThreshold = Readonly<Record<EventTier, number>>` — the shape every tiered threshold
  is expressed in. A season whose threshold does not tier states the same number three times
  and says so in a comment; the DATA shape is uniform so a correction is a one-line edit.
- `RpParsedResult` — what a season module's `parse` returns for one alliance:
  `{ thresholdVariables: Record<string, number>; bonusFlags: Record<string, boolean>; recordedBonusFlags: Record<string, boolean>; winRp: number; tieRp: number; totalRp: number }`.
  `bonusFlags` are RECOMPUTED from raw fields; `recordedBonusFlags` are TBA's own booleans read
  verbatim — keeping both is what makes the reconciliation test a comparison rather than a
  restatement.
- `RpRuleModule` — the per-season interface, structurally mirroring `SeasonComponentMap`:
  `{ readonly season: number; readonly thresholdVariables: readonly RpThresholdVariable[]; readonly bonusNames: readonly string[]; readonly maxRp: number; readonly winRp: number; readonly tieRp: number; parse(rawBreakdownJson: unknown, side: "red" | "blue", eventType: number): RpParsedResult; readonly diagnosticKeys?: readonly string[] }`.
  `maxRp` is `winRp + bonusNames.length` and is what sizes the pmf array in plan 03-03.
- `assertFiniteThresholdVariables(vars, context)` — the RP-side twin of
  `assertFiniteComponents`, throwing loudly rather than letting a non-finite value reach the
  Kalman fold or the Cholesky draw in plan 03-03.
- `ELIMINATION_RP_TOTAL = 0` with a comment recording the verification: RP is a
  qualification-tournament mechanic; both `red_rp_earned` and `blue_rp_earned` are 0 for 100%

  0/2613, 2023 0/2795, 2024 0/2867, 2025 0/3056, 2026 0/3212), not a sample.

  <action>
Build the test that discharges SC-4's proof half (D-12) and doubles as the discovery mechanism
for the two UNPINNED thresholds.

Sample per season: played, non-offseason `qm` matches with `has_score_breakdown = 1`, joined to
`events` for `event_type`, selecting `match_key, event_key, event_type, comp_level, winner,
red_score, blue_score, red_rp_earned, blue_rp_earned, score_breakdown_raw`,
`ORDER BY match_key ASC`. Use the FULL season population rather than a 2000-row prefix cap —
the tier-concentrated failure signature is invisible in a prefix sample because event keys sort
alphabetically and the higher-tier events cluster. If full-season runtime proves unacceptable,
sample per tier instead (a bounded number of matches from EACH `event_type` value present), and
say why in a comment. Never sample in a way that can omit an entire tier.

Assertions per season:
1. **Bonus flag reconciliation.** For each alliance of each sampled match, the recomputed
   `bonusFlags` equal TBA's own `recordedBonusFlags`, bonus by bonus. Report failures grouped
   by `event_type` and by bonus name, printing the mismatch COUNT and RATE per group before
   asserting — a mismatch concentrated at one tier is a threshold error, and the group report
   is what makes that visible instead of a wall of individual failures. Assert an exception
   rate of exactly 0 for every season and bonus, with ONE documented exception: 2022's
   `cargoBonus`, whose measured rate is roughly 0.29% at `event_type = 0` and 0.28% at
   `event_type = 1` with zero mismatches at every higher tier and mismatches running in both
   directions — inconsistent with a threshold error and consistent with a small number of
   anomalous events' data. Encode that as a named constant with the EXACT measured rate this
   run observes plus a small margin, a comment naming the affected event keys the run finds,
   and a note that this tolerance covers a data artifact and must never be widened to cover a
   rule change. Do not tune the 2022 rule logic to chase it.
2. **Summed RP reconciliation.** For each alliance, `winRp` (or `tieRp`, or 0) plus the count
   of true recomputed bonus flags equals `red_rp_earned` / `blue_rp_earned`. This is what pins
   the 2025/2026 win-RP change to 3 as a test rather than a claim.
3. **Exact-boundary behaviour.** For each season and bonus, find the sampled matches whose
   threshold variable equals its tier threshold EXACTLY and assert the recomputed flag is
   `true` for all of them (`>=`, never `>`). If a season and tier has zero such matches, log
   that fact explicitly and skip that sub-assertion with a message — never pass silently on an
   empty set, since "no boundary case observed" is a different finding from "boundary case
   confirmed" and is exactly the situation this plan's `backstop` truth records for the upper
   tiers.
