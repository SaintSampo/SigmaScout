## Data Dependencies (blocking — read before planning)

This UI-SPEC is written against the **post-D-01…D-05 published schema**, not the schema that exists on disk today. `packages/harness/pageArtifacts.ts`'s `TeamSeasonArtifactSchema`/`TeamSeasonMatchSchema` as of this research pass (2026-08-25, verified by direct read) do **not yet** carry:

1. **Per-alliance own predicted-score variance** (D-01) — today only the red+blue *sum* (`variance`) exists on `TeamSeasonMatchSchema`; TEAM-05's "predicted scores for each alliance ± 1 SD" needs the **two separate** own-variance numbers Sigma1 already computes internally (`sigma1/index.ts:684`, `redScoreVarianceOwn`/`blueScoreVarianceOwn`) but currently discards. **This is the single highest-priority prerequisite** — resolves `publish-match-predictive-variance.md`, and the sketch findings state plainly: *"any interval display of a match prediction is wrong until this ships."*
2. **Actual RP per match** (D-02) — only predicted RP (`redRpPmf`/`blueRpPmf`, on the upcoming-match shape) exists; there is no actual-RP field on the played-match shape at all.
3. **Robot image URL** (D-03) — no field on `TeamSeasonArtifactSchema` today.
4. **Per-metric percentile** (D-04) — no field anywhere in `MetricsRecordSchema`/`TeamMetricSchema`; required for D-17's tier boxes.
5. **`activeYears`** (D-05) — no field on `TeamSeasonArtifactSchema` today; required for D-18's constrained year dropdown and D-19's empty-state links.
6. **Optional actual fields on a match row** (D-09) — `TeamSeasonMatchSchema` currently *requires* `actualWinner`/`actualRedScore`/`actualBlueScore` on every row, which makes an unplayed (upcoming) match structurally unrepresentable. TEAM-04's "attended **or upcoming** event" cannot render until this is relaxed, with a validation-rule replacement per D-09's explicit instruction (a played match must carry scores, enforced as a test, not a type).

None of this blocks writing the UI contract below — every display rule is specified against the **field names D-01…D-05 name or imply**, flagged `(exact field name TBD by planner)` where CONTEXT.md did not commit to one. It blocks *building* until the publish-side plan wave lands. The planner must sequence the schema/publisher/republish work before any component that reads these fields.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, badge inline padding, tier-box internal padding |
| sm | 8px | Compact element spacing, table cell vertical padding, chip gaps |
| md | 16px | Default element spacing, table cell horizontal padding, header stat-grid gap |
| lg | 24px | Section padding, event-section vertical rhythm |
| xl | 32px | Layout gaps between major page regions (header → event list, tab content padding) |
| 2xl | 48px | Major section breaks (between event sections) |
| 3xl | 64px | Page-level spacing |

**Exceptions:**

- **44×44px minimum tap target**, inherited from Phase 5 — applies here to the tab triggers, the year-dropdown trigger, and the mobile horizontal-scroll affordance on the match table.
- **Chart/match-table geometry constants are locked pixel values, not on the 4px base scale** — carried verbatim from `chart-craft.md`/`uncertainty-display.md` and must not be re-derived: `BAND_H = 8`, `DOT_H = 12`, `TICK_H = 14`, `PLOT_H = 44`, with `Y_RED = 12`/`Y_BLUE = 24` (12px between alliance centres within one match row) against a measured ~47px between-match gap (the ~4× proximity ratio `chart-craft.md` found necessary for correct visual pairing). **Every derived `top` value must come from one computed source** (`centre = yBand + BAND_H / 2`, etc.) — this is the exact bug the chart-craft reference names as already having shipped once and been caught only by direct inspection.

## Typography

Inherited unchanged from `05-UI-SPEC.md`.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label | 12px | 600 | 1.3 |
| Heading | 20px | 600 | 1.2 |
| Display | 28px | 600 | 1.2 |

Two weights only: 400 (regular) and 600 (semibold) — no 500 or 700 anywhere.

**This phase's usage additions:**

- **Team name/number (page header):** Display 28/600 — this phase's first non-wordmark use of Display scale; the team page is the one place a "hero number" (the team number) belongs.
- **Event section heading (event name + date):** Heading 20/600, same role as the Teams/Events page titles.
- **Match table cells (scores, RP, times):** Body 14/400, `numeric-cell` class (tabular figures) for every numeric value — team numbers, scores, RP, confidence percentage.
- **Sigma display format is unchanged from D-07** (Phase 5, locked): `{value} ± {spread}`, value at Body 14/400 primary ink, ` ± {spread}` suffix at Label-size/400-weight (the one deliberate Body-weight-at-Label-size exception) in `--color-text-muted`. This applies identically to the season-header metric chips (D-17) and, where variance exists, the match-prediction bands.
- **D-17's tier-boxed header grid** reuses this same value/spread typography *inside* a `.metric-tier` box (see Color section) — the tier box changes background/foreground color and padding, never the type scale or weight.

## Color

Inherited unchanged from `05-UI-SPEC.md`'s 60/30/10 split — no new surface colors this phase.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#F8FAFC` (slate-50) | Page background |
| Secondary (30%) | `#F1F5F9` (slate-100) | Event-section card surfaces, robot-image fallback tile background, alternating chart event-bands |
| Accent (10%) | `#4F46E5` (indigo-600) | See extended reserved-for list below |
| Destructive | `#DC2626` (red-600) | Error-state icon/text, retry-button border, chart-load-failure state — never a fill on a primary action (still no delete/remove action exists in this phase) |

**Accent reserved for (extends Phase 5's list — same token, no new hex, additive elements only):** the active ribbon link's underline (unchanged), the "View on TBA" external-link CTA (new this phase — see Copywriting Contract), **the active tab indicator** (Overview / Metric History — new this phase), the D-19 empty-state active-year link chips (new this phase), focus rings on every interactive control, the sort-active column arrow (unchanged, N/A on this phase's tables since none are sortable), and the search dropdown's keyboard-highlight tint (unchanged). **Never used for:** alliance identity (red/blue are a separate, non-negotiable domain vocabulary — see below), tier boxes (their own three-color system), body text, or any static surface.

**Two additional locked color systems from the sketch findings — neither is part of the 60/30/10 split, both are non-negotiable domain vocabulary, not "accent":**

**1. Alliance colors** (`uncertainty-display.md`, validated ΔE 29.9 protan — safe as-is, do not adjust):

```css
--alliance-red:       #DC2626;   --alliance-red-soft:  rgba(220, 38, 38, .30);
--alliance-blue:      #2563EB;   --alliance-blue-soft: rgba(37, 99, 235, .30);
--loser-ink:          #94A3B8;
```

Used exclusively in the match table: soft band = predicted ±1σ per alliance, solid tick = predicted score, ringed donut dot = actual score (**always in alliance color, never greyed** — greying a plotted mark is explicitly disallowed, see `chart-craft.md`). The Actual-column *text* greys the losing number only (`--loser-ink`), a different job from the plotted dot — do not apply the same greying rule to both (this was a real, corrected mistake in sketch 003).

**2. Rarity tier tokens** (`colour-and-tiers.md`, validated — the sky value is load-bearing, see below):

```css
--tier-rare-bg:      #E0F2FE;  --tier-rare-fg:      #0369A1;   /* Rare: 50th-75th percentile */
--tier-epic-bg:      #F3E8FF;  --tier-epic-fg:      #7E22CE;   /* Epic: 75th-95th percentile */
--tier-legendary-bg: #FEF3C7;  --tier-legendary-fg: #B45309;   /* Legendary: 95th-100th percentile */
/* Common (0-50th percentile) has NO tokens — renders as a plain, untreated cell. */
```

**THE TIER BLUE MUST STAY SKY `#0EA5E9`/`#E0F2FE`, never true blue `#3B82F6`.** Against tier purple, true blue measures ΔE 1.3 under deuteranopia — Rare and Epic (45% of the field combined) become the same color to ~6% of male users. This was tested and rejected once already; do not re-propose it. Any future change to either value must be re-run through the dataviz skill's `validate_palette.js` before shipping.

**Where tiers apply this phase (D-17, resolving the sketch findings' "where tiers earn their place" question for the team page specifically):** the season-header metric grid tier-boxes **every** component column, including Total — this is explicitly the one-team view the sketch findings identify as the case where a single team's components genuinely span tiers (worked example: team 3313, Rare overall but Epic in Hub Auto). This differs from the Teams table, where the sorted Total column is deliberately left unboxed because it's flat by construction — the team page has no such flatness, so Total is boxed here too.

**Call-column glyphs use plain text ink, not a new success/failure color.** The match table's ✓/✗ "did the predicted winner match" column renders in `--color-text-primary`, not green/red — this project's validated palette has no success-green token, and introducing one unvalidated for a single glyph column would violate "color carries meaning, never decorates." `aria-label="Prediction correct"` / `"Prediction incorrect"` carries the semantics for assistive tech instead of a color pairing.
