    Create `packages/harness/percentiles.ts` exporting `percentileRanks(values: readonly number[]):
    number[]` and `withPercentiles(metricsByTeam, teamKeys)`.

    Lock the formula as the **mid-rank percentile**: for a metric name, over every team in the pool
    that has a value for it, a team's percentile is
    `(countStrictlyBelow + 0.5 * countEqual) / n * 100`. Equal values therefore receive an equal
    percentile, which is what makes the ordering deterministic and the tier boundary well-defined.
    Teams with no value for that metric receive no percentile at all — never a coerced 0, which
    would read as bottom-of-field. Compute in one pass per metric name using a sort plus a rank
    sweep, not an O(n^2) comparison, since the pool is roughly 3,700 teams per season across three
    algorithms.

    Round each percentile with `roundTo(pct, ROUNDING_RULE.percentile)` so the published value is one
    decimal, matching the tier reference's own worked precision.

    `withPercentiles` returns a new metrics record with `percentile` merged onto each
    `TeamMetric` — it must not mutate its input, because `metricsByTeam` is shared by both downstream
    consumers.

    In `publish.ts`, call `withPercentiles(metricsByTeam, teamsThisSeason)` immediately after
    `metricsByTeam` is assembled and before either consumer reads it. That single point is what makes
    the ranking run once per (algorithm, season) rather than twice. Per RESEARCH's open question 2,
    build it so both consumers *could* read it, but wire only the per-team artifact's consumption
    this phase — the teams-table artifact's own tier boxes are a later phase's decision, and widening
    the teams artifact's published surface here is beyond what D-04 authorizes.
