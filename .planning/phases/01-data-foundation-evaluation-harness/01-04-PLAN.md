<objective>
Turn the tracer's working-but-narrow OPR into the honest no-variance baseline ALGO-01 asks for, and fix
the rating-eligibility policy that D-07 leaves partly open.

Purpose: OPR is the number every later algorithm is measured against. If it is quietly bad — rank
deficient early in a season, distorted by surrogate appearances, or silently divergent — then "Sigma1
beats OPR" means nothing. RESEARCH.md Pitfall 2 names the specific trap: solved per-event with too few
matches the system is rank deficient, which is the identifiability failure this project's failure log
already recorded once. Two mitigations applied together fix it — pool observations across every event a
team has attended so far this season, and add a ridge penalty so the solve stays well posed while the
design matrix is still thin.

D-07 locks that a surrogate appearance produces no rating update and no record impact for the surrogate,
and explicitly leaves open how that surrogate's slot is treated in the alliance observation for the other
five teams. This plan resolves that within D-07's constraint.

Output: An OPR baseline whose behavior is proven on synthetic data with known answers, and a documented,
tested rating-eligibility policy.
</objective>

  <action>
    Rewrite the OPR implementation around season-scope pooling and a regularized solve.

    `OprState` holds the accumulated alliance-score observations for the season so far, the team index
    mapping team key to matrix column, and the most recently solved rating per team. `update` appends the
    two alliance observations from a completed match to the accumulated set and re-solves. `predict` sums
    the current rating of each alliance's rating-eligible teams into a predicted alliance score and
    converts the predicted margin into a red-win probability through a logistic function.

    Implement `solveRidgeOpr(observations, teamIndex, lambda)` following RESEARCH.md Pattern 4: build the
    participation matrix with a 1 in each participating team's column, form the normal equations, add
    `lambda` times the identity before solving, and solve with ml-matrix's singular value decomposition.
    Do not hand-roll the linear solve — early-season systems are ill-conditioned by construction and a
    bespoke Gaussian elimination is exactly the kind of code that looks finished until one team's row makes
    it diverge.

    Pool at season scope, not event scope. A team's observations from every event it has attended so far
    this season all contribute to its rating at the next match. Solving per event reintroduces rank
    deficiency at the start of every single event; pooling means the design matrix only ever accumulates.

    Name the ridge coefficient `OPR_RIDGE_LAMBDA` and the logistic scale `OPR_LOGISTIC_SCALE` as exported
    constants with a comment giving the reasoning behind each value, so Phase 3's optimizer has an
    obvious, single place to search and nobody has to hunt for a magic number. Choose the logistic scale
    so that a margin of roughly one typical alliance-score standard deviation maps to a clearly confident
    but not saturated probability, and state the reasoning in the comment.

    Keep both functions pure. Phase 4 runs this same module inside a Cloudflare Worker where state is
    rehydrated per invocation, so mutating the state argument would work here and fail there.

    Re-solving on every update is acceptable at this phase's scale and keeps the implementation obvious;
    incremental solving is a Phase 3 concern driven by measured cost, not a guess made now.

    Write `packages/core/algorithms/opr.test.ts` covering every behavior above, driven entirely by
    synthetic fixtures with known answers so failures point at the math rather than at the corpus.

  <action>
    Implement `ratingEligibleTeams` and `allianceObservation` to resolve the surrogate question D-07 leaves
    open, within D-07's constraint that a surrogate receives no rating update and no record impact.

    The approach: treat the surrogate as a known quantity rather than an unknown. For an alliance
    containing a surrogate, place a 1 in the design-matrix column of each non-surrogate team only, and
    subtract the surrogate's current rating from that row's target alliance score. The surrogate's
    contribution is thereby accounted for as a fixed offset instead of being either attributed to
    teammates or thrown away with the whole row. The surrogate's own column never appears, so it receives
    no update — which is exactly what D-07 requires — while its teammates keep a correctly-scaled
    observation. Dropping the entire row instead would discard real information about two or three
    non-surrogate teams; leaving the surrogate's column in would update its rating in violation of D-07.
    Where the surrogate has no rating yet, use the current league-mean per-team share as the offset and
    note in a comment that this is the cold-start substitute.

    Take the opposite position on disqualifications, and say why in the source. A disqualified team
    physically played the match and physically contributed to the alliance's score; a disqualification is
    a ranking-and-record ruling, not a statement that the robot was absent. OPR models score contribution,
    so removing a disqualified team's column would misattribute its real contribution to its teammates.
    Keep the column and update the rating. No locked decision covers this, so record the reasoning in a
    comment next to the code and in the plan summary — the data to reverse the call is stored by Plan 03
    either way.
