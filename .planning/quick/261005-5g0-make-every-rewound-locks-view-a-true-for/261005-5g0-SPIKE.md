### The format as built

Team tuple `T = [spr | null, sigma | null, vars | null]` with `spr = [muL, pL, muS, pS]`, `sigma = [meanWeight, mean, varWeight, sumSquares, talent]`, `vars = [[weight, weightSquares, mean, m2] | null, ...]` in rule-module order.

League tuple `L = [logTau, scale, sigPopSumSquares, sigPopTalentSquares, sigPopCount, (n, mean, m2) x V, (count, sum) x V]`.

INDEX team entry, per the coordinator's mid-task change: `{ f, l, p: [prevEventKey, prevSortTime] | null, s, x }`, with `s` always present. `prevSortTime` is the sort_time of the team's last row at the previous event. The earlier layout (`s` only where `p` is null) is measured as a variant; it carries `p`, not `from`, so it is one number per entry larger than the first brief's layout.

Every match in the stream has a row, including Week 0 rows that never fold and fully demo rows SPR skips (state unchanged). Counts are in the table below.

Threshold variable count V per season: 2016 8, 2017 4, 2018 3, 2019 1, 2020 1, 2022 3, 2023 2, 2024 3, 2025 7, 2026 2.

## 4. Part 3: browser time, full Michigan rewind at season start

Payload: for each fim event with a qualification schedule, `eventKey`, `eventType`, `week`, tier, sorted roster, the real qualification schedule as roster indexes with surrogates, matches per team, and the season-start tuple per roster team from Part 2's lookup, plus one league tuple. 27 district events (1,061 roster slots, 2,122 quals) and 4 dcmp division events (161 roster slots, 322 quals). `2026micmp` is left out: it has no qualification match, and the offline bake excludes a divisioned DCMP parent too.

Payload size: 280,771 B raw, 75,954 B gzip, 41,641 B brotli (district events only: 243,448 / 66,138 / 38,462).

Draw count: the district simulation Web Worker uses `SIMULATION_DRAWS = 1000` and `DEFAULT_SIMULATION_SEED = 20260830`, defined in `apps/web/src/workers/simulationProtocol.ts` and re-exported by `districtSimulationProtocol.ts`. Arm R and Arm B use exactly that pair.

Arms. Each arm runs in its own fresh page (cold JIT), on the page main thread.

- **Arm R**: per event, rebuild the as-of pricer, price every real qualification match (`roundPmf` on both pmfs), build `DistrictLedgerEventInput` (`fieldSize` = roster size, `allianceCount` 8, zero baselines, `ratings` from the pricer, `ZERO_AWARD_PROFILE` for every team), one `simulateDistrictEvent(input, 1000, 20260830)`.
- **Arm G**: per event, 40 schedules x 100 draws, mirroring `bakeDistrictEvent` and `buildPricedSyntheticSchedules` (same `generate|n|mpt|k` and `eventKey|version|shuffle|k` seeds, surrogates filtered the same way, draw seed `shuffleSeed ^ 0x44157ca7`, pooled per team). 12 matches per team at every event (`matchesPerTeamFor`).
- **Arm B**: Arm R's work with pricing off the clock, so only the simulation is timed. This is what the rewound view costs today.

Throttle is CDP `Emulation.setCPUThrottlingRate`. A fixed in-page loop read 51.1 ms at 1x, 214.7 ms at 4x (4.2x) and 335.6 ms at 6x (6.6x).

## 5. What did not work, and where the code differs from the brief

1. **A team can be at two events at once, and the walk-back assumes it cannot.** The lookup treats a team's rows at one event as one unbroken interval. Counted on sort_time intervals, team and event pairs that overlap another event of the same team:

   | Season | Real teams | Demo robots |
   |---|---|---|
   | 2016 | 1 | 0 |
   | 2017 | 13 | 0 |
   | 2018 | 28 | 4 |
   | 2019 | 2 | 7 |
   | 2020 | 0 | 0 |
   | 2022 | 0 | 23 |
   | 2023 | 29 | 66 |
   | 2024 | 8 | 51 |
   | 2025 | 2 | 138 |
   | 2026 | 0 | 19 |

   Real-team cases are a DCMP or championship parent interleaved with its divisions (`2023oncmp` with `2023oncmp1`, `2023cmptx` with `2023arc`, `2024necmp` with `2024necmp2`), paired events sharing a field (`2018zhrcc` with `2018zhrcc2`, `2018txntx` with `2018txsg`), and same-weekend offseason events (`2023iri` with `2023txri`). A cut that falls inside such an overlap resolves that team from the wrong event. 2026 has none for a real team, which is why Part 2 is clean. This needs a rule before any season other than 2026 is trusted: for example a per-event log lookup whenever intervals overlap, or an INDEX flag on the overlapping entries. Not built, not measured.

2. **Demo robots.** SPR holds every demo robot under one shared pseudo key, so a demo key's SPR part changes whenever any demo robot plays anywhere. The capture stores the pseudo state at each demo row, but a per-key walk-back can return a stale SPR part for a demo key. No demo robot is in a fim roster and none mismatched in the truncation check (cut b is early in the season). Not otherwise tested.

3. **A time equal to the cut row's time cannot be ordered without a row index.** Section 3.2: 6 avoidable hops and 1 avoidable LOG read at cut c. Within 2026 no two rows of one event share a sort_time (measured: 0), but 183 sort_times are shared across events, which the `(t, eventKey)` ordering handles.

4. **`resolveTeamStateAt` is synchronous** over an in-memory file source. A browser version needs the same logic over fetched objects, with INDEX fetches discovered hop by hop (at most 3 outside-district INDEX files per cut here).

5. **`2026miche_qm40` is row 38 of its log, not row 39**: one earlier qualification match has no played row in the stream order before it. The cut is addressed by row index, so nothing depends on the match number.

6. **dcmp tier.** The brief's dcmp set is 5 events. `2026micmp` (the parent) is in Part 2 for ratings and in the size sums, and is out of Part 3 because it has no qualification match.

7. **Arm B is today's simulation cost on these inputs, not a replay of today's page.** The as-of pricer mirrors `makeRankingPointFiller`, which returns no outcome and bonus decomposition, so `SimMatchInput.outcome` is absent in all three arms, exactly as in the offline district bake. Today's page feeds the simulation rows that may carry the decomposition; that path was not timed.

8. **Arm G stops at the pooled histograms.** `bakeDistrictEvent`'s `encodeAndRound` goes through a zod schema in `pageArtifacts.ts`, which the browser-safe import rule excludes. The constants `DISTRICT_BAKE_SCHEDULE_COUNT`, `DISTRICT_BAKE_DRAWS_PER_SCHEDULE` and `DISTRICT_BAKE_DRAW_SALT` are copied into `browserRun.ts` for the same reason. Arm G's pooled output was not compared with a real `bakeDistrictEvent` run.

9. **Every season was captured with its own rule module**, where the oracle folds a Sigma-only layer for warmup seasons. Sigma folding never reads the rule module, and the 2026 results match the oracle bit for bit, which confirms the carry into 2026 is unaffected.

10. **JSON cannot carry `-0`.** None of the comparisons hit one. It would show up as an `Object.is` mismatch.

11. **Not measured:** the live Worker capture path, R2 write counts per tick, async fetch latency in a real page, the pricing error of the reduced-precision encodings, any season other than 2026 against the oracle, and the bundle increment against the real web app.
