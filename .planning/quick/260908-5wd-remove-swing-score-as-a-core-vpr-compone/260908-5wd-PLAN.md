<objective>
Relocate Swing Factor — the `Y` in `X ± Y` — from "a thing VPR emits" to "a thing
the site computes, for every algorithm, in the browser", and give the ribbon a
switch that turns it off.

Purpose: the developer's framing is that Swing Factor stopped being part of VPR's
model long ago and is now an extra metric bolted onto it. VPR's predictive output
does not depend on it (it is excluded from the tuning search space and invisible to
the objective), so nothing about prediction quality changes here — what changes is
whose number it is. After this task it belongs to the site, works for OPR and EPA
as well as VPR, and can be hidden.

Output: a pure, tested browser estimator; a Total-tile Swing Factor for OPR and EPA
on the team page where there was none; a persisted ribbon toggle that gates every ±
on the site from one place; a rewritten methodology guide; and a written, reasoned
deferral of the core code deletion.
</objective>

<scoping_findings>
Verified against the code before planning. These are the facts the three tasks are
shaped around; an executor that finds one of them false should stop and say so
rather than work around it.

**1. Swing is display-only, so removing it from core cannot change a prediction.**
`packages/harness/searchSpace.ts`'s `SEARCH_EXCLUSIONS` names both `swingScale` and
`swingHalfLifeMatches` as display quantities the objective is structurally blind to.

**2. The formula is already algorithm-generic.** A team's per-match deviation is its
share of its alliance's residual, `(observed - predicted) / n`. For the `total`
metric key that is exactly `(actualAllianceScore - predictedAllianceScore) / n`,
and `TeamSeasonMatchSchema` (`packages/harness/pageArtifacts.ts`) publishes every
term of it: `predictedRedScore`, `predictedBlueScore`, `actualRedScore`,
`actualBlueScore`, and required `redTeams`/`blueTeams` rosters. Artifacts are
algorithm-scoped, so the OPR artifact carries OPR's predictions and the EPA artifact
carries EPA's — the browser can compute this for any algorithm with no new data.

**3. The team page is the only surface with the input data, and that is a hard
limit, not a preference.** `TeamSeasonArtifactSchema.events[].matches[]` carries the
per-match rows. `TeamsTableRowRawSchema` (the `/teams` artifact) carries aggregate
`metrics` only — no per-match anything — so a browser-computed Swing Factor is not
reachable on the teams table without a payload change and a republish, both out of
scope here. The event artifact has matches but only for one event, which is a
different (within-event) quantity and is deliberately not built in this task.

**4. Published-wins is what makes this safe to ship against live artifacts.** The
`sketch-findings-sigmascout` skill's load-bearing rule is *one ± quantity,
everywhere*: a team's `spread`, an alliance's combined ±, and a match row's band
reconcile by summing squares. `redScoreVarianceOwn` is defined in the schema as the
sum of its three teams' `spread` squares. If the browser value replaced a published
VPR spread, that identity would break silently and the teams table would print a
different Swing Factor than the team page for the same team. So the browser value
**only fills a spread the artifact did not publish** — which today means OPR and EPA
and never VPR. This is the same merge discipline `lib/metricGroups.ts`'s
`withDerivedGroupMetrics` already uses, for the same reason.

That merge rule is also the removal path: when a future model version stops
publishing `spread`, the browser value takes over on its own, with no further code
change. That is why deleting it from core now buys nothing.

**5. Deleting swing from core is a major params bump and is deferred, with a
reason.** `Sigma1ParamsSchema` is a `z.strictObject`; dropping `swingScale` /
`swingHalfLifeMatches` forces a params major, a new `legacyParams.ts` migration, a
`stateSnapshot.ts` shape bump (7 -> 8) that invalidates live worker D1 state, and a
migration pass over every promoted set in `data/algorithm-versions/`. The task
constraints forbid touching those artifacts and forbid re-running tuning, so the
deletion cannot be done here. Task 3 records it as a pending todo tied to the next
model major rather than leaving it unstated.

**6. No new dependencies.** `zustand@5.0.15` is already in `apps/web/package.json`
and its `persist` middleware ships in the package. Nothing is installed, so no
package legitimacy gate applies.
</scoping_findings>
