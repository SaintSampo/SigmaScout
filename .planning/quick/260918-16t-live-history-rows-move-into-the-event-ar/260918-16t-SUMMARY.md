## The strip-on-republish proof

The publisher parses with `EventArtifactSchema`, which does not declare `live`; zod objects strip unknown keys. So the next republish emits a body with **no `live` key at all**, with no publisher change and no delete call anywhere. That asymmetry is the whole ephemerality mechanism.

Proven in three places:

1. `packages/harness/pageArtifacts.test.ts` — a live body carrying a populated block, parsed by `EventArtifactSchema`, comes back with no `live` key. The assertion message says this strip is what makes a republish drop the rows, and names the failure mode if someone adds the key to the publisher's schema.
2. `packages/harness/liveEventRows.test.ts` — the same claim end to end, on a body produced by the **real** merge and a **real** serialization, with a non-vacuity check that the body going in really carried populated rows.
3. **Mutation-verified.** Adding `live: EventLiveBlockSchema.optional().catch(undefined)` to `EventArtifactSchema` fails both tests (see Mutation testing below).

## Carry-by-reference, and what the sidecar's 9.5 ms actually was

Per the orchestrator's amendment, `mergeEventLiveBlock` carries stored rows **by reference**. The only copy is of the array (`[...existing.rows]`) — one allocation — so the caller's fetched object is not mutated in place. Rows are constructed once and never mutated afterwards by the merge, by the body they are embedded into, or by `liveRowsForTeam`, which only reads. No defensive copy was needed anywhere, so no call site had to justify one.

The deleted sidecar's merge did `existing.rows.map(row => ({ m, t: [...row.t], v: row.v.map(values => [...values]) }))` — at 147 rows × 6 teams that is ~1,030 row objects plus ~1,030 team arrays plus 147 `t` arrays ≈ **2,200+ allocations per tick**, and with the inner value arrays the ~4,400 figure is the right order.

**What was learned about the 9.5 ms: nothing conclusive, and that is the honest answer.** The measurement never separated bytes from per-row work, so the deep copy remains a *live suspect* rather than a *finding*. Two things address it rather than leaving it to hope:

- The deep copy is gone, and its absence is pinned **by identity** (`expect(block.rows[0]).toBe(first.rows[0])`), which fails the moment anyone restores it.
- The probe now has a separating arm (below), whose difference from the full arm **is** the per-row cost.

This is written into the bar's "what weakens the prediction" section so a clean number cannot be read as having explained the 9.5 ms.

## The size guard

| Quantity | Bytes | Source |
|---|---|---|
| `event` page ceiling | 350,000 | `PAGE_BUDGET_MAX_BYTES.event` |
| largest published event body | 228,971 | `v1/event/2016micmp/spr@4.0.0+baseline.json` |
| live row | ~330 | measured 260917-jr4 |
| a 241-match 2016-shaped event's live rows | ~79,530 | 241 × 330 |

**Worst realistic case: 228,971 + 79,530 = 308,501 B — 88% of the ceiling, 41,499 B spare. It FITS.** The 140-match championship division against the same body is 275,171 B (79%).

The guard: when the body **read from R2 this tick** exceeds 300,000 bytes, the merge retains only the most recent 40 rows and logs `event-live-block-trimmed`. The input is free (`.length` of text the tick already holds), so no second stringify. Never a throw, never a truncation of anything but live rows.

The named gap — **a live event carries an `EventStateBlock` a finished published event does not**, sized by roster — is stated in the threshold constant's own doc comment rather than guessed at, along with what the chart loses when the trim fires. A Node-run test pins `EVENT_LIVE_BLOCK_TRIM_THRESHOLD_BYTES < PAGE_BUDGET_MAX_BYTES.event` so the two cannot drift (the constants live in `pageArtifacts.ts`, not `publishBudget.ts`, which imports `node:path` and is not Worker-safe).

## The probe arms as built

Built as **one arm with a suffix**, not two arms: `liveRows=N[:carry]`.

- **`liveRows=147`** — seeds 147 rows into the event body **by string splice onto `measuredEventText`, before the measured parse**, then lets the tick append its own folded rows. The splice is the load-bearing instrumentation decision and its reason is in the function's doc comment: a parse-then-restringify of a ~121 KB body would bill this arm ~2 ms the real tick never pays — the same confound `phaseBUpcoming=scheduled` already warns about.
- **`liveRows=147:carry`** — **the separating arm** (orchestrator amendment 2). Same seed, appends **nothing**, by handing the merge an empty `realTouchedTeams`, which makes `maintainedLiveBlock` carry the block forward by reference and never call `mergeEventLiveBlock` at all. So `:carry` prices **bytes only** (bigger parse, same O(1) guard, bigger stringify), and `liveRows=147` − `liveRows=147:carry` is **the work done per carried row**. A test pins that both arms produce byte-identical seeded bodies, so their difference is attributable to that work and nothing else.

Reported counters: `liveRowsSeeded`, `liveRowsMerged`, `liveBlockBytes`, `seededEventTextBytes`, plus `params.liveRows` / `params.liveRowsAppend`.

**One improvement on the plan:** the plan asked for `liveBlockBytes`. Computing it as `JSON.stringify(mergedEvent.live).length` would be a *second* serialization the real tick never performs, billed to the very number the arm produces. It is instead the **spliced block text's own length**, measured at splice time for free. A test pins `seededEventTextBytes === eventArtifactBytes + liveBlockBytes + 1` (the comma), so the counter is not merely asserted but arithmetically checked.

Also built: the **retired-parameter guard** — a present `sidecar=` pushes a loud warning naming the deletion and both replacements, and changes nothing else. Values derived from the row index, never a clock (`Date.now()` is never called in that file), so two runs at the same N are byte-identical. The synthesized text's validity under the **real shipped** `EventLiveBlockSchema` and `LiveEventArtifactSchema` is proven in `stateProbe.test.ts`, never by a runtime parse in the arm.

## The pre-registered bar

Committed in `.planning/todos/pending/rp-fold-exceeds-worker-cpu-budget.md`, immediately **above** the `IT DID NOT WORK` sidecar verdict. Nothing in it is a number this change produced.

Arms: `allPhaseB`, `pbTeams0`, `pbLiveRows` (`liveRows=147`), `pbLiveCarry` (`liveRows=147:carry`, explanatory only).

**VALIDITY GATE, all four before reading any result:** `allPhaseB` mean within 17.5 ± 3.0 ms; `pbTeams0` mean within 9.9 ± 3.0 ms; fold counters / `bandsProduced` / `liveRowsSeeded` identical across the arms that ran them; zero non-ok outcomes.

**Prediction (committed before any number):** ~45 KB at 147 rows onto a body already being parsed, at the event half's measured ~15.7 µs/KB, is roughly **0.7 ms** — so `pbLiveRows` should land near `pbTeams0` (12.2 ms) rather than near `pbSidecar` (21.7).

**IT WORKED — all three required:** `pbLiveRows` − `pbTeams0` ≤ 3.0 ms; AND `pbLiveRows` mean ≤ 14.0 ms with p50 ≤ 14; AND `allPhaseB` − `pbLiveRows` ≥ 4.0 ms and larger than the two arms' combined standard errors.

**IT DID NOT WORK — any one:** `pbLiveRows` − `pbTeams0` ≥ 6.0 ms; or `pbLiveRows` mean ≥ 17.0 ms; or `allPhaseB` − `pbLiveRows` not resolved above the combined standard errors.

**Stated in advance so a good number cannot be over-read:** a clean pass does **not** close the todo. The prediction is about 12.9 ms mean, still over the 10 ms budget, and fresh isolates stay at 35–45 ms untouched by anything here. What a pass buys is that **Phase B stops being the blocker** — not that the tick fits.
