These were settled during planning against the source files. Implement them; do not re-open
them mid-task. Where a choice remains open it is named as such.

**S-1 — `LiveEventArtifactSchema` carries the block; `EventArtifactSchema` must never.**
`LiveEventArtifactSchema = EventArtifactSchema.extend({...})` already exists for exactly
this class of live-only widening (`upcoming` rows may be schedule-only). Declaring `live` in
that `.extend()` and nowhere else buys three things at once with no new mechanism:
the Worker's writer validates it (`SCHEMA_BY_PAGE.event` is `LiveEventArtifactSchema`), the
web parses it for free (`apps/web/src/lib/api/event.ts` parses with the same schema), and the
offline publisher — which stays on `EventArtifactSchema` — **strips it on the next
republish**, because zod objects strip unknown keys. The publisher needs NO change and never
sees the block. That strip is the answer to both "how is it marked ephemeral" and "what
happens at the next republish", and it replaces the sidecar's `ephemeral: true` literal with
a structural guarantee rather than a convention.

**S-2 — what travels, and what the block drops.** Keep the sidecar's compact positional
encoding verbatim: a `metricKeys` header stated ONCE, and per-row `m` (match key), `t` (team
keys) and `v` (per-team value arrays index-aligned to the header, `null` for absent). Values
only — no `spread`, no `percentile`, no `matchIndex` — and every value rounded through
`roundMetric`, so no published number changes. The block DROPS eight of the sidecar's
wrapper fields as redundant, because the event artifact already carries them at top level:
`sidecarVersion`, `ephemeral`, `eventKey`, `season`, `algorithmId`, `algorithmVersion`,
`computedAt` and `complete`. Nothing read `complete`. The block is therefore exactly
`{ metricKeys, rows }`.

**S-3 — staleness needs no new guard.** Both of the sidecar's guards survive unchanged and
for the same reasons: the algorithm VERSION is a segment of the event artifact's own key, so
a model change ships under a new key rather than a bad merge; and the consumer drops any row
whose match key the published history already covers.

**S-4 — the size guard.** The arithmetic, from `docs/publish-budget.md`'s committed budget
block and the 260917-jr4 row measurement:

| Quantity | Bytes | Source |
|---|---|---|
| `event` page ceiling | 350,000 | `PAGE_BUDGET_MAX_BYTES.event` |
| largest published event body | 228,971 | `v1/event/2016micmp/spr@4.0.0+baseline.json` (a 241-match 2016 DCMP) |
| p95 published event body | 105,559 | same block |
| live row | ~330 | measured 260917-jr4 (~45 KB at 147 rows) |
| a 140-match championship division's live rows | ~46,200 | 140 x 330 |
| a 241-match 2016-shaped event's live rows | ~79,530 | 241 x 330 |

Worst realistic composition — the largest published body carrying its own event's full
weekend of live rows, never republished: **228,971 + 79,530 = 308,501 B, 88% of the
ceiling, 41,499 B spare.** The 140-match championship division against the same largest
body is 275,171 B (79%). **The worst realistic case FITS.** One term is not in that
arithmetic and must be named in the guard's doc comment rather than guessed at here: a LIVE
event carries an `EventStateBlock` that a finished published event does not, sized by roster.

So the guard is a backstop for a defect or a genuinely unforeseen shape, not an expected
behavior: **when the event body READ FROM R2 this tick already exceeds
`EVENT_LIVE_BLOCK_TRIM_THRESHOLD_BYTES` (300,000), the merge retains only the most recent
`EVENT_LIVE_BLOCK_TRIM_RETAIN_ROWS` (40) live rows and logs `event-live-block-trimmed`.**
That input is free — the tick already holds the fetched text and its `.length` — so the
guard costs no second stringify. Never a throw (a throw loses the tick's rows permanently;
the cursor has already advanced) and never a truncation of anything but live rows.

**What the chart loses when the trim fires**, stated rather than discovered later: the
EARLIEST live rows at that event vanish, leaving a gap between the last published row and
the retained ones. `buildMetricSeries` plots array position, so the x-axis compresses across
that gap. `preMatchMetrics` for a match inside the gap falls back to the row preceding it —
now the last published row, stale but true, not wrong. `endOfEventMetrics` and
`officialSnapshotRow` take the LAST matching row and are unaffected. It self-heals at the
next republish.

**S-5 — import-graph split.** `packages/harness/liveEventRows.ts` is on the BROWSER's import
graph and may import nothing but `zod`, `./rounding.js` and types from `./pageArtifacts.js`.
The tick-side builder that folds `SIGMA_METRIC_KEY` and `touchedSigma` into a row's value map

**S-6 — the new subrequest arithmetic.** `estimateEventSubrequestCost` becomes **`2 + 4A`**:
claim, event detail, Phase A read + write, Phase B event read + write. The sidecar's `2A`
term is deleted. It stays FLAT in the touched-team count, so `liveAlgorithmTier.test.ts`'s
property test survives unchanged in intent.
