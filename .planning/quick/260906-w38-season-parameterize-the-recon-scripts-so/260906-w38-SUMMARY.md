# Quick Task 260906-w38: Season-parameterize the recon scripts — Summary

The three TBA reconnaissance probes now sit on a shared spine and take `--seasons`, so extending
the corpus to 2018, then 2017, then 2016 requires **no new script files**. This is investment #2
of the two named in `extend-corpus-2018-2017-2016.md`'s "Then 2017, then 2016"; investment #1
landed as quick task 260906-8kd.

**Task 3** (`89fae189`, by the orchestrator — see below for why).

## The substantive change: enumerate, don't name-filter

The obvious design — discover RP flags by matching `/RankingPoint|Achieved|Bonus/` — is wrong, and
a probe on 2026-09-06 showed it fails in **both** directions:

- **False negatives.** 2016's actual bonus RPs are `teleopDefensesBreached` and
  `teleopTowerCaptured`. No RP-shaped name exists in that season at all, so a name filter reports
  *zero* RPs for 2016 and says nothing about it. 2016 is explicitly in this job's scope.
- **False positives.** `quintetAchieved` (2022) is a prerequisite; `coopertitionCriteriaMet`
  (2023/2025) is not an RP; 2025's `g206Penalty`/`g410Penalty`/`g418Penalty`/`g428Penalty` are
  penalties. All would be presented as ranking points.

So the probes now enumerate every boolean field and report each one's base rate, leaving the
"which of these is a ranking point" judgement to the human reading the output. Boolean counts run
2–8 per season, so there is no volume argument for filtering. Two fixture tests pin this
behaviourally — a 2016-shaped false-negative case and a 2022-shaped false-positive case — so
rewording a comment cannot invalidate them.

## Equivalence proof — run before the old scripts were trusted as retired

All probes wrote to a scratch directory outside the repo, so no run could touch `docs/data/`.

**Tier A — single event `2020isde1`:**
- Fields probe: 12 matches, 24 alliance-sides, 34 distinct keys, `rp` present. The 34-row key
  table compared **mechanically** against the committed `## 2020` section — identical.
- Rates probe: enumerated exactly the six booleans the committed field table records for that
  event, including `tba_shieldEnergizedRankingPointFromFoul` — the sixth, which the old hardcoded
  five-flag list never tracked. That row is the visible evidence that enumeration is a genuine
  superset.

**Tier B — numeric equivalence:**
- Fields, `--seasons 2019,2020`: both the 2019 (51-row) and 2020 (34-row) key tables byte-identical
  to the committed document.
- Rates, full 2020 walk: 186 in-season events listed, 52 that played quals, 3,806 qualification
  matches, 7,612 alliance-sides; `shieldEnergizedRankingPoint` 0 (0.0%), `shieldOperationalRankingPoint`
  1,119 (14.7%), `stage1Activated` 5,033 (66.1%), `stage2Activated` 37 (0.5%), `stage3Activated`
  0 (0.0%); `rp` distribution 0→3,612 (47.5%), 1→217 (2.9%), 2→2,835 (37.2%), 3→948 (12.5%).
  Every figure matched.
- Thresholds, full 2020 walk: 7,640 alliance-sides, and a containment check confirmed all five
  committed 2020 rows reproduce **byte-identically**.

2020 was the only season walked in full, chosen because it is the fragment season (52 events with
quals against 2019's 189) — a deliberate rate-limit boundary.

## 7,640 vs 7,612 — both correct, and now guarded

The rates probe filters events by `IN_SEASON_EVENT_TYPES` (types 0–6); the thresholds probe filters
by `EVENT_TYPE_TIERS`, which also admits preseason. The same 2020 season is therefore 7,612
alliance-sides in one document and 7,640 in the other. The planner caught this; unifying the two
filters in the shared module is the obvious-looking cleanup and would have silently moved every
number in `tba-rp-thresholds-2019-2020.md`. The filters are kept distinct, with the evidence
commented at the definition site and restated in both the evidence doc and the todo.
