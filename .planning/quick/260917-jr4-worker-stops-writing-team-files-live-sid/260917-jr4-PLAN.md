## Design decisions, settled before any code

These are settled. Do not re-open them; if one turns out to be wrong, STOP and report rather than
substituting a different one.

### D-01 — The sidecar's key, shape and lifecycle

**Key.** `v1/live/{eventKey}/{algorithmId}@{version}.json`, built by a new exported
`liveMetricSidecarKey({ eventKey, algorithmId, version })`. A NEW top-level prefix, a sibling of
`v1/event/` and `v1/presim/`, chosen so a list-driven sweep can delete the whole prefix and so
nothing can mistake it for a published page. `preScheduleKey` in `packages/harness/pageArtifacts.ts`
is the precedent for the one-function-one-spelling rule: the Worker and the web must import the
SAME function, never re-spell the key.

**Home.** `packages/harness/liveMetricSidecar.ts` — a new node-free, zod-only module, split for the
same reason `metricHistorySchema.ts` is split: it sits on the browser's import graph. It is
deliberately NOT in `pageArtifacts.ts`, so the sidecar can never join `PageKind` or
`SCHEMA_BY_PAGE`, which is the structural half of "never readable as authoritative published data".

**Shape** (compact by necessity — the sidecar is parsed and re-stringified every tick, so its bytes
are this change's new per-tick CPU cost):

- `sidecarVersion` — literal `1`.
- `ephemeral` — literal `true`. A reader that does not understand this key fails the parse.
- `eventKey`, `season`, `algorithmId`, `algorithmVersion` — identity.
- `computedAt` — the writing tick's ISO instant.
- `complete` — boolean, set `true` on the tick where the event's last match folds.
- `metricKeys` — the metric key header, stated ONCE for the whole sidecar, in the order the values
  arrays use. Includes `SIGMA_METRIC_KEY` as an ordinary member for a Sigma algorithm; there is no
  special case for Sigma anywhere in the encoding.
- `rows` — append-only, in fold order. Each row is one match: `m` the match key, `t` the array of
  team keys, `v` a parallel array of per-team value arrays index-aligned to `metricKeys`, with
  `null` for a key that team has no value for.

**What travels and what does not.** Values only. `spread` is NOT carried: SPR emits it
(`spr.ts` lines ~873 and ~888), it is read by nothing, `MetricValue` refuses to render it, and
`MetricHistoryChart` bands from the sigma entry precisely so it cannot regress onto it (finding 3
of the 260917-1zs audit). `percentile` is NOT carried: the live tick computes none today either —
`touchedEventTeamMetrics`'s own doc comment records that as a known limitation. `matchIndex` is NOT
carried; see D-06.

**Which teams.** `realTouchedTeams`, not `touchedTeams` — the same scope the team-artifact loop uses
today, so demo pseudo-team keys stay out.

**Size.** At roughly 330 bytes per match (match key, six team keys, six five-number arrays), a
147-match 2026 event ends at about 48 KB and a 241-match 2016-shaped event at about 80 KB. Add a
named byte ceiling constant and a `console.warn` above it. Do NOT throw and do NOT truncate: a
throw loses the tick's rows permanently (see D-04) and truncation would silently punch a hole in
the chart.

**Lifecycle.** Created lazily by the first tick that folds a match at the event (a 404 read
bootstraps an empty sidecar). Read-modify-appended on every tick that folds. Written on the
last-match tick with `complete: true`. NEVER deleted by the Worker. It becomes inert on its own the
moment the event is republished, because every row it carries is then a duplicate the browser drops
(D-05). Orphan cleanup of the `v1/live/` prefix is a follow-up todo, not this task; the bound is
tens of KB per live event.

**Staleness.** There is no generation check, and that is deliberate: the tick's own
`stamp.generation` is `tick-{nowMs}` (`scheduled.ts` line 1111), invented per tick, never the
publisher's — so a generation comparison against a team artifact is structurally impossible.
Two real guards replace it, and together they are exact rather than heuristic:

1. **The version segment of the key.** A model change ships under a new algorithm version (Jacob,
   2026-09-14: changed published numbers MUST ship under a new version). A new version is a new key,
   so a sidecar from a superseded model is a 404, not a bad merge.
2. **Match-key dedup** (D-05). A sidecar row for a match the published `metricHistory` already
   covers is dropped, whether the sidecar is stale or fresh — it is redundant by construction.

**Key-set drift.** If a tick's computed `metricKeys` differ from the stored header, discard the
stored rows and bootstrap a fresh sidecar rather than mis-aligning the value arrays. Log it.

### D-02 — The new subrequest arithmetic, stated

Today: `estimateEventSubrequestCost(A, T) = 1 (claim) + 1 (event detail) + 2A (Phase A read+write)
+ 2A(1 + T) (Phase B: event plus T teams, read+write each)`, i.e. `2 + 4A + 2AT`. At `A=3, T=6`
that is 50, the figure `liveAlgorithmTier.test.ts` uses as its counterfactual.

New: the team term disappears entirely and a sidecar read+write appears per algorithm:
`1 (claim) + 1 (event detail) + 2A (Phase A) + 2A (Phase B event) + 2A (Phase B sidecar)`, i.e.
**`2 + 6A`**. `A=1` gives **8**; `A=3` gives **20**.

Consequences to handle explicitly, not by accident:

- `touchedTeamCount` leaves the signature. Every caller and test must be updated.
- A realistic spr-only event tick falls from 30 (`A=1, T=12`) to **8**. Against ~47 usable
  subrequests, events affordable per tick goes from about 1 to about 5.
- **The subrequest counterfactual for the spr-only live tier evaporates.** `A=3` was 50 against
  ~41 usable; it is now 20, which fits. `liveAlgorithmTier.test.ts`'s budget-shaped regression test
  must be restated so it still says something true — the live tier's remaining justification is the
  CPU budget, not subrequests. Do NOT leave a test asserting a number that no longer constrains
  anything.
- `SUBREQUESTS_PER_LIVE_TICK = 64` in `scheduled.rp.test.ts` is an OBSERVED whole-fixture count.
  Re-derive it from the delta (minus 2 per team artifact removed, plus 2 per algorithm-event that
  wrote a sidecar), record the predicted value in a comment BEFORE running, then run. If the
  observed value differs from the prediction, STOP and report — do not re-pin whatever falls out.

### D-03 — Predicted per-tick CPU

From the warm pass in RE-MEASURED AFTER F2: team merge+stringify ×12 costs 2.6 ms over roughly
400 KB parsed plus 400 KB stringified (~6.5 µs/KB); event merge+stringify costs 1.3 ms over
~146 KB (~9 µs/KB). A 48–80 KB sidecar therefore costs roughly 0.4–0.7 ms warm, and scaling by the
team half's own cold/warm ratio (7.6 cold vs 4.4 warm, ~1.7x) gives **roughly 0.7–1.2 ms cold**,
plus its shape guard.

**Prediction, written before the measurement:** the new tick lands at about **11 ms mean** on the
reused-isolate stratum — `pbTeams0`'s 9.9 ms plus about 1 ms — against today's `allPhaseB` 17.5 ms.
That is a ~6.5 ms reduction and **still over the 10 ms budget**. Task 3's bar is built on this
prediction and is registered before the run.

### D-04 — Idempotency, failure and correctness

- **A tick that folds two matches** writes two rows, both carrying the SAME end-of-tick metrics,
  because `info.touchedMetrics` is read once per tick. This is exactly what `mergeTeamSeasonArtifact`
  does today (`matches.map` reuses one `metrics` record for every row). The flaw is PRESERVED, not
  introduced, and not fixed here. Name it in the sidecar module's doc comment.
- **A re-run tick** cannot re-fold a match: `claimEventAdvance`'s compare-and-swap on
  `event_cursor.last_folded_match_key` runs before any state is read. Belt-and-braces anyway: the
  merge replaces a row with an existing `m` in place rather than appending a duplicate.
- **A failed sidecar WRITE is permanent for those matches.** The cursor has already advanced, so
  those matches will never be folded again. Phase B is best-effort (`runPhaseBAndReport`'s blanket
  catch). What the page sees: a gap in the metric-history chart for those matches, and nothing else
  wrong — `endOfEventMetrics` and `officialSnapshotRow` both take the LAST matching row, so the
  later rows still carry correct tiles. It self-heals at the next republish. Accepted; log it under
  a named message.
- **A failed sidecar READ must not bootstrap over the sidecar.** `readArtifactObject` already
  distinguishes a genuine miss (`undefined`) from budget exhaustion (a thrown
  `ArtifactReadBudgetExhaustedError`). A THROW must skip the sidecar write entirely for that tick;
  only `undefined` bootstraps. A shape-guard rejection also bootstraps — losing prior rows is the
  correct self-healing outcome for a corrupt sidecar, and it matches the artifact read path's own
  contract.
- **A team playing two events in the same window** gets two sidecars, one per event, each with that
  team's metrics as of its own tick. The browser orders the blocks by the published
  `events[].startDate`, then within a block by sidecar order (D-06). A team cannot physically play
  at two events at once, so that reproduces chronological order; if two events share a start date,
  the published `artifact.events` order breaks the tie. State the limitation, do not engineer around
  it.

### D-05 — What the browser derives, exactly, and where it lives

New pure module **`apps/web/src/lib/liveTeamSeason.ts`** (no React, no Recharts), so the team page,
the metric-history tab and the match page all read ONE implementation. The design point is that it
has exactly ONE extension primitive and every existing consumer is fed by it UNCHANGED:

- `extendMetricHistory({ artifact, sidecars })` returns a `MetricHistoryRow[]`: the published
  `artifact.metricHistory`, then per live event (ordered by that event's `startDate` in
  `artifact.events`, ties broken by `artifact.events` order) that sidecar's rows for this team, in
  sidecar order, **dropping any row whose match key already appears in the published history**. That
  drop is the double-count guard and the staleness guard at once.
- With that array in hand, **`officialSnapshotRow`, `endOfEventMetrics`, `buildMetricSeries`,
  `detectEventBands`, `drawsSigmaBand` and `preMatchMetrics` are all UNCHANGED** and become correct
  during a live event for free. Do not write a second chart path, a second snapshot resolver or a
  second pre-match resolver.
- `deriveSeasonRecord({ artifact, overlaidEvents, eventArtifactsByKey })` returns
  `{ wins, losses, ties }`. **The double-count hazard, explicitly:** the published
  `seasonStats.record` already counts every played row the PUBLISHER saw. The overlaid rows include
  those same matches re-sourced from the event artifact. So the increment set is keyed on the
  PUBLISHED team artifact's own rows — a match counts only if its published row at that event is
  unplayed (no `actualWinner`) and the overlaid row is played. Never key the guard on the overlaid
  list, which contains both. And match `mergeTeamSeasonArtifact`'s own scoping: only an event whose
  `eventType` is official increments the record.
- `deriveMetricsBasis(...)` mirrors `mergeTeamSeasonArtifact`'s rule: `last-official-match` when
  every counted match is at an official event, `season-final` otherwise.

Hook side: **fold the sidecar fetch into `useTeamUpcomingOverlay`** and rename it
`useLiveTeamSeason`, returning `{ events, metricHistory, seasonStats }`. One hook owns the live-event
set (`teamEventNeedsLivePricing`), so the two `useQueries` calls can never disagree about which
events are live. `overlayTeamEventMatches` stays exactly as it is and stays shared with the event
page.

Fetcher: **`apps/web/src/lib/api/liveSidecar.ts`**, modelled line-for-line on
`apps/web/src/lib/api/preSchedule.ts` — **404 returns `null`, not a throw** (an absent sidecar is
the ordinary, expected state for every event that is not live), every other non-ok status still
throws, and `markArtifactParsed()` is NOT called.

Match page: `match.$matchKey.tsx` already fetches six team artifacts and one event artifact. Add ONE
sidecar fetch for that event and feed `preMatchMetrics` the extended history per robot. Without
this the match page silently regresses — its pre-match cells would go blank for every match folded
since the last republish, which today the Worker's team-artifact write covers.

### D-06 — Ordering for the chart

No season-wide index is invented. Derived rows get `matchIndex` = their ARRAY POSITION in the
extended array, which is exactly what `buildMetricSeries` uses (`x: index + 1`) and what
`preMatchMetrics`, `endOfEventMetrics` and `officialSnapshotRow` all depend on.

This is honest rather than a compromise: `matchIndexByKey` is built at `scheduled.ts` line 579 from
the EVENT's own ordered match keys, so the live tick has always written an event-local index into a
field documented as season-wide. Nothing in production web reads it. Record that finding in the
todo.

### D-07 — Where the parity claim moves

`scheduled.rowParity.test.ts`'s team-season half loses its subject. Its claim moves to the browser:
**a derived team-page row must equal what the publisher would write for the same match, minus the
fields shown to be unreachable.** Two halves:

- **Match rows** — already covered by the shipped, tested `teamRowFromEventRow` /
  `overlayTeamEventMatches` (260915-m4j), running in production for live events today. Strengthen it
  with a test comparing a derived row against `buildTeamSeasonArtifact`'s row for the same match,
  with the exception list stated as data, not prose: `coldStart` (corpus-global, unreachable),
  `variance` (dead — never written by `publish.ts`, never read).
- **Metric-history rows** — new. A derived row must equal the publisher's row minus `spread`
  (D-01), minus `percentile` (the Worker computes none today either), with `matchIndex` as array
  position (D-06).

`mergeTeamSeasonArtifact` leaves the live path but is NOT deleted: `stateProbe.ts` needs it to run
the `allPhaseB` baseline arm the whole measurement compares against. Mark it in place with a doc
comment stating it is no longer on the live path and why it survives, and file its deletion in the
todo alongside the probe's own scheduled deletion.

### Unsound / risky parts, called out rather than built quietly

1. **The overlay cliff is a real new regression and is FIXED in this task, not accepted.**
   `teamEventNeedsLivePricing` currently requires the event's schedule to still be current
   (`eventScheduleIsCurrent`, 7 days past the last scheduled match). Today that is harmless because
   the Worker writes results into the team artifact. Under this shape, once the window closes the
   team page would show a finished event's matches as UNPLAYED until the next republish. Fix:
   for the team page's gate, keep "the team has an unplayed published row at this event" and drop
   the currency conjunct. Cost: an abandoned event whose matches were never played keeps one extra
   CDN-cached fetch per team page forever — bounded, cheap, and strictly better than a correctness
   cliff. Keep `shouldPollEventArtifact`'s currency test unchanged; that one governs POLLING, not
   fetching, and polling a dead event is the thing the currency test exists to stop.
2. **The team page's live correctness now depends on a second fetch succeeding.** If the event
   artifact fetch fails, the page shows the pre-event published state with no results, where today
   it would show Worker-written results. Accepted: the event page already has this property, and the
   overlay already degrades to published rows on a failed query.
3. **A corrupt team-season artifact stops self-healing during an event.** Today a failed read guard
   triggers a fresh bootstrap write. It now stays stale until the next republish. Accepted; small.
4. **This does nothing for fresh isolates.** `allPhaseB` averages 40.8 ms there and nothing inside
   the tick touches that. Say so in the todo write-up; do not let a good Phase B number read as
   "the tick fits now".
5. **The 2-matches-one-tick metrics flaw is carried forward** (D-04). Do not fix it here; fixing it
   would change published numbers and needs its own version bump.
