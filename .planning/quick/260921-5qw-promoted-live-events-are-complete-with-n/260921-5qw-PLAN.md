# 260921-5qw: a promoted live event is complete with no rebaseline

## Why a rebaseline was needed, and why it cannot simply be scheduled

Since 260920-lny the Worker promotes a zero-match event to live folding once TBA shows matches. All 40
fall 2026 events hold zero matches and NO team list on TBA, so none has an event artifact (404) and
none appears in any team's season file. A promoted event therefore has no name, no tier cuts, no
state block (so no upcoming pricing) and no robot-page entry until someone runs `pnpm rebaseline`.
Scheduling that command is the wrong fix: it needs the 565 MB corpus that lives on one PC, and it
rewrites all ten seasons, about 109,000 R2 writes a run against a 1,000,000 a month free tier that
September's 17 republishes have probably already passed.

## The three parts

**A. Stub event artifacts (publisher, offline, zero tick cost).** Every event that gets a PROBE
window also gets an event artifact: identity (`name`, dates, location, `week`, `eventType`), the
season's `tierCuts`, empty `matches`, `upcoming` and `teams`. One shared predicate decides "probe
window" for the manifest builder and the publisher, so the two cannot disagree. The Worker's merge
already carries `tierCuts` and the identity fields forward.

**B. The Worker completes the state block itself (one D1 read, only when the block is incomplete).**
In Phase B, after the existing artifact is read: the keys the block NEEDS are
`stateBlockScopeKeys(touched teams plus every team on a still-upcoming match)`. If the block is
absent or lacks any needed key not already known absent, and `budget.tryConsume(1)` succeeds, the
tick reads exactly those rows from D1 (which already reflects this tick's write) and the merge
builds or extends the block. Keys D1 has no row for are recorded on the block as `absentKeys`, so a
rookie or a beliefless demo robot does not cost a read on every later tick; such a team re-enters
through the ordinary splice when it first plays. No budget left means no read this tick and the
next tick tries again: self-healing, never a failure. The subrequest ESTIMATE is unchanged because
the read is opportunistic.

**C. Robot pages find a promoted event (one tiny object per event, written only when its roster
grows).** The Worker writes `v1/live-roster/{eventKey}.json` (event identity plus team keys) when the
merged artifact's team count differs from the existing one's, which is the first fold and any later
roster growth, again behind `tryConsume`. The robot page reads the live-windows manifest it already
knows how to read, and for each OPEN window that is not already among the team's events fetches
that roster (404 is the ordinary answer for an unpromoted event). A roster naming the team adds the
event to the page's live set, and the existing overlay fills its matches from the event artifact.

## Guards

- No published number changes; no algorithm version bump.
- Every new Worker subrequest is behind `tryConsume`, so the pinned estimates (6, 14, 28) hold.
- Tests first for B and C. Full suite from the repo root and all three typechecks, judged by output.
- Ship order: Worker deploy, then publish (it carries the stubs), then push the web.

## What stays manual, and is not time-critical

Making results permanent in the team season files needs an ingest and a publish. The live rows stay
in the event artifact until then, so nothing is lost and any ordinary republish covers it.
