# Quick Task 260819-2x6: Add getOwnPropertyDescriptor and ownKeys traps Summary

Closed EVAL-01 / Phase 1 success criterion 4 — the sole blocker on the v1.0 mid-milestone audit — by adding `getOwnPropertyDescriptor` and `ownKeys` traps to `toLeakProofUpcoming`'s Proxy handler, closing the two reflection bypasses (descriptor read, key enumeration) that let an algorithm's `predict()` reach real outcome data around the existing `get` trap.

## What Was Built

`packages/harness/replay.ts`'s `toLeakProofUpcoming` now guards outcome-bearing fields on all three Proxy surfaces instead of one:

- **`get`** (pre-existing, untouched) — throws `Outcome leakage: ...` for a direct read of any of the 7 `OUTCOME_KEYS`.
- **`getOwnPropertyDescriptor`** (new) — throws the byte-identical error for `Object.getOwnPropertyDescriptor`/`Reflect.getOwnPropertyDescriptor` on any outcome key. Both traps call a single new module-level helper, `denyOutcomeKey(target, prop)`, so the two surfaces cannot drift onto two different message strings.
- **`ownKeys`** (new) — forwards to `Reflect.ownKeys(target)` and filters out the 7 outcome keys, rather than throwing (D-A: a whole-object operation like `console.log`/`util.inspect` has no per-key failure shape to throw into). This is legal under the ES `[[OwnPropertyKeys]]` invariant only because every `MatchResult` is an extensible plain object literal with configurable properties (D-B) — pinned by a dedicated test.

A consequence of the `ownKeys` filter (D-D, deliberately accepted): `{...wrapped}`, `JSON.stringify(wrapped)`, `Object.values`, and `Object.entries` now complete silently with only the 10 non-outcome fields, instead of throwing as they did before (they previously threw only because they invoke `[[Get]]` per key and hit the `get` trap for outcome keys that were still enumerated).

`packages/harness/replay.test.ts` gained four new `describe` blocks:
1. Extended the pre-existing `get`-trap `it.each` to include the previously-missing `hasScoreBreakdown` key (was 6/7).
2. `Object.getOwnPropertyDescriptor`/`Reflect.getOwnPropertyDescriptor` throw for all 7 outcome keys, naming the match key.
3. `Reflect.ownKeys`/`Object.keys`/`Object.getOwnPropertyNames` omit all 7 outcome keys and retain all 10 non-outcome keys.
4. Derived-path pinning: `Object.getOwnPropertyDescriptors`, `Object.values`/`entries`, spread, `JSON.stringify`, and `for...in` each carry exactly the 10 non-outcome keys with real values; the D-B precondition (raw fixture extensible, all 7 outcome keys configurable) is asserted directly; and a frozen-`MatchResult` boundary test proves `Object.keys` on the wrapper throws an engine `TypeError` (asserted by constructor, and asserted to NOT match `/Outcome leakage/`) rather than our custom error — the documented hazard that makes D-B a real constraint, not just prose.

`packages/core/algorithms/types.ts`'s module docblock and the `scoreBreakdownRaw` field docblock were updated to name all three trap surfaces instead of describing the guard generically.

`.planning/phases/01-data-foundation-evaluation-harness/01-VERIFICATION.md`'s `gaps[0]` and `.planning/v1.0-MILESTONE-AUDIT.md`'s EVAL-01 requirement entry and Seam-2 integration entry each gained an append-only `resolution:` key. No `status`, `evidence`, `reason`, `artifacts`, `missing`, or `audit_verdict` field was rewritten. The EVAL-01 resolution also records a correction: the audit's recorded claim "object spread copies every outcome field silently" was never reproducible — spread invokes `[[Get]]` per key and already threw via the pre-existing `get` trap, both before and after this fix. The real pre-fix enumeration leak was narrower (key names only, via `ownKeys`-derived paths); the value leak was exclusively the `getOwnPropertyDescriptor` path.

## TDD: Observed RED, then GREEN (Task 1)

Wrote the three new test groups in `replay.test.ts` first and ran them against the untouched single-trap `replay.ts`. Observed 17 failures for the stated reasons, e.g.:

```
FAIL replay.test.ts > ... Object.getOwnPropertyDescriptor throws for outcome field winner ...
AssertionError: expected [Function] to throw an error
- Expected: null
+ Received: undefined
```
(`getOwnPropertyDescriptor` forwarded to the untrapped target and returned `undefined`/a real descriptor instead of throwing — exactly the bypass the plan describes.)

```
FAIL replay.test.ts > ... Reflect.ownKeys omits every outcome key ...
AssertionError: expected [ 'matchKey', 'eventKey', …(15) ] to not include 'winner'
```
(the wrapped object's key list still contained all 7 outcome keys — the enumeration bypass.)

17 failed / 16 passed (the 16 passes were the pre-existing tests, untouched). After adding the two traps to `replay.ts`, re-ran the same file: 33/33 passed. No pre-existing assertion needed modification beyond widening its `it.each` list to include `hasScoreBreakdown`.

**Task 2's tests did not follow a fresh RED-then-GREEN cycle of their own** — they pin behavior that Task 1's traps already produce (derived paths like `Object.getOwnPropertyDescriptors`/spread/`for...in` all consume `ownKeys` under the hood per D-C, so once `ownKeys` was fixed in Task 1, every path Task 2 pins was already correct). Writing and running Task 2's tests immediately produced 51/51 passing across all three `replay*.test.ts` suites, with no code change to `replay.ts`. This matches the plan's Task 2 `<action>`, which only adds tests — no trap changes.
