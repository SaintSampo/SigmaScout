## Verified current behavior (reproduced 2026-08-19 against the real export, not assumed)

A probe wrapping a `MatchResult` with `redScore: 999`:

| Path | Today | Leak |
|------|-------|------|
| `p.redScore` | throws `Outcome leakage:` | none (the `get` trap works) |
| `Object.getOwnPropertyDescriptor(p, "redScore").value` | returns `999` | **real value, silently** |
| `Object.getOwnPropertyDescriptors(p)` | returns every descriptor | **every real value, silently** |
| `Reflect.ownKeys(p)` / `Object.keys(p)` | includes all 7 outcome names | key/shape presence |
| `Object.values` / `Object.entries` / `{...p}` / `JSON.stringify(p)` | **throw** `Outcome leakage:` | none |
| `"redScore" in p` | `true` | existence only (constant, see below) |

**Correction to the audit's wording:** `v1.0-MILESTONE-AUDIT.md`'s EVAL-01 evidence says
"object spread copies every outcome field silently". That is not what happens — spread
(`CopyDataProperties`), `JSON.stringify`, `Object.values`, and `Object.entries` all invoke
`[[Get]]` per key and therefore already hit the `get` trap and throw. The real enumeration
leak is narrower: `ownKeys` exposes the *names*. The value leak is entirely via the
descriptor path. Task 3 records this correction rather than propagating the wrong claim.

## Design decisions (Proxy invariants — required by the task constraints)

**D-A. `ownKeys` FILTERS, `getOwnPropertyDescriptor` THROWS.** Asymmetric on purpose:

- A deliberate, direct probe (`Object.getOwnPropertyDescriptor(upcoming, "redScore")`) has no
  innocent reading — it should fail as loudly as `upcoming.redScore` does.
- `ownKeys` has no per-key call shape: it either returns a list or throws for the *whole
  object*. Throwing would blow up on every wrapped match for benign whole-object operations
  (`console.log`, `util.inspect`, any debugger), since every `MatchResult` carries all 7 keys.
  Filtering is the only workable choice, and is what both the audit and `01-VERIFICATION.md`
  prescribe.

**D-B. Filtering `ownKeys` is legal here, and here is exactly why.** The ES `[[OwnPropertyKeys]]`
invariant is: the trap result must include every *non-configurable* own key of the target, and
if the target is *non-extensible* the result must match the target's keys exactly. Verified on
a real `MatchResult`: every outcome property is `configurable: true` and the object is
extensible (it is a plain object literal built in `packages/corpus/db.ts`; `Object.freeze` /
`seal` / `preventExtensions` appear nowhere in `packages/**` or `pipeline/**` — grepped). So
omission is permitted. Task 2 pins this precondition with a test so a future change that starts
freezing match objects fails with a pointer to this decision instead of a bare engine TypeError.

**D-C. A throwing `getOwnPropertyDescriptor` cannot deadlock the filtered `ownKeys`.** Two
independent reasons: (1) the engine validates an `ownKeys` trap result against the *target's*
`[[GetOwnProperty]]`, never the proxy's trap; (2) every spec algorithm that walks an object
(`Object.keys`, `Object.entries`, `Object.getOwnPropertyDescriptors`, spread, `JSON.stringify`,
`Object.assign`, `util.inspect`) calls `ownKeys` first and only queries descriptors for keys the
trap *returned*. An omitted key is therefore never passed to the throwing trap by any derived
operation — only a direct probe reaches it.

**D-D. Accepted behavior change: spread and `JSON.stringify` stop throwing.** Today `{...upcoming}`
throws; after this change it silently yields the safe subset (outcome keys simply are not there).
That is the correct trade — invisible beats loud-but-present for the *derived* paths, while the
*direct* probe stays loud via D-A — but it is a real change and Task 2 pins the exact post-fix key
set with a test so it is a recorded decision, not a later surprise.

**D-E. The `has` trap is a deliberate non-goal.** `"redScore" in upcoming` will still return
`true`. It leaks no outcome value and no data-dependent bit: every `MatchResult` the harness
wraps carries all 7 keys, so the answer is the constant `true` regardless of the result. Adding a
`has` trap is not part of the audit's remediation and is not done here; this line is the record
that it was considered and why it was left.
