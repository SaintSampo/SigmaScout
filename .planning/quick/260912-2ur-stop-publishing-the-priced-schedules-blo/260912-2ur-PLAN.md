# 260912-2ur — The priced block stays in memory and leaves the bytes

## Why

Step 1 of the pre-schedule count work, and a hard prerequisite for step 2 (raising
`PRESIM_SCHEDULE_COUNT` from 20 to 1,000, already decided). At 1,000 schedules one sidecar is
~18 MB if the block stays; across the 641 sidecars a publish writes that is ~11.5 GB of presim
alone, on top of the 4.2 GB the rest of the publish already writes, against a **10 GB R2 free
tier**. Dropping the block takes the same file to ~24 KB.

Measured on the live object today: `v1/presim/2026mrcmp/bpr@3.0.0+baseline.json` fetched
388,484 B, of which 12,275 B is actually read — 96.8% discarded, on the page whose stated top
priority is load speed.

## The wrinkle that shapes the whole design

**This is not a field deletion.** The block must survive IN MEMORY and vanish only from the
PUBLISHED bytes. `scripts/measureFieldAveragedRanks.ts` reads `artifact.schedules` at lines
880, 950, 1253 and 1256, and `scripts/measureGeneratedSchedules.ts` reads it through that
module and directly at ~12 more sites. That pair is the rung-1/rung-2 acceptance harness and is
needed intact for the generator work that comes next. `buildPreScheduleArtifact` must keep
returning `schedules` exactly as it does now, and **neither script may be edited by this task.**

## The schema decision, and why the low-churn candidate was rejected

The brief proposed making `schedules` optional on the single `PreScheduleArtifactSchema` and
guarding its two refinements on presence. **Rejected**, for a reason that only shows up after
reading the call sites: `PreScheduleArtifact` is the *inferred* type of that schema, so making
the field optional makes `PreScheduleArtifact["schedules"]` possibly-`undefined` everywhere —
including at `measureFieldAveragedRanks.ts:1253/1256` and across ~10 sites in
`measureGeneratedSchedules.ts`, which read it unguarded. Under `strict`, those become
typecheck errors, and fixing them is exactly the "rewrite the scripts to route around a removed
field" this task forbids. It would also weaken the builder's own return type, which today
*guarantees* the block exists.

**What lands instead: two schemas over one shared base.**

| | `PreScheduleArtifactSchema` (unchanged name) | `PublishedPreScheduleArtifactSchema` (new) |
|---|---|---|
| what it describes | the builder's IN-MEMORY artifact | the PUBLISHED bytes |
| `schedules` | required, fully typed, all five refinements | optional legacy remnant, read only for its length, dropped by a `.transform()` |
| `scheduleCount` | absent | present on the output, always a number |
| who uses it | `preSchedule.ts`, both measurement scripts, their tests — **all untouched** | `publish.ts` (writer) and `apps/web` (reader) |

Both are built from one shared base object, so the field list has one home, and the three
roster/baked-histogram invariants are shared predicates called by both, so those bounds have one
home too — which is the exact claim `apps/web/src/lib/preScheduleResult.ts`'s doc comment already
rests on ("the schema is the single home for these bounds").

This has direct precedent in the same file: `TeamsArtifactWireSchema` → `TeamsArtifactSchema`,
where a `.transform()` drops `metricKeys` as "a wire-level implementation detail of the
positional encoding, not a fact any consumer of the DECODED artifact needs." Same move here.

### Why the published schema tolerates the legacy shape

Every presim object on R2 today carries `schedules` and no `scheduleCount`, and **this task does
not run a publish**. If the client required `scheduleCount`, every existing sidecar would fail
`parse` and the Simulation tab would render an error to visitors the moment the deploy landed,
until a republish. So the published schema accepts both shapes and resolves the count:
`scheduleCount ?? schedules.length`, with a refinement rejecting an object carrying neither. No
flag day, no deploy/republish ordering constraint.

Its `schedules` is declared `z.array(z.unknown()).optional()` — length is the only thing read
from it, and its *contents* were already validated at build time by the strict schema's five
refinements, which still run inside `buildPreScheduleArtifact`. Re-validating an array the
transform is about to discard buys nothing. The three refinements that protect a READER —
roster-uniqueness, one histogram per roster team, and every histogram's length-and-sum — stay
required and unchanged on both schemas, because they are what makes `rankRows.ts`'s
`MalformedRankHistogramError` unreachable in front of a visitor.

## The client regression this must not ship

`SimulationTab.tsx:408` passes `preSchedule?.schedules.length` into `StartMatchPicker.tsx:83`'s
`preScheduleScopeText`, which renders to visitors whenever the pre-schedule view is selected.
If that input goes missing it falls through `StartMatchPicker.tsx:264`'s `?? 0` and publishes
"across 0 randomly generated schedules" with nothing failing. **No test renders that line today**
(verified by grep — `preScheduleScopeText` has no test caller at all). Task 2 adds one, and it
must assert the rendered count is the real one, not merely non-null.
