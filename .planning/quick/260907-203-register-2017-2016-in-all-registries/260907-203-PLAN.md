## F-1 (BLOCKER, brief correction) — the breakdown reconciliation is NOT qual-scoped

The brief states: *"every reconciliation test in this repo is scoped to QUALS, [so] omitting these
four fields would look perfectly correct in CI."* **That is true of `rp/reconciliation.test.ts` and
false of `breakdown/reconciliation.test.ts`.**

`sampleBreakdowns` (`breakdown/reconciliation.test.ts:107-127`) has **no `comp_level` filter**:

```
WHERE e.year = ? AND m.has_score_breakdown = 1 AND m.winner IS NOT NULL AND e.is_offseason = 0
ORDER BY m.match_key ASC LIMIT 2000
```

Match keys sort alphabetically, and within an event `f` < `qf` < `qm` < `sf` — so **finals and
quarterfinals sort BEFORE quals**. The 2,000-row window is playoff-inclusive. Measured by the
planner, 2026-09-07:

| season | f | qf | qm | sf | window spans |
|---|---|---|---|---|---|
| 2016 | 47 | 189 | 1,680 | 84 | `2016abca_f1m1` .. `2016cthar_qm47` |
| 2017 | 51 | 185 | 1,641 | 123 | `2017abca_f1m1` .. `2017code_qm15` |
| 2018 | 43 | 184 | 1,686 | 87 | (for reference) |

**Two consequences, both load-bearing:**

1. **The four playoff-only bonus fields are not merely morally important — they are required for a
   green suite.** `kPaBonusPoints`/`rotorBonusPoints` (2017) and `breachPoints`/`capturePoints`
   (2016) are counted by TBA inside `teleopPoints` and therefore inside `totalPoints`. Omitting
   them produces a non-zero gap on **every playoff side in the window**. The brief's warning stands
   and gets stronger: state the hazard in both headers, and the suite now proves it rather than
   trusting it.
2. **2016 needs a `KNOWN_BREAKDOWN_TOLERANCES` entry after all** — see F-2. The brief's prohibition
   ("the mechanism stays 2018-only") rested on the qual-scoping premise that F-1 falsifies.

## F-2 (BLOCKER) — 2016 has three real reconciliation exceptions; 2017 has none

The planner ran the suite's **exact** identity (`sum(own components) + adjust + foulPoints ===
totalPoints`, which is what `offensiveSum + foulsCommittedByOpponent` reduces to) using the
component sets specified below, over the **full official non-offseason population, all comp
levels**:

| season | sides | exceptions | rate |
|---|---|---|---|
| **2017** | **30,880** | **0** | **0.000%** |
| **2016** | **26,604** | **3** | **0.01128%** |

2016's three, in full — every one an **elimination** match:

| match | side gap | TBA's own identity gap | our auto half vs `autoPoints` | our teleop half vs `teleopPoints` |
|---|---|---|---|---|
| `2016capl_f1m1` | **+25** | −25 | 0 | 0 |
| `2016milsu_qf4m1` | **+25** | −25 | 0 | 0 |
| `2016mndu2_f1m2` | **−25** | +25 | 0 | 0 |

This is **TBA's own arithmetic, not a mapping defect**, proven the identical three ways
`breakdown/2018.ts`'s header uses: our auto half reconciles exactly against TBA's own `autoPoints`,
our teleop half reconciles exactly against TBA's own `teleopPoints`, and **all 3 of 3** also fail
TBA's own `totalPoints == autoPoints + teleopPoints + foulPoints + adjustPoints` with the exact
opposite-signed gap.

**Exactly one of the three — `2016capl_f1m1`, blue side, gap +25 — falls inside the suite's current
2,000-row window.** Measured directly: 2016 red 0/2000, 2016 blue **1/2000**; 2017 red 0/2000,
2017 blue 0/2000. So without a tolerance, **2016 blue ships red.**

**The tolerance is therefore EARNED by measurement, not unearned.** It ships as:

```
{ season: 2016, rate: 0.001, maxAbsGap: 25 }
```

- `rate: 0.001` — the binding measurement is the sampled-window rate **1/2000 = 0.0005**; the
  full-population rate is 3/26,604 = 0.0001128. 0.001 is exactly **2x** the binding rate, the
  smallest round margin that does not sit *on* the boundary of the single observed exception, so a
  one-row shift in the `match_key`-ordered window cannot flip the suite red for a reason unrelated
  to the component map. Record both ratios in the comment.
- `maxAbsGap: 25` — the exact observed magnitude. Any larger gap still fails regardless of rate.
- **`direction` MUST BE OMITTED.** The signs are **mixed** (+25, +25, −25). Only the `+25` one is in
  today's window, so an executor who measured only the window would set `direction: "positive"` and
  encode a sampling artifact as a fact. The field's own doc comment forbids exactly this: *"Only set
  when every observed exception carries the same sign — never encoded from an assumption."*

**2017 gets no breakdown tolerance.** 0/30,880 over the full population, all comp levels.

## F-3 — `diagnosticKeys` has ONE consumer and it treats the whole list as FOUL fields

The brief proposes an eight-name 2016 `diagnosticKeys` list including `towerEndStrength` and
`position1crossings`..`position5crossings`. **Do not ship that list.**

`diagnosticKeys` is read in exactly one place: `packages/harness/identifiability.ts:200`, which
passes it to `foulDiagnosticKeys` and then, at line 253:

```
const hasFoul = diagnosticFields.some((key) => Number(red?.[key] ?? 0) > 0 || Number(blue?.[key] ?? 0) > 0);
if (hasFoul) matchesWithAnyFoulRecorded++;
```

Adding the crossings and the tower would make `hasFoul` true for essentially every 2016 match that
had any defense crossed, reporting a near-100% foul rate in `reports/identifiability.json` and in
the printed line at `identifiability.ts:582`. That is a silent corruption of a published
diagnostic — the exact defect class this project keeps catching.

**Both seasons ship `diagnosticKeys: ["foulCount", "techFoulCount"]`** — which is the fallback the
brief itself pre-authorized. The header records *why*: the six other raw counts are not "unread",
they are read by the **RP** module as threshold variables, and the single consumer of this field
would misclassify them as fouls.
