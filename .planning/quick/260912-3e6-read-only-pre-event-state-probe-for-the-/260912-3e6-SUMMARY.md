# Quick task 260912-3e6: Read-only pre-event state probe Summary

Built a separate, write-binding-free Cloudflare Worker (`stateProbe.ts` + `wrangler.probe.toml`) that
answers two questions a live tick's own green log cannot: whether the currently-deployed Worker
bundle can actually deserialize the rows now sitting in live D1, and what a tick that genuinely runs
the ranking-point fold path costs in real Workers CPU time. Both questions were previously
unanswerable because the live-windows manifest is `windows: []`, so every tick since the 2026-09-12
seed returns before reading a single league row — a `cpuTime` of 1 ms that looks healthy and means
nothing.

## What was built

**The probe** (`apps/worker/src/stateProbe.ts`). A fetch-only entrypoint bound to exactly one D1
database (`DB`), with no R2 or KV binding at all. For each of the three published algorithms
(`opr`/`epa`/`bpr`) it discovers a roster and an event key by querying `scope_kind, scope_key` only
(never `state_json`), reads scoped state through the real `readScopedState`, and calls the real
`deserializeState` — reporting per-algorithm success/failure, the observed `snapshotShapeVersion`,
and row-count breakdowns. For `bpr` specifically (matching the live tier's own
`LIVE_ALGORITHM_IDS`), it resumes the real `SwingFactorAccumulator`/`SigmaScoreAccumulator`/
`RpMomentsAccumulator` from the rows just read, then drives the identical sequence
`scheduled.ts`'s `processEvent` drives: `folded` synthetic played matches (predict → band →
`analyticRpPmf` → update → fold) and `upcoming` synthetic still-upcoming matches (predict → band →
`analyticRpPmf`, read-only), followed by `serializeState` + the four `with*Beliefs` passenger
writers — then discards the result rather than calling `writeScopedState`. Every gate the real tick
applies (the partial-roster RP suppression, the RP-eligible-event-type check, the never-cold-start
rule) is reproduced rather than bypassed, because those gates are part of what the probe exists to
measure, not overhead to strip out.

**The two-layer write guarantee**, stated identically in three places (the probe's own header,
`wrangler.probe.toml`'s header, and the runbook): R2 and KV are structurally absent (no binding
exists in this deployment's config at all), but Workers has no read-only D1 binding — `DB` is bound
read-write like any other D1 binding, and what actually stops a write is that `stateProbe.ts` never
calls a write helper and never imports `scheduled.ts`, a property held by
`apps/worker/test/stateProbe.test.ts`, not by the config.

**The test** (`apps/worker/test/stateProbe.test.ts`, 26 tests, 4 groups). Group 1 is static: it walks
the probe's transitive local import graph (resolving `.js` specifiers to their on-disk `.ts` files)
and asserts `scheduled.ts`/`artifactWriter.ts` are unreachable, then scans the comment-stripped
source for banned write/timing identifiers — with a positive control proving the comment-stripper
actually strips rather than vacuously passing every negative assertion — and checks
`wrangler.probe.toml`'s shape (no R2/KV/triggers, exactly one D1 binding, correct name/main/
`nodejs_compat`). Group 2 asserts `probeSelectionsFor` is deep-equal to the real `selectionsFor`
across opr/epa/bpr/empty-roster. Group 3 is the behavioral core: it seeds a fake D1 with real
opr/epa/bpr state (built via `initState`/`update`/`serializeState` and real Swing/Sigma/RP
accumulators that folded actual seed matches — never hand-written JSON), drives the probe end to
end over 2 folded + 5 upcoming matches, and asserts `rpPmfsProduced === 7` by **equality** (not
`> 0`) — the assertion that would catch six-of-seven silently suppressed — plus zero D1 write
statements recorded by the fake. Group 4 seeds a stale league-row shape version and asserts the
response is valid JSON naming `LeagueRowShapeVersionError` with both version numbers in its message,
never an opaque failure.

**The runbook** (`docs/worker-operations.md`, new "Pre-event probe" section between "Before an
event" and "Watching it"). States why a green idle tick is not evidence, the same-commit
deploy-then-probe ordering rule, the full param table, a table of conditions under which the
reported `cpuTime` is not a measurement (`rpPmfsProduced: 0`, `bandsProduced: 0`, any
`algorithms[].ok: false`, a non-empty `warnings` array), the Phase-A-only scope limit, and the
two-layer write guarantee restated in the runbook's own words. A new troubleshooting-table row
points here.

**The todo** (`.planning/todos/pending/worker-state-shape-unexercised-since-seed.md`) got a
`## Status — 2026-09-12` section recording that the instrument now exists but stays open, and stays
in `pending/`, until it has actually been deployed and run against live D1.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `rpPmfsProduced` was double-counting per alliance instead of per match**
- **Found during:** Task 2, writing the equality assertion `fold.rpPmfsProduced === 7`
- **Issue:** The played and upcoming loops in `runBprFold` incremented `rpPmfsProduced` once for
  `redRpPmf` and again for `blueRpPmf`, so 2 folded + 5 upcoming matches produced 14, not 7 — the
  test's own equality check against `folded + upcoming` caught this immediately on first run.
- **Fix:** Removed the second (`blueRpPmf`) increment in both loops — the RP gates are all-or-
  nothing per match, so one increment per match is the correct, and now documented, count.
- **Files modified:** `apps/worker/src/stateProbe.ts`
- **Commit:** `0ebee02d`

**2. [Plan-sanctioned option] Imported `selectChangedRows` rather than reproducing it inline**
- The plan explicitly offered both options ("either is fine"). Since `./stateStore.js` was already
  imported for `readScopedState`/`MAX_SCOPE_KEYS_PER_READ`, importing the pure comparison function
  too added no new module to the probe's import graph and avoided a drift-prone duplicate.
- **Files modified:** `apps/worker/src/stateProbe.ts`
- **Commit:** `e7993fbf`

No architectural deviations (Rule 4). No authentication gates. No checkpoints.
