# 260912-3e6 — Make the unasked question askable

## Why

`.planning/todos/pending/worker-state-shape-unexercised-since-seed.md` names two questions that
nothing in the system currently answers, and that will otherwise be answered for the first time
during a live event, in front of visitors.

**Question 1 — can the deployed bundle read the rows now in D1?** Answered locally this session:
the real `deserializeState` was run over rows pulled verbatim from live D1 and opr, epa and bpr all
deserialize, including OPR's event-scope rows. What is *not* answered is whether the **deployed**
bundle does — the Worker carries whatever `STATE_SNAPSHOT_SHAPE_VERSION` it was built with, so this
is a deploy-ordering property, not a code property, and only something running inside the deployed
runtime can settle it.

**Question 2 — what does a tick that actually folds cost?** Completely unmeasured. Live ticks
report `cpuTime` 1 ms, and that number is worthless: the live-windows manifest is `windows: []`, so
`processEvent` returns at its `newlyFolded.length === 0` check (`apps/worker/src/scheduled.ts:1002`)
**before a single league row is read**. Every green tick since the 2026-09-12 seed is green for a
reason that has nothing to do with the question. The Phase 9 ranking-point work — `analyticRpPmf`
per match, on every still-upcoming match at the event — has never executed inside the Workers
runtime against real beliefs.

A separate, write-binding-free Worker answers both without waiting for an event and without
touching the production tick.

## The brief's one claim that is false, and what replaces it

The brief states that the absence of write bindings in `wrangler.probe.toml` is "the structural
guarantee it cannot mutate anything." **That is true for R2 and KV and false for D1.** Workers has
no read-only D1 binding — the probe needs `DB` bound to read state at all, and a bound D1 is
writable. A `writeScopedState` call from the probe would land rows in the live table.

So the guarantee is two layers, and they are not equally strong. Both the config comment and the
runbook section must say this in these terms rather than the brief's:

| Surface | What stops a write | Strength |
|---|---|---|
| R2 (`ARTIFACTS`) | binding absent from `wrangler.probe.toml` — `env.ARTIFACTS` does not exist | structural; no code change can write an artifact |
| KV (`MANIFEST`) | binding absent — `env.MANIFEST` does not exist | structural |
| D1 (`DB`) | the probe never calls a write helper, and no write helper is in its import graph | **test-enforced only** (`apps/worker/test/stateProbe.test.ts`) |

This is why Task 2's test is load-bearing rather than decorative, and why the probe must not import
`scheduled.ts` (see below): keeping `writeScopedState`/`writeEventCursor`/`artifactWriter` out of
the probe's import graph entirely is what makes a future editor unable to reach one by autocomplete.

## Design decisions that only show up after reading the call sites

### 1. The probe cannot import `scheduled.ts`, so it duplicates one 8-line helper — and a test pins the duplicate

`selectionsFor` (`scheduled.ts:373`) is exactly the helper the probe needs, and importing it pulls
`artifactWriter.ts`, `writeScopedState` and `writeEventCursor` into the probe's graph, which is the
one thing Task 2 exists to forbid. The probe therefore carries its own `probeSelectionsFor`.

That duplicate is a real drift risk, and `selectionsFor`'s own doc comment describes exactly what
drift costs ("the consequence is not a missing optimization, it is silent data destruction"). It is
neutralised in the **test**, which is free to import both: `stateProbe.test.ts` asserts
`probeSelectionsFor` and the real `selectionsFor` produce deep-equal output across a case table
including the `opr` event-scoped case. That is a stronger check than a shared import would be — a
shared import makes drift impossible but also makes the equivalence invisible; the pinned test makes
it a named, failing assertion.

### 2. The expensive part of a tick is the UPCOMING loop, not the folded one

`processEvent` prices `newlyFolded` (typically 1–2 matches per tick) and then loops over **every
still-upcoming match at the event** (`scheduled.ts:1253`), each getting a `predict`, two `bandFor`
reads and a full `analyticRpPmf`. Early in a qual schedule that is 60+ matches. A probe that folded
2 matches and stopped would report a number that is wrong by more than an order of magnitude and
would read as reassuring. The probe therefore takes **two** counts — `folded` (default 2) and
`upcoming` (default 60) — and prices both loops.

### 3. Serialize-and-discard, because the write payload's construction is part of the tick's CPU

Phase A's cost does not end at `update()`. It includes `serializeState` over every touched team,
plus `withSwingBeliefs`/`withRpBeliefs`/`withSigmaBeliefs`/`withSigmaPopulation`, plus
`selectChangedRows` — all of which re-parse and re-stringify every row. The probe runs that whole
chain, reports `changedRowsDiscarded`, and throws the rows away. Building rows is not writing them,
and the absence of any call to a write helper is what the test pins.

### 4. The probe discovers its own scope keys, because a roster without beliefs silently under-prices

Three gates in the fold path suppress work when beliefs are missing: `bandVarianceFor` returns
`undefined` for an unresumed roster, the partial-roster gate in `rpFieldsFor` returns `{}` the moment
any team is not in `rpKnownTeams`, and `foldObservedRp` no-ops without a parseable breakdown. A probe
run against hardcoded team keys that happen not to be seeded would produce **no pmfs at all** and
report a small, comfortable `cpuTime`. That is the exact failure mode this whole task exists to stop
from happening in production, reproduced inside the instrument.

So the probe runs two `scope_key`-only discovery queries and folds rosters drawn from what it finds.
Those queries select `scope_kind, scope_key` and **never** `state_json` — they cannot deserialize
anything, so they are not a second state reader; `readScopedState` remains the only path by which a
state payload enters the probe. Say that in the comment at the query.

And the JSON body carries `rpPmfsProduced` / `bandsProduced` / `rpObservedFolds` counters so an
under-priced run is visible on its face rather than mistaken for a cheap one.

### 5. The probe must not try to time itself

Cloudflare freezes `Date.now()` and `performance.now()` between I/O operations as a Spectre
mitigation — a self-timed probe would report `durationMs: 0` and be believed. Timing comes from the
runtime's own `cpuTime`, off `wrangler tail`. The probe reports counters only; Task 2's test greps
the comment-stripped source for `Date.now(` and `performance.now(` to keep it that way.

### 6. Comment-text discipline: the test strips comments before matching

The probe's header comment *should* name `writeScopedState` and `artifactWriter` — that is what a
reader needs. The test negative-greps for those same identifiers. A naive grep would make the file's
own explanation of why it is safe the reason it is reported unsafe. The test therefore strips `//`
and `/* */` comments **before** matching, following `liveAlgorithmTier.test.ts`'s
`extractVarsValue` precedent ("dropping comment lines BEFORE matching"), and carries a positive
control for the stripper — a stripper that returned `""` would make every negative assertion in the
file vacuously true.

## Scope limits, stated rather than left implicit

The probe prices **Phase A only**. It does not measure Phase B (artifact merge, R2 reads/writes),
TBA polling, the KV manifest read, or the global rebuild. The runbook section says so; a Phase-A
number read as a whole-tick number would be an under-estimate.

The probe is evidence about the deployed Worker **only if both were built from the same commit**.
That is the operational rule Task 3 writes down: deploy the Worker, deploy the probe from the same
commit, then run the probe.

## What this task does NOT do

No deploy, no `wrangler` invocation, no network command of any kind — executor sandboxes on this
machine have no network (`project_subagent_network_block`). **The live deploy and the live `cpuTime`
measurement are run by the main context after this plan lands.** The todo therefore stays in
`pending/`; Task 3 appends a status pointer to it rather than closing it, because the probe existing
is not the same as the probe having been run.

`runTick` and every other production path in `scheduled.ts` are untouched. No dry-run flag.
