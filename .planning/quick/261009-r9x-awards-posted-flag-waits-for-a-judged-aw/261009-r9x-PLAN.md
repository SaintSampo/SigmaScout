## Orchestrator decisions, 2026-10-09 (binding; they supersede CONTEXT D3 where they differ)

- **R-A2. The watch is driven by the list changing** (it replaces R-A, and there is no pending state in the cursor: the flag on the artifact says whether an event is posted). The awards cursor row stores the ETag of the last awards response the pass MERGED, whatever the flag says.
  1. Before the gate: every member window event that has an awards cursor row is asked CONDITIONALLY with its stored ETag (a row with a null ETag is asked with none). A 200 means the list changed: keep the body, and the district passes the gate. A 304 means no awards news from that event.
  2. The gate passes on a rankings 200, a match observation, or any awards 200 from step 1. Otherwise the cheap steady state stands, with no R2 read.
  3. Inside the loop (gate passed), for each member event with playoffs done: if step 1 gave a 200, use that list. If the flag of the event is NOT yet true and step 1 gave a 304 or the event had no cursor row, ask UNCONDITIONALLY now so the rule has the list. This is the only unconditional ask, and it happens only on ticks that already read the artifact. If the flag is already true and step 1 gave a 304, there is nothing to do.
  4. Every list in hand is merged (D2) and the rule is evaluated after the rankings merge (D1).
  5. Cursor writes stay LAST, after the R2 write or the unchanged comparison: each event whose list was fetched this tick stores the ETag of that response, also when the list is empty or holds only Winner and Finalist, so the next quiet tick is a cheap 304.
  - Consequences: a DCMP Winner listed on an otherwise quiet tick changes the list, so step 1 returns 200 and it is recorded on that tick. An event waiting on points with an unchanged list costs one conditional request per tick and no R2 read. When the points arrive the rankings 200 passes the gate and step 3 fetches the list. A row left by the old code carries an ETag and simply continues as a conditional ask.
  - Planner readings under R-A2, each flagged in the report: (i) an event whose flag is already true and that has NO cursor row (the offline publisher set the flag, or a cursor write failed) is asked once inside the loop with no ETag, playoffs done or not, so it gets a row and joins step 1. R-A2 does not name this case, and without it such an event would never be asked again. (ii) A list in hand for an event the loop skips is not merged, so its ETag is not stored. (iii) A response with no ETag header is stored as a null ETag. (iv) The row is written only when the ETag differs from the stored one or no row exists, so a quiet waiting event costs no D1 write.
- **R-B. An awards request that fails is not fatal to the district.** It applies to every awards ask, in step 1 and in step 3 of R-A2. A network error, a status other than 200 or 304, or a schema failure logs one warn (`district-awards-poll-failed`, with the district key, the event key and a short reason), counts as no awards news for that event this tick (flag unchanged, nothing merged, no cursor written for it), and the district carries on with its rankings merge. `districtsFailed` is not incremented. A failed event is not asked a second time in the same tick.
- **R-C. The comment only rewording in `champLedgerStatus.ts` (~994) and `champJointLock.ts` (~174) is allowed**, with the same proof as before: every changed line in those two files is a comment line, and `champJointLock.test.ts` prints the same passing count (40 at c5029590 in the planner run).
