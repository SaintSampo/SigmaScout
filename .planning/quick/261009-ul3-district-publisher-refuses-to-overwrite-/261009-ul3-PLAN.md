## Premises of CONTEXT the code contradicts (plan what the code supports)

- **C1. `getObject` has no retry and no typed 404.** CONTEXT says it "has the retry policy of the client". It makes one request and throws a plain `Error` whose only 404 signal is the text of its message. The plan adds `getObjectIfExists` beside it on `sendWithRetry` with success meaning 2xx or 404, so a 404 is a value (null), a transient 5xx is retried and every other status throws. `getObject` is not edited: `scripts/replayRig.ts` calls it and `r2ClientList.test.ts` pins it.

## Readings this plan fixes (each binding)

- **R1. Real upload means `options.dryRun` is false.** Nothing else decides it (C2).
- **R2. Event presence.** An event is present in an artifact when any team has an `eventPoints` row, a `remainingEvents` row or a `qualifyingAwards` entry naming it. Only keys present in both artifacts are compared (D1).
- **R3. One state per event, the same fold on both sides.** Over every `eventPoints` and `remainingEvents` row for the event that carries a `state`: a flag is true when any such row has it true, and `qualMatchesPlayed` is the largest value. Both producers write one state to every row of an event, so the fold changes nothing for a real artifact, and an identical artifact always compares clean.
- **R4. No state on this run's side is the strict side.** When the live fold shows a true flag or a played count above zero and this run has no state block for that event at all, that is a regression, printed with this run's value as `no state`. (Ambiguous in D1, so refuse.) A live state of zero played and three false flags against no state is not a regression: nothing is lost.
- **R5. `--allow-regress` overrides regressions only.** A read failure refuses with or without it, because the list it must still print cannot be built. (Ambiguous in D2, so refuse.) In a `--dry-run --check-live` run a read failure is printed and the run goes on, because D2 says that run never fails and it uploads nothing.
- **R6. Two passes on a real run.** The check runs right after every season is composed and before any bake, so a stale corpus is refused in seconds and not after a 3.5 minute replay. It runs again after every season is baked and immediately before the first byte gate and upload, because the Worker writes every minute and the first read is minutes old by then. Both passes cover every district of the run and both precede the first upload, which is what D2 requires. A dry run with `--check-live` makes the first pass only. To make the second pass mean something, every season is composed and baked before any season uploads. Per object order inside a season is unchanged (details, sidecars, index).
- **R7. What is compared is the composed artifact, before `bakedEvents` is attached.** That field is not a D1 fact.
- **R8. A flag with nothing to do is accepted.** `--check-live` on a real run (it always checks) and `--allow-regress` on a dry run (nothing to override) are not errors.
- **R9. Reads go 16 at a time and results are handled in input order,** so two passes over 109 districts cost a few seconds and the output is deterministic.
- **R10. Where the tests live.** The comparison and the guard's mode table are tested with no corpus (they run in CI). The ordering facts (before any write, a dry run reads nothing) can only be seen on `run`, which opens the real corpus, so those tests sit in the corpus guarded style the existing `run()` tests use and skip where the corpus is absent.
- **R11. Residual, stated and not fixed.** The Worker can still write between the second pass and that district's upload, a window of seconds. Closing it fully needs a conditional put, which is not in CONTEXT.
