<decisions>
## Implementation Decisions — LOCKED

### D-1 — One version, per-season sets. NOT one version per origin.

D-2's own reasoning, unchanged: artifact keys embed one `{algorithmId}@{version}` and the manifest
names exactly one version per algorithm. Four (now five) promoted files would force the manifest,
the Worker and every client to learn per-season version resolution — a far wider blast radius than
changing `promote.ts`'s file shape and the digest definition.

### D-2 — The replay must switch parameter sets at season boundaries

`runBoundedSeasons` (`tune.ts:406`) currently drives ALL seasons through ONE `AlgorithmModule`,
built once from a single param set, carrying state across boundaries. Per-season params breaks that
assumption and it is the architectural core of this task.

**Preferred: swap the MODULE at each boundary, keeping `makeSigma1`'s contract unchanged.** The
carried state is plain data (`Sigma1State`) and the code version is identical across seasons, so a
new module built from the incoming season's params can adopt it. This confines the change to the
replay driver, `promote.ts`, the loader and the manifest.

**Rejected unless the above proves impossible: making `makeSigma1` resolve params per season
internally.** That changes the module contract for EVERY consumer including the Worker
(`manifestSchemas.ts:106` — "a Worker rebuilds the module with `makeSigma1({ params, ... })`"), for
no gain the swap does not already give.

### D-3 — At a boundary, the INCOMING season's set owns the carry parameters

`carrySeason(state, boundary, params)` reads `carryMeanReversion`, `carryPriorYearShare` and
`consistencyCarryDecay`. Those three shape the INCOMING season's opening prior, not the outgoing
season's results, so the incoming set owns them. State the choice in a comment — it is a real fork
and a later reader must not have to guess which way it went.

### D-4 — THE EQUIVALENCE GATE: a uniform map must be bitwise identical

If `paramSetsBySeason` carries **the same set for every season**, the replay MUST produce a
prediction stream bitwise identical to today's single-set replay, and therefore the identical
`predictionStreamSha256`.

This is the acceptance bar, and it is strong: it proves the per-season machinery is a faithful
generalisation rather than a rewrite that happens to run. It is the same discipline D-T1's
reparameterisation and quick task `260903-3bv`'s gap fix both had to clear. Prove it against the
CURRENT promoted digest, not against a freshly computed baseline.

### D-5 — One digest over the full replay, never one per season

`predictionStreamSha256` stays a single hash over the whole ordered stream, exactly as
`computePredictionStreamDigest` produces today. Per-season digests would multiply the artifact's
identity and defeat D-1's whole point.

### Claude's Discretion

- Whether a keep-incumbent season stores a full copy of the incumbent set or a reference to it.
  Prefer whichever makes a hand-read of the file unambiguous — this file is evidence.
- The `paramSetName` string (D-2 suggested `rolling-YYYY-MM`).
- Whether `SIGMA1_CODE_VERSION` needs a bump. A parameter-shape change alone does not; a change to
  how the replay resolves params might. Decide deliberately and say why.

</decisions>

<specifics>
## Specific Ideas

**The inputs exist on disk** (gitignored, backed up to the session scratchpad):
`reports/tune-joint-on-origin2022.json` and `reports/tune-joint-on-origin2026.json` carry the two
accepted winners. Their `-acceptance.json` siblings carry the verdicts. The incumbent is
`data/algorithm-versions/vpr@7.0.0+tuned-2026-08.json`.

**Both accepted arms are `adaptation ON`.** 2022 accepted on both arms and the ON arm was better
(+0.001247 vs +0.000969); 2026 accepted on ON only. So the promoted map is ON-armed at both seasons
— and `adaptationEnabled` therefore differs from the incumbent's setting at those seasons. Check
what the incumbent carries and make sure the map's per-season sets are internally consistent.

**Provenance must survive.** `selectionProvenance.ts` reads `provenance.tuneSeasons` to decide
headline eligibility, and it is now the ONLY reader of that field. A per-season map makes
"selected on" per-season too: 2022's set was selected on 2019–2020, 2026's on 2019–2025. The
provenance shape must express that, or eligibility silently regresses to a single list that is
wrong for at least one season. **This is load-bearing — quick tasks `260903-n2o` and `260903-tk6`
exist entirely because that flag was allowed to describe the wrong parameter set.**

**Out of scope, deliberately:** the republish itself, the client, re-measuring SC-3 / the rewind gap
/ the baseline fingerprint, and the 2027 preseason `--seasons` run. This task builds the
representation and promotes into it. Nothing downstream re-runs here.

**Do NOT** run a tuning search. The searches are done; their artifacts are the input.

**Known traps** (project memory): never `timeout <n> pnpm <cmd>` — swallows output, exits 0. Run
`npx vitest run` from the REPO ROOT; run `npx tsc --noEmit` separately in `apps/web`. Check
`git status --porcelain` before starting and after finishing.
