# Quick Task 260904-100: D-2's `paramSetsBySeason` representation — Summary

The rolling-origin re-tune produced a real result that nothing could ship, because `promote.ts`
wrote one parameter set per version file and the result needs a per-season map. This builds D-2's
representation and promotes into it.

## The equivalence gate — PASSED, against the committed digest

A uniform `paramSetsBySeason` synthesised from the current incumbent reproduces
`380c598065c72897e8c7a944b6de77a32a69177eab7ff7541d386cb83e7783fb` **bitwise** through the new
facade — verified against the committed literal AND the file's own recorded digest. Both existing
version files still reproduce their own digests through the same path.

That is the proof this is a faithful generalisation rather than a rewrite that happens to run. A
corpus-gated second leg replays a real 2022→2023 boundary through a plain module and through the
facade over a uniform map and gets byte-identical streams — evidence, explicitly not the bar.

## The promoted file

`data/algorithm-versions/vpr@7.0.0+rolling-2026-09.json`, seven seasons, one digest:

| season | source | selected on |
|---|---|---|
| 2019, 2020 | carried incumbent | 2022, 2023, 2024 |
| **2022** | **search winner** (`tune-joint-on-origin2022`) | 2019, 2020 |
| 2023, 2024, 2025 | carried incumbent | 2022, 2023, 2024 |
| **2026** | **search winner** (`tune-joint-on-origin2026`) | 2019–2025 |

Seven, not five: the corpus holds 2019 and 2020, and `publish` walks boundaries across all of them,
so those seasons must carry the incumbent explicitly or the replay throws mid-run.


**`{2022, 2025, 2026}`.** 2022 is newly eligible because its parameters were genuinely chosen
without looking at it — the point of the whole exercise, finally cashing out.

**Correction to the executor's own summary:** it reported 2026 as ineligible "(selected on 2026)".
That contradicted its own data — 2026's set was selected on 2019–2025, which does not contain 2026
— and was a transcription error, not a code defect. The orchestrator caught it by evaluating the
rule directly against the file. No test encoded the wrong claim.

Live eligibility remains `{2025, 2026}`, because `PROMOTED_VPR_VERSION_PATH` deliberately still
points at the incumbent. Moving the pin is the republish's job.

## The catch that mattered most

`scripts/reparamEquivalence.ts` was a **fourth** reader of `promoted.params` that the plan had not
listed — it builds its own multi-season replay with manual `carrySeason` threading, and would have
silently fallen back to `DEFAULT_SIGMA1_PARAMS` on a per-season file. Found by the plan's own grep
check rather than by any test. Same shape as the three-drivers problem, with a fourth site.
