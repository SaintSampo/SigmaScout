## What the planner determined (do not re-derive these — they were verified against the working tree on 2026-09-04)

### 1. Every replay driver, and whether they share a helper

**They do NOT share a helper. Three independent multi-season loops exist, each a deliberate copy:**

| Driver | Location | Shape | How its modules are built |
|---|---|---|---|
| `runSeasons` | `packages/harness/cli.ts:649` | season loop, `carrySeason` threading via `liveStates` | `applyPromotedOverrides(resolveAlgorithms(...))`, built ONCE before the loop |
| `runBoundedSeasons` | `packages/harness/tune.ts:406` | its own loop; header says "Mirrors `cli.ts`'s exported `runSeasons` season loop" | caller builds candidate + incumbent modules once (`tune.ts:1597-1598`) |
| the publish loop | `packages/harness/publish.ts:~1540-1690` | its own loop; header at `publish.ts:1493-1499` says it "Mirrors `cli.ts`'s `runSeasons` ... rather than importing it" | `resolvePublishAlgorithms` -> `applyPromotedOverrides` (`publish.ts:2090`) |

Three more sites replay a SINGLE season and still need the right season's set: `promote.ts`'s `main()` (the digest slice), `publish.ts`'s `--event` mode (`publish.ts:~2151-2175`), and `digest.test.ts`. Two more build modules from the algorithms MANIFEST rather than a version file: `scripts/replayRig.ts:239` and `apps/worker/src/scheduled.ts:263`.

`baselineFingerprint.ts:413` and `eventScopeDiagnostic.ts:662` also loop over seasons but read committed `predictions-{season}.jsonl` sidecars — they run no algorithm and need nothing here.

**Consequence, and the reason this plan does NOT edit the three loops:** patching a per-season module swap into one loop leaves the other two silently running one set for all seasons, with a green suite. D-2 assumed one driver. The fix that survives three copies is to move the swap DOWN into the module the loops already receive — a harness-layer facade — so every driver, present and future, gets it by construction and no loop signature changes.

### 2. The module swap is viable — and it is already the production pattern

- `Sigma1State` (`packages/core/algorithms/sigma1/index.ts:225-258`) is plain data: `season`, `componentOrder`, `teams` (Map), `league`, `allianceScoreStats`, `priorSeasonRatings`, and two counters. No functions, no params, nothing closed over.
- `makeSigma1` (`sigma1/index.ts:1698-1723`) resolves `params` ONCE and closes it over `predict`/`update`/`teamMetrics`/`carrySeason`. The closure lives in the MODULE, never in the state.
- Decisive existing evidence: `apps/worker/src/scheduled.ts` rebuilds modules from the manifest EVERY tick (`buildAlgorithmModules`, line 263) and adopts state loaded from D1 through `packages/harness/stateSnapshot.ts`'s `serializeState`/`deserializeState`. A `Sigma1State` produced by one module instance being adopted by another is the shipped production path.

So a state carried out of a module built with params A can be adopted by a module built with params B at the same code version. The swap is viable; D-2's rejected alternative (making `makeSigma1` resolve params internally) is not needed and must not be built.

### 3. How provenance expresses per-season selection

`selectionProvenance.ts` reads `provenance.tuneSeasons` as ONE flat list and is its only reader. `score.ts`'s `isHeadlineEligible(season, corpusSeasons, selectedOnSeasons)` asks `selectedOnSeasons.includes(season)`. Under a per-season map that single list is wrong for at least one season. Verified from the real artifacts:

| season | governing set | its own selected-on seasons | headlineEligible |
|---|---|---|---|
| 2019, 2020 | incumbent (carried) | `[2022, 2023, 2024]` | 2019/2020 are eligible-by-selection but have no strictly-prior corpus season, so clause 1 governs |
| 2022 | NEW, `reports/tune-joint-on-origin2022.json` (`seasons: [2019,2020]`) | `[2019, 2020]` | ELIGIBLE (today it is NOT) |
| 2023, 2024 | incumbent (carried) | `[2022, 2023, 2024]` | ineligible (unchanged) |
| 2025 | incumbent (carried) | `[2022, 2023, 2024]` | eligible (unchanged) |
| 2026 | NEW, `reports/tune-joint-on-origin2026.json` (`seasons: [2019,2020,2022,2023,2024,2025]`) | that list | ELIGIBLE (unchanged, different reason) |

`selectedOnSeasonsFor` must therefore stop returning `Record<string, readonly number[]>` and start returning `Record<string, (season: number) => readonly number[]>`, where `vpr`'s resolver returns the `selectedOnSeasons` recorded on the map entry that GOVERNS the asked-about season — never a union of all entries, never `provenance.tuneSeasons`, and never `[]` for an uncovered season (throw instead: a `[]` reads as "never fitted", which is exactly the failure `260903-n2o` and `260903-tk6` exist to close). A uniform function type is used for every id — no union, no branch, so the shape cannot drift back.

The top-level `provenance.tuneSeasons` becomes ambiguous under a map. It is therefore made structurally unreachable: the schema FORBIDS it (with `searchArtifact` and `objective`) on a `paramSetsBySeason` file, so no future reader can pick up a wrong flat list.

### 4. The Worker path: one small, honest manifest change

`AlgorithmManifestEntrySchema` (`manifestSchemas.ts:106`) carries a single optional `params` for the Worker to rebuild the module. The Worker only ever runs the LIVE season, so it needs exactly ONE season's set — a per-season map in the manifest would buy nothing and would widen the blast radius to the published manifest shape.

`buildAlgorithmsManifest` (`manifests.ts:244`) currently writes `params: promoted.params` with no season in scope, so under a map it would either crash or silently pick a season. The change is: `paramsSeason` becomes a REQUIRED option (no default — a default is how the wrong season gets picked silently), `params` is resolved for that season, and the entry records `paramsSeason` so the manifest states which season's set it carries.

Adding `paramsSeason` to the manifest entry does NOT touch the client: `apps/web/src/lib/api/manifests.ts` declares its own `AlgorithmManifestEntryClientSchema` in Zod's default (non-strict) object mode and silently strips every key it does not name (its own header says so). `apps/worker/src/scheduled.ts` and `scripts/replayRig.ts` read `entry.params`/`entry.paramSetName` and are unchanged.

`publish.ts:2015` is the only production caller; it threads `paramsSeason` from the maximum season it is publishing.

### 5. `SIGMA1_CODE_VERSION` stays at 7.0.0 (Claude's Discretion, decided)

D-13's rule (`promote.ts` header, quick task `260903-5dp` / D-N3) is that the code version moves when the OUTPUT moves. Here `makeSigma1` is untouched, the individual parameter sets keep the exact 7.0.0 field set, and the equivalence gate proves the same set on the same season produces the same bytes. What changes is WHICH set ships per season — and that is precisely what the `+paramSetName` half of `{codeVersion}+{paramSetName}` exists to name. `paramSetName` moves `tuned-2026-08` -> `rolling-2026-09`; no `legacyParams.ts` migration is added (nothing inside a parameter set moved). Bumping would also drag `PROMOTED_VPR_VERSION_PATH`, `INCUMBENT_VERSION_PATH` and `selectionProvenance.ts`'s derived path onto a file that does not exist yet, forcing a pointless re-promotion of the incumbent.

### 6. Corpus seasons and the completeness rule

`SELECT DISTINCT year FROM events WHERE is_offseason = 0` returns **2019, 2020, 2022, 2023, 2024, 2025, 2026** (no 2021 — the cancelled season). The map MUST cover all seven, or `publish`/`harness` runs that replay 2019-2020 will throw at a boundary. `promote` enforces this before writing.
