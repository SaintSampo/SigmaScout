# Publish `tierCuts` on the team-season artifact

The one visible regression quick task 260923-3w7 recorded is closed. Since that task the robot
page reads only its own team-season artifact, so a live-folded metric-history row (a metric value
the tick wrote, carrying no `percentile`) rendered untiered until that event's next republish,
because the rarity-tier cut points lived only on the event artifact the page no longer fetches.

`tierCuts` was never per-event. It is built once per (algorithm, season) from `rankingPools`
(`buildTierCutsFromPools`) and merely rode each event artifact, so the publisher now attaches the
same object to every team-season artifact as well. A key and a carry-forward, not a new
computation, not an approximation, and not a second fetch.

**Published numbers did not change.** No algorithm version bump, no `PAGE_ARTIFACT_SCHEMA_VERSION`
bump (additive optional key). No visual change.

**Net: 22 files changed, 774 insertions, 167 deletions.**

## What changed, per commit

### 1. Schema and publisher (`b01dc288`)

`TeamSeasonArtifactSchema` gains `tierCuts: SeasonTierCutsSchema.optional().catch(undefined)`, the
identical schema object the event artifact declares. Declaring it is load-bearing:
`writeArtifactObject`'s write-side parse strips every undeclared key, so an undeclared key would be
silently undone on every live tick. The pair was renamed `EventTierCut*` to `SeasonTierCut*`
(identifiers only; the wire key is still `tierCuts` on both artifacts). Tests: schema round-trip,
malformed-degrades-to-absent, the pre-republish absent-key case, both schemas accept the identical
block, and an end-to-end `publishSeasons` pin that every published team artifact's `tierCuts` is
byte-equal to both events' artifacts for the same (algorithm, season).

### 2. Worker carry-forward (`c73e3b18`)

No Worker code change was needed; five new cases establish it. `mergeTeamSeasonArtifact` spreads
`existing` first, so once the key is declared it rides a tick untouched and survives the write-side
parse. A bootstrap merge carries none, the same policy as `mergeEventArtifact`. `mergeTeam` split
into `mergeTeamRaw` and `mergeTeam` to separate "the merge carried the key" from "the parse kept
the key". Also corrected a stale doc comment in `touchedEventTeamMetrics` that named the completed
`rp-fold-exceeds-worker-cpu-budget` todo as a live gate.

### 3. Web (`61ef739b`)

`EventSectionList` passes `artifact.tierCuts`; `EventSection` resolves its Total tile and three phase
tiles against it via `resolveMetricTier`. A published `percentile` still always wins, and `sigma`
stays untiered. Restored the three `EventSection` cases 260923-3w7 deleted (three, not two) plus
four more, and two route-level cases: tiered from the team artifact with zero `/v1/event/` fetches,
and a pre-republish file that still loads and renders that row untiered. `MetricHistoryTab`,
`metricHistorySeries`, `MetricHistoryChart` and `MatchTable` render no rarity tier for a history
row, so `EventSection` was the only robot-page surface with a tier to lose.

### 4. Docs and todo (`e0496acb`)

`docs/worker-operations.md`'s regression paragraph replaced by what an operator needs now, including
that a republish is owed to populate the key. `.planning/todos/pending/live-merges-drop-percentiles.md`:
the tier half is closed on every surface; the percentile-number half stays open, and with the
account on Workers Paid the compact-pool direction is feasible on the tick today.

## Is a republish needed?

Yes, one per (algorithm, season), to populate the key. A team artifact published before this task
parses and renders a live-folded row untiered until republished, never worse than before. No Worker
deploy is required for correctness (the carry-forward is inert until a block exists).

## Deliberate calls

- Renamed the type rather than leaving `EventTierCuts` on a block two artifacts carry.
- Did not wire `SeasonHeader`: its `seasonStats.metrics` tiles tier from a published `percentile`
  and never had cuts, so they thin during live folding today as they did before 260923-3w7. A
  pre-existing gap, cheap to close the same way, recorded here as a follow-up rather than a regression.
