# 260920-q75: make a mid-event re-baseline safe

## The defect (diagnosed, not to be re-investigated)

On 2026-09-20 a `pnpm publish:seasons` run (generation `e5cf1304`) finished at 20:12 UTC with four
events holding open live windows. The D1 seed was applied minutes later. In between, tick
`tick-1789935145177` folded all four events against the PREVIOUS generation's D1 state, advanced each
`event_cursor.last_folded_match_key`, and rewrote the event artifacts. The seed then replaced
`algorithm_state` but never touches `event_cursor`, so `2026onsca1` now sits 2 matches past its
seeded state and `2026tnkno` 1 past — permanently missing from live state until the next
re-baseline. Had the seed landed first, the tick would instead have re-folded all 70 already-included
`2026cc` quals. Both directions are silent.

Two independent causes, and this plan fixes both:

1. The seed owns `algorithm_state` but not `event_cursor`, so the two can disagree after any
   mid-event re-baseline.
2. Nothing stops a tick folding in the window between "new manifests are live in R2" and "D1 is
   seeded from that same run".

## What was verified in the source before writing these tasks

1. **The tick-meta read is the widening opportunity.** `runTick` already spends one D1 round trip on
   `readTickMeta` (`scheduled.ts:1395-1396`), which reads exactly one `event_cursor` row by key
   (`readEventCursor`, `stateStore.ts:190`). Widening that one statement to `WHERE event_key IN (...)`
   returns the tick-meta sentinel AND the baseline markers for the same single subrequest. It sits
   AFTER both the nothing-live early exit (`scheduled.ts:1353`) and the probe-only early exit
   (`scheduled.ts:1371`), so neither of those paths pays anything new.

2. **`event_cursor` needs no migration for either row.** Its columns are
   `event_key` (PK), `tba_etag`, `last_folded_match_key`, `last_polled_at`, `last_advanced_at`
   (`migrations/0001_algorithm_state.sql`). The tick-meta sentinel already abuses
   `last_folded_match_key` as a payload column under the key `__scheduler_meta__`
   (`scheduled.ts:150,173`), so a per-algorithm marker row carrying a bare generation string is the
   same, already-established shape — and a bare string needs no `JSON.parse` at all.

3. **`algorithm_state` is the WRONG home for the marker.** `readScopedState` only ever runs inside
   `processEvent`, per event, per algorithm — far too late to decide whether to fold. Its
   `StateRowScopeKind` union is `team | event | league`, so a marker row would need a type change,
   and nothing on the live path reads `algorithm_state` once per tick. `event_cursor` wins on both
   counts.

4. **The ordering CAN differ, and that is a real hazard.** The publisher's replay order is
   `selectMatchesChronological`'s `ORDER BY m.sort_time, m.event_key, comp-level rank, set_number,
   match_number` (`packages/corpus/db.ts`, quoted by `replay.ts:87-95`). The Worker sorts
   `[...normalized].sort((a, b) => a.sortTime - b.sortTime)` (`scheduled.ts:789`) — a stable sort, so
   ties keep TBA's array order. `hasAlreadyFolded` (`stateStore.ts:232`) compares INDEXES in the
   Worker's list, so a tie straddling the seeded cursor flips a match from "unfolded" to "already
   folded" and drops it forever. Task 1 removes the divergence by making the Worker sort by the same
   total order, which is strictly more deterministic than TBA array order.

5. **The fold gate is inside `update()`, not the tick.** `foldsIntoRatings` is applied by each
   algorithm (`opr.ts:296`, `epa.ts:717`, and inside SPR's layer), so the cursor means "last match
   CONSUMED for this event", not "last match that changed a rating". Week 0 changes nothing here: the
   publisher passes those matches to `update()` too, so publisher and Worker agree on what the cursor
   counts.

6. **The replay stream is the exact fold sequence.** `buildSeasonStream` (`replay.ts:100`) returns
   `selectMatchesChronological` for the season, which selects played matches only, and
   `simulator.runAll` walks it in order (`publish.ts:1866`). The last entry per `eventKey` in that
   array IS the publisher's last folded match for that event. No extra corpus query is needed.

7. **Only 5 test files drive `runTick` with a D1 fake** — `scheduled.test.ts`,
   `scheduled.liveRows.test.ts`, `scheduled.replay.test.ts`, `scheduled.rp.test.ts`,
   `liveAlgorithmTier.test.ts` — and all five pin their algorithms manifest at `generation: "gen-1"`.
   Each has its own `FakeD1Database` class whose `FROM event_cursor` branch reads `args[0]` and
   returns one row. That is two one-line edits per file, not forty.

## Design decisions this plan locks

- **Cursor rows and markers live together in ONE file, `reports/publish/seed-cursors.sql`, applied
  LAST.** Splitting the markers into the three per-algorithm seed files was considered and rejected:
  `seed-spr.sql` landing would then flip spr's marker to the new generation while the cursors were
  still the old ones — reproducing the exact incident. One file applied last makes the cursor rewrite
  and the permission to fold arrive together.
- **Each marker INSERT is guarded by `WHERE EXISTS (SELECT 1 FROM algorithm_state WHERE algorithm_id
  = '<id>' AND generation = '<gen>')`.** If the operator applies the cursors file first by mistake,
  the markers silently do not land, the tick keeps refusing, and re-running the file after the state
  seeds fixes it. Cursor rows themselves are unconditional, and are inert while the marker guard
  holds.
- **The marker is compared for the LIVE tier only** (`algorithmModules.keys()`), not for every
  published algorithm. An algorithm that never folds live cannot desync its state from the cursor,
  and a partial publish (`--algorithm spr`) must not brick folding for a tier it did not touch.
- **On mismatch the whole tick folds nothing** — not just the mismatched algorithm. `event_cursor`
  has no per-algorithm granularity, so a partial fold would desync the un-advanced algorithms, which
  is the failure mode `processEvent`'s own header already warns about (`scheduled.ts:6-11`).

## Constraints held

No published number changes. No algorithm version bump. No `STATE_SNAPSHOT_SHAPE_VERSION` bump. No
D1 migration. Zero added D1 round trips on the nothing-live path, the probe-only path AND the live
path. No new JSON parsing of anything large (the marker is a bare string).

<objective>
Make a mid-event re-baseline safe in both directions: the offline seed becomes the authority for
`event_cursor` as well as `algorithm_state`, and the tick refuses to fold while the two disagree.

Purpose: a publish run that lands while an event is live currently corrupts live state silently, in
one of two directions depending on which of two unsynchronised writes happens to win.
Output: a fourth seed file the operator applies last, a per-algorithm baseline marker the tick
checks for free, a shared match-order comparator, tests for every direction, and a corrected runbook.
</objective>
