# Can FRC awards be predicted, and at what accuracy?

A feasibility test, not a feature. Two steps, in this order: **widen the award ingest, then measure
walk-forward.** The deliverable is a table of measured top-1 accuracies next to their baselines —
not a model, not a surface, not a shipped algorithm.

## Why

The question is currently unanswerable from the corpus. `event_awards` holds 6,170 rows covering
**four** award types (0 Impact, 1 Winner, 9 Engineering Inspiration, 10 Rookie All Star) from
**district events only** — 0 of 2026's 56 regionals, 0 championships. Every judged award that isn't
one of those four has never been fetched. Measuring "award predictability" against that slice would
measure the ingest filter, not the awards.

The filter is deliberate and correct for what it was built for: it feeds
`packages/core/districts/qualification.ts`, which is a shipped surface.

## The two features, and only these two

1. **Prior award history** — has this team won this award before, how often, how recently. **Prior
   seasons only.**
2. **On-field strength** — the team's BPR rating going into the event.

Jacob considered and **did not select** team age / veteran status, or event context. Do not add
them, do not sneak them in as a derived quantity (no "seasons since first appearance", no event
week/district/country term).

**Rookie All Star is therefore handicapped and stays handicapped.** Without an age feature the model
cannot identify which candidates are rookies, so it is being asked to pick a rookie out of a pool it
cannot see rookies in. Report the number it earns. Do not special-case it, do not exclude it, do not
add `rookie_year` "just for that one award". The handicap showing up in the result *is* a finding.

## What must not move

**`event_awards` is not widened in place.** `packages/core/districts/qualification.ts:94` **throws**
on any `award_type` outside `{0,1,9,10}` ("no declared display label for award_type ..."). Widening
the existing table would break the shipped district-qualification path and its four test files
(`locks.test.ts`, `qualification.test.ts`, `prequalified.test.ts`, `reconciliation.test.ts`). So:
a **new additive table**, a **new normalize function**, a **new ingest mode**.
`normalizeEventAwards` and `QUALIFICATION_RELEVANT_AWARD_TYPES` (`packages/ingest/districts.ts:101`)
are read-only reference material here.

**`packages/harness/publish.ts` and `packages/harness/publish.test.ts` must not be opened, edited, or
staged.** Another session is mid-edit on both, uncommitted, in this same checkout. Nothing in this
task needs them.

The zod parse boundary needs **no** work: `packages/ingest/schemas.ts:360` already models
`award_type` as a plain `z.number().int()` on purpose, and `tbaAwardRecipientSchema` already carries
both `team_key` and `awardee` as nullable. Every field this task wants is already parsed and then
thrown away at the normalize boundary.

## Tasks

### T1 — additive table + `--awards-all-only` ingest mode (executor, offline)

Model the whole thing on `--event-teams-only`, which solved the identical "the existing mode only
covered district events" problem: pure helpers in their own module (`packages/ingest/eventTeams.ts`),
CLI loop in `cli.ts:916+`.

**`packages/corpus/schema.sql`** — new table, additive, applied by the existing
`CREATE TABLE IF NOT EXISTS` exec at `db.ts:216`:

- `event_awards_all(event_key, award_type, award_index, recipient_index, team_key, awardee, name, year, fetched_at)`
- PK `(event_key, award_type, award_index, recipient_index)`; `team_key` and `awardee` both
  **nullable** (TBA's real shape: a person-only recipient carries `team_key: null`).
- `award_index` = position in the response array, `recipient_index` = position in `recipient_list`.
  The key is positional, so writes are **delete-then-insert per event inside one transaction**, never
  a bare upsert — otherwise a shrinking award list leaves stale rows behind.
- Doc comment must state *why this table exists alongside `event_awards`* and that `event_awards`
  keeps its four-type contract.

**`packages/corpus/db.ts`** — `CorpusEventAwardAll` interface + `replaceEventAwardsAll(db, eventKey, rows)`
(DELETE by `event_key`, then INSERT each, in a transaction). Store `name` and `awardee`: the current
table discards both, they are free, and a research table without the award's human name is painful to
read.

**`packages/ingest/awardsAll.ts`** — the testable core, split out of `cli.ts`:

- `selectAllEventKeysForYear(db, year)` — **every** event in `events` for that year, ascending.
  Deliberately **not** gated on `isOfficialEventType`: Jacob asked for all event types, so offseason
  (99) and preseason (100) get *stored*. The experiment excludes them at scoring time and reports the
  count — that split is honest; filtering at ingest would be unrecoverable.
- `normalizeEventAwardsAll(response)` → `{awardType, awardIndex, recipientIndex, teamKey, awardee, name}[]`.
  **No award-type filter. No null-team-key skip.** Both of those are the exact lines that make
  `normalizeEventAwards` the wrong function here. `null` body and `[]` body both return `[]`, never
  throw — same contract as every other normalize in this codebase.
- `eventAwardsAllEtagKey(eventKey)` → `` `/event/${eventKey}/awards#all` ``.

**The ETag trap — this is load-bearing.** `readEtag`/`writeEtag` are keyed by the URL *string*
(`db.ts:723`). `--awards-only` already cached `/event/{key}/awards` for every district event. If the
new mode reuses that key it gets a **304 with no body** on exactly the events that already have
awards, and silently stores nothing — a backfill that looks like it worked. Hence the `#all` suffix:
a separate cache namespace for the same fetch URL. `fetchEventAwards(ctx, eventKey, cachedEtag)`
(`tbaClient.ts:285`) builds the real URL itself, so passing a different cache key is a one-line change
and costs nothing.

**`packages/ingest/cli.ts`** — `--awards-all-only` flag (parse it alongside `awards-only` at `:189`,
thread it through all three `CliOptions` returns, dispatch near `:1097`) and
`ingestSeasonAwardsAllOnly(db, ctx, year, force)` copied in shape from `ingestSeasonEventTeamsOnly`:
per-event fetch, `HTTP 404` logged-and-skipped, 304 counted, `writeEtag` under the `#all` key on a
200. The summary line must print the **304 count prominently** — a run that 304s everything is the
one failure mode that otherwise looks like success.

Keep `THROTTLE_INTERVAL_MS = 100` untouched.

**`package.json`** — `"ingest:awards-all": "tsx --env-file=.env packages/ingest/cli.ts --awards-all-only"`.

**`packages/ingest/awardsAll.test.ts`** — fixture-driven, no network:
an award type outside `{0,1,9,10}` is **kept**; a `team_key: null` person recipient is **kept** with
its `awardee`; a multi-recipient award produces one row per recipient with distinct
`recipient_index`; two awards of the same type at one event stay distinct via `award_index`;
`null`/`[]` bodies return `[]`; `eventAwardsAllEtagKey` is **not equal** to the `/event/{key}/awards`
fetch URL (pin the trap above with an assertion, not a comment); `selectAllEventKeysForYear` returns
offseason and preseason events.

### T3 — the experiment (executor, offline)

`scripts/measureAwardPredictability.ts` + `scripts/measureAwardPredictability.test.ts`, following the
`measure*.ts` convention already in `scripts/`. Add `"measure:award-predictability": "tsx scripts/measureAwardPredictability.ts"`.
No network: it reads `data/corpus.sqlite` only. Written after T2 lands so it can be run, but it does
not depend on T2 to compile or to pass its own fixture tests.

**Unit of prediction.** One `(event, award_type)` instance for every award actually given at an
in-scope event with at least one team recipient. The model **ranks every candidate team at that
event** and its top-1 pick is scored correct if that team is in the actual recipient set.

**Candidate pool** = `event_teams` roster ∪ teams appearing in that event's `matches`. Report
instances whose actual winner is outside the pool as a separate count — that is a data-integrity
readout, not a model error, and hiding it would flatter the accuracy.

**Pre-event on-field strength.** One chronological replay of `loadMatches("data/corpus.sqlite")`
mirroring `packages/bpr/evaluate.ts:91`'s predict-before-update sequencing exactly (read it; the
`carryover.ts:104-118` loop is the closest existing copy). **Do not modify `runEval` or
`evaluate.ts`** — write the experiment's own loop. At each event's **first** match, snapshot
`model.snapshot()` for that event's candidate teams **before** calling `model.update` on it. That
snapshot is the event's strength feature, and it is pre-event by construction. Params:
`packages/bpr/frozen-params.json` merged over `DEFAULTS`, the `carryover.ts:96-98` pattern.

**Feature vector (four numbers, two families, nothing else):**

| # | Family | Definition |
|---|--------|------------|
| f1 | prior award history | `log1p(count)` of this team's prior wins of **this** award type |
| f2 | prior award history | recency: `1/(1 + seasons since last win of this award type)`, `0` if never |
| f3 | prior award history | `log1p(count)` of this team's prior wins of **any** award type (decoration) |
| f4 | on-field strength | pre-event BPR rating, standardized **within the event's pool** |

f1–f3 are three encodings of the one selected history feature. f4 is standardized within the event so
a 2016 rating and a 2026 rating are not compared on a drifting absolute scale.

**Walk-forward is mandatory and is the whole point.** For scored season Y, every feature and every
fitted weight comes from seasons **strictly less than Y**. First scored season is 2017 (2016 has no
prior). 2022's prior set is 2016–2020 — the 2021 gap is real, not an off-by-one. A model fit on all
seasons and scored in-sample is not an acceptable answer to this question.

**Model.** Per award type, a conditional logit (softmax over the event's candidate pool — the shape
that matches "exactly one instance, one winner set"), fit by plain gradient ascent on the prior-season
instances. When an award type has **fewer than 30 prior instances**, fall back to the decoration
heuristic and mark every row it produced as `thin-prior` in the output. Don't tune it; a tuned
feasibility probe answers a different question.

**Baselines, all three reported next to every model number:**

- **B0 random** — expected top-1 = `|recipients| / |pool|` per instance, averaged. An accuracy with no
  baseline is not an answer.
- **B1 most-decorated-team-present** — rank by prior wins of this award type, tie-break on prior wins
  of any type, then ascending team number. **Tie-breaking on BPR is forbidden** — that silently makes
  B1 a two-feature model and stops it being a baseline.
- **B2 strongest-team-present** — rank by pre-event BPR alone. Free single-feature ablation: it says
  whether the fit beats either feature used by itself.

**Output table** — per award type × season, and a pooled row per award type: `n` instances, mean pool
size, mean recipient-set size, top-1 for model / B0 / B1 / B2, and a `thin` flag for pooled `n < 30`.
Sample size per award type is not optional decoration: several judged types will have a handful of
instances and the reader must be able to tell those from the real ones at a glance.

**Award type 1 (Winner) prints in its own section, labelled reference-only.** It is the on-field
elimination result, it is already the match predictors' domain, it has 3–4 recipients per instance,
and it will score high. It is a sanity check that the rig works — presenting it as the headline
judged-award result would be dishonest.

**Exclusions, each counted and printed:** offseason/preseason events (99/100); award instances with no
team recipient (person-only awards — Woodie Flowers, Volunteer); instances with an empty candidate pool.

**Tests** (`scripts/measureAwardPredictability.test.ts`, synthetic fixtures, no corpus):

- **Leak test, the important one:** the feature builder for season Y sees zero input rows with
  `year >= Y`. Assert it directly on a fixture that would change the answer if leaked.
- Pre-event snapshot is taken before the event's first `update`, not after.
- Top-1 counts a hit when the pick is any member of a multi-recipient set.
- B0/B1/B2 compute as specified on a hand-checkable fixture; B1 never consults BPR.
- The `thin-prior` fallback fires below 30 prior instances and is flagged in the row.

### T4 — run it and write down the answer

`pnpm measure:award-predictability`, full output captured into the task SUMMARY.

**Pre-commit the verdict rule now, before seeing numbers:** an award type counts as **predictable**
only if the model's pooled top-1 beats **both** B1 and B2, with pooled `n >= 30`. Anything else is
reported as **not demonstrated** — not as "promising", not as "directionally positive". Rookie All
Star's number is reported with the handicap named, and is not retried with an age feature.

The SUMMARY's first paragraph must answer the actual question in plain words: which award types are
predictable, at what top-1, against which baseline, on how many instances.
