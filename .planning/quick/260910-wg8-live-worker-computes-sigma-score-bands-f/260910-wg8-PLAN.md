# Quick task 260910-wg8 — the live Worker learns Sigma Score

Closes `.planning/todos/pending/sigma-score-live-worker-divergence.md`.

## The defect

Sigma Score drives BPR's match bands in the offline publisher. The live Worker does not know about
it, and **BPR is the live tier** (`DEFAULT_LIVE_ALGORITHM_IDS = ["bpr"]`). So a match the Worker folds
during an event gets a **Swing Factor** band while every offline-published row around it carries a
**Sigma Score** band. Swing prints 1.92σ, Sigma prints an honest 1σ, so live-touched matches would
read roughly twice as wide as their neighbours.

Silent: nothing throws, both paths look healthy.

## Ordering, which is the correctness crux

Offline (`SigmaScoutLayer.foldPlayed`) does: **read band → fold → apply talent as of after this
match**. The Worker must match exactly, or the two produce different numbers from the same matches.

In the Worker's loop that means: read band from the accumulator, `state = algorithm.update(...)`,
fold the match, then read `algorithm.teamMetrics(state, roster)` and `observeTalent`. Talent taken
from the post-update state is admissible evidence for the team's NEXT match, never for this one.

## The band is already the RP input

`SigmaScoutLayer` feeds the same band variance into the ranking-point pmf. Changing BPR's band
therefore changes BPR's RP probabilities too. That already happened offline in the ship commit; this
task only brings the Worker into line with it.

## A decision this forces, recorded rather than buried

The Worker cannot recompute percentiles — it has no season-wide pool — so it cannot produce a Sigma
**tier**. Offline it publishes `{ value, percentile }` under `SIGMA_METRIC_KEY`.

**Decision: the Worker updates the metric entry's `value` and leaves its `percentile` untouched.** A
fresh number beside a slightly stale ring beats a tile frozen whole for the length of an event, and
live freshness is the entire point of the Worker. The alternative (leave both stale) was rejected;
the old `swingFactor` field is NOT written for Sigma algorithms, since nothing renders it and the
offline publisher stopped emitting it for them.

## CPU

`teamMetrics` gains one call per newly folded match, only for Sigma algorithms. BPR's `teamMetrics`
is a per-team map read plus `state.scale / 3`, not a solve. Idle ticks are unaffected. Worth a
measured look at a real fold tick after deploy, since the budget is genuinely thin.

## Verification

- The replay digest covers the band, and **fails with the Sigma path reverted** — otherwise the parity

- Full root suite.

## Out of scope

Publishing and re-seeding. A deploy carrying shape 11 against un-re-seeded D1 rows takes live folding
down until the seed runs, so **seed first, deploy second**, and both follow the republish.
