<objective>
On the Teams page's bubble chart, hovering a point shows that team's number in a
tooltip, and clicking the point opens that team's page.

Purpose: the chart currently shows the shape of the field but tells you nothing about
any individual in it — an interesting outlier is an anonymous dot you cannot follow up
on. Hover names it; click takes you there. That turns the chart from a picture into a
way in.

Output: two new pure functions and one shared label constant in the model module, hover
and click on the chart component, one navigate call in the route, and tests across all
three.

**Decision IDs.** D-01 through D-04 are the developer's locked decisions D1 through D4,
renumbered to this project's `D-NN` convention. They are not to be revisited:

- **D-01 — Tooltip content.** Team number first and most prominent, then the nickname,
  then the two plotted values: the Total metric and Swing Score. The labels are the
  SAME ones the chart's axes and the table's columns already use, read from a shared
  source and never re-typed. Values are formatted the way the table formats them. The
  algorithm's own internal confidence field must never appear in the tooltip or anywhere
  else on screen — enforced structurally (no field on `BubblePoint` can hold it) and
  asserted on the tooltip's rendered text.
- **D-02 — Click target.** Clicking a point goes to `/team/$teamNumber` with the same
  `params` and the same `search` carrying `year`/`algorithm`/`tab` that `columns.tsx`'s
  team links already carry, so a team reached from the chart lands in the same state as
  one reached from the table. No hand-built URL string.
- **D-03 — Overlapping points.** The hit test resolves to the single nearest point
  within a hit radius. Ties break deterministically on lowest team number, so the same
  pixel always yields the same team. No "all N teams under the cursor" list.
- **D-04 — Accessibility, honestly.** A 3,700-point cloud does not become 3,700 tab
  stops. The svg keeps its existing `role="img"` + `aria-label` contract; hover and
  click are a pointer-only affordance layered on top; the table stays the accessible and
  keyboard route to every team page and every value. See `<accessibility_decision>` for
  the reasoning, including why the arrow-key walk is declined rather than shipped as a
  checkbox.
</objective>

<the_central_problem>
This is the whole reason the task needs a plan rather than a one-liner, and every task
below is shaped by it.

`TeamsBubbleChart.tsx` renders the entire point cloud as **at most four `<path>` nodes**,
one per rarity tone, built by `tonePathData()`. There is deliberately **no DOM node per
point** — that was the explicit performance decision one hour ago (quick task 260909-tom,
`rendering_decision`): at the real 2026 field size of ~3,700 teams, Recharts'
one-component-per-point was rejected for exactly this reason.

So hover and click must arrive **without** regressing to per-point DOM nodes. That means
pointer-position hit-testing: convert the pointer's client coordinates into plot
coordinates, find the nearest point within a hit radius, and render ONE highlight mark
plus ONE tooltip. A uniform grid bucketed over the plot rect, built once per
`[model, plot]` in the pure model module, keeps the per-move cost bounded rather than a
3,700-point linear scan on every `pointermove`.

Three consequences the tasks below make explicit:

1. **The header comment currently asserts the opposite of what the component will do.**
   It says "No tooltip and no per-point hover — that is the whole reason the point cloud
   costs four DOM nodes." A comment that contradicts the code is precisely the failure
   mode this project's CLAUDE.md names. Task 2 rewrites it.
2. **The node-count invariant stays under test.** The existing "at most four `[data-tone]`
   paths" assertion must survive, and a new test must fail loudly if someone later
   "simplifies" this into per-point `<circle>` elements.
3. **The tone-path memo must stay keyed on `[model, plot]` and must never gain hover
   state as a dependency.** This is the single most likely way to get this wrong: a hover
   in the dependency list rebuilds ~3,700-point path strings on every mouse move, which
   is strictly worse than the per-point DOM this design exists to avoid.
</the_central_problem>

<navigation_decision>
**The component takes an `onSelectTeam` callback; the ROUTE owns the navigate call.**
Settled here rather than left to the executor, because the obvious alternative breaks
eleven passing tests.

`TeamsBubbleChart.test.tsx` renders the component bare — no `RouterProvider`. Calling
`useNavigate()` (or rendering a `<Link>`) inside the component makes it throw outside a
router context, which would force all eleven existing tests into a router harness for no
gain. So:

- `TeamsBubbleChart` gains `onSelectTeam?: (point: BubblePoint) => void` and imports
  nothing from `@tanstack/react-router`. It stays a pure presentational unit.
- `teams.tsx` — which already has `year` and `algorithm` in scope — passes a handler that
  calls `navigate({ to: "/team/$teamNumber", params: { teamNumber: String(point.teamNumber) },
  search: { year, algorithm, tab: "overview" } })`. That is D-02's link shape verbatim,
  typed against the generated route tree, so a drift between this and `columns.tsx`'s
  `<Link>` is a compile error rather than a broken URL.

**The honest cost, which must be written into the header comment rather than glossed:**
a programmatic navigate has no `href`, so a chart point offers no middle-click, no
cmd-click-to-new-tab, no right-click-copy-link and no status-bar preview. The table's
rows carry real anchors and remain the route for all of that. This is the same tradeoff
D-04 makes and it is made for the same reason: an anchor per point is a DOM node per
point, which is the one thing this component exists to avoid.
</navigation_decision>

<accessibility_decision>
D-04 asks for honesty rather than a checkbox, so the reasoning is recorded here.

**Kept:** the svg's existing `role="img"` and its existing `aria-label` (which already
names the plotted team count and both axes). Task 2 must not change that string — an
existing test asserts on it, and more importantly the element genuinely is an image.

**Added:** one muted, visible hint line beside the key row reading
`Hover a point for its team; click to open that team's page.` It is real DOM text, so it
is available to a screen reader as well as to a sighted reader, and it describes the
affordance accurately without claiming operability. **It must contain neither the string
`Total` nor the string `Swing Score`** — both are asserted by existing single-match
`getByText` calls, and a second match makes those calls throw.

**Declined: the arrow-key walk.** A focusable chart whose arrow keys step through points
in X order is superficially attractive and is not shipped here. At the real density it is
a 3,700-press linear scan with no way to skip, jump or search — it would let a keyboard
user reach any *particular* team only by exhausting the ones before it, which is not a
usable route to anything. Meanwhile the table is one click away, gives every team a real
table row and a real anchor, and is sortable, filterable and searchable — it is already
the genuinely usable keyboard and screen-reader route to exactly this data. Adding
`tabIndex` and key handling would also mean the element stops being honestly describable
as `role="img"`, trading a true statement for a false one. If a future need appears, the
right answer is a "jump to team" control shared with the table's search, not an arrow
walk.

**The tooltip carries `aria-hidden="true"`.** It is a transient, pointer-only duplicate of
a table row. The alternatives are both worse: announcing it needs an ARIA live region,
which at pointer-move rate is a firehose that interrupts the user continuously; leaving
it exposed and silent puts a node in the accessibility tree that appears and vanishes
under a pointer the AT user is not driving.
</accessibility_decision>

<performance_decision>
`pointermove` fires at screen rate. Four concrete rules, all of them things this is
otherwise likely to get wrong:

1. **The tone-path memo keeps its exact current dependency list, `[model, plot]`.** Hover
   state must never enter it. Building the four `d` strings is the only expensive work
   this component does; it belongs to the data and the geometry, not to the pointer.
2. **A uniform-grid spatial index, built once per `[model, plot]`, replaces a linear
   scan.** Cell size equals the hit radius, so the 3x3 neighbourhood of the pointer's cell
   is provably exhaustive. Buckets are a FLAT array indexed `row * cols + col` holding
   point indices — no string keys, no Map lookups, and therefore **zero allocation per
   pointer move**.
3. **The svg's bounding rect is cached in a ref, not measured per move.**
   `getBoundingClientRect()` immediately after a React commit that moved the highlight
   forces a synchronous layout flush — the classic layout-thrash pattern, and it would
   run at pointer rate. The ref is filled lazily on first use and invalidated (set to
   `null`, which costs nothing) by the existing resize listener and by a passive,
   capturing window `scroll` listener.
4. **State only changes when the resolved point changes.** The handler compares the new
   hit index against the current one and returns before `setState` when they match, so
   sliding the pointer across a single dot's 12px hit disc causes no re-render at all.
</performance_decision>

<test_strategy>
jsdom does no layout, so `getBoundingClientRect()` on the `<svg>` returns all zeros and a
hover test that just fires a pointer event hits nothing. Every hover/click test in Tasks 2
and 3 follows the same four steps. Write them once as helpers at the top of each test file
and reuse them.

1. **Render.** jsdom measures the container as 0, so the component falls back to
   `BUBBLE_CHART.fallbackWidth` (880) and the svg's viewBox is `0 0 880 420`.
2. **Stub the rect on the svg node**, before dispatching anything:

       const svg = container.querySelector("svg")!;
       svg.getBoundingClientRect = () =>
         ({ left: 0, top: 0, width: BUBBLE_CHART.fallbackWidth, height: BUBBLE_CHART.height,
            right: BUBBLE_CHART.fallbackWidth, bottom: BUBBLE_CHART.height, x: 0, y: 0,
            toJSON: () => ({}) }) as DOMRect;

   With `left`/`top` at zero and `width` equal to the svg's own width attribute, the
   scale factor is 1 and client coordinates ARE svg coordinates — so a test can name a
   target position directly.
3. **Derive the target coordinates from the rendered `d` attribute**, never by
   recomputing the projection in the test. Parse the first `M{cx},{cy}` out of the tone
   path for the team under test. A test that re-derived the projection would pass even if
   the component and the hit index disagreed about where the dot is, which is precisely
   the bug worth catching.
4. **Fire with real coordinates.** jsdom 30 implements `PointerEvent`, so
   `fireEvent.pointerMove(svg, { clientX, clientY })` and
   `fireEvent.click(svg, { clientX, clientY })` both carry them through.

Two further rules:

- **Scope tooltip queries to the tooltip node** — `within(screen.getByTestId("bubble-chart-tooltip"))` —
  because the card repeats the strings `Total` and `Swing Score` that the axis titles
  already render, and an unscoped `getByText` for either would throw on multiple matches.
- **The pure hit test is unit-tested in the model module, not through the DOM.** The
  component tests prove the wiring (a pointer at these coordinates produces this
  tooltip); Task 1's tests prove the search is correct. Do not try to test nearest-point
  resolution, tie-breaking or radius behaviour through rendered output.
</test_strategy>
