### The design choice that keeps the browser simple

Sigma publishes under **its own metric key**, not by overwriting `swing`. The UI therefore renders the
column and tile **exactly when `metrics.sigma` is present** — there is no algorithm-ID list anywhere in
`apps/web`. Changing which algorithms carry Sigma is a one-line pipeline change with no web change at
all.

### The fallback that was deliberately removed

Both surfaces used to fall back to the top-level `swingFactor` field when the metric entry was absent.
That is gone. `swingFactor` holds a Swing Factor — a different estimator at roughly twice the scale —
so falling back would print a Swing number under a heading that says Sigma. Two tests were **inverted**
to pin the new behaviour rather than deleted.

**Intended consequence:** between deploying this and republishing, the site shows **no consistency
column at all**. That is correct — the honest state is "no data yet", not "here is the old number".

## Two defects found by verification

1. **`buildSingleEventPublish` still fed Swing to the ranking-point filler** while `publishSeasons` fed
   Sigma, so the two paths produced different RP probabilities for the same event (0.46525 vs 0.47).
   This is precisely the second-write-path drift `sigmaScoutLayer.ts`'s header was written about, and
   `publish.test.ts`'s sidecar-parity test caught it. Fixed at `publish.ts:3474`.
2. **`sigmaFor()` mutated on read.** The belief accessor inserted an entry, so merely *pricing* a match
   recorded that team, and `scoreByTeam()` iterates exactly those keys — making results order-dependent
   between the two orchestrations. Split into `#readBelief` (returns a frozen zero belief, inserts
   nothing) and `#mutableBelief` (write paths only).
