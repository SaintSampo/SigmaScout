<objective>
Add two independent, individually-inert elimination-match mechanisms to VPR, and register their
knobs. Tuning them is explicitly a separate, later task.

**Feature 1 — elim observation-noise multiplier (affects learning).** One dimensionless
`Sigma1Params` field, default exactly `1`, that scales the measurement noise `R` of an
ELIMINATION observation everywhere `R` enters that match's score-side fold. Searchable, so the
accuracy-primary tuner can rule on it.

**Feature 2 — within-season learned elim score offset (affects displayed elim scores only).** A
league-level additive correction for elim alliance totals, learned online as an EWMA of the raw
prediction residual, applied in `predict()` for elimination matches, reset at every season
boundary. Default OFF.

Purpose: the shipped `reports/rolling-2026-09b` walk-forward backtest (offseason excluded)
measured two distinct elim defects. VPR's elim winner accuracy TRAILS its quals accuracy in 2023
(73.1% vs 75.8%) and 2024 (71.2% vs 75.0%) at n≈2800/season, while OPR gains +5 to +11 points at
elims every season — the model converts late-event information into no elim edge at all. And elim
score bias SHIFTS REGIME by season: elim-minus-qual per-alliance bias runs −3.5 (2022), −2.8
(2023), +4.2 (2024), +0.5 (2025), −15.2 (2026) points, so no fixed cross-season correction can
transfer and anything score-side must be learned WITHIN the season. Elim win-probability
calibration is already fine (ECE 0.015–0.044, no systematic overconfidence in high-confidence
bins), so no link or variance change is wanted, and foul prediction is not the source of the bias
(the foul component is within ±1 point everywhere).

Output: three new parameters, one new pure leaf module, one new state field, their wiring, their
search-space registration, their persistence, and the tests that prove each is inert at default
and live when moved.
</objective>

<decisions>
Locked design decisions. Cite the D-number in comments where the reasoning would otherwise be
invisible.

- **D-1 — one new pure leaf, `sigma1/elim.ts`.** Both features' pure functions live there,
  including a single shared `isElimination(compLevel)` predicate so the two mechanisms can never
  disagree about what an elim is (the same "one shared predicate, never a second drifting
  eligibility rule" discipline `isRpEligibleEventType` already carries). It imports ONLY
  `type Sigma1ResolvedParams` from `./scale.js` and `type CompLevel` from `../types.js` —
  type-only, so it adds no runtime import edge and cannot participate in the module-evaluation
  TDZ cycle `params.ts`'s header records. `params.ts` must NOT import it.

- **D-2 — three new `Sigma1Params` fields, all with Zod schema defaults.**
  `elimObservationNoiseMultiplier: number` (default exactly `1`),
  `elimScoreOffsetEnabled: boolean` (default `false`),
  `elimScoreOffsetEwmaAlpha: number` (default `0.05`).
  All three are DIMENSIONLESS and pass through `resolveSigma1Params` untouched. Their
  `DEFAULT_SIGMA1_PARAMS` entries are bare literals — the `adaptation*` / `rpMonteCarlo*`
  precedent for genuinely-new hyperparameters with no pre-existing constant to import.
  In `Sigma1ParamsSchema` each gets `.default(...)`, which is what lets every already-committed
  `vpr@8.0.0+*.json` file keep parsing.

- **D-3 — `SIGMA1_CODE_VERSION` is NOT bumped, and the non-bump is recorded.** Applying the file
  header's own rules rather than guessing: every recorded bump fired on one of exactly two
  triggers — (a) the parameter SHAPE changed such that `z.strictObject` makes no old file
  parseable, or (b) the observable OUTPUT changed. With D-2's schema defaults, (a) does not fire:
  all four committed files parse unchanged and acquire the inert values. And both features are
  provably inert at their defaults, so (b) does not fire. `8.0.0+tuned-2026-08` therefore still
  denotes exactly ONE computation before and after, which is precisely what D-13's invariant
  protects. `digest.test.ts` reproducing all four committed prediction-stream digests bitwise
  under the new code IS the proof — the same instrument every prior bump used, here used to
  justify not bumping.

- **D-4 — the multiplier composes into the existing seam.** `update()` computes
  `elimNoiseFactor(result.compLevel, resolved)` and MULTIPLIES it into the existing
  `measurementNoiseMultiplier`. No signature changes anywhere. `elimNoiseFactor` returns EXACTLY
  `1` for `compLevel === "qm"` — an exact IEEE-754 `1.0`, so `base * 1 === base` bitwise for every
  finite `base`, which is what lets the identity test assert byte-identical rather than "close".

- **D-5 — the innovation-based estimators stay multiplier-free, deliberately.** `varianceSample`
  and its `covarianceSample` twin estimate the TRUE per-team `R` from
  `E[innovation^2] = sum P + R_true`, which is a statement about the observed data. Inflating what
  the filter CHOOSES to believe about `R` does not change the innovation's distribution, so the
  unbiased sample is already correct and must not be rescaled. This is not a new rule: the
  pre-existing `FALLBACK_NOISE_MULTIPLIER` travels the identical seam and leaves the identical
  estimators untouched. The runaway this prevents is concrete — `measurementNoise` is the SUM of
  the teammates' own consistency estimates times the multiplier, so folding an inflated sample
  back into `consistency` would compound the multiplier geometrically across an elim bracket.

- **D-6 — the normalized innovation DOES see the multiplier, and that is correct.**
  `pooledVariance = sumP + measurementNoise` is the filter's own consistency check against its OWN
  uncertainty claim, so a filter claiming more noise should expect proportionally smaller
  normalized innovations. Self-consistent, and inert at default. One line of comment, no code.

- **D-7 — the offset is an EWMA of the RAW residual.** Fold `observed - predicted_raw`, where
  `predicted_raw` is the cross-attributed total BEFORE the offset is applied. The EWMA of the raw
  residual IS the bias estimate. Folding the OFFSET-CORRECTED residual instead would make the
  accumulator converge toward zero and the correction would silently evaporate — name this trap in
  the doc comment.

- **D-8 — one shared cross-attributed-score expression.** Extract D-04's
  `allianceOffensiveTotal(own) + (opponent[FOULS_COMMITTED_COMPONENT]?.mean ?? 0)` into a single
  named helper called by BOTH `predict()` and `update()`'s offset fold. The extraction must keep
  the same two operands, the same operator and the same order — IEEE-754 addition is not
  associative and `teamOwnComponentVarianceSum`'s doc comment records a re-association that flipped
  both committed digests once already. `digest.test.ts` is the instrument; if it goes red, the
  extraction re-associated something and gets reverted.

- **D-9 — one guard covers every skip case for the offset fold.** Fold an alliance's residual only
  when its `redUpdateTeams` / `blueUpdateTeams` list is non-empty. That single predicate already
  means "not ruling-zero AND not all-surrogate", exactly as `applyAllianceUpdate`'s own early
  return uses it — never a second eligibility rule that could drift. A fully-demo match is already
  dropped by `update()`'s first line. A `usedFallback` match DOES fold: the alliance TOTAL is
  always known even when its breakdown is not, which is the same fact `allianceScoreStats` relies
  on.

- **D-10 — both the fold AND the application are gated on `elimScoreOffsetEnabled`.** At default
  the accumulator never leaves its cold start, so the inertness claim covers the STATE and not just
  the predictions, and no extra `allianceComponentPredictions` work is done per match.

- **D-11 — the offset resets at a season boundary and at cold start**, following `swing`'s D-Y1
  argument: its input is in POINTS under one season's scoring rules, and 2024 points are not 2025
  points. State explicitly why `allianceScoreStats`'s opposite choice does not apply — a SCALE
  carries usefully because sigma moves slowly and resetting it would leave the first matches of
  every season with no scale at all, whereas a stale additive BIAS is actively wrong and a missing
  one is merely zero, which is the honest neutral.

- **D-12 — search-space partition.** `elimObservationNoiseMultiplier` is SEARCHABLE (it moves the
  Kalman gain, hence beliefs, hence predicted margins, hence `pRedWin` — fully visible to the
  objective). Both offset fields are EXCLUDED: `elimScoreOffsetEnabled` for the `adaptationEnabled`
  reason (a boolean MODE has no bound, no scale and no meaningful neighbour, so a coordinate step
  over it is undefined) AND, independently, because a symmetric offset cannot move `pRedWin` at
  all; `elimScoreOffsetEwmaAlpha` for the `swingScale` reason (the objective is structurally blind
  to a display-only quantity, so searching it would be optimising noise).

- **D-13 — KNOWN LIMITATION, carried in the code.** A symmetric league-wide offset added to BOTH
  alliances cancels in the margin, so it moves no `pRedWin`, no winner accuracy and no Brier. Be
  precise about the arithmetic: it cancels ANALYTICALLY, not bitwise — `(a+k) - (b+k)` is not
  guaranteed to equal `a-b` in IEEE-754 — so with the flag ON, `pRedWin` may differ at ULP scale
  and a flag-ON digest is not guaranteed to reproduce a flag-OFF one. At the default `k = 0` the
  cancellation IS exact, because `x + 0 === x` for every finite `x`.
</decisions>
