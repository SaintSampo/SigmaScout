## Deviations from Plan

None in content — both ORCHESTRATOR OVERRIDE/CORRECTION blocks were applied as written
(`priority: high` with the caveat kept in prose; the 65.5pt/18.8% pair recorded as two distinct
statistics rather than one derived from the other).

**One verification gate was satisfied by a different method than the plan specified.** The plan's
`<verification>` step 2 gate asserts `git status --porcelain -- packages apps pipeline data docs
scripts` is empty. It reports one hit — `apps/web/.tanstack/`, an untracked build-output
directory belonging to a concurrent session, present in this conversation's very first
`git status` snapshot before any file here was touched. The gate as written cannot distinguish
"this task was scope-clean" from "the working tree was already dirty".

Scope was therefore verified the stronger way, by the ORCHESTRATOR rather than on the executor's
report: `git show --name-only` on both commits returns exactly one path each —
`.planning/todos/pending/extend-corpus-2018-2017-2016.md`. Nothing under `packages/`, `apps/`,
`pipeline/`, `data/`, `docs/`, or `scripts/` was created, modified, or staged by this task.

**Concurrency incident — it happened, and explicit-path staging did NOT prevent it.** Another
session was editing this same checkout throughout. The executor's two task commits were clean
(the `--name-only` check above is the proof). The ORCHESTRATOR's own docs commit was not: it
absorbed `apps/web/src/styles/theme.css` and `apps/web/src/components/team/MatchTable.test.tsx`,
92 and 114 added lines of another session's in-progress work.

The mechanism is worth recording, because the standard mitigation does not cover it. Staging by
explicit path (`git add <3 paths>`) is necessary but NOT sufficient — those two files were
**already in the index**, staged by the other session before this commit ran, and `git commit`
commits the whole index regardless of what the immediately preceding `git add` named. The
`git diff --cached --name-only` check run right before the commit did surface all five paths;
the fix was to read that output rather than assume the `git add` defined the commit.

Repaired by `git reset --soft HEAD~1`, `git restore --staged` on the two foreign paths, then
re-committing the three intended files. Verified: `git hash-object` on both foreign files is
byte-identical before and after (`ddabf59d…`, `4664ad07…`), so no content was lost — they are
simply unstaged modifications again, and the other session must re-`git add` them.
