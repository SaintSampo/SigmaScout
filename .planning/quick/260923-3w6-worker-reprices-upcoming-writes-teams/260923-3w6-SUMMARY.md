# The Worker prices upcoming matches and writes team artifacts again

Jacob decided on 2026-09-23, on `260923-1tu-FINDINGS.md` items C1 and C5, to reverse the three
CPU-budget workarounds of 260915-isq (browser pricing from a `state` block), 260917-jr4 (no team
artifact writes) and 260918-16t (an ephemeral `live` block plus browser overlays). The account is on
Cloudflare Workers Paid since 2026-09-22: 30 s of CPU per cron tick instead of 10 ms. This task is
the **Worker and publisher half**; the web half is quick task **260923-3w7**.

**Net: 41 files changed, 1,504 insertions, 6,210 deletions, about 4,700 lines removed.**

**Published numbers did not change.** One extracted pure pricer is called by the Worker, the web
and the offline publisher, and the equivalence is asserted three ways: the block arm and a new
in-memory-model arm in `eventStatePricing.parity.test.ts`, and the Worker's own written rows
against `sbOfflineAt(k).upcoming` in `scheduled.rp.test.ts`.

## What changed

### 1. The pure upcoming pricer, extracted (`44c2d9d0`)

New browser-safe `packages/harness/upcomingPricing.ts`: `priceUpcomingRows` takes an in-memory
`UpcomingPricingModel` (algorithm module, state, Sigma Scores, RP accumulator, mean shift, rule
module) instead of an `EventStateBlock`. `priceUpcomingFromState` becomes the block half: validate,
deserialize, delegate. `ScheduledMatchInput` and `PriceUpcomingResult` move with the pricer and are
re-exported from `eventStatePricing.ts`, so the web's imports are untouched. The offline unseen-team
rule is now structural: the model carries `scoreByTeam()`, so nothing in the pricer's scope can
invent a prior for a never-seen team.

### 2. The Worker prices upcoming matches in Phase B (`f33b8108`)

Phase A captures the model at the same instant as `touchedMetrics`; Phase B prices every
still-upcoming match and writes the publisher's row shape into `upcoming`. `sortTime` comes off the
existing artifact and is never re-derived from TBA's `time`.

Phase A's D1 read widened from the touched teams to the touched teams plus every team on the
remaining schedule, because the offline rule gives an alliance no band and the match no RP when any
roster team has no Sigma belief. `readScopedStateChunked` chunks that read at
`MAX_SCOPE_KEYS_PER_READ` (SQLite's bound-parameter limit); the "chunked reads are deliberately not
implemented" comment argued from the retired 50-subrequest cap.

A latent divergence the widening exposed, now guarded: untouched roster teams ride in the
deserialized state and their re-serialized rows differ from D1's in key order only (the publisher
attaches Sigma passengers before RP, the tick attaches RP first). The write set is restricted to the
teams that actually folded, so `selectChangedRows` never stamps a fresh generation onto state that
never advanced. `scheduled.rp.test.ts`'s untouched-row oracle caught it and pins it.

A pricing failure logs `upcoming-pricing-failed` and rethrows into Phase B's blanket catch: the
event's artifacts lag one tick, its state stays durable. Never degraded to `upcoming: []` and never
to a schedule-only row.

### 3. The `state` block is gone (`407213c6`)

Deleted: `maintainedStateBlock`, the `blockD1Rows`/`blockReadKeys` merge parameters,
`spliceEventStateBlock`, `completeEventStateBlock`, `missingStateBlockKeys`,
`eventStatePricing.splice.test.ts`, `PerAlgorithmFold.writtenRows`, Phase B's second D1 read,
`buildEventStateBlock`'s call in `publish.ts` with its `stateRows` parameter and both `state blocks:`
log lines. `eventScheduleIsCurrent`'s gate went with it; the function and its unit test stay.
A promoted event's first tick now spends one state statement, not two, and an event published
before its schedule existed needs no operator re-baseline to price its schedule.
`mergeEventArtifact` still destructures `state` out of the existing artifact so every artifact
published before the reversal has its block dropped on the next write.

### 4. Per-team artifacts are written again (`d851dc9a`)

`readExistingTeam` returns, through `checkTeamSeasonArtifactShape`. `mergeTeamSeasonArtifact` gains
`upcomingRows`: this team's own rows filtered out of the same `priceUpcomingRows` result the event
artifact's `upcoming` comes from, so a team page and an event page cannot disagree about a scheduled
match. The write is unconditional, offseason and Week 0 included; only the `teams/{year}` feed stays
gated on `isOfficialEventType`. The bootstrap retry covers team artifacts again, so a corrupt
published team file self-heals.

`matchIndexByKey` is deleted rather than restored: the publisher fills it from the whole season's
match stream, which the Worker cannot know, and nothing reads it (array position is what
`buildMetricSeries` and the browser use). Carry-forward, documented: a roster team that played
nothing this tick gets no write, so its own unplayed rows keep their last published price.

### 5. The `live` block and the live roster are gone (`8ec12c32`)

`buildTickLiveRows`, `maintainedLiveBlock`, the `existingBodyBytes` size-trim input,
`realTouchedTeams` and `touchedSigma` leave the event merge. `writeLiveRosterObject` is deleted from
`artifactWriter.ts` and `buildLiveRoster`/`rosterGrew` from `packages/harness/liveRoster.ts`.
`mergeEventArtifact` destructures both blocks out and re-appends neither.
`scheduled.liveRows.test.ts` is renamed `scheduled.phaseBWrites.test.ts`.

### 6. Dead scripts deleted (`bc69375d`)

Ten files, about 4,250 lines: `localPricingFixture` (+ test) served a real artifact with a block for
the web pricing path; `measureReplayParity`, `replayParityMirror`, `browserFoldEntry`,
`measureEngineDeterminism`, `measureBoundedDrift` (+ 3 tests) were the browser-relay experiment
Jacob closed negative twice on 2026-09-18. `reports/replay-parity/*.json` are kept as the recorded
measurements. No `package.json` script referenced any deleted file.

### 7. Docs (`347ce6fd`)

`docs/worker-operations.md`: "Live events need no operator" loses two of three mechanisms; the
260915-isq section becomes a short historical note; the two `event-state-block-*` troubleshooting
rows become the one `upcoming-pricing-failed` row. `docs/publish-budget.md` gains the live Worker in
"Storage and write volume": about 390,000 R2 Class A writes in a peak month, of which about 218,000
is two full republishes, against the 1,000,000 that Workers Paid did not raise.

## Operator-visible changes

- No event artifact carries a `state` or `live` block; no `v1/live-roster/` object is written. Stale
  roster objects sit read-only in R2 until a prune.
- The five `event-state-block-*` and `event-live-block-*` log lines can no longer appear;
  `upcoming-pricing-failed` is the one new line.
- A promoted event needs no operator step to price its schedule.
- **A republish is owed before the next live event**, and the Worker must be deployed before it.
  Nothing breaks without one: the tick drops the stale block on its first write.
