# Does a team-age feature change the award answer?

Add **one** new feature family — team age — to the award-predictability measurement, and re-measure
both arms side by side. The deliverable is a delta table: what age buys, per award type, against the
no-age arm from 260912-5n8. Not a model, not a surface, not a shipped algorithm.

## Why

5n8 answered "can awards be predicted?" and got a real answer: judged awards land at 10–28% top-1
against a 2.5–3% random baseline, but **on the flagship judged awards the fitted model LOST to the
one-line heuristic** "pick the most decorated team in the room" (Impact 22.1 vs 24.5, Engineering
Inspiration 9.6 vs 12.1, Safety 22.8 vs 28.2). Age was considered and declined for that probe. It is
now the one feature that could plausibly move that finding, and it is the only thing this task adds.

## The trap this plan exists to not repeat

5n8's three rookie award types showed large apparent model wins — Rookie All Star (10) +18.1pp,
Highest Rookie Seed (14) +14.4pp, Rookie Inspiration (15) +12.1pp — and **all three were artifacts**.
Both baselines are *structurally* pinned at exactly 0.0% there: the most-decorated baseline cannot
pick a team with no prior wins, and the strength baseline cannot pick a team with no rating. The fit
was isolating the all-zero feature vector `[0,0,0,0]` that only a never-played, never-decorated team
can hold — an implicit age detector assembled from the **absence** of the two allowed features.
`scripts/measureAwardPredictability.ts:452-470` already documents this in an INTERPRETIVE HAZARD
block. Read it before writing a line.

**Handing the model an explicit age feature while leaving those baselines pinned at zero repeats the
identical fallacy in reverse, and manufactures a much larger fake win.** So:

> **LOAD-BEARING REQUIREMENT.** This task adds rookie-aware **baselines** in the same commit as the
> age feature, never the feature alone. RB1 "most-decorated rookie present" and RB2 "strongest rookie
> by pre-event BPR" are added alongside B1/B2, and the pre-committed verdict rule changes from
> "beats B1 and B2" to **"beats the best of B1, B2, RB1 and RB2"**. That single change is what kills
> the artifact. A plan that ships f5–f7 without RB1/RB2 has failed, whatever its numbers say.

## Grounding — verified 2026-09-12, do not re-derive

`rookie_year` is **absent from the entire corpus**. It appears in exactly two places, both prose:
`scripts/measureAwardPredictability.ts:26` (the 5n8 prohibition) and `scripts/publishDistricts.ts:42`

### T1 — `rookie_year` through the ingest (executor, offline)

**`packages/ingest/schemas.ts:18`** — add `rookie_year: z.number().int().nullish()` to
`tbaTeamSchema`. `nullish`, not required: TBA reports null for some teams, and `tbaEventSchema:44`
is the established precedent for "legitimately absent, describe TBA's real contract rather than
coerce". `tbaTeamListSchema` (`:24`) is the array of the same schema and inherits it for free, and
the comment at `:17` already states this schema serves both `GET /team/{key}` and elements of

**`packages/corpus/schema.sql`** — `rookie_year INTEGER` on `teams`, nullable.

**The migration trap — this is load-bearing, and it is this task's equivalent of 5n8's ETag trap.**
`schema.sql` is applied with `CREATE TABLE IF NOT EXISTS` (`db.ts:225`), so adding the column to the
CREATE statement does **nothing** to the existing corpus — and the widened `upsertTeam` then throws
`no such column: rookie_year` on the first write. Follow the established additive-nullable-column
exception, mirroring `MATCH_VIDEO_COLUMNS` / `hasMatchVideoColumn` / the `ALTER TABLE` block
(`db.ts:189`, `:198`, `:305-320`) **exactly**: a `TEAM_ROOKIE_YEAR_COLUMNS` one-entry list, a
`hasTeamRookieYearColumn(db)` predicate that the migration and its test both read, and an
`ALTER TABLE teams ADD COLUMN` block in `openCorpus` after the `hasWinnerImputedColumn` guard, with
the same post-ALTER re-check and named error. `rookie_year` is a **new source fact** that is honestly
NULL until refetched — precisely the case the exception at `db.ts:240-250` is scoped to, not a
derived value like `winner_imputed`. Do not generalise this into a migration framework.

**`packages/corpus/db.ts:342`** — `CorpusTeam` gains `rookieYear?: number | null`. **Optional, not
required**, and this is not a style preference: `packages/harness/publish.test.ts:1318` and `:2517`
call `upsertTeam(db, { teamKey, teamNumber, nickname })`, that file is off-limits this task (another
session is mid-edit on it), and a required field would break its typecheck with no legal way to fix
it. `upsertTeam` binds `team.rookieYear ?? null` and the `ON CONFLICT` clause sets
`rookie_year = excluded.rookie_year` by **plain assignment, never `COALESCE`** — a team TBA now
reports as null must read null, not silently retain a stale value.

**Nothing else pins the `teams` shape — checked, and the answer is in this plan because it was
asked for.** There is no `SELECT *` on `teams` anywhere in the repo. `packages/harness/publish.ts:2076`

**No existing `*-only` CLI mode refreshes `teams` — verified, so a new one is needed.** `fetchAllTeams`

### T3 — the age feature and the rookie-aware baselines (executor, offline)

Both in one commit. Extend `scripts/measureAwardPredictability.ts` and its test file; the script stays
offline, credential-free, and opens `data/corpus.sqlite` **read-only** via `openCorpusReadOnly`.

**Age is computed as of the event's season**, `eventYear - rookieYear`, clamped at `>= 0` — never as
an absolute constant, and a data error that would produce a negative age yields 0 rather than a
negative log. Three numbers, replacing `FEATURE_COUNT = 4` with 7 in the age arm:

| # | Definition |
|---|------------|
| f5 | `isRookie` — 1 if age is known and equals 0, else 0 |
| f6 | `log1p(age)` — monotone veteran-ness, compressed so a 30-year veteran does not dominate |
| f7 | `ageKnown` — 1 if `rookie_year` is non-null, else 0 |

**f7 is not decoration.** A null `rookie_year` must never be encoded as "rookie" — that is the single
most dangerous available error here and it would inflate exactly the rookie rows this task exists to
de-flatter. Unknown age is `f5=0, f6=0, f7=0`; a known rookie is `1, 0, 1`; a known one-year-old is
`0, log 2, 1`. Unknown is therefore distinguishable from every known case, which is the whole point.

**Both arms run in one pass and print side by side.** The existing 4-feature arm stays **exactly as
it is** — same features, same fit, same defaults — and the 7-feature arm is added next to it. The
per-award-type output carries both accuracies and the delta in percentage points. Do not delete or
"upgrade" the no-age arm: the delta *is* the deliverable, and a new absolute number with nothing to
subtract from answers a different question.

**RB1 — most-decorated rookie present.** Rank candidates whose age is known and equal to 0 by prior
wins of this award type, then prior wins of any type, then ascending team number. Like `pickMostDecorated`
(`:668`), **it takes no ratings argument**, so the "silently becomes a two-feature model" mistake is
unavailable at the signature level.

**RB2 — strongest rookie present.** Rank the same known-age-0 subset by pre-event BPR alone.

Both **abstain** when the pool contains no known rookie. An abstention scores as a miss for that
baseline and is **counted and printed separately** — a baseline that abstained on 90% of instances
and a baseline that guessed wrong on 90% are different facts and must not average into one number.

**The verdict rule changes, and this is the change that matters.** `isPredictable` (`:814`) becomes:
pooled model top-1 beats **`max(B1, B2, RB1, RB2)`** with pooled `n >= 30`. `verdictMarginPp` (`:834`)
takes the max over all four. A rookie award can no longer be "won" against a structural zero, because
RB1 and RB2 are not structurally zero there. Apply this to the no-age arm too, so the two arms are
scored by one rule and the comparison means something.

Also print, per award type, the **mean fraction of the candidate pool with a known age**. If that is
low the rookie baselines are weak for a data reason rather than a modelling one, and the reader has
to be able to see which.

**Leak status, stated so it is not mis-argued later.** `rookie_year` is a static historical fact
fetched today, and a team's rookie year is known before any event it ever plays, so it introduces no
look-ahead. That is an argument for why the feature is legal, **not** a licence to skip the check:
extend the existing leak test so it runs over the 7-feature vector and still asserts the feature
builder for season Y sees zero input rows with `year >= Y`.

**Noise discipline carries forward, and extends to the delta.** `NOISE_MARGIN_PP = 1` stays, margins
stay printed, sub-1pp verdicts stay tagged — raising `--iterations` from 200 to 1500 moves pooled
accuracy by at most 0.6pp, enough to flip any verdict inside that band. **An age arm that beats the
no-age arm by under 1.0pp on an award type is optimizer noise and prints as "no change", not as a
win.** The 7-feature fit keeps the same default 200 iterations and the same `--iterations` flag; no
tuning, a tuned probe answers a different question.

**Tests** (extending `scripts/measureAwardPredictability.test.ts`, synthetic fixtures, no corpus):

- Age is event-year-relative: one team, two events in different seasons, two different ages.
- Unknown `rookie_year` yields `f5=0, f6=0, f7=0` and is **not** encoded as a rookie — assert on a
  fixture where the wrong encoding flips the pick.
- A negative raw age clamps to 0 and produces no negative or `NaN` log.
- RB1 and RB2 pick only from known-age-0 candidates; both abstain on a rookie-free pool; the
  abstention is counted, not silently scored.
- RB1 never consults BPR (signature-level, same guard as B1).
- The verdict rule uses the max of all four baselines: a fixture where the model beats B1 and B2 but
  loses to RB1 is **not** predictable.
- The leak test, extended to the 7-feature vector.
- The no-age arm's numbers are unchanged by the presence of the age arm on a shared fixture.

**Pre-commit the verdict rules now, before seeing any number:**

1. An award type is **predictable** only if the model beats **all four** baselines with pooled `n >= 30`.
2. Age **helps** on an award type only if the 7-feature arm beats the 4-feature arm by **>= 1.0pp**
