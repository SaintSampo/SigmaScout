# Quick task 261018-3ju: process live events concurrently inside a Worker tick

## Why

On 2026-10-17, 13 offseason events were live at once and `runTickCore` walked them one at a
time. From `ingest_log`, tick span (`tick_at` to last `observed_at`) was median 143 s, p90 266 s,
max 530 s; TBA `post_result_time` to artifact `published_at` was median 203 s, p90 281 s. The cron
fires every minute, so ticks overlap and freshness is set by the sequential walk, not by the cron.
Wall time is the problem, not cpuTime (the Worker is on Workers Paid; never propose cpuTime work).

Target: tick span under 30 s with 10+ live events.

## What the orchestrator already established (do not re-derive)

- The four per-event walks in the tick, all `for (const eventKey of ...) { try { await ... } catch }`:
  1. `runProbes` — `apps/worker/src/scheduled.ts` ~line 1081 (`for (const eventKey of ordered)`).
  2. `runRosterPass` — ~line 1345 (`for (const eventKey of eventKeys)`). NOTE its state-generation
     mismatch branch does `return { rostersPolled, rosterTeamsAppended }` from inside the loop,
     i.e. it stops walking the remaining events.
  3. The fold loop in `runTickCore` — ~line 2507 (`for (const eventKey of orderedEventKeys)`),
     calling `processEvent`. `processEvent` catches internally and returns `{ status: "failed" }`
     (~line 1881-1887); the loop has no try/catch of its own.
  4. `runLiveEventPass` — `apps/worker/src/liveEventPass.ts` line 156
     (`for (const eventKey of sortEventKeys(...))`). The user named three loops, but this fourth
     one writes `endpoint` rows whose `observed_at` is part of the measured tick span, so it is
     in scope for the same treatment. Flag this explicitly in the SUMMARY.
- Shared state that is NOT safe under concurrency today:
  - `algorithmContext` lazy accessor (~line 2350): memoizes the RESOLVED value
    (`tickAlgorithmContext`), so two concurrent first callers both pass the `undefined` check and
    both load. Must memoize the in-flight PROMISE instead so it loads at most once.
    `scheduled.test.ts` pins one `buildAlgorithmModules` call per tick.
  - `touchedTeamsByAlgorithm` merge in `runPhaseBAndReport` (~lines 2024-2074): reads
    `seasonMap = get(compositeKey) ?? new Map()`, then awaits inside the team loop, then
    `set(compositeKey, seasonMap)` at the end. Two events sharing an algorithm+season would each
    create a fresh map and the later `set` would drop the earlier event's teams. Fix WITHOUT
    changing the "nothing lands if the loop throws" semantics: build a per-event LOCAL map inside
    the loop, then after the loop merge it synchronously into the shared map (metrics replace,
    `matchDelta` adds). The merge has no `await`, so it cannot interleave.
  - `packages/ingest/tbaClient.ts` `throttle()` (line 64-72): reads `lastRequestAt`, sleeps, then
    sets it. Concurrent callers all read the same stale value and fire together. Replace with a
    slot reservation: `const slot = Math.max(now, nextSlotAt); nextSlotAt = slot + INTERVAL;
    if (slot > now) await sleep(slot - now)`. Sequential behaviour is identical (same waits), and
    N concurrent callers are spaced exactly `THROTTLE_INTERVAL_MS` apart. Do not change the
    constant. The existing test at `packages/ingest/tbaClient.test.ts:122` stays green.
- Shared state that IS safe (synchronous or keyed per event): `SubrequestCounter.spend`,
  `TbaRequestCounter`, `matchDerivedState.set(eventKey, ...)`, `IngestLogBuffer` (every method
  filters by `eventKey`; `#rows.push` is synchronous), `live.phaseFacts` (per event key),
  `probeResult.promoted` (per event key, filled before the fold loop starts), `stamp` (read-only).
- Each event has its own compare-and-swap fold claim (`claimEventAdvance`) and its own cursor rows,
  so two events never contend on D1 rows. The schedule-only path is documented idempotent.
- Cloudflare Workers allow 6 simultaneous open outbound connections per invocation; more queue
  rather than fail. A concurrency of 6 events is the natural match. Name it
  `EVENT_CONCURRENCY = 6` in `apps/worker/src/scheduled.ts` and reuse it from `liveEventPass.ts`
  (export it, or move it next to the helper).
- `rotate`/`sortEventKeys`/`rotationOffset` logic is unchanged: the runner starts events in
  `orderedEventKeys` order; the offset still advances by `eventsAdvanced`.
- The test harness (`apps/worker/test/scheduled.test.ts`) stubs `fetch` via `makeTbaFetchStub`
  (line 345), fakes D1/R2, and `RunTickDeps.ingestClock` (scheduled.ts line 2226) is the clock the
  ingest log stamps `observed_at` from. There is already a "two concurrent live events" describe
  block at line 632.
- Tests pinning ordering: `sharedLog` (line 454-513) asserts the last D1 batch comes before the
  first R2 put for a SINGLE event — still true per event; check it still holds in the test's
  single-event setup (it should, since only one event is processed there).

## Tasks

### Task 1 — pure bounded-concurrency helper with its own test

Files: `apps/worker/src/boundedConcurrency.ts` (new), `apps/worker/test/boundedConcurrency.test.ts` (new).

- `export async function mapWithConcurrency<T, R>(items: readonly T[], limit: number, fn: (item: T, index: number) => Promise<R>): Promise<PromiseSettledResult<R>[]>`
  - Starts items in input order, never more than `limit` in flight, returns settled results in
    input order (same shape as `Promise.allSettled`). `limit < 1` throws a plain `Error`.
  - No dependencies on Workers types; pure.
- Tests: results in input order; never exceeds the limit (track in-flight max with a counter in
  `fn`); a rejection is reported as `{ status: "rejected" }` without stopping other items; an empty
  list resolves to `[]`; a slow first item does not delay a fast second item from completing
  (record completion order with real timers and small delays, e.g. 30 ms vs 0 ms).

Commit: `feat(worker): add mapWithConcurrency, a bounded-concurrency runner for per-event passes`

### Task 2 — the four per-event passes run concurrently; shared state made safe

Files: `apps/worker/src/scheduled.ts`, `apps/worker/src/liveEventPass.ts`, `packages/ingest/tbaClient.ts`, `packages/ingest/tbaClient.test.ts`.

1. `algorithmContext`: memoize the promise. Keep the counter spends and the order of work inside
   the body identical; keep the header comment but add why the promise (not the value) is cached.
2. `runProbes`: replace the loop body with a per-event async function run through
   `mapWithConcurrency(ordered, EVENT_CONCURRENCY, ...)`. Keep the try/catch INSIDE the per-event
   function so `eventsProbed`/`eventsFailed` and the `probe-failed` warn line keep their meaning.
   `promoted.set` is keyed per event and stays.
3. `runRosterPass`: same shape. Replace the mid-loop `return` on mismatch with a shared
   `let suspended = false` flag: the per-event function returns early at its start if `suspended`
   is already true (so no further event starts a poll), and on detecting the mismatch sets it,
   warns `roster-suspended` and returns. In-flight events that reach `algorithmContext()` also see
   the same mismatch and write nothing. The returned counters keep their meaning (`rostersPolled`
   counts completed polls).
4. The fold loop: run `processEvent` per event through the helper; tally
   `eventsPromoted`/`eventsPriced`/`eventsConsidered`/`eventsAdvanced`/`eventsFailed` from the
   settled results AFTER the runner returns (synchronous tallies, in `orderedEventKeys` order, so
   the result object is identical to today's). `processEvent` returns `failed` rather than
   throwing; if a settled result is `rejected` anyway, rethrow it after all events have settled
   (today a throw aborts the tick; the difference is only that other events are no longer left
   unprocessed). Say so in a comment.
5. `runPhaseBAndReport`: the local-map-then-synchronous-merge fix for `touchedTeamsByAlgorithm`
   described above.
6. `runLiveEventPass`: same runner shape, try/catch inside the per-event function, counters
   tallied the same way. Import `EVENT_CONCURRENCY`.
7. `tbaClient.ts` `throttle()`: slot reservation as described. Add a test in
   `packages/ingest/tbaClient.test.ts`: three `tbaFetch` calls started concurrently against a
   stubbed `fetch` have start times spaced at least `THROTTLE_INTERVAL_MS` apart (record
   `Date.now()` inside the fetch stub).
8. `runGlobalRebuild` and `runDistrictRefresh` still run once, after the fold runner has fully
   settled, exactly where they are now. Do not move them.

Do NOT change: fold math, artifact schemas, cron expression, `THROTTLE_INTERVAL_MS`, any counter
field name, the tick result object's shape, the probe-before-manifest ordering, or any log line's
`msg` value.
