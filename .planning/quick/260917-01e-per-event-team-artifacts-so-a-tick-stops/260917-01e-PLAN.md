## THE SHAPE DECISION — read this before Task 1

Three shapes were priced against the numbers already measured. **The task brief named (a); the
arithmetic says (c).** The difference is large enough that it must go to Jacob before a line
changes, which is why Task 1 is a blocking decision checkpoint.

### Shape A — fully per-event team artifacts plus a season rollup

| Quantity | Today | Shape A |
|---|---:|---:|
| `team` objects per publish | 101,397 | ~261,300 per-event **+** 101,397 rollups = **~362,700** |
| Total objects per publish | 108,976 | **~370,300** |
| Class-A (PUT) ops per publish | ~109,000 | **~370,000** |
| Full republishes inside the 1,000,000/month free tier | **9.2** | **2.7** |
| Publish wall time (48-way concurrency) | 34 min | **~100 min** |
| Extra R2 storage | — | ~+45 MB of repeated preamble (negligible; **Class-A is the binding constraint, not storage**) |
| Per-tick subrequests, 3 algorithms × 12 touched teams | 86 | **158** — against a usable budget of 46 (`SUBREQUEST_CAP` 50 − `SUBREQUEST_RESERVE` 4). Structurally impossible. |

The 2.577× multiplier is the brief's own measured 262,215 team-events / 101,756 team-seasons.

Shape A has a fatal internal contradiction beyond the cost. To keep the tick cheap it must write
only the per-event object and not the rollup — but the rollup is where `seasonStats`,
`metricHistory` and the event list live, so those go stale live anyway and the browser has to
derive them **regardless**. Shape A therefore pays 2.6× the Class-A budget and an extra serial
round trip on every team page (the rollup must resolve before the browser knows which event files
to fetch) to arrive at the same browser-side derivation Shape C does for free. **Recommend
against.**

### Shape B — the tick writes a small per-event delta object; the publisher keeps writing whole seasons

| Quantity | Today | Shape B |
|---|---:|---:|
| Published objects / Class-A per publish | 108,976 / ~109,000 | **unchanged** — 9.2 republishes/month preserved |
| Per-tick subrequests | 86 | **unchanged** (read + write per touched team, just a smaller object) |
| Team half of Phase B | 7.6 ± 1.8 ms | **~2.9 ms** (cost scales with bytes: 28.8 KB median season ÷ 2.577 events ≈ 11.2 KB) |
| Full-tick mean | 17.5 ms | **~12.8 ms — still over budget** |
| Team-page fetches during a live event | 2 (team + event) | 3 (team + event + delta), parallel, no added RTT depth |

Honest and survivable, and it keeps the team artifact self-sufficient from one file plus one
sibling. But it does not reach the measured floor, and it leaves the subrequest formula — and with
it the three-algorithm deferral recorded in `docs/publish-budget.md`'s "Worker runtime budget"
section — exactly where it is.

### Shape C — RECOMMENDED — the tick writes no team object at all; the browser derives the live delta from the event artifact it already fetches

| Quantity | Today | Shape C |
|---|---:|---:|
| Published objects / Class-A per publish | 108,976 / ~109,000 | **unchanged** — 9.2 republishes/month preserved |
| R2 storage | ~3.91 GB of page objects | **unchanged** |
| Per-tick subrequests (`2 + 2a + 2a(1+T)` → `2 + 4a`) | 86 at a=3, T=12 | **14, independent of team count** |
| Phase B | 11.8 ± 1.8 ms | **~4.2 ms** |
| Full tick | 17.5 mean / p50 16 / 100% over | **9.9 mean / p50 9 / 31% over — the already-measured `pbTeams0` arm** |
| Team-page fetches, live event | 2 | **2 — unchanged** |
| Team-page fetches, finished + republished season | 1 | **1 — unchanged** |
| Schema version bump | — | **none** |
| Published numbers changed | — | **none** |

Shape C is possible only because of work already shipped: since 260915-m4j the team page **already**
fetches a live event's artifact and overlays its played rows (`overlayTeamEventMatches` clause (c))
and its priced upcoming rows (clause (d)) on top of the published team artifact. The tick's twelve
team writes are, for the match rows, already redundant with a file the browser has open.

It also closes a second problem as a side effect. `docs/publish-budget.md` records that
`estimateEventSubrequestCost(3, 6) = 50` against ~41 actually-available subrequests, so a
three-algorithm event **defers every tick, forever**. Shape C's `2 + 4a = 14` is the first time that
arithmetic fits.

### What Shape C gives up, and where each is recovered

1. **The team's W-L-T record during and after a live event.** Recovered: derived in the browser from
   the overlaid played rows that the published artifact does not yet carry as played. Pure, cheap.
2. **`seasonStats.metrics` on the header tiles.** Recovered: the event artifact's `teams` rows
   already carry each touched team's current metrics (`mergeEventArtifact` writes them through
   `touchedEventTeamMetrics`), so the browser reads them from a file it already has.
3. **Intermediate `metricHistory` points during a live event.** Partly recovered: the browser
   synthesizes ONE current point per live event, at the team's latest played match, from (2). The
   points between the last publish and that one fill in at the next republish. **This is a real,
   visible, accepted degradation of a secondary tab and must be stated in the SUMMARY, not hidden.**
   It is not recovered by growing the event artifact: a full per-match history block would add
   ~76 KB to a p95-105 KB event artifact, paying on the hottest page in the app for a cold tab.
4. **The post-event, pre-republish window.** Today the tick leaves the team artifact correct after
   an event; Shape C does not, and `teamEventNeedsLivePricing`'s 7-day `eventScheduleIsCurrent` gate
   would stop the overlay covering it. Recovered by replacing the time window with an
   artifact-freshness comparison — overlay whenever the team has unplayed rows at an event whose
   last scheduled match is later than the team artifact's own `computedAt`. Self-heals at the next
   republish, exact rather than heuristic.
5. **An event the corpus did not hold at the last publish** has no entry on the team artifact at
   all, so there is nothing for the browser to overlay onto. Today the tick creates the entry (with
   `eventName: eventKey`, i.e. a raw key on screen). **Accepted, not recovered:**
   `docs/publish-budget.md` already makes "republish before and after an event weekend" the standing
   re-baseline cadence, so this is a dependency on a documented operating procedure rather than a
   new one. It must be named in the SUMMARY.

### What would make me recommend NOT doing this

- **If 31%-over is still judged unsafe.** Shape C reaches the floor of this lever and no further:
  fresh isolates still cost 40.8 ms and nothing inside the tick touches them. If the answer has to
  be "the tick fits", the remaining lever is the tick-splitting valve (option (d) in the
  260915-t7o assessment) and Shape C is a prerequisite for it, not a substitute.
- **If the team artifact must be correct from one file.** Shape C makes a live team page depend on
  the event artifact. If that coupling is unacceptable, Shape B is the answer, at ~12.8 ms instead
  of 9.9 ms.
- **If the republish cadence cannot be relied on.** Costs (3), (4) and (5) all decay gracefully but
  all assume a republish happens within weeks. Shape A makes that *worse*, not better (2.7/month),
  so this argues for B, never A.
