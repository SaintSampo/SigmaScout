<objective>
Close mechanism 5 of `docs/models/epa-statbotics-gap.md` — the foul model — by
moving EPA's foul term from INSIDE the margin to a single scalar applied to both
alliances AFTER the win probability is computed, with the rate estimated the way
`epa@9.0.0+baseline` already estimates `score_sd`: live during week 1, frozen from
week 2 on.

Purpose: this is Stage 3 of the gap doc's recommended sequence and it fixes all
nine season rows at once. It is also the stage that changes the predicted WINNER,
because today red's and blue's foul means are different numbers and therefore move
SigmaScout's margin, which is the inverse of what Statbotics does. Building the
no-foul week-1 accumulator the rate needs also closes R3 residual gap 1 — the
carry anchor stops reading a named neighbour of `get_constants`'s quantity and
starts reading the quantity itself.

Output: an `epa@10.0.0+baseline` whose fouls cannot touch a win probability, a
frozen week-1 foul rate and no-foul mean, `STATE_SNAPSHOT_SHAPE_VERSION` 14, two
updated register entries, and an honestly-reported before/after measurement
against `epa@9.0.0+baseline`.

THE GOAL IS REPRODUCTION FIDELITY, NOT ACCURACY. A winner-accuracy or Brier
regression is an expected and acceptable outcome of this task. Report it; do not
reach for a knob.

<decided_design>
Five questions this plan DECIDES so no task re-litigates them mid-run. Each carries
its reason. If evidence found during execution contradicts one, stop and report —
do not quietly pick the other branch.

**D-1 — `foulsCommitted` KEEPS being rated per team. Only its place in the
prediction changes.** The brief asks for the smaller change where both reach the
same predicted numbers, and they do: `predictCore`'s `redOffensiveTotal` already
excludes an alliance's OWN `foulsCommitted`, so it already IS the no-foul total
Statbotics scales. Dropping the cross-attribution term therefore reaches exactly
the same predicted score as deleting the component would, while leaving four
things untouched that deleting it would disturb:

  - the published per-team `foulsCommitted` metric entry (`teamMetrics`) — a
    published metric disappearing is a user-visible change needing its own
    justification, and it has none here;
  - `breakdown/groups.ts`'s `UNGROUPED_COMPONENTS`;
  - `carrySeason`'s fouls-INCLUSIVE carryover input, pinned by a dedicated test in
    `epa.test.ts`. Changing it would move every carried rating — a second,
    unmeasured change smuggled into this one's measurement;
  - `fallbackObserved`'s cross-alliance netting in `update`, which converts a raw
    alliance score into an imputed OFFENSIVE observation. That is a fact about the
    OBSERVATION, not about where the prediction puts fouls, so it stays correct and
    stays untouched. If `epa.test.ts`'s CR-01 fallback test goes red, the wiring is
    wrong — do not edit its expectation.

The remaining divergence — Statbotics rates no foul entry per team at all — is
already recorded as part of mechanism 1 ("plus `foulsCommitted`" in every season
row) and stays there. Say so in the gap doc rather than closing it silently.

**D-2 — the no-foul / foul split is taken from the SCORE, not from the component
sum.** Per reference §2, `foul_points = foulPoints + adjustPoints` and
`no_foul_points = score - foul_points`. So, per alliance, using values this repo
already parses and with NO new breakdown field and NO season-map edit:

  - red's foul side  = `blueParsed[FOULS_COMMITTED_COMPONENT] + redParsed[ADJUST_COMPONENT]`
  - red's no-foul    = `result.redScore - (that foul side)`
  - and symmetrically for blue.

The cross-side lookup is correct and is the easiest thing in this file to get
backwards: `breakdown/{year}.ts` sets `result[FOULS_COMMITTED_COMPONENT] =
opponent.foulPoints`, so RED's parsed `foulsCommitted` holds BLUE's received
points, and the points RED received are therefore in BLUE's parsed slot. Verify
this against `packages/core/algorithms/breakdown/2024.ts` (the `foulPoints` Zod
field comment and the `parse()` assignment) before writing the fold, and pin the
direction with a test.

Deriving no-foul by summing own offensive components instead was CONSIDERED and
REJECTED: a season whose component map does not span the whole score would shift
the aggregate silently, and Statbotics' own definition is score-based.

Taking the complement of no-foul as the foul side makes
`noFoulMean + foulMean == scoreMean` hold by construction, so
`(1 + foulRate) * noFoulMean == scoreMean` exactly — the rate is precisely the
inflation from a no-foul total to a real score.

NAMED UNCERTAINTY, to be written down rather than hidden: the module that writes
`Match.red_foul` / `red_no_foul` was never fetched, so whether upstream's
`red_foul` includes `adjustPoints` is an inference from §2's shared cleaner rather
than a transcription. §2 is the citation; record the inference in the gap doc as a
residual.

**D-3 — two populations, mirroring `epa@9.0.0+baseline` exactly.** The frozen value
comes from a WEEK-1-only accumulator pair inside `EpaWeekOneState`. The pre-seal
LIVE value comes from a SEASON-WIDE expanding accumulator pair on `EpaState`,
exactly as `predict`'s SD denominator uses season-wide `allianceScoreStats` before
the seal and the frozen week-1 SD after it. Using the week-1 accumulator as its own
live estimate was CONSIDERED and REJECTED: null-week preseason play happens BEFORE
week 1 in every season (2024's null-week events start 2024-02-03, week-1 events
2024-02-24), and those matches would then all be predicted with a zero foul rate.

Both accumulators fold ONE alliance observation at a time and both apply the SAME
exclusions `allianceScoreStats` already applies:

  - a ruling-zero alliance (`redIsRulingZero` / `blueIsRulingZero`) is never
    folded. This is not tidiness: the `2026bc2_sf14m1` shape is `adjustPoints:
    -456` against a 0 score, and folding it would put a ~456-point garbage no-foul
    observation into a constant every later prediction divides by;
  - an alliance whose breakdown did not PARSE is never folded, because the fallback
    path imputes its components from the very foul means this accumulator feeds —
    folding an imputed value would be circular. State it in the code.

**D-4 — both version bumps are required.**
`epa.version` 9.0.0 -> `10.0.0+baseline`: MAJOR, because every predicted winner can
change. `STATE_SNAPSHOT_SHAPE_VERSION` 13 -> 14 is load-bearing for exactly the
reason the 12 -> 13 block already writes down — `apps/worker/src/stateStore.ts`'s
`readScopedState` filters rows by `algorithm_id` only and never by version, so
bumping `epa.version` alone leaves a stale row reachable. A shape-13 league row
would deserialize with the foul accumulators absent, leaving the live Worker on a
permanently-zero foul rate while the offline publisher used the frozen one — the
two disagreeing on every published predicted score with no error, no NaN and no
malformed row to find.

**D-5 — refuse, never fudge, a degenerate rate.** `EPA_FALLBACK_FOUL_RATE = 0`
applies when fewer than `EPA_WEEK_ONE_MIN_FOUL_OBS = 1` observation exists, or the
no-foul mean is not finite and strictly positive, or the resulting rate is not
finite and non-negative. 1 is a mean's own contract boundary (a mean is defined at
one observation) exactly as `EPA_WEEK_ONE_MIN_OBS = 2` is `standardDeviation`'s —
neither is a searched or tuned threshold, and nothing here may be chosen by looking
at an accuracy number. Upstream's own guard is `(self.no_foul_mean or 1)`; this
project refuses the divide instead of substituting a denominator, which is the
`sealWeekOneIfPast` precedent.
