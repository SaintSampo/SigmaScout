<facts_established_during_planning>

Read these before starting. They are load-bearing and were confirmed against HEAD, not assumed.

1. **Write-side validation already runs on every put.** `artifactWriter.ts:85` calls
   `schema.parse(artifact)` before `JSON.stringify` and before `budget.tryConsume`, for every page
   kind, on both the live Worker and (per its header) the offline `r2Client.ts`. So *every object in
   R2 was schema-validated by whichever writer wrote it.* The read-side parse in
   `scheduled.ts:391`/`:401` is therefore a **second** validation of an already-validated object,
   and moving validation "to the write" costs nothing new — it is already paid. Do not price it as
   an addition.

2. **The event `state` block already degrades safely without the read-side parse.**
   `EventArtifactSchema.state` is `EventStateBlockSchema.optional().catch(undefined)` on BOTH sides.
   A malformed block that reaches `spliceEventStateBlock` throws `EventStateBlockError`, which
   `maintainedStateBlock` (`artifactMerge.ts:224`) already catches and logs. A malformed block that
   survives the splice is `.catch`-ed to `undefined` at write. Either way the artifact still
   publishes, minus its block — the same outcome today's read-side parse produces.

3. **The team write schema has no `.catch`.** A malformed merged team artifact throws in
   `writeArtifactObject`, and `runPhaseBAndReport`'s blanket `catch {}` swallows it — so that team
   would stop publishing *permanently*, where today the read-side parse degrades it to a bootstrap.
   This is the one protection that genuinely needs recovering, and it is what the bootstrap-retry in
   Task 3 exists for.

4. **`LiveEventArtifactSchema.upcoming` is `z.union([EventUpcomingMatchSchema,
   EventScheduledMatchSchema])` (`pageArtifacts.ts:1598`) and the two options are mutually
   exclusive.** `EventScheduledMatchSchema` is the file's one `z.strictObject`, so a priced row
   fails it on unrecognized keys; `EventUpcomingMatchSchema` requires `predictedWinner`, `pRedWin`,
   `predictedRedScore` and `predictedBlueScore`, so a schedule-only row fails it on four missing
   keys. **Exactly one option can ever match any row**, so union ORDER cannot change the parse
   result — only its cost. Today's order makes every schedule-only row fail an 8-refine, ~24-field
   schema first. **The Worker reads its own writes**, which are schedule-only since 260915-isq, so
   the live read path pays that failure on every upcoming row on every tick after the first. The
   probe's published test artifact has *priced* upcoming rows, so the 2026-09-15 measurement
   under-prices this; that is what `phaseBUpcoming=scheduled` exists to fix.

5. **The live tier is `spr` only** (`DEFAULT_LIVE_ALGORITHM_IDS`, `scheduled.ts:190`), so the per-tick
   team-artifact count is 12, not 36. The probe's `phaseBTeams` default already mirrors this.

6. **`phaseBTeams=0` does not currently zero the team half.** `runSprPhaseB` parses the fetched team
   artifact once *before* the loop and initializes `teamParsesRun` to 1 (`stateProbe.ts:1322`,
   `:1327`). At `phaseBTeams=12` the total is unchanged by moving that parse inside the loop
   (1 + 11 = 12); only the zero case changes, from 1 to 0. Task 1 must make that move so the
   team-half root arm is honest.

7. **Subrequest accounting is unaffected by every change in this plan.** `writeArtifactObject`
   validates *before* `budget.tryConsume(1)`, so a validation failure and a bootstrap retry consume
   the same single subrequest. `estimateEventSubrequestCost` is untouched, and
   `scheduled.rp.test.ts:697` must still read 64.

</facts_established_during_planning>
