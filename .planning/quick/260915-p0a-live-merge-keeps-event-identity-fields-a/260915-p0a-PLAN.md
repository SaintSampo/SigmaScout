<decisions>
DD-1 Spread-then-override, not an allow-list (task item 1).
- `existing` has been through `LiveEventArtifactSchema.parse`, which strips unknown keys, so spreading it carries exactly the schema-known keys.
- A key the publisher adds later survives a tick automatically. An allow-list is how this bug happened: `name`/`startDate`/`location`/`week`/`alliances` were added to the schema after the merge was written, and the merge silently dropped them.
- The keys the tick owns are listed explicitly after the spread. When an owned key is overridden, it keeps its original position.
- An owned key the tick may decide to omit must be destructured out of `existing` before the spread. Otherwise a stale value would survive. Today that is only `state`, which `maintainedStateBlock` drops for non-SPR artifacts and for events with no upcoming match; destructuring it out also re-appends it last, where the schema wants the large block.
- `rpOutcomeRp` and `eventType` already fall back to `existing`, so carrying them through the spread is correct.
- Trade-off: a future key that really should be tick-owned is carried stale until someone adds it to the owned list. That is the project's documented carry-forward policy (the Sigma entry, teams-row tiers, the teams-row record), so it is the right default.

DD-2 Touched standings rows keep their published rank/record/rp (task item 2).
- These are TBA's official standings. The Worker neither fetches `/event/{key}/rankings` nor recomputes them.
- They are preserved as last published, so they are stale until the next republish. Recommendation: preserve. Stale-but-true TBA values beat a standings table whose columns vanish mid-event. This matches how the Sigma entry is carried forward and how `runGlobalRebuild` keeps the teams-row `record`.
- Rows are replaced IN PLACE, so standings order no longer moves touched teams to the end. A touched team with no prior row is appended with the existing bootstrap shape (teamKey, `fallbackTeamNumber`, nickname `""`, metrics).

DD-3 Team-season `seasonStats` (task item 3).
- Write `{ ...existing?.seasonStats, record, metrics, metricsBasis }`.
- The tick owns `metrics`, so it owns the label describing them. `metricsBasis` is `"last-official-match"` when every folded match is official (per `isOfficialEventType`, where `-1` counts as official, the same gate as `incrementRecord`) and `"season-final"` otherwise.
- Blindly carrying the published `"last-official-match"` through an offseason tick would mislabel the unscoped value that `live-merges-drop-percentiles` already records. That scoping defect and the missing percentiles stay OPEN and are not claimed.
- The top level and the per-event objects already spread (`{ ...existing }`, `{ ...e, matches }`), so this task only pins them.
- The new-event entry for a team's first match at an event with no entry (eventName = event key, startDate = tick date, no rank/totalTeams) is a bootstrap path and stays unchanged.

DD-4 Played-row parity (task item 4): IN SCOPE. Per-field assessment:
- `actualRedRp`/`actualBlueRp`: PRODUCIBLE. `MatchResult.redRpEarned`/`blueRpEarned` are already threaded by `toMatchResult` from the polled match's `score_breakdown.{color}.rp`. Apply the same `toIntegerRpOrNull` policy.
- `redScoreVarianceOwn`/`blueScoreVarianceOwn`: PRODUCIBLE. They are on the `predict()` output already in `newPredictions`.
- `actualRedBonusRp`/`actualBlueBonusRp`: PRODUCIBLE.
  - Inputs: `MatchResult.scoreBreakdownRaw` and `RP_RULE_MODULES[season]`, both already in the Worker bundle.
  - Cost: one breakdown parse per newly-folded match per tick, in Phase B, algorithm-independent. It is computed once, not per algorithm. Offline flags are algorithm-independent too, so OPR/EPA rows carry them.
  - Degrade: when the event-detail fetch fails, `eventType` is `-1` (RP-ineligible), so the flags publish `null`, meaning "not derivable". That is honest and heals at republish.
- `video`: PRODUCIBLE. `CorpusMatch.videoKey` comes from the same polled match list.
  - Caveat: TBA usually attaches videos after a match, and a played row is folded once, so most live rows will have no `video` until republish. Absence is the schema's single "no video" state.
- `sortTime` (played): PRODUCIBLE when TBA reports a time. The corpus `sort_time` the publisher reads is `normalizeMatch`'s chain (actual, then predicted, then scheduled, times 1000), and the Worker sees the same TBA match.
  - When TBA reports no time, the Worker must not publish its window-start approximation (the 260915-isq rule). The row takes that artifact's own prior row's published `sortTime` for the match, otherwise no key. This case is pinned by a test, not by value parity.
- Team-season played rows are also missing `setNumber`, `matchNumber` and `redBonusRp`/`blueBonusRp` (predicted marginals) today, which the audit did not list. They are fixed by construction through the shared `teamSeasonMatchRow`.
- `coldStart`: NOT PRODUCIBLE. Offline comes from `corpusColdStartIndex`, a corpus-global first-appearance index; the Worker has no corpus. D1 team-row presence is an unproven proxy, and publishing it under a name that asserts corpus-global provenance would be a false attribution. It becomes an explicit exception in the parity test, and live rows must not carry the key.
- Upcoming rows stay schedule-only by design (260915-isq) and are out of scope.

DD-5 Parity by construction.
- The played-row builders move from `publish.ts` into `packages/harness/publishedRows.ts`, which is browser- and Worker-safe and already in the Worker graph through `eventStatePricing.ts`. The publisher and the Worker then call the same code, and the parity test pins what the lookups feed in.
- The Worker's hand-built `buildEventMatchRow`/`buildTeamSeasonMatchRow`/`liveBonusRpFields`/local `matchBandFields` are deleted, along with the false "byte-identical" comments.
