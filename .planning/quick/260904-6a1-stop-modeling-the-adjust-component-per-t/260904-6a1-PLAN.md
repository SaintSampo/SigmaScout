**What happened there.** The red alliance (frc190/frc3467/frc237) genuinely scored ~456 points. A

**Corpus measurement** (`data/corpus.sqlite`, measured in the orchestrating session — treat these

- 306 alliance-sides carry breakdown `adjustPoints <= -30`.
- 211 of those are score-zeroed rulings.
- 207 of the 211 carry full DQ flags and are **already** dropped by `dq.ts` today.
- Exactly **4** slip through as zeroed-via-adjust with empty DQ lists:
  `2022mibro_qf1m1` (offseason), `2024isde4_sf5m1` (official), `2026bc2_sf14m1`, `2026bc2_sf18m1`
  (both offseason).

So the new predicate overlaps the DQ predicate heavily by construction; the **union** is what
matters, and the marginal new population at the `<= -30` threshold is those 4 alliance-sides.

<design_notes>

Read this before starting Task 1. It records decisions already made, so the executor does not
re-litigate them mid-task.

## D-1 — the new predicate reads the PARSED breakdown only

`isFullyDqZeroScoreAlliance` needs only `(teams, dqs, score)` — all three are on `MatchResult`. The
new predicate additionally needs the alliance's `adjustPoints`, which lives in the parsed component
vector. Two vectors are in scope at the call sites and they are **not** interchangeable:

- `redParsed` / `blueParsed` — the real breakdown, `null` when `tryParseBreakdownPair` returned
  `absent` or `malformed`.
- `redObserved` / `blueObserved` — `redParsed` **or**, when that is `null`, the D-05
  fallback-imputed vector from `distributeResidual`.

The predicate must read the **parsed** vector. Feeding it the fallback vector would let an
*imputed* adjust value (a number this project invented, not one TBA reported) drop a real
observation. A match with no parsed breakdown therefore cannot trigger the predicate at all —
adjust is unknown, and unknown is not negative.

## D-2 — predicate signature

Sibling shape to `isFullyDqZeroScoreAlliance`, taking the adjust value rather than a whole vector so
`dq.ts` stays free of any breakdown-package import:

```
isAdjustZeroedAlliance(
  teams: readonly string[],
  allianceScore: number,
  parsedAdjustPoints: number | undefined
): boolean
```

True only when `teams.length > 0` **and** `allianceScore === 0` **and** `parsedAdjustPoints` is a
number **and** it is `< 0`. Empty `teams` returns `false` for exactly the reason the sibling
documents (that case is already a no-op at every call site). `undefined` returns `false` — that is
the no-parsed-breakdown case from D-1.

## D-3 — combined at the call sites, never merged into one predicate

Both algorithms already compute `redIsDqZero` / `blueIsDqZero` and use them at **two** seams: the
per-alliance component update, and the `allianceScoreStats` fold. Keep the two predicates separate
in `dq.ts` (each stays independently testable and independently documented) and combine them at the
call site into one `redIsRulingZero` / `blueIsRulingZero` boolean that drives **both** seams. A
ruling-zero is not an observed alliance score whichever way the scorekeeper encoded it, so the
expanding-window SD must skip it in both cases.

## D-4 — Sigma1 ordering constraint

In `sigma1/index.ts`'s `update()`, `redIsDqZero`/`blueIsDqZero`/`redUpdateTeams`/`blueUpdateTeams`
are currently computed **above** `tryParseBreakdownPair`. The new predicate needs the parse result,
so the `redUpdateTeams`/`blueUpdateTeams` derivation must move **below** the parse block. Their
first consumer is `applyAllianceUpdate`, well below the parse, so this move is safe — verify by
reading, not by assuming.

EPA already computes the DQ booleans after the parse; no reordering needed there.

## D-5 — how `adjust` gets pinned at 0 (Change 2)

`ADJUST_COMPONENT` **stays** in the breakdown parse and stays registered in every season's
component list. The reconciliation invariant (`breakdown/reconciliation.test.ts`) needs the parse to
account for it, and keeping the component registered keeps the published artifact shape stable —
`apps/web/src/lib/metricGroups.ts` already documents `adjust` as an ungrouped component. It is
pinned at exactly `0`, not removed.

Follow the established `FOULS_COMMITTED_COMPONENT` precedent: one named component treated
differently at specific, individually-commented seams, never a general "special component" mechanism.

**EPA seams:**
1. `applyComponentUpdate` — for `ADJUST_COMPONENT`, write `0` into the team's record and skip the
   two-stage EWMA entirely. Skip it in the `predictedAllianceTotals` pre-pass too.
2. The cold-start divisor (`componentColdStartValue`'s `componentCount` argument) — see D-6.
3. `nonFoulsComponents` (the D-05 fallback residual split) must also exclude `ADJUST_COMPONENT`, so
   the imputed observation is distributed only across components that actually get modeled. A share
   routed to a pinned component would simply vanish and the imputed total would no longer reconcile.
4. `carrySeason` spreads a carried total across `toSeasonComponents` — exclude `ADJUST_COMPONENT`
   from that divisor and set the carried `adjust` entry to `0`. Without this, every team's adjust
   estimate becomes nonzero again at every season boundary.

**Sigma1 seams:**
1. `applyAllianceUpdate`'s per-component Kalman loop over `componentOrder` — return early for
   `ADJUST_COMPONENT`, leaving its belief, its zero-initialized residual slot, its innovation slot
   and its variance-sample slot untouched.
2. The post-loop per-component folds in the same function (the consistency fold and the swing fold
   that iterate `componentOrder` again) — skip `ADJUST_COMPONENT` in each, so its consistency and
   swing entries stay exactly as seeded rather than being EWMA'd toward a manufactured zero sample.
3. `coldStartTeamState` — seed `adjust` at `{ mean: 0, variance: 0 }` and consistency `0`, bypassing
   `leagueMeanFor` and `seedConsistencyFor`. The floor `seedConsistencyFor` applies exists to keep a
   brand-new team's Kalman gain nonzero on its first observation; a component that is never folded
   has no gain to protect, so the floor does not apply and a raw `0` is the honest value.
4. `applyTeamProcessNoise` — do **not** apply process noise to `adjust`. Its mean never moves, so
   growing its variance every match would inflate `allianceComponentVarianceSum`, and through that
   `predict()`'s reported variance and the published `±`, for a quantity that carries no
   uncertainty at all.
5. `nonFoulsComponents` in `update()` — same fallback-split reasoning as EPA seam 3.
6. `carrySeason` — same reasoning as EPA seam 4: exclude `adjust` from the share divisor and set its
   carried belief to `{ mean: 0, variance: 0 }` with consistency `0`.

Note that Sigma1's update loop iterates `componentOrder`, not `Object.keys(observed)`, so the extra
`adjust` key riding along in `observed` is inert there. EPA's loop iterates the observed vector, so
EPA needs the explicit skip. `assertFiniteComponents` keeps checking `adjust` in both — that
invariant is unchanged.

## D-6 — cold-start divisor decision (LOCKED)

**`adjust` is EXCLUDED from the cold-start component divisor in both algorithms.**

EPA spreads `EPA_INIT_COMPONENT_TOTAL` evenly across the season's registered component count;
Sigma1 spreads `params.coldStartTeamTotal` the same way. Leaving `adjust` in the divisor while never
seeding it would silently shrink every rookie's seeded total to `TOTAL * (C-1)/C` — a real, unasked-
for change to the cold start hiding inside an unrelated fix. Excluding it from the divisor keeps a
cold-start team's summed belief exactly `EPA_INIT_COMPONENT_TOTAL` / `coldStartTeamTotal`, which is
what those constants are documented to mean.

The same divisor rule applies at the season boundary in both `carrySeason` implementations, so a
carried total is preserved rather than partially routed into a pinned component.

Consistency requirement inside EPA's `applyComponentUpdate`: the `?? coldStart` fallback in the
`predictedAllianceTotals` pre-pass and the one in the per-team loop must remain
character-for-character the same expression, exactly as the existing comment there demands. Compute
the modeled component count **once** per `update()` / `carrySeason()` call and thread it through the
existing `componentCount` parameter — this should be a change of *value*, not a new parameter.

## D-7 — version identity and the digest gate

Both changes alter `update()`'s observable output for every match, so both algorithms need a MAJOR
version bump under D-13's "no version string may stand for two different computations" rule:
`epa.ts` `2.0.0+baseline` -> `3.0.0+baseline`, `SIGMA1_CODE_VERSION` (`sigma1/params.ts`)
`7.0.0` -> `8.0.0`.

`packages/harness/digest.test.ts` re-runs **every** committed `data/algorithm-versions/*.json` file
on its own recorded slice, rebuilding the algorithm from **current** code, and asserts the recorded
prediction-stream SHA and headline metrics bitwise. This change moves those digests. Three files are
committed today, all at `vpr@7.0.0`: `+rolling-2026-09` (a `paramSetsBySeason` file covering
2019/2020/2022-2026), `+tracer-check` and `+tuned-2026-08` (both flat `params` files). All three
must be re-promoted by the final code and the stale `7.0.0` files removed.

Hand-editing, regenerating-to-match, or deleting-without-replacing a committed digest is prohibited
(the standing rule from quick task 260901-is2). A digest is only meaningful if the code that
produced it is the code that ships, which is why re-promotion is the LAST task, after both model
changes are final.

`promote.ts`'s `codeVersion` param-shape dispatch currently routes `=== SIGMA1_CODE_VERSION` to the
current schema and has explicit branches for `6.`/`5.`, `4.` and `3.`, throwing for anything else.
Once the constant is `8.0.0`, a `7.0.0` source file falls off the end of that chain. No parameter
changed in this task, so `7.x` shares the current shape: add `7.` to the first branch, do not
invent a migration.

## D-8 — deliberately out of scope

This changes model identity. The baseline fingerprint (`data/baselines/`), the published R2
artifacts, `scripts/epaVsStatbotics.ts --check` against
`data/baselines/epa-vs-statbotics-2026-09.json`, and `docs/models/epa-vs-statbotics.md` all describe
a model that this change supersedes. Re-measuring and republishing is a separate job with its own
cost, and it interacts with the pending re-tune
(`.planning/todos/pending/retune-sigma1-rolling-origin.md`). Task 3 **records** that follow-up; it
does not perform it.
