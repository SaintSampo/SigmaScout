# Quick Task 260904-586: Teams List Shows Only Latest Official Play — Summary

The Teams-list metric snapshot is now scoped to official play end-to-end — offline publisher, live
Worker, and browser team-page header all read one shared `isOfficialEventType` predicate — and a
full 2022-2026 republish shipping the fix has been independently verified against the corpus.

## What Was Built

### Task 1 — one shared official-play predicate, wired through the offline publisher

`packages/core/algorithms/eventTypes.ts` (new) exports `OFFSEASON_EVENT_TYPE = 99`,
`PRESEASON_EVENT_TYPE = 100`, and `isOfficialEventType(eventType)` — true for everything except
those two constants, and true for an unknown/sentinel type (including `-1`) so a failed lookup
degrades toward keeping data fresh rather than freezing it. It imports nothing, satisfying
`packages/core/isomorphic.test.ts`'s forbidden-import fitness test.

`packages/harness/publish.ts` gained a new exported `lastOfficialMetricsByTeam(metricHistoryByTeam,
officialEventKeys)`: walks each team's chronological per-match metric-history rows and keeps the
metrics from the LAST row whose event is official, omitting a team entirely when it has none. Wired
into the per-algorithm loop right after `metricHistoryForAlgo` is bound, widened with the SAME
`withPercentiles(..., teamsThisSeason)` call the season-final snapshot already used (unchanged pool,
narrows itself by skipping absent teams), and repointed the `teamsRows` map's `metrics` field at
that widened record. Every other consumer of the season-final `metricsByTeamWithPercentiles` —
`seasonStats`, `metricHistory`, per-event sections — is untouched.

`apps/web/src/lib/officialSnapshot.ts`'s private `isOfficialEvent` now delegates its `eventType`
check to the shared predicate while keeping its pre-existing `!row.isOffseason` conjunct, so a
published events artifact whose two fields ever disagree still resolves the conservative way and
current behaviour is preserved bit-for-bit.

Twelve new tests: 3 in `eventTypes.test.ts` (isOfficialEventType boundaries), 4 direct unit tests for
`lastOfficialMetricsByTeam`, and an end-to-end `publishSeasons` pair against a synthetic temp-dir
corpus proving (a) an official-then-offseason team's teams-row metric equals its official-event
value while its team artifact still carries the offseason event and its history rows, and (b) an
offseason-only team keeps its teams-list row with empty metrics.

### Task 2 — the live Worker stops folding offseason metrics into the season leaderboard

`runPhaseBAndReport` now takes the TBA-resolved `eventType` (including its `-1` degradation
sentinel) as an explicit parameter from `processEvent`, rather than re-deriving it from
`newlyFoldedResults[0]` (which can be empty). Inside the function, ONLY the
`touchedTeamsByAlgorithm` contribution — the feed `runGlobalRebuild` folds into `teams/{year}` — is
gated on `isOfficialEventType(eventType)`. `mergeEventArtifact`'s `event/{eventKey}` write and
`mergeTeamSeasonArtifact`'s `team/{teamKey}/{year}` write both stay unconditional, so an offseason
or preseason event is still fully visible on its own event page and every participating team's page
— it only stops moving the season leaderboard. The module header's GLOBAL REBUILD documentation was
extended to record this new scope boundary.

Five new `scheduled.test.ts` cases cover event_type 99, event_type 100, event_type 0 (still
contributes, byte-equivalent), the `-1` unknown-type sentinel (still contributes — treated as
official), and that D1 state/cursor still advance for an offseason event so the same matches are
never re-folded.

## Issues Encountered

**The republish's background process appeared to die mid-run, but had not.** Partway through the
run (after replaying season 2025, before season 2026 had logged), this executor's own tracking of
the backgrounded task reported it as killed. A live check of the shipped artifacts showed teams/2022
through teams/2025 already on a NEW generation while teams/2026 was still on the OLD one — a
genuinely inconsistent, partial-publish state if left as-is. Rather than restart (which would
duplicate 2022-2024's already-successful work and risk a concurrent-writer conflict) or patch only
season 2026 (which would incorrectly cold-start it, since `publishSeasons` only bridges
season-to-season carried algorithm state within one call — no mechanism exists to resume with
carried-forward state across separate invocations), a direct process-list check
(`Get-CimInstance`) showed the underlying `node`/`tsx` process tree was in fact still alive and
executing — only this executor's own tracking had lost the connection. The run was left alone,
observed to completion, and confirmed as one single, internally consistent publish: every sampled
key across all five seasons reports the identical `generation`/`computedAt` pair, and
`pnpm verify:subset`'s generation-uniformity check confirms one distinct value.

**WINDOWS.md ledger append failed on a pre-existing CRLF parsing issue, unrelated to this task.**
`gsd-tools windows append` threw `Ledger frontmatter line is not key: value:
"last_updated: 2026-08-29T00:00:00.000Z\r"` — a trailing `\r` in the committed file's frontmatter
that the parser does not tolerate. Per the workflow's own guidance, ledger population is
best-effort and does not block execution; the `team/{teamKey}/{year}` budget overage finding is
recorded in `docs/publish-budget.md` itself (both its prose and its machine-readable block) but was
NOT additionally mirrored into `.planning/WINDOWS.md`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `scheduled.test.ts`'s shared TBA-detail fixture was missing the schema-required `name` field**
- **Found during:** Task 2, while writing the new event_type-gating test cases
- **Issue:** `makeTbaFetchStub`'s detail-endpoint branch built a response object without `name`,
  which `tbaEventSchema` requires — every test in the file that resolved `eventType` through this
  fixture silently threw inside `processEvent`'s swallowed try/catch, degrading `eventType` to the
  `-1` sentinel regardless of the fixture's configured `event_type`. Invisible before this task
  because every pre-existing test used `event_type: 0`, and `isOfficialEventType(-1)` and
  `isOfficialEventType(0)` both resolve to "official" — the same outcome either way. This task's new
  99/100 gating tests needed a GENUINE non-official `event_type` to reach the parse, which is what
  surfaced the defect.
- **Fix:** Added `name: eventKey` to the fixture's detail response.
- **Files modified:** `apps/worker/test/scheduled.test.ts`
- **Verification:** All 28 tests in `scheduled.test.ts` + `liveAlgorithmTier.test.ts` pass; the new
  99/100 cases now genuinely exercise a resolved `eventType` of 99/100, not `-1`.
- **Committed in:** `dfed6a47` (Task 2 commit)
