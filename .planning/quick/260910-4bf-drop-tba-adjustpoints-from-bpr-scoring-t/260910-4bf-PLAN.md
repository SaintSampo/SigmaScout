<objective>
Remove TBA's `adjustPoints` — a manual scorekeeper correction — from BPR's scoring
target, in both the offline research model and the shipped live port, keeping the two
behaviourally identical.

Purpose: a Kalman filter currently takes a scorekeeper's correction at full weight as
though a robot scored it. Mean |adjust| is only ~0.15 points/match, but single
corrections reach 150+. Scorekeeper corrections are not robot performance.

Output: `redOut`/`blueOut` computed as `score - foulPoints - adjustPoints` in both
modules; a cross-module identity test; corrected provenance comments on both sealed
files.

## Extraction route: shallow raw-field read, in BOTH modules

The task brief points at `ADJUST_COMPONENT` / `tryParseBreakdownPair`, which is what the
experiment used (`experiments/phase-bpr/data.ts:92-100`). **The shipped port cannot use
that route**, for two reasons verified against HEAD:

1. **`state.season` is `null` for the whole first replayed season.** `initState` sets
   `season: null` (`packages/core/algorithms/bpr.ts:387`), `update` returns
   `season: state.season` unchanged, and both drivers only call `carrySeason` when a
   prior state exists — `packages/harness/cli.ts:743` and `packages/harness/publish.ts:2284`
   both guard on `priorState !== undefined`, so the first season in any range never gets
   one. `foldPhases` short-circuits on `season === null` (`bpr.ts:540-541`). Routing the
   scoring target through that guard would make adjust invisible for an entire season in
   the port while `packages/bpr/data.ts` (which always has `meta.year`) subtracted it —
   precisely the cross-module divergence this task is asked to prevent.
2. **`componentMapForSeason` throws for an unregistered season.** That throw sits outside
   `tryParseBreakdownPair`'s `try` by design. Putting it in the scoring path would turn a
   future unregistered season into a hard failure of the live update path.

The shallow route is numerically identical to the component route on every successfully
parsed payload: every registered season maps `ADJUST_COMPONENT` to exactly the raw field
`adjustPoints`, with no arithmetic — as a key lookup in 2016/2017/2019/2020/2022/2023/2024/2025
and as `(side) => side.adjustPoints` in 2018/2026. It also mirrors how `foulPoints` is
already read in both modules today, and it makes "missing or malformed yields 0, never a
skipped update" true by construction rather than by a discriminated-union branch.

**Task 3 verifies this empirically** against the real corpus rather than asserting it.
</design_decision>
