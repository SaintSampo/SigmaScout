## The ordering hazard that forced a push first

`v1/compare/{year}.json` is **not version-scoped** (`pageArtifacts.ts:154`), so a republish
overwrites it live with no versioned predecessor. The previously deployed client REQUIRED
`seasonLabel`, and the new publish path no longer writes it — republishing before pushing would
have broken the live Compare page.

Sequence taken: push (54 commits, Pages deploy green, site 200) → verify the tolerant client reads
today's 5.0.0 artifacts → republish. Live artifacts were also snapshotted locally first, converting
the plan's "costly" reversibility into a real restore path.

## Six copies of the pin, five moved

Moving a pin is precisely the operation that exposes duplicated-fact drift, and this repo had six
copies. Collapsed to one leaf module. `tune.ts`'s stays put deliberately — see decisions.

The executor's own sweep found a **fourth** file still constructing the old path
(`tune.test.ts`) beyond the plan's expected three; it is a legitimate test of the deliberately
non-moving incumbent, recorded rather than silently folded into the expected set.

## Two corrections to my own earlier claims

1. **"The fixtures will change and that is the success signal" — WRONG.** `publish` writes to R2
   only and never touches the repo. `apps/web/src/routes/__fixtures__/compare-*.json` are
   deliberately byte-pinned test data, and were already at `vpr@2.1.0+tuned-2026-08` — five majors
   behind production before this republish. Nothing to commit there. D-4 in this task's own CONTEXT
   was a bad assumption.
2. **Only 2022 reproduces its acceptance number exactly.** 2026 publishes at `0.144841` against the
   acceptance's `0.144809`, because the acceptance replayed the candidate params across the WHOLE
   window while the shipped configuration uses per-season sets (2023-2025 on the incumbent) — a
   different state trajectory. 2026 still beats the incumbent, by 0.00153 rather than the validated
   0.00222. 2022 matches exactly only because it immediately follows a cold start.
