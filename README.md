# SigmaScout

FRC match prediction & analytics, **statically hosted**. Heavy model training
happens offline; the browser loads compact model-state JSON and runs inference
live — so hypothetical alliances, what-if brackets, and score/win predictions
all work with no server.

## Architecture

```
Offline pipeline (Node/TS)                Static site (Vite + React)
──────────────────────────                ───────────────────────────
FIRST/TBA data  ──►  train model  ──►  public/data/*.json  ──►  browser loads
(fetch.ts)           (train.ts:                                 model state and
                      Kalman + EM)                              runs inference
                                                                (src/core/*)
```

The **same `src/core` code** computes predictions offline and in the browser, so
training-time and serving-time math can never drift.

- `src/core/` — framework-free shared core: `types.ts` (the data contract),
  `stats.ts` (normal CDF, P(A>B)), `inference.ts` (combine 6 teams → score
  distribution → calibrated win probability).
- `src/lib/data.ts` — browser fetch of the static JSON artifacts.
- `src/components/` — React UI (match predictor, team ratings).
- `public/data/` — the static "API": `manifest.json` + `seasons/<year>.json`
  shards. Currently **mock data**; regenerated by the pipeline once wired up.
- `pipeline/` — Node/TS `fetch → train → emit`. **Stubbed** for now
  (`npm run pipeline` fails loudly by design) — data collection is deferred.

## Develop

```bash
npm install
npm run dev            # local dev server
npm run build          # static build → dist/
npm run typecheck      # app + node configs

# Data pipeline (needs TBA_AUTH_KEY in .env)
npm run pipeline                   # build all seasons (2016-2025, no 2021)
npm run pipeline -- 2024           # fetch + fit + emit seasons/2024.json
npm run pipeline -- inspect 2024   # find a sample match, verify the decomposition
npm run eval -- 2024               # walk-forward sweep of the learning rate
```

## Seasons & score decomposition

Every FRC game has a different score breakdown, so each season has a decomposer
(`pipeline/fetch.ts`) mapping TBA's fields into `auto` / `teleop` / `endgame`.
Most years follow one pattern (`auto = autoPoints`, `endgame = <game field>`,
`teleop = teleopPoints − endgame`); 2016 and 2023 are special-cased. Each mapping
is **verified against a live match** (`inspect` checks `auto + teleop + endgame ==
totalPoints − fouls`) — this caught real bugs in 2016 (breach/capture) and 2023
(links sit outside teleopPoints). Fouls are excluded (opponent-caused). 2021 is
skipped (at-home season, no comparable alliance scores).

**Two different "scores".** Fouls are excluded from the component decomposition
that feeds the model (a team shouldn't get skill credit for the opponent's
fouls). But fouls DO count on the scoreboard and decide who actually won — so
match **results and W/L use the official alliance totals** (`alliances.*.score`,
foul-inclusive), never the component sum. Deriving outcomes from the
foul-excluded sum silently flips matches decided by fouls (e.g. 2026 ISR champs
qm53). Eval win/loss labels use the official totals too.

## The model (design)

Per team, per scoring component (auto/teleop/endgame), a latent skill is tracked
with a Kalman filter: it random-walks over time (process noise = "how fast the
model learns"), and each match is a noisy observation of the *sum* of three
teammates' skills. Alliance score = sum of components; win probability comes from
integrating both alliances' score **uncertainty**, not just the mean margin.

Process noise is **gap-aware** — inflated across event boundaries — and the
learning rate is fit by maximizing walk-forward predictive accuracy
(`npm run eval`). The optimum is α≈0.01 on **both** 2016 (Stronghold) and 2024
(Crescendo) — two very different games — so it's used as a shared default. On
2016, letting skills drift beats a static rating (log-loss 0.568 → 0.559, score
RMSE 21.5 → 19.9); 2024 predicts better overall (75% accuracy, 0.513). Learning
too fast is worse than not adapting — the tension the eval harness settles.

**Cross-season carryover (hierarchical layer).** Ratings live in per-game point
units, so a team's end-of-season strength is normalized to a season-agnostic
z-score (`normalizedRating`, comparable across games) and a regressed version
(ρ·z) seeds its prior the next season — returning powerhouses start strong,
rookies start at the league mean with full uncertainty. ρ is tuned by a
multi-season walk-forward eval (`npm run eval:carry`): the optimum ρ=0.6 cuts
**early-season** log-loss 0.619 → 0.587 (~5% over ~20k early matches) and helps
overall too, with too much carryover (ρ=0.9) hurting — year-over-year strength is
correlated but not identical. See `pipeline/carryover.ts`.

An **innovation-driven per-team adaptive gain** (boost process noise for a team
whose recent corrections run one direction — a real change, not a one-off
outlier) is implemented (`adaptStrength`/`adaptDecay`) but **off by default**: on
2016 it did not beat a well-tuned fixed rate (κ=0 optimal in the joint sweep).
Two reasons it may yet earn its place: (1) the boost is multiplicative on base Q,
so it can't bootstrap learning from α=0 — an additive form is worth trying; (2)
aggregate log-loss over 14k matches is dominated by well-behaved matches, so it
needs a segmented eval that isolates the post-change tail. Revisit with more
seasons.

Implementation: `pipeline/kalman.ts` (time-varying filter + per-team priors),
`pipeline/carryover.ts` (cross-season normalization + prior seeding),
`pipeline/opr.ts` + `pipeline/priors.ts` (ridge-OPR baseline + noise/prior
seeding), `pipeline/train.ts` (the static-OPR baseline, kept for reference). The
tuned global hyperparameters (α, ρ, κ) are recorded in `manifest.json`.

## Deploy

GitHub Actions builds and deploys to Pages via the **Actions source** (Settings →
Pages → Source: GitHub Actions), so generated data never bloats git history. See
`.github/workflows/deploy.yml`. A future `schedule:` trigger (commented in) can
refresh FRC data on a cron; a local PC script remains an option for tighter
cadence.
